# Modules: adding a kind of thing, and taking it away again

**4 September 2026.** The question, as asked: how does isocan get *great*
extensibility — a module you can add and remove, that can expose node types,
toolbar tools, agent tools, inspectors, panels, and whole sections of UI the
way the workbench is one? And concretely: what would it mean to publish
`@isocan/whiteboards`, `@isocan/documents` and `@isocan/sandboxes`?

The list of things a module should be able to expose came from a note of
Dion's on a canvas. I could not find the note itself — not in the repo, not
in `scratch/`, not on the canvases this daemon lists — so the list below is
the four he named plus everything the code shows has been added by hand in
the last fortnight, which turns out to be the better source: the repository
has been building modules without calling them that, and the diffs say what
one costs.

Every number here was counted in the tree today. Every claim about another
product was read from its documentation today and is marked as such.

## The short version

- **isocan already has three extension idioms, and none of them is a
  module.** *Files* (slash commands, personas, skills — home- or repo-wide
  markdown that agents read). *Items with roles* (`role=design-system` today;
  the [extensions design](../projects/extensions/design.md)'s `role=tool`,
  `role=panel` and the [workbench](../projects/workbench/design.md)'s
  `role=view` — canvas-carried, versioned, undoable). *The storage seam* (one
  interface, two workspaces, a test that holds it). A module is a fourth
  thing: **a package of code, installed by whoever runs a home, that
  contributes to registries on both surfaces.**
- **The registries it would contribute to are all closed, and were counted:**
  8 item kinds, 6 tools, 5 dock panels, 17 palette actions, 13 built-in slash
  commands, 139 CLI verbs in one 10,313-line file, 33 operation types, 64
  routes. Adding the last dock panel touched **12 source files across three
  packages**; the mind map — a node type in all but name — touched 7 across
  three. That is what a module costs today, paid by hand, and the codebase
  paid it five times in a fortnight: context, personas, mind map, areas, the
  design system.
- **The finding that makes removal safe is already in the data model.** An
  item is a file with a mime type and a property bag, and the 33 ops know
  nothing about kinds. A module leaves no trace in the oplog except a mime
  and some property keys. Remove it and its items render as files — the
  reducer cannot be broken by a missing module. tldraw, measured for
  comparison, **throws** when a document holds a shape whose util is not
  registered. isocan's file-first model is the opposite failure mode, and
  it was chosen for other reasons years before anybody asked this question.
- **Modules and extensions are two trust classes, and the design must not
  blur them.** An extension (an item) is trusted like a collaborator: it may
  only ask for what a person could ask for. A module (a package) is trusted
  like the CLI you installed: app-origin code, chosen by the operator of a
  home. isocan.io's modules are chosen by its operator; a canvas that needs a
  module its home lacks degrades to files and says so.
- **The recommendation is to make things removable before making them
  addable.** Move one in-tree feature into a module directory and prove the
  app builds without it; then ship Mermaid as the first node-type module
  (recommended twice already, zero ops); then documents, which is the module
  that needs an inspector and a page; then runtime loading for self-hosted
  homes; and sandboxes last, gated on three things that do not exist.

## 1. What extensibility isocan already has

| Idiom | Where | Scope | Who trusts it | Surfaces |
| --- | --- | --- | --- | --- |
| **Slash commands** | `~/.isocan/commands/*.md`, merged over 13 built-ins in `core/commands.ts`; installed with `isocan command add --from <owner/repo/path>`, which prints the whole file before `--yes` | home-wide | the person who installed it; every future agent reads it | both — a command is a comment |
| **Personas, skills** | `.agents/personas/*.md`, `.agents/skills/`, symlinked into `.claude/` | repo-wide | the repo | agents |
| **Items with a role** | `role=design-system` (`core/designsystem.ts`, rendered by `DesignSystemView`); `role=tool`, `role=panel` designed in extensions; `role=view` designed in the workbench | one canvas — the canvas carries its own UI | a collaborator: versioned, undone per actor, revocable through the desk | both — the manifest is an item |
| **Harnesses and adapters** | `api/harness.ts` (four built-in, `config.json` adds one), `cli/acp.ts` (`BUILTIN_ADAPTERS`, config adds more) | machine | the machine's owner | CLI |
| **The storage seam** | `Store` in `server/store.ts`, two backings, `test/seam.test.ts` holds every method to the conformance suite | the daemon | the operator | daemon |

Three observations fall out of the table.

The **file idiom is the cheapest and the most used**, and it has the install
ceremony the extensions doc wants for everything else: source named, body
printed, nothing lands before `--yes`. A module should inherit that ceremony
rather than invent a second one.

The **item idiom is the only one that travels with a canvas**, which is why
the extensions design chose it. But it can only carry what the app already
knows how to draw — a declarative tool is rendered by isocan's own
component, a hosted panel by a frame. An item cannot teach the app a new
kind, because the code that renders kinds is on the app's origin. So the
item idiom *needs* a module idiom underneath it: a whiteboard item on a
canvas needs, at the home rendering it, code that knows what a whiteboard is.

The **storage seam is the one real precedent for a code boundary in this
repo**, and its lesson is not the interface, it is the test: a method the
conformance suite does not exercise fails the build. A module registry
should land with the same shape of guard or it will be a convention.

Two things to notice.

**The rows that cost the most are the rows with no registry.** A panel is
twelve files because "the set of panels" is spelled five times — a union, five
booleans, a rail, a menu, a stage rule — and nothing reads a list. A kind is
seven files for the same reason: `ItemKind` is a type, and the renderer is an
`if` chain that does not consult it. The mind map is the counter-example that
proves the point: it is already a module in everything but its address. It has
a core file, a web component, a CLI family, a guide section, property keys of
its own (`map`, `mapParent`), and no ops. Nothing about it is in a registry
because there is no registry; it is simply well-behaved.

**Five features in a fortnight each added zero operations.** That is the
finding underneath the whole question. The op vocabulary is the contract
between the surfaces, and the repo has been adding whole features — a graph
you can drag, a week-long ritual with phases, a room for agents — on top of
`item.add`, `item.update` and properties. Modules are possible *because* the
vocabulary is already closed against them, not despite it.

## 3. What a module is, then

> **A module is a package that contributes to those registries on both
> surfaces at once, and that can be removed leaving every item it made still
> readable as a file.**

Both halves are load-bearing. The first is the isomorphism applied to
packaging: a module that ships a renderer and no verb is the web-only feature
AGENTS.md forbids, in a box. The second is what makes add-and-remove honest
rather than a slogan.

### The manifest

VS Code's shape is the right one for declaring, and it was read today: an
extension's `package.json` carries a `contributes` block of some thirty-seven
declarative keys — `viewsContainers`, `views`, `customEditors`, `commands`,
`menus`, `languages` — and code is reached only through activation. The
mapping onto isocan is almost one-to-one: `languages` is kinds,
`customEditors` is renderers, `views` and `viewsContainers` are panels and
pages, `commands` and `menus` are actions and the context menu. Declared, so
the daemon can print what a module adds before it is installed, exactly as
`command add --from` prints a command's body.

```jsonc
{
  "name": "@isocan/mermaid",
  "isocan": { "engines": ">=0.1" },          // refused with a sentence, never crashed on
  "kinds": [{
    "id": "diagram",
    "mimes": ["text/vnd.mermaid"],           // the file is the truth — a kind is a mime first
    "label": "Diagrams", "icon": "diagram",  // icon from the named set tier 1 mandates
    "editable": true                          // editableText() by mime, as today
  }],
  "tools": [],       // { id, key, label, icon } — a tool is a pointer mode that makes a kind
  "inspectors": [],  // { for: kind | mime, ... } — the slot that does not exist yet
  "panels": [],      // { id, label, icon, side } — one panel, one CLI question
  "pages": [],       // { segment, label } — a route family, a lazy mount, a gate, an open flag
  "actions": [],     // palette entries; web only, like today's
  "commands": "./commands",   // slash commands, merged as a third source after built-in and home
  "guide": "./agent-guide.md",// a section of --agent-help, present only while installed
  "web": "./dist/web.js",     // the renderer, the panel, the inspector: prebuilt ESM
  "cli": "./dist/cli.js"      // a verb family registered on the same commander program
}
```

### What a module may add

Mimes. Property keys, **namespaced** (`whiteboard.grid`, never `grid`),
because property keys replay forever and a removed module's keys must be
visibly orphaned rather than silently reused by the next one — the workbench
design's rule for `view.for`, made general. Roles. Slash commands. CLI verbs.
Guide sections. Renderers. Panels. Inspectors. Tools. Pages. Palette actions.

### What a module may not add

**Operations, ever.** The extensions design's sentence holds for modules
without a word changed: an extension that needs a new op is proposing a
product feature. **Protocol messages**, for the same reason. **Server routes,
at first** — a route is a door, and the desk's whole job is that every door
runs the same test; if a module ever needs one it is `/api/m/<name>/…` behind
the same badge check, and not before a second real module asks. **A hidden
store**: module state is an item, visible and versioned, as the extensions
doc already decided. **Reading the desk.**

The extensions design's rule was *an extension may only ask for what a
person could ask for.* The module's rule is its sibling:

> **A module may only add what a person could already do with a file and a
> verb.**

A new kind is a file with a new mime. A new panel is a list the CLI can
already print. A new tool is a gesture whose intent has a verb. A module that
cannot be described that way is asking for a product change.

### Both surfaces, enforced

`surface.test.ts` reads the verbs the CLI registers and fails when one is
missing from the guide. It generalises to manifests without a new idea: every
kind has a verb that creates one; every verb the module registers is in its
guide section; every panel names the CLI question it answers (the workbench
design's parity table, made a field). A module that fails the test does not
load, which is the same teeth the repo already has, pointed at a package.

## 4. Two trust classes, not one

This is the part that is easy to get wrong by getting it *almost* right.

The extensions design says **no app-origin JavaScript**, and it is correct
about the thing it is designing: an item on a canvas was put there by a
collaborator, and a collaborator's code must not run as the app. But a module
is not put there by a collaborator. It is installed on a machine by the
person who runs that machine's daemon, the way the CLI itself was — and the
CLI already runs as the app, unattended, on every managed install, from
whatever is on `release`. The [auto-upgrade](../projects/auto-upgrade/phases.md)
project names that trust boundary as open. A module is the same boundary
with a second package on the other side of it. Nothing about modules makes
it wider; nothing about modules makes it narrower either, and the doc that
closes it should close it for both.

So:

| | Extension (item) | Module (package) |
| --- | --- | --- |
| Put there by | anyone on the canvas | the operator of a home |
| Travels with | the canvas | the machine |
| Runs as | a sandboxed frame, or isocan's own component from a declaration | the app, on its origin |
| Trusted like | a collaborator | the CLI you installed |
| Attributed as | its own actor, with a grant | nothing — it is the app |
| Revoked by | the desk | uninstall |

And the relationship between them: **a module is the runtime an extension may
need.** A whiteboard item is an extension in the sense that matters (a thing
on a canvas, versioned, undoable); the code that draws it is a module at the
home. Where the module is absent the item is still there, as a file, with the
module's name on it.

For **isocan.io** this is not a new decision: the operator chooses what runs
there, as with any hosted software. A canvas homed at isocan.io can use the
modules isocan.io has. A private home can add more. A canvas moved between
them (teleport, backup) carries its bytes, and bytes are files.

## 5. Removal, which is the actual test

"Add and remove" is a claim about remove. Adding is easy in every plugin
system ever built; what distinguishes them is what a document looks like
after the plugin is gone.

**Items.** An item of a removed module's kind falls through the renderer chain
to the file view it has today (`file-view`: filename and mime). One
improvement is worth making: the card can say *made with `@isocan/whiteboards`,
not installed here* from the mime alone, because the mime carries the module's
name (`application/vnd.isocan.whiteboard+json`). No lookup, no stored
reference. `isocan ls --kind` groups them under `other`, as it would any
unknown file, which is correct.

**Commands.** Menu entries vanish. Comments that invoked them stay as text —
they were always text. A parked agent without the module reads `/whiteboard`
as an unknown command, exactly as it reads a home command it does not have
today. This is the file idiom's existing behaviour and needs no design.

**Verbs and the guide.** The `whiteboard` family is not registered; its guide
section is not printed. `surface.test.ts`'s rule that a verb nobody is told
about does not exist has a pleasant inverse: a verb nobody has is not
described.

**Property keys.** They stay, forever, namespaced, harmless. `isocan get`
shows them; nothing else reads them.

**The oplog.** Untouched. This is the sentence the whole note turns on: **no
operation anywhere names a module, a kind, a panel or a tool.** The history
of a canvas reads as what was made, and what was made is files.

For contrast, measured today rather than remembered: tldraw's document stores
each shape by `type`, and its editor's `getShapeUtil` **throws "No shape util
found for type"** when a document holds a type whose util was not passed in
`shapeUtils` (tldraw issue 5295 is the UI crashing on exactly this; the docs
offer `hasShapeUtil` as the non-throwing check). That is what a plugin system
looks like when the data model was built for plugins first and documents
second. isocan's was built the other way round, and for this question it is
the right way round.

**Which modules a canvas uses is derived, not stored.** The
[repo-admin note](2026-08-30-repo-admin-canvas.md)'s rule — every fact is
derived-and-regenerated or decided-here-and-nowhere-else, never both — applies:
the set of modules a canvas needs is the set of vendor mimes present on it,
readable by either surface in one pass, and a stored list would be a second
copy that drifts. Should a module ever have state with no item to carry it,
that is the moment to revisit, and not before.

## 6. Delivery: what publishing `@isocan/x` actually means

Nothing is published today. All six workspaces are `private: true`; the CLI
installs from `github:dglazkov/isocan#release`, and `bin/workspace-loader.mjs`
resolves `@isocan/*` **by path**, not through `node_modules`, for a reason its
comment spells out (link dependencies broke every reinstall). The web app is a
Vite build the daemon serves from `packages/web/dist`, made by CI, never on a
user's machine.

That last fact decides the mechanics. **A module's web half cannot be
compiled into the bundle where it is installed**, because nothing there can
compile. Two shapes remain, and they are stages rather than rivals:

1. **Build-time modules.** A distribution chooses its modules when it builds:
   `packages/modules/*` in this repo, included by the web build and the CLI
   the way workspaces are today. isocan.io gets what CI built. A self-hosted
   home that wants a different set rebuilds. This is where the in-tree
   features go first (§ 8), and it needs no loader, no import map, no
   registry on disk — only the contribution registries in code.
2. **Runtime modules.** A module ships **prebuilt**: `manifest.json`,
   `web.js` (ESM, React and `@isocan/core` as externals resolved through an
   import map the shell emits), `cli.js`, `commands/`, `agent-guide.md`. The
   daemon serves `/modules/<name>/web.js`; the shell fetches `/api/modules` at
   boot and registers what it finds; the CLI's program loads each `cli.js`
   before parsing argv. `isocan module add <spec>` puts it in
   `~/.isocan/modules/<name>/`, printing the manifest — every kind, verb,
   panel and page it adds — before `--yes`. This is Obsidian's shape exactly,
   read from its docs today: a `manifest.json` with `id`, `version` and
   `minAppVersion`, a `main.js` loaded at runtime, `registerView(type,
   factory)` and `registerExtensions(exts, viewType)` as the two calls that
   make a plugin a kind and a view. Their one rule worth carrying over
   verbatim: *never keep references to views; the factory may be called
   many times.*

The **`@isocan` scope** is registered nowhere. A published module compiles
against `@isocan/core`'s types, which means [iso-api](../projects/iso-api/design.md)
phase 4 — a published API package — is a precondition for anybody outside
this repo to build one, or modules use git specs (`github:owner/repo#release`)
the way the CLI already installs itself, which works today and needs no
account. The scope is a distribution decision, not a technical one; the
note records it and does not make it.

**Versioning is the contract.** A module declares the isocan range it was
built against; a daemon that does not satisfy it refuses the module with a
sentence naming both versions and loads everything else. The
[auto-upgrade](../projects/auto-upgrade/design.md) machinery already knows
how to say which commit a home is; that is the number a module pins.

**The web bundle.** The app is 484 KB gzipped
([React Flow and tldraw](2026-08-31-react-flow-and-tldraw.md)); the workbench
and the palette are already lazy chunks. A module's `web.js` is another one,
loaded when its kind is first seen or its page first opened, never at boot.
The performance persona's ceiling on the largest chunk is the guard.

## 7. The three packages, honestly

**`@isocan/whiteboards`** is mostly the product. Ink is the `drawing` kind;
words are `text`; areas are a titled region things are placed in; the pen and
the text tool are two of the six. What a module could add that is not here is
a *bounded* whiteboard — a node with its own ink clipped to it, a kind whose
blob is the strokes (`drawing.ts` already has the format), a pen that draws
inside it, `isocan whiteboard new / add`. Useful, small, zero ops. But the
more valuable reading is the other one: **whiteboards is the "can you remove
it" test applied to the core product.** Moving pen, text and area into
`packages/modules/whiteboard` and proving the canvas still builds without
them is the proof that modules are real, and it is a proof nobody would
install separately, because it is the default. A pilot for internal
modularity; a poor first *published* module.

**`@isocan/documents`** is the one to build second, because it is the module
that needs the two slots that do not exist. Markdown already renders and
edits (CodeMirror, `item.addVersion`); what a documents module adds is an
editor made for prose — the [WYSIWYG note](2026-08-26-wysiwyg.md) placed
TipTap, Lexical and ProseMirror as "the right layer for a future markdown
lens, wrong species for screens", and this is that lens — an **outline
inspector** (the first real inspector, keyed to a kind), a **Documents page**
(a doc-centric section beside the workbench: the same four things a page
costs), `/outline` and `/summarize` as commands, and export. Every edit is
`item.addVersion`; every fact is a file. It exercises kinds, inspectors,
pages, commands and verbs in one module, which is what makes it the right
second.

**`@isocan/sandboxes`** is compute, and *isocan never runs compute* is a given
in the [architecture](../architecture.md). The honest shapes are two: a
sandbox node is HTML and JavaScript that run **in the viewer's browser**, in a
frame on the [content origin](../projects/atlas/content-origin.md) — the
extensions design's tier 3, which is not built — or a thing an agent runs
**where the agent is**, the way `isocan edit` opens `$EDITOR` on the agent's
machine rather than anywhere isocan controls: `isocan sandbox run` executes in
the harness that typed it and posts the result as a version. A Sandboxes
section in the workbench — logs, a terminal — is a page plus a hosted panel.
It waits on three unbuilt things by name: the content origin, extension actors
(who stamps a sandbox's writes), and the compute-consent question
[agent-custody](../projects/agent-custody/design.md) left open. And on the
workbench review's exfiltration finding, which is load-bearing here: a frame
that runs code and can `fetch` anywhere is a frame that can send what it was
handed anywhere, and the served CSP has to say `connect-src <content-origin>`
before the first sandbox renders. Last, and gated, and the gates are named.

## 8. Prior art, read today

- **VS Code** — `contributes.*` in `package.json`, thirty-seven declarative
  keys; `viewsContainers` and `views` for sections and panels, `customEditors`
  for kinds, `languages` for mime-to-kind, `commands` and `menus` for actions.
  Declared first, code on activation. *The shape to copy for the manifest.*
- **Obsidian** — `manifest.json` (`id`, `version`, `minAppVersion`), `main.js`
  loaded at runtime from the vault, `registerView` and `registerExtensions`
  as the two calls that make a plugin a kind and a view; the instruction never
  to hold view references because the factory is called repeatedly. *The
  shape to copy for runtime delivery.*
- **tldraw** — a `ShapeUtil` per kind: `type`, `props`, `getDefaultProps`,
  `getGeometry`, `component`, `indicator`, passed as `shapeUtils`; a shape
  tool pairs with a util. A document holding an unregistered type throws.
  *The shape to copy for what a kind must declare, and the failure mode to
  avoid.*
- **Figma** — two halves, a main-thread sandbox with the document and no DOM,
  an iframe with the DOM and no document, `postMessage` between them; the
  manifest declares `networkAccess`. *Already the extensions design's tier 3;
  nothing new to take.*
- **The field's convergence on MCP plus a skill** ([agents on the canvas](2026-08-23-agents-on-the-canvas.md))
  is the agent-tools row of § 2 from outside: a module's agent tool is a
  skill (a command file) plus a verb, and if an MCP surface is ever generated
  from the CLI as that note recommends, a module's verbs ride along without
  a second declaration.

## 9. The walk

0. **Name it and count it** — this note. The counts in § 2 are the baseline;
   the ratchet, if one is wanted, is the number of files a new panel touches.
1. **Internal modules.** A `ModuleContribution` type in core naming the
   registries; the web shell and the CLI program each read a list rather
   than a union; `packages/modules/<name>/` as a workspace shape. Move
   **the mind map** first — it is already a module in all but address, with
   zero ops and every surface covered — and the acceptance test is literal:
   delete the directory, `npm run build` and `npm test` pass, and `map` is
   not in `--help`. Then context, personas, the sprint. The panel count in
   § 2 is what this stage is measured against: a sixth panel should touch
   the module and nothing else.
2. **Mermaid, the first node-type module.** `text/vnd.mermaid`: one mime, one
   renderer, one guide line, `isocan add diagram.mmd`. Recommended by two
   notes already, zero ops, and small enough that it settles the `kinds`
   contribution's shape without a second thing riding on it.
3. **Documents.** The inspector slot and the page slot, with a customer.
4. **Runtime loading**, for self-hosted homes: `isocan module add / rm / ls`,
   `~/.isocan/modules`, served chunks, the engines check, the manifest
   printed before `--yes`. Not before stage 1 has made the registries real,
   because a loader with nothing to load into is a loader.
5. **Sandboxes**, after the content origin, extension actors and compute
   consent — in that order, each of which is somebody else's project.

## Open

- **Unions become strings.** `ItemKind`, `Tool` and `Panel` are string
  unions the compiler checks; a registry makes them `string` with a lookup
  and a fallback. Exhaustive switches stop being exhaustive. The cost is
  real and should be paid on purpose, in one commit, with the fallback
  tested — not discovered when the first unknown kind reaches a `switch`.
- **The guide grows per module**, and it is 96 KB already with #124 asking
  for fewer tokens. A module's section should be printed only when its kind
  is present on the canvas or its verb is asked about — the
  [local-agents note](2026-08-24-local-agents.md)'s short-brief idea, applied
  per module.
- **Who owns `@isocan` on npm**, and whether git specs are enough for the
  first year. Nothing in this note needs the answer.
- **Inspectors have no precedent here.** The extensions design's tier-2
  declarative panel — rows over properties, `row-does` a command — is the
  cheap first inspector, and it may be all most kinds need. Code inspectors
  wait for documents to ask.
- **Hosted homes running modules** is the operator running a package's code
  on isocan.io. It is the same decision as running `release` unattended,
  which auto-upgrade left open; one answer should cover both.
- **A tool that is not a kind.** Every module tool imagined here makes a
  thing. A pointer mode that does not (a measuring tape, a laser pointer)
  is web-only by nature, which the palette already allows; the question is
  whether the rail should, and it is deferred until one is asked for.
