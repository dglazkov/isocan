# WYSIWYG on the stage

**26 August 2026.** The ask: edit the text and properties of a *screen* —
an agent-written HTML artifact — without opening its source. "I don't want
to go into HTML source to change some text."

Everything below is sorted by one observation that no off-the-shelf
comparison covers: **the decisive constraint is not editor features, it is
the sandbox physics of isocan's frames** — and those were measured in this
browser today, not assumed.

## The isocan-shaped problem

A screen is not a document in an editor's data model. It is an arbitrary
HTML file some agent wrote, stored as a blob, rendered in a sandboxed
iframe, and versioned — every edit must end as `item.addVersion`, the same
op `isocan edit` and the stage's ⌘S already send, or the isomorphism breaks.
So the question is never "which editor component do we embed"; it is **"how
does a change made by pointing at a rendered page become a new version of
the source that produced it"**. Three sub-problems:

1. **Reach** — can our chrome touch the rendered DOM at all?
2. **Capture** — does the tool require owning the document in its own data
   model, or can it edit what an agent wrote as-is?
3. **Fidelity** — does the round trip preserve the source, or reformat it?
   (Agents diff their own files; a save that rewrites every line makes every
   version a churn-diff.)

## The physics, measured

Probed today with srcdoc iframes in this app (a test page with an `<h1>` and
an inline `<script>` that marks the body when it runs):

| `sandbox=` | parent reaches `contentDocument` | page scripts run | `designMode` edit works |
| --- | --- | --- | --- |
| `allow-scripts` *(today's item frame)* | **no** — opaque origin | yes | — |
| `allow-same-origin` *(no scripts)* | **yes** | **no** | **yes** |
| `""` | no — opaque origin | no | — |

Three consequences, each load-bearing:

- **Today's frame cannot be visually edited from outside, period.** Any
  in-place editing needs a *second rendering mode* for the stage.
- **`allow-same-origin` alone is the safe edit mode, today, before the
  content origin lands.** The page becomes reachable *because* its scripts
  are dead — nothing executes, so nothing can read a cookie or call an API.
  A frozen page is also the right editing surface: nothing fights the caret.
- **Serialization normalizes.** `documentElement.outerHTML` of the edited
  document came back with the doctype gone and a `<head>` injected that the
  source never wrote. Whole-DOM serialize is faithful to the DOM, not to the
  file — the fidelity question is real and decides the patch strategy below.

One wrinkle found by reading our own server: the blob route serves
`Content-Security-Policy: sandbox allow-scripts` as a **response header**
(http.ts), and a response-header sandbox intersects with the iframe's — so
an edit-mode frame must not load the blob URL. It renders **fetched text via
`srcdoc`**, exactly the path the stage's draft preview already uses.

## The field, surveyed

### A. Page-builder frameworks — GrapesJS, Puck, Craft.js

**GrapesJS** is the mature open-source page builder: BSD-3-Clause, v0.23.2
(June 2026), healthy commit cadence, ~25k stars — and **~500KB gzipped with
a couple of plugins**, which is our entire current bundle again, for one
pane. The disqualifier is capture, in its own documentation's words:
round-tripping requires registering component types, or an element "will
load back as a generic div and lose any custom behavior," and importing
existing HTML/CSS brings "unexpected behaviors." Our screens are *nothing
but* existing, unregistered, agent-written HTML. GrapesJS is built for
documents born inside GrapesJS. *(Its commercial Studio SDK exists; not
evaluated — the capture problem is upstream of pricing.)*

**Puck** (MIT, React) is clean and genuinely embeddable — but a Puck page
*is Puck's JSON*, rendered by your registered React components. It cannot
ingest an arbitrary HTML file at all. Right tool if isocan ever grows
block-based authoring of NEW pages from a component kit; wrong species for
editing what agents already wrote. **Craft.js**: same data-model capture,
lower level, steeper — same verdict.

### B. Code-aware visual editors — Onlook

**Onlook** ("Cursor for designers," ~40 contributors) is the closest
philosophical cousin: visual manipulation that lands as *real code edits*.
But it instruments **React + Next.js + Tailwind projects** running in a
CodeSandbox-SDK container — a stack coupling and a runtime we don't have,
for artifacts that are static HTML files. Second-hand throughout (not run
here). The architecture lesson transfers even though the tool doesn't:
**map the rendered element back to the source location and patch the
source** — which is exactly option D.

### C. Document rich-text editors — TipTap, Lexical, ProseMirror

The 2026 consensus is stable: **TipTap** (MIT) is ProseMirror with a
practical API and ~100 extensions (2–4 weeks to production, per the field's
own estimates); **Lexical** is Meta's leaner alternative when performance
is the constraint; raw **ProseMirror** is months of primitives. TipTap's
cloud tier is paywalled but irrelevant — the library is free and versions
are our collaboration model.

The verdict for *this* ask: **wrong layer.** These editors own a document
model (their JSON/steps), not arbitrary HTML pages — pointing TipTap at a
screen has GrapesJS's capture problem wearing a nicer API. Where one of
them **does** belong is a different, real gap: a rich-text lens for
`text/markdown` *document* items on the stage, where owning the document
model is correct. Worth its own small stage mode later; TipTap is the
default candidate when that day comes.

### D. The native path — edit the rendered DOM, patch the source

No framework: render the artifact in the measured `allow-same-origin`,
no-scripts frame; our chrome reaches in. Two tiers:

**Text, surgically.** Double-click any text node on the stage → that node
gets `contentEditable="plaintext-only"` → on save, map the node back to its
**byte range in the source** and splice only the new text in. parse5 (the
WHATWG-compliant parser HTML tooling standardizes on) exposes exactly this
as `sourceCodeLocation` offsets per node — *not yet a dependency here, so
unmeasured; its API is documented and this is its designed use.* The rest
of the file survives **byte-for-byte**: an agent diffing its own file sees
one text change, not a reformat. This is "change some text" solved whole,
with zero framework and one parser dependency an order of magnitude smaller
than CodeMirror.

**Properties, honestly scoped.** Select an element → a slim panel for the
inline-style/attribute cases that surgical patching can address the same
way (an element's `style="…"` and attributes have source locations too).
Editing *stylesheet rules* is a genuinely harder mapping (a selector serves
many elements; specificity decides) — phase two, and the moment DESIGN.md
tokens enter it becomes a token-picker rather than a color wheel, which is
the more isocan-shaped feature anyway.

**The fallback tier** — whole-DOM serialize — stays available for "restyle
everything" edits where normalization is acceptable, labeled as what it is.

## Recommendation

**D, staged: text first, element properties second; frameworks declined;
TipTap noted for document items when a markdown lens is wanted.**

The reasoning in one paragraph: every framework surveyed either owns the
document (GrapesJS/Puck/Craft — our screens would have to be born inside
them), owns the stack (Onlook), or owns a document *model* (TipTap et al) —
and our documents are already owned, by the agents that write them and the
version stacks that keep them. The one approach that edits what actually
exists is direct DOM editing in the frame mode we measured today, with
saves that patch source ranges and land as ordinary versions. It is also
the only option whose cost is a parser, not a platform.

Fit with what already exists: the edit-in-place mode is a third state of
the stage's existing pane system; save is the editor's existing
`item.addVersion` path (drafts, dirty-gating, the landed-under note all
reuse); and an agent parked on `wait --item X --op item.addVersion` wakes
on an in-place text edit exactly as it wakes on everything else — the
isomorphism holds without a single new op.

## Built, same day: the V0

The recommendation's first stage shipped hours after this doc did — the
**unique-match text edit** — and its live run confirmed the doc twice over:

- **"Edit text"** sits in the stage's Saved-preview header (offered only
  when the editor pane is folded: two pens on one file is a conflict
  machine). It renders the artifact in the measured frozen frame
  (`allow-same-origin`, scripts dead, srcdoc — never the blob URL, whose
  response-header CSP would force its own sandbox). Double-click any text
  node → `plaintext-only` editing on that node; Enter keeps it, Esc puts it
  back; edits accumulate and fold (a re-edit chains to the ORIGINAL the
  file still holds). Save applies the unique-match rule — verbatim AND
  exactly once, judged against the source as patched so far — and lands as
  ordinary `item.addVersion`. One refusal refuses the whole save, by name.
- **Measured on a real artifact**: a 477KB screen took a headline edit and
  the v6→v7 diff was **one line** — the byte-exact splice working at size.
- **The refusal fired in the wild exactly as the tests predicted**: the
  first edit attempted contained `&`, which the source spells `&amp;`, and
  the save declined with "does not appear verbatim … needs the editor"
  instead of guessing.
- **The limitation showed its face too**: script-RENDERED screens (the
  Stitch Loop mockups draw their text from JS) freeze to a skeleton with
  nothing to double-click. Text that lives in JavaScript needs the editor —
  or, someday, the parse5 upgrade will not help either; that tail belongs
  to a different feature.

Still open from below: element properties, and the `<pre>` whitespace check.

## Built, next day: the parse5 upgrade

**27 August 2026.** The recommendation's second stage, and it retires both
refusals the V0 shipped with.

The V0 matched by string — verbatim, exactly once — which could not corrupt a
file and could not edit two things people do: text the source spells with an
entity, and text that appears twice. The fix is the correspondence this
document guessed at and the frame turned out to guarantee: **parse5
implements the same parsing algorithm the browser does, and the edit frame's
scripts are DEAD, so nothing mutates the DOM out from under that
equivalence.** The nth text node in the frame IS the nth text node parse5
sees. So an edit names its node by ORDINAL, `sourceCodeLocation` gives the
byte range, and the splice is exact — entities are irrelevant because nothing
is searched for, and repeats are unambiguous because a position is not a
string. `from` survives as a CHECK: if the node no longer says what it said
when you clicked it, the file moved under the edit and the save is refused.

Proven on a real artifact, v1 → v3, both cases in one file:

- `<h1>Rest &amp; Play</h1>` → `<h1>Work &amp; Play</h1>` — the exact case
  that refused on the V0's first outing, and it goes back in **encoded**, so
  text a person types can never become markup.
- `<button>Submit</button><button>Submit</button>` →
  `<button>Submit</button><button>Send</button>` — the second one, the first
  untouched. The V0 could reach neither.

Costs and findings, honestly:

- **parse5 is 164KB in its own lazy chunk** (48KB gzip), imported inside the
  save path, so it is fetched only by somebody who actually saved an edit —
  a parser, not a platform, as this document argued.
- **Whitespace text nodes count**, in the walk and in the browser's, and
  miscounting one would point every later edit one node off. It is pinned by
  a test rather than trusted.
- **`<script>` and `<style>` are refused**: their content is not
  entity-decoded, so encoding on the way back in would corrupt them. They are
  invisible in the frozen frame anyway; the refusal makes that true rather
  than assumed.
- One real bug found by driving the thing: an engine sometimes REPLACES the
  text node instead of mutating it (select-all-then-type does), and the
  first version of the ordinal lookup then had nothing to point at. The
  element is the stable thing, so a detached node falls back to its parent's
  first text child.

## Open questions, for the build

- **parse5 in the browser or on the daemon?** Client-side keeps the loop
  local (one more lazy chunk); daemon-side patching would be new write
  surface. Client-side is the default answer.
- **Whitespace-only normalization inside the edited text node** (the DOM
  collapses runs): store the DOM's text but splice at source offsets —
  acceptable, but verify against agent-written files with significant
  whitespace (`<pre>`).
- **Multi-select and repeated text** — two identical strings on one page
  must patch by *node location*, never by string search. `sourceCodeLocation`
  makes that free; a regex implementation would be the bug.
- **When the content origin lands**, the edit-mode frame moves there with
  everything else; nothing in this design depends on waiting for it.
