# Seam

**An open workbench for people, agents, and tools.**
*Commoditize the foundation. Compete on what people can create.*

**12 September 2026.** A strategy in one page. Nothing built, on purpose:
this is the page that decides what the next things get built *under*.

## What we learned, four times

Four experiments ran this summer, and each proved one thing the others did
not:

- **isocan** proved the isomorphism. A canvas driven equally from a browser
  and a terminal, because both speak the same 33 ops to one reducer. People
  and agents collaborate on it; agents park on it and wait (`isocan rc`), one
  name across many canvases.
- **The sandbox canvas** proved a node can be a *machine*: each one an e2b
  VM, with inspectors that show what is running inside it.
- **anatomy**, now ported onto isocan, proved a canvas can hold a project's
  *understanding*: explore the code, set goals, watch them kept.
- **The live canvas** proved a canvas can have *semantics*: Gemini in live
  mode at the centre, image and video models at the edges, the whole map
  mirrored into a knowledge graph, every node reasoned over and cached so
  meaning sits on top of the pixels.

Every one of them wanted the same underlying thing — a node, an inspector
for its kind, an agent that can act on it from a CLI — and every one built
it again from scratch. That is the finding. Put together, they point at
something larger than a canvas: **a living project that people and agents
can understand, inspect, execute and change together.** The next step is
not a bigger app. It is the place where nobody builds the foundation a fifth
time.

## What Seam is

Seam is an open-source umbrella where independent tools, agents and ideas
become more useful together without giving up their independence. It takes
Eclipse's modular spirit into the agent era: a runtime-extensible workbench,
not a fixed application with a plugin menu. Eclipse's insight was
"everything is a plugin" — the IDE was just the plugins that shipped first.
Ours is the same sentence. **The canvas is just the modules that ship
first.**

The name is exact. A *seam*, in Michael Feathers' definition, is a place
where you can change a program's behaviour without editing it there. That is
what a module contract is, so every module in Seam is a seam. Closed
platforms sell *seamless*. We show the seam, because a join you can see is a
join you can inspect, reopen and replace. And Seam is not defined by the
boundary between Google and everyone else. It is defined by the connections
between independent systems.

## What people would use it for

Seam is for the moment after the first prompt: a thing exists, several
people and several agents care about it, and everyone needs to see it, point
at it, change it and run it together. Chat tools are built for the first
prompt. Repos are built for the ledger. Nothing is built for the room. The
problems, each with what Seam does about it and the evidence we already
hold:

- **Working with someone else's agent, live.** Today the only shared
  surface two people with two harnesses have is a repo, so they collaborate
  through commits and pull requests: asynchronous, lossy, and the agent's
  reasoning is gone by the time it lands. On a canvas my harness and your
  harness act on the same live state, every op is attributed, and the repo
  goes back to being the record. *Evidence:* Claude Code, Codex, pi and
  Antigravity already run on one canvas with no config, and in the 3 Sep
  corpus one human ask in eight was a person pointing an agent at something
  rather than asking for work.
- **Change the thing you made.** Editing beats making two to one: people
  make a thing once and then talk to it. Prompt-to-artifact tools lose the
  artifact, so you cannot point at it, version it or undo it. On a canvas the
  artifact is on the table, with versions and undo, and a kept version is a
  preference pair the person produced for free. *Evidence:* 39% of human
  asks were edits of an existing thing, against 18% that asked for something
  new.
- **Knowing what your agents are doing, and whether they are there.**
  Agents run in terminals and cloud tabs. Nobody can see a fleet, and the
  failure we watched happen on 6 Sep is an agent that reports healthy while
  doing nothing. The canvas is where agent work is visible: presence,
  receipts, a summons with a deadline, *here* against *answerable* against
  *enrolled*. This is where cheap sheep earn their place: a cheap agent that
  stays is only useful if you can see it staying, and a fleet of cheap ones
  overnight needs an expensive one to check in. *Evidence:* the summons
  receipt and the findings queue that reddens after three days are built.
- **Understanding a project before you or your agent touches it.** Every
  onboarding and every "go fix this" starts with a picture nobody has.
  anatomy on the canvas: explore the code, set goals, watch them kept.
- **Seeing the thing run beside the conversation about it.** Agents produce
  things you cannot see running. A node that is a machine, with an
  inspector, next to the thread that asked for it, closes that loop.
  *Evidence:* the sandbox canvas.
- **Making the tool into your team's tool without forking it.** Every team
  ends up building a bespoke internal tool for its workflow, and every one
  rebuilds a canvas, inspectors and agent plumbing. Runtime modules let a
  team morph Seam into that tool. *Evidence:* the design competition, a
  whole new experience, needed zero new ops, only modules.
- **Finding out whether your agents are getting better, for free.** The
  oplog records more evaluation signal than most products collect on
  purpose: undo is a labelled failure, a kept version is a preference. A
  team working on a canvas learns whether its agents and skills improve
  without building an eval harness. *Evidence:* skill lift and judge
  calibration already run on it.
- **A project that knows about itself.** Lessons, decisions, roadmap and a
  docket where a finding is decided by people and agents together, on the
  canvas. *Evidence:* this repository runs that way today.

Constant experiments, and being in the conversation about what is new in
this space, are a reason for us rather than a use for them. They live under
"How we build".

## What we build

A small, opinionated kernel with public contracts, and everything else as a
module. The commitments, stated so they can be checked:

1. **Fully open source, on GitHub, and only on GitHub.** Code, issues,
   design discussion, tests, CI, releases, contribution paths.
2. **Bring your own agent, model and execution environment.** Claude Code,
   Codex, pi, Gemini, a shell script: anything that can read a skill and run
   a CLI is a first-class collaborator. No preferred model, in the code or in
   the culture.
3. **Isomorphic by construction.** The visual interface, the CLIs and the
   agents operate on the same capabilities and the same live state. A module
   that adds a node type adds its verbs, so what an agent can do and what a
   person can click are one set. isocan's guarantee, promoted to a rule.
4. **Any node, with an inspector per kind and agent-callable operations.**
   Code, documents, goals, media, running applications, VMs, agents. Remove
   the module and its items degrade to files, never to errors.
5. **A semantic graph beneath the canvas.** Relationships, provenance and
   cached analysis, so agents can reason about the project and revisit a
   conclusion when its inputs change.
6. **Standing agents and sheep as persistent participants**, not tools
   invoked for one turn. An agent that parks on a laptop and an agent that
   lives in a cell and wakes on demand are two answers to *how an agent
   stays*, and Seam prefers neither.
7. **First-party code uses the same contracts as everyone else.**
   Permissions explicit, behaviour inspectable, every component replaceable.

The four experiments become the first four modules, keeping their names.
That is the whole migration plan.

## Why this is strategically right

Twenty-five years ago IBM took a forty-million-dollar IDE, gave it a name
widely read as a swipe at Sun, and gave it away. The IDE was the complement
to what IBM actually sold, and a free, excellent, extensible complement made
the whole market bigger while denying anyone else the chokepoint. It worked.
Eclipse is still here.

**Commoditize our complement: the generic infrastructure around AI
creation.** Canvases, execution adapters, inspectors, agent integrations,
the semantic layer — make them abundant and interoperable instead of
rebuilding them inside every closed product. This is the layer where model
quality gets *felt*. If it is captured, whoever holds it taxes every model
and every product above it. If it is open, ubiquitous and boring, demand
flows to whatever is best on top of it.

That is the bet: lowering the foundation's cost expands what people can
create, and lets the products above it compete on what only a product can
offer — taste, coherent workflows, better outcomes. Seam is the workbench,
not the product. Products can be built with this ecosystem, and so can
things we have not imagined; none of them should be its gatekeeper. Other companies, including competitors, will benefit. That
is a consequence of genuine openness, not a loophole to close. We earn
preference through quality, not dependence.

## Why this is not the Stitch product factory

Stitch is a product factory: it takes an idea all the way to a shipped
product, with the opinions, the taste and the end-to-end workflow a factory
needs. Seam is not that. Seam is an **agentic development environment**: the
bench where a person and their agents understand a project, run it, inspect
it and change it. A factory has a bench in it. The bench is not the factory.

The distinction decides what each is allowed to be. A factory has to be
coherent, opinionated and finished, because its output is a product someone
will use. A development environment has to be open, inspectable and
unfinished at the edges, because its output is understanding and the next
change. Seam optimises for the second. It will never have a happy path from
prompt to shipped app, and that is not a gap.

What moves between them is ideas, not the roadmap. A node type, an
inspector, a way of watching an agent work, a semantic layer that turns out
to make agents reason better: any of these can be taken into a product
factory once it has proved itself on the bench, and rewritten there with the
factory's opinions. In that sense Seam is an experimental area for Stitch,
and for anything else built on top. But the flow is one way, and by choice.
Nothing in Stitch's plan depends on Seam shipping it, and nothing in Seam
bends to Stitch's release calendar. That is what keeps one open and the
other exceptional.

The test, when a request arrives: if it makes the bench better at
understanding, running, inspecting and changing a project with agents, it
belongs here. If it is about producing a finished product for an end user,
it belongs in a factory.

## Independence is a design constraint

Someone outside Google must be able to build, test, run, self-host and
contribute without Google infrastructure, internal tooling, or a Google
account. Google services are optional integrations, never hidden
prerequisites. If a workflow needs them to run, it is not in the project.

This keeps us honest, too. Everyone on the team should regularly build real
workflows with non-Google agents, models and infrastructure, and feel their
strengths, limits and differences firsthand rather than through an
abstraction that hides them. Working non-Google configurations are part of
continuous testing and everyday use. That feeling is data we cannot buy any
other way.

## How we build

isocan is four weeks old and already works this way. Seam inherits it, and
none of it is aspiration; every line below is in the tree.

- **There are no one-way doors.** We will rewrite the whole thing at any
  time, and the record shows it. The on-demand design withdrew its own first
  draft in review before a line was built. The sheepdog note was designed and
  superseded the same day; launch was superseded by on-demand within the
  week; the marketing directory was folded into the app and deleted, its
  guard carried across. A road not taken is written down beside the one
  taken, because it costs less to read than to re-walk. The one one-way door
  we did ship, a canvas you could archive and not bring back, lasted a day
  and became lesson 40.
- **We use all of the agents, all of the time.** Claude Code, Codex, pi and
  Antigravity run as harnesses with no config: whichever one you live in,
  your agents run on it. Agents commit. Nine personas review the tree every
  night, each with a number it owns, and a market researcher with none who
  says so. The night shift converges a canvas one item at a time and leaves
  a morning comment. The failure we watch for is an agent that reports
  healthy while doing nothing, so a finding left unanswered for three days
  reddens the suite.
- **We keep improving the system that builds this.** How we work lives in
  the repo, derived and checked, never kept by hand: 53 lessons, each an
  actual failure with the guard that now catches it; 65 decisions read out of
  the designs' own lines; a roadmap generated from every doc's front matter
  so it cannot disagree with the doc; 38 notes and projects tied to issues; a
  changelog page per day, written from the commits, drafted nightly for the
  days nobody wrote; a docket on the canvas where a finding is decided with a
  reaction; skill lift measured with and without, as fire, help and cost;
  judge calibration with a kappa. Every project runs on the conductor model:
  one subagent per phase, the conductor verifying the named proof itself
  rather than taking a subagent's word. When the 7 Sep note found that six
  systems ran the project and none knew about the others, that became the
  next project.
- **We are aggressively "ship it".** Every push to main is a release: CI
  rebuilds the install branch from each commit, and the last green commit
  deploys the shared dev home. Three refs, three jobs, no release meeting.
  Designs close the day they are written: on-demand and iso-api were designed
  and built in a day, multi-identity the day after. Machine pull requests
  merge themselves when the diff is entirely theirs and drain their
  predecessors. What guards the speed is a ratchet, not a gate: numbers that
  may not get worse, run on every push, that say something rather than block
  something, because a red check nobody believes is switched off within a
  week.

Seam changes none of this. It gives it more places to run.

## How we begin, and how we know it is working

A new umbrella, not a rewrite for its own sake. Extract the proven
capabilities, let the projects keep their identities, and compose one
reference journey that touches all of them:

**Understand a repository → establish goals → enlist an agent → run the
result → inspect it → iterate across code and media.**

Keep the shared contracts dependable and let modules and experiences stay
exploratory. The kernel is held to a high standard; everything above it is
allowed to be an experiment with a README. Graduation is the only process —
an example project lives in its own repo until it becomes a module — and
"should we support X?" is always answered by "is there a module?"

**The first proof:** an outside contributor adds a node and its inspector
without touching the core, then completes the journey with their own agent
and no Google services. **What we measure:** time to a useful extension,
independent contributions, cross-provider workflows, and learning that
materially improves what we build on top. Not features shipped.
