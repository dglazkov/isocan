# Live mode: voice on an isomorphic canvas

**24 August 2026**

The question: *how could isocan add voice through Google's Live API — a live
mode where a person talks to the agents and the agents talk back — and what
does that do to the isomorphism, and to the UX we already have?*

The short answer, which the rest of this argues: **voice is a new input
surface for the operation vocabulary that already exists, not a new
vocabulary.** Two facts about the Live API draw the architecture almost by
themselves, and one property of the canvas solves the problem that makes voice
assistants bad everywhere else.

**On provenance.** Google's own documentation hosts (`ai.google.dev`,
`docs.cloud.google.com`) fail certificate verification from this machine, so
every number below came from Google's published skill
(`google-gemini/gemini-skills`, `skills/gemini-live-api-dev/SKILL.md`) or from
an SDK's generated docs, and is marked where it is second-hand. The isocan
numbers are from this repository today.

---

## What the Live API actually is

A **stateful, bidirectional WebSocket**. Not request/response.

```
wss://generativelanguage.googleapis.com/ws/
  google.ai.generativelanguage.v1beta.GenerativeService.BidiGenerateContent
```

| | |
| --- | --- |
| Audio in | raw PCM, little-endian, 16-bit, mono, **16 kHz** — `audio/pcm;rate=16000` |
| Audio out | raw PCM, little-endian, 16-bit, mono, **24 kHz** |
| Session (audio only) | **15 min** uncompressed; unlimited with context-window compression |
| Connection lifetime | **~10 min**; session resumption tokens valid 2h, resumable within 24h |
| Context | 128k tokens (native audio) / 32k (standard) |
| Interruption | server sets `interrupted`; the client stops playback and clears its queue |
| Transcription | `input_audio_transcription` / `output_audio_transcription` are **config flags** — both sides come back as text |
| Voice | `speech_config.voice_config.prebuilt_voice_config.voice_name` (e.g. `"Kore"`) |
| Tools | `tools: [{ function_declarations: […] }]`; server sends `toolCall {function_calls:[{id,name,args}]}`, client answers `toolResponse [{id,name,response}]` |

Client→server on the open socket: `realtimeInput` carrying
`{audio:{data, mime_type}}`, plus the activity signals `activity_start`,
`activity_end` and `audio_stream_end`. Server→client: `serverContent` with
`model_turn`, `turn_complete`, `generation_complete`, `interrupted`.

## The two facts that decide the design

### 1. Function calling is synchronous, and that is a gift

> "function calling is synchronous only. The model will not start responding
> until you've sent the tool response." — Google's own skill, which also lists
> async function calling as **not yet supported**.

Read as a limitation this is annoying. Read as a constraint it draws exactly
the line isocan needs, because it forbids the design that would have been
wrong anyway.

A tool call blocks the conversation. So a voice tool may only be something that
finishes inside a turn — tens of milliseconds, not minutes. That rules out
"build me a checkout screen" as a function call, and it should: a person who
says that does not want the room to go silent for ninety seconds.

isocan already has the mechanism for the other kind of work. **Slow work is not
a tool call; it is a comment.** The voice agent posts to the main thread, which
"wakes every parked agent with no `@`-mention needed", and the agents that were
sitting on `isocan wait` pick it up and answer on the thread. The person hears
*"I've asked Charlie to build it — it'll land on the canvas"* and the
conversation continues.

So the vocabulary splits cleanly, and the split is not arbitrary — it is
**everything except making content**:

| Voice tools (fast: one local POST) | Dispatched to a parked agent (slow) |
| --- | --- |
| `item.move`, `items.move`, `item.resize` | `item.add` — make a screen |
| `item.update` — retitle, star, set a property | `item.addVersion` — edit into a new version |
| **`item.setCurrentVersion`** — *keep the second one* | anything needing judgement |
| `item.delete` / `item.restore`, `trash.empty` | anything needing a browser |
| `thread.create`, `thread.reply`, `thread.setMain` | |
| `thread.setAnchor`, `comment.update` | |
| viewport, selection, `format`, `align`, `distribute` | |

Twenty-eight operations exist. All but two of them finish fast enough to be a
voice tool.

**And note which one is in the left column.** `item.setCurrentVersion` is the
convergence operation — the one
[the night shift research](2026-08-24-the-night-shift.md) found the canvas has
never really used: 9 fan-outs against 2 deliberate choices. *"Keep the second
one"* is a one-second spoken gesture. If voice does nothing else, making
convergence a sentence rather than a hunt is worth the build.

### 2. The socket belongs to the daemon, not the browser

The obvious build puts the WebSocket in the browser: microphones are a browser
API, and Google ships ephemeral tokens precisely so a page can hold the socket
without seeing a key.

It is the wrong place here, for a reason specific to this product. **A feature
only one surface can reach is half a feature** — the house rule — and a
browser-held socket makes voice a web feature forever. Worse, the tool calls
would land as HTTP from the page, so the *place ops are minted* would depend on
which surface you spoke to.

Put the socket in the daemon and everything falls into line:

- The **mic stays a client capability**, like a screen. The browser captures
  PCM and ships it over the WebSocket it already holds to `127.0.0.1`; audio
  comes back the same way. A local hop costs ~1 ms against a network round trip
  of hundreds — it does not move the latency budget.
- **Tool calls become ops through the one engine**, exactly as a click or a
  CLI command would. That is the isomorphism, kept for free.
- The **key never reaches a browser**, so ephemeral tokens are not needed for
  the local case at all. (They become necessary the day a canvas is served from
  a real home to a remote browser — worth knowing now, not solving now.)
- A terminal with a microphone can have `isocan listen`, which is not a
  gimmick: it is the surface an agent-run session would use.

## Voice is an input surface, not a vocabulary

The rule that keeps this from rotting the product:

> **Every voice action produces the same operation a click would.** If
> something can be said but not expressed as an operation, that is a missing
> operation, not a voice feature.

The temptation with a voice mode is a parallel universe of "voice commands"
that do things the rest of the product cannot. Six months later the canvas has
two vocabularies, and undo, replay and the CLI all know only one of them. The
oplog is the product's memory; anything that bypasses it did not happen.

This also gives the feature its test, in this repo's idiom: **a spoken session
must be replayable from its oplog with no audio.** If the ops do not
reconstruct what happened, the voice mode is doing work outside the record.

## What the canvas gives voice that nothing else does

Voice assistants are bad at **deixis** — *this one, that one, move it left, no
the other one*. Speech has no pointer, so a voice interface either makes you
name everything ("open the file called checkout dot html") or guesses.

isocan already publishes the missing referent. **Selection is shared state.**
`PresenceSession.selection` is on the wire; `comment.items` already carries
what a person had selected when they spoke, which is why "make these two match"
already names its two. The daemon knows what "this" is before the sentence
ends.

So the resolution order for a spoken reference, all of it from parts that
exist:

1. **The speaker's selection** — `this`, `these`, `it`.
2. **What they are pointing at** — presence carries a cursor and
   `session point`; the item under it is a real answer to *that one*.
3. **A title** — the `#Title` roster the composer and `wait` already resolve
   against, and `<item>` arguments already accept a title prefix.
4. **What was just discussed** — the thread's `comment.items`.
5. **Ask.** Cheap in voice, and the one place a voice interface is *better*
   than a GUI: "the checkout screen or the settings one?" costs a second.

That list is why voice on this canvas can be good rather than a novelty. The
hard problem is already solved by the shared cursor.

## Three tiers of trace, which the product already has

The mistake available here is transcribing everything into the main thread. A
twenty-minute conversation becomes two hundred comments, and the thread that
was the project's channel becomes a log nobody can read next week. The agent
guide already refuses the text version of this: *"A thread full of 'working…'
posts is a thread nobody can read next week."*

Both transcripts are available (`input_audio_transcription`,
`output_audio_transcription`). The design question is where each tier lands,
and the product already draws all three lines:

| Tier | Where it goes | Why |
| --- | --- | --- |
| **The live transcript** | **Presence** — `session say`, the status under the face | Ephemeral by design: "costs no op, leaves no trace in the history, and vanishes when you stop." It is what the room sees while you talk. |
| **Decisions** | **One comment**, on the thread it belongs to | "Agreed: the slab type, and the answers move to a sans." Written when the exchange resolves, not while it happens. |
| **Actions** | **Operations** | Already ordered, replayable, undoable, and visible on both surfaces. |

The transcript is not the record. **The ops are the record**, and that is
already true of everything else on this canvas.

## Who speaks, when several agents are here

Voice has no `@`-mentions and no colour. A canvas with Charlie, Gina and Nico
on it needs an answer to *which of you just said that*, and it has to work
without looking at the screen.

- **A voice per agent.** `speech_config…voice_name` is per-session, and
  identity colour is already per-actor (`isocan identity --color`). A voice is
  the same idea in the other modality: assign it at the same moment, show it in
  the same places.
- **One microphone, one floor.** Do not open N Live sessions on one room. Three
  models listening to one microphone is three bills, three VADs racing to
  answer, and a conversation nobody can steer. **One live session holds the
  floor**; the others stay parked on `wait` and are reached the way they always
  are — through the thread.
- Which makes the live agent the vision's own **emissary**: the one in the
  room, speaking for and to a team that is not.

Handing the floor is then an ordinary sentence — *"ask Gina to look at the
type"* — which is a `thread.reply` mentioning Gina, which wakes her. No new
concept.

## A minute of it, concretely

> **You:** *(selects two screens)* "These two should use the same type scale."
> **Charlie:** "The slab one or the sans one?"
> **You:** "The sans."
>
> `session say` under Charlie's face: *"reading Type C and Type A…"*
> — and a `thread.create` anchored to the first screen.
>
> **Charlie:** "Gina's better at type — I've put it on the thread, she's parked."
> **You:** "Meanwhile move the settings screen under checkout."
>
> `items.move`. One op, one undo, on your screen before the sentence ends.
>
> *(Gina's version lands as v2 while you keep talking.)*
> **Charlie:** "Gina's back — there's a second version on Type C."
> **You:** "Fan it out… keep the new one."
>
> `item.setCurrentVersion`. The convergence op, spoken.

Every line above is an existing operation or an existing presence call. Nothing
in that minute needs a new concept — only a new way in.

## The honest costs

- **Audio leaves the machine, and that is a documented property being spent.**
  The daemon binds to `127.0.0.1` and `evals.md` names "nothing leaves the
  machine" as a Stage 0 property. Voice sends a person's speech — and everyone
  else's in the room — to Google. This must be a mode somebody turns on, never
  a default, and **presence must show it**: on a shared canvas, a live
  microphone is a fact the other people need to see. The product's own rule is
  that presence is honest.
- **Money, per minute, silently.** Every other expensive thing here is
  per-action. An open socket bills while nobody is talking. Ending the session
  when the tab is hidden is not an optimisation, it is the feature.
- **The 10-minute connection.** Sessions resume, but the reconnect is real and
  has to be invisible. Anything less and voice feels broken in a way clicking
  never does.
- **A model with hands.** A tool call is an op, and ops are real. `trash.empty`
  is not undoable and `canvas delete` needs `--force` — those must not be
  voice-callable at all, however the model asks. The safe set is a decision to
  write down, not a default to inherit.
- **Transcription is not free of consequence.** A wrong transcript that becomes
  a comment is a fabricated record. Decisions written from voice should be
  read back — "so: slab display, sans answers?" — before they are posted.

## What to build first

1. **The relay, with no tools.** Daemon holds the socket; browser streams PCM
   both ways; transcript to `session say`. Zero operations, zero risk, and it
   answers the question everything else depends on: is the latency good enough
   to talk to?
2. **Read-only tools.** `ls`, `show`, `who`, `activity` as function
   declarations. The agent can answer *"what's on this canvas?"* and still
   cannot change anything.
3. **The fast write set** — move, resize, retitle, star, `setCurrentVersion`,
   `thread.reply`. Undo already covers every one.
4. **Dispatch.** Slow asks become a comment on the main thread; the parked
   agents were already listening.
5. **A voice per agent, and the floor.**

Steps 1 and 2 are worth building even if the rest is never built, because they
answer the only question that matters early: whether talking to a canvas is
better than pointing at one, for the things people actually do here.

---

## What would make it fail

- **A second vocabulary.** Voice that can do things no operation expresses.
  The test is the replay: ops without audio must reconstruct the session.
- **Narrating instead of doing.** An agent that says what it is about to do,
  at length, is worse than a spinner. Presence already narrates visually; the
  voice should mostly be quiet.
- **The thread as a transcript.** Two hundred comments is a destroyed channel.
- **Voice as the only way to something.** Anything sayable must stay clickable
  and typable, or the isomorphism has quietly become three surfaces, one of
  which needs a quiet room and working ears.
- **A room that does not know it is being recorded.**
