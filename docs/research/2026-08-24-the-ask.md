# The ask: what the field built for the moment an agent needs a person

**24 August 2026**

**Where this stands, 29 Aug 2026: BUILT.** `openAsk` and `openAsks` were
already in core with the roster's `blocked` tier derived from them; the CLI
surface this recommended — `isocan ask` and `comment list --open` — landed on
29 Aug, which was the half that mattered. Before it, a person could see that
an agent was waiting and the agent could not list what it was waiting on,
which is the wrong way round for a feature about the moment an agent needs a
person.

One thing the recommendation could not have known: `itemThread` — the rule
that an item has ONE conversation, which ⇧C was fixed to respect — lived in
the web. `ask --item` was a line away from minting a second thread on an item
that already had one, reproducing the exact bug ⇧C had been fixed for. The
rule is in core now, where both surfaces read it.

The question: *when an agent needs a person — a decision, a confirmation, a
fact it cannot find — what has the field built to carry that moment, and what
would isocan's version be?*

Two earlier runs walked up to this hole from opposite sides without naming it.
[Agents on the canvas](2026-08-23-agents-on-the-canvas.md) found that the whole
category shipped divergence and skipped convergence;
[convergence.md](../projects/atlas/convergence.md) then designed the **answering** half
— `item.adopt`, `isocan choose`, the losers folded into the stack. Nobody has
designed the **asking** half. The atlas journey needs it too and says so in
plain words: Scene 2 has the skill "propose the structures it intends to show
and ask whether the shape is right", and Priya "answers the skill's other
question". Two questions, asked in prose, answered in prose, with nothing
anywhere recording that a question was outstanding.

The short version: between June 2025 and July 2026 every serious agent platform
grew a first-class object for *"I am blocked on a human"*, and they converged on
the same three parts — a question carrying a machine-readable shape, a state the
surface renders differently from ordinary chatter, and an answer that resumes
the work. isocan has the third part built and neither of the first two. The
version that fits here costs **zero operations**, because an open question is
something you *derive* from a thread rather than store on one.

## Standing findings, re-checked

- **[Agents on the canvas](2026-08-23-agents-on-the-canvas.md) (23 Aug)** —
  **changed, and in a way that re-grades its runner-up.** That survey's central
  observation ("the category converged on MCP plus a skill") treated MCP as a
  stable transport. It is not: the **2026-07-28 specification**, finalised on
  that date, is the largest revision since launch. The `initialize`/`initialized`
  handshake and the `Mcp-Session-Id` header are **gone**; each request carries
  its protocol version, client identity and capabilities in `_meta`; the core is
  now request/response and stateless. Tasks and MCP Apps became **extensions**
  rather than core features, and **Roots, Sampling and Logging are deprecated**
  (functional for at least twelve months). See §4 for what that does to the cost
  of an isocan MCP adapter — it fell, a lot.
- **[Design systems and tokens](2026-08-24-design-systems-and-tokens.md)
  (today)** — untouched by this run.
- **[JSON Canvas](json-canvas.md)**, **[agent skills](agent-skills.md)**,
  **[feature readiness](feature-readiness.md)** — checked on 22–23 Aug and not
  re-run one day later. One row gains a sibling: "Trigger agents on events —
  Assemble" is the *wake* half of the loop this survey is about; the ask is the
  *sleep* half, and it is cheaper.

## 1. What the field built, and what is actually in it

Six independent implementations, three of them specifications rather than
products. They do not cite each other and they arrived at the same object.

| where | the mechanism |
| --- | --- |
| [MCP elicitation](https://modelcontextprotocol.io/specification/2025-06-18/client/elicitation) (spec 2025-06-18) | a server sends `elicitation/create` with a `message` and a `requestedSchema` — deliberately a **restricted** JSON Schema: flat objects, primitives only, no nested structures, no arrays of objects, so any client can render a form without a schema engine. The response is one of three actions |
| [MCP 2026-07-28](https://blog.modelcontextprotocol.io/posts/2026-07-28/) | the same idea rebuilt for a stateless core: **Multi Round-Trip Requests**. The server returns `resultType: "input_required"` carrying the input requests plus an opaque `requestState`; the client gathers answers and **re-issues the original call** with `inputResponses`. The pending question stops being a held connection and becomes data in a payload |
| [Linear Agent Interaction](https://linear.app/developers/agent-interaction) | an `AgentSession` has six states — `pending`, `active`, `error`, `awaitingInput`, `complete`, `stale` — and the agent never sets them. It emits **activities** (`thought`, `action`, `elicitation`, `response`, `error`); emitting an `elicitation` is what moves the session to `awaitingInput`. The human's answer arrives back as a `prompted` webhook |
| [Linear's guidelines](https://linear.app/developers/aig) | the principles behind it, and two are load-bearing: an agent must make its internal state legible — "thinking, waiting for input, executing, or finished working" — and **"an agent cannot be held accountable"**, so responsibility stays with a named human through the delegation |
| [A2A, life of a task](https://a2a-protocol.org/latest/topics/life-of-a-task/) | `input-required` and `auth-required` are **interrupted** states, formally distinct from terminal ones (`completed`, `failed`, `canceled`, `rejected`). Work that is paused on a person is not work that has stopped, and the protocol refuses to let the two look alike |
| [LangChain](https://docs.langchain.com/oss/python/langchain/human-in-the-loop) / [OpenAI Agents SDK](https://openai.github.io/openai-agents-js/guides/human-in-the-loop/) and kin | the framework version: middleware pauses before a tool call, the run serialises, and resuming continues "as if it had never been interrupted" |

Read across the row and the mechanism is the same three parts every time.

**One: the question carries a shape.** Not "the agent wrote a sentence with a
question mark in it" — a structure a surface can render as a control. MCP's
choice is the instructive one, because it is a restriction rather than a
capability: enums with `enumNames`, booleans, strings, numbers, and explicitly
*not* nested objects. A question shaped so simply that no client can fail to
draw it.

**Two: the state is derived from the activity, not asserted by the agent.**
Linear is emphatic — "you don't need to manage agent session state manually".
The agent says what it did; the platform decides that this means it is waiting.
An agent that had to remember to set and clear a flag would forget, and a stale
`awaitingInput` is worse than none.

**Three: declining is not ignoring.** MCP's three-action model is the sharpest
statement of it — `accept` with content, `decline` (an explicit no), `cancel`
(dismissed without choosing) — and servers are told to handle all three
differently. The distinction that matters for a canvas is the one at the
bottom: silence is not an answer, and a surface that renders silence and
consideration identically has thrown away the only signal that anybody is
stuck.

Underneath, the complaint that makes this worth building. The practitioner
literature on running several agents at once is unanimous that verification, not
generation, is the bottleneck — and the sharpest version of it is that a
reviewer "receives a completed diff without the same implementation journey or
decision trail, and has to reconstruct intent" (secondary sources, surveying
2026 practice; the underlying benchmark numbers are second-hand and are
therefore not quoted here). The ask is where the decision trail is *cheapest* to
capture, because at that moment the agent already knows what the decision is.

## 2. Whether we already have it: most of it, and not the part that matters

This is the half of the survey that took the longest, and it changed the
recommendation twice.

**We have the wake.** `isocan wait` blocks until something addressed to this
agent lands, and its help already says a comment wakes you when it @-mentions
you, lands in a main thread, **or lands in a thread you wrote in**. So an agent
that asks a question in a thread and then parks is already woken by the answer.
The resume half — the expensive half in every framework in that table — needs
nothing. It is done.

**We have the pause.** While parked, the agent's cursor says "waiting for
you…", and waking on a summons moves its presence onto the thread that woke it.

**We have "somebody picked it up".** `onit.ts` and `OnIt.tsx` answer the
question from the other direction — `workersOn` for who claimed a thread,
`summonedBy` for who was woken but has not spoken yet, `listeners` for whether
anybody *could* pick it up. The file's own comment names the motivation: "asking
for work and hearing nothing is the worst moment in this app".

**We have a comment that is a control message.** `/cancel` is a comment whose
body parses as a slash command, read by `latestCancel` and `cancelledSince`, and
the reasoning is written down: a cancellation "lands in the history where 'why
did this stop halfway' gets answered later, it reaches every surface, and it
needs no new op". That is the precedent this proposal runs on.

**We have the answer's payload, already structured.** A comment resolves its
`#Title` references at authoring time into `comment.items` — an array of item
ids. So `which of these ships? #Warm #Cool #Loud` **already stores the candidate
set as data**. The machine-readable shape MCP had to invent a schema subset for
is, for the one question a canvas asks most often, sitting there unused.

**What we do not have is the state.** Nothing on a canvas distinguishes a
comment that needs an answer from a comment that reports one. The unread
machinery — pin badge, dimmed face in the pile, tab title count, toast — is
*read-state*, kept per viewer in the browser. It tells you something arrived and
clears the moment your eye passes over it. Read the question, get distracted,
and the canvas has forgotten that anybody is stuck. And there is no query, on
either surface, for "what am I holding up" — `isocan comment list` lists
threads, not obligations.

So the gap is exact: **isocan can be asked and cannot be seen to owe an
answer.** OnIt made silence legible in one direction. The other direction is
still silent.

## 3. The shape here: an open question is derived, not stored

The whole feature is one pure function.

**The ask is a comment.** `/ask which of these ships? #Warm #Cool #Loud`, posted
by `thread.reply` or `thread.create` like anything else. No new operation, no
new field, no reducer change, no inverse — the same move `/cancel` already
makes, for the same reasons.

**Open-ness is computed, never written.** In core, beside `latestCancel`:

```ts
openAsk(thread): { comment: Comment; candidates: string[]; asker: Actor } | null
```

A thread has an open ask when its last `/ask` has no comment after it from
anybody but the asker. That is it. Posting an answer closes it *by
construction*, which is Linear's rule ("you don't need to manage session state
manually") arrived at from the other end — there is no flag to leave stale,
nothing to desynchronise between the two surfaces, and no op whose inverse could
be wrong. `candidates` is `comment.items`, already resolved.

**Both surfaces, per the house rule.**

- **CLI, asking**: `isocan ask "<question>" [--item <ref>…] [--thread <ref>]` —
  posts into the main thread by default, or anchors a new one to an item. The
  verb exists so the agent guide can name it; the op underneath is
  `thread.reply`.
- **CLI, reading**: `isocan comment list --open` — the open asks on this canvas,
  who is waiting on each, and how long. A flag on a verb we have, not a verb we
  do not.
- **Web, asking**: `/ask` in any composer, like every other slash command.
- **Web, answering**: the ask renders with its candidates as chips that are
  already item references — so the answer is a click, and once
  `item.adopt` lands, *the same click is `isocan choose`*. Before it lands, the
  click posts a reply naming the item, which is what a person does by hand
  today.
- **Web, noticing**: an unanswered ask is the one thing that must **not** clear
  on read. Its author's face in the pile wears a mark that clears when somebody
  replies, not when somebody looks. That is the whole product of this feature in
  one sentence.

**What it deliberately does not have.** No schema. MCP needed `requestedSchema`
because a chat client has no other way to render a control; a canvas has items,
and `#Title` chips are a better answer to "pick one of these" than a JSON enum
because the options are the actual things, in the actual place, with their own
versions and threads. If a second shape is ever needed, add it when two real
asks want it — the rule extensions.md already sets for its declarative
vocabulary.

**And no third action.** MCP separates `decline` from `cancel` because a
protocol cannot read prose. Here the answer *is* prose, and the only distinction
worth machinery is open versus answered. Say so, and do not build the enum.

**The cost, honestly.** One pure function in core with a test, one CLI verb, one
list flag, one render, one line in the agent guide. It touches no reducer, adds
no op, needs no auth, needs no model, and cannot be undone wrongly because there
is nothing new to undo. This is the cheapest thing in any of the five surveys in
this directory that changes what the product *is*.

**The risk to design against**, since every feature here gets one: an ask that
somebody answers by editing an *earlier* comment rather than posting a new one
leaves the question open forever. `comment.update` exists and working notes use
it heavily. `openAsk` must key on position in the thread, not on timestamps, or
a rewritten note will silently close somebody else's question.

## 4. The frame that could speak, and a spec that says how

The second finding fell out of checking the first, and it is the more surprising
one.

**MCP Apps** ([blog](https://blog.modelcontextprotocol.io/posts/2026-01-26-mcp-apps/),
[spec `2026-01-26`](https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/2026-01-26/apps.mdx))
shipped as the first official MCP extension and, as of the 2026-07-28 revision,
is a permanent one. The mechanism: a server publishes an HTML resource under the
`ui://` scheme with mime type **`text/html;profile=mcp-app`**; a tool binds to it
through `_meta.ui.resourceUri`; the host renders it in a sandboxed iframe and
opens a **JSON-RPC channel over `postMessage`**, on which the frame may call a
fixed, named set of methods.

Now put that beside isocan.

| `ext-apps` method | what it already is here |
| --- | --- |
| `ui/notifications/size-changed` | `item.resize` |
| `ui/message` | `thread.reply` on the main thread — a canvas has a host chat, and it is docked on the left |
| `ui/open-link` | `item.add` of a `text/uri-list` blob: the mini-browser (`browseritem.ts`) |
| `tools/call` | an `Operation`, or a slash command |
| `resources/read` | the blob route / `isocan get` |
| `ui/request-display-mode` | fit the item — a camera act, correctly not an op |
| `ui/initialize` | a handshake that would have to say which actor the frame speaks as |
| `ui/update-model-context` | **nothing.** isocan ships no model, and this method has no meaning here |

Eight methods; six of them are things isocan can already do and has verbs for.
An MCP App is an HTML file with a mime-type parameter, and isocan items *are*
files with mime types — so the artefact needs no conversion at all.

And then the part that is genuinely startling, found in the code rather than
inferred. `packages/web/src/lib/measure.ts` **already implements this bridge**.
It builds a frame with the same `sandbox="allow-scripts"` the real item gets,
injects a probe that calls `parent.postMessage({ isocanMeasure: true, width,
height }, "*")`, listens for it, guards with `if (e.source !== frame.contentWindow)
return` — the correct guard, because an opaque-origin frame's messages arrive
with `origin: "null"` and an origin check would be worthless — and gives up
after 2500ms so a page that never answers cannot hang the gesture. Its comment
says the design rule out loud: "Measuring must not be a reason to relax it, or
the measurement becomes the hole."

`isocanMeasure` **is** `ui/notifications/size-changed`, invented here
independently, one message wide. The host, the sandbox, the guard and the
timeout are built. What is missing is a name for the protocol.

**What that means concretely.** Two of those rows can ship without touching the
sandbox at all, because receiving a message needs nothing — a frame with
`allow-scripts` can already post to its parent, which is exactly what measuring
proves. `ui/notifications/size-changed` becomes a live item that keeps its box
right, and `ui/message` turns an agent-built prototype into a thing that can
*talk back*: a click inside a mock lands in the main thread, and the agent
parked on `wait` hears it. That is the ask and the answer again, drawn instead
of typed.

**And the collision, which is the finding.** The spec says hosts rendering UI
content **MUST** sandbox with `allow-scripts` *and* `allow-same-origin`.
`ItemView.tsx:670` renders an HTML item with `sandbox="allow-scripts"` and
nothing else, and [content-origin.md](../projects/atlas/content-origin.md) spends a page
explaining why adding the second token on the app's origin hands a file somebody
dropped on a canvas the badge cookie and the whole API. So **conformance is
blocked on the content origin** — which that document already called
load-bearing for three separate things. This is the fourth, and the first
argument for it that comes from outside this repo.

Two rules would have to travel with any of it, both already written in
[extensions.md](../projects/extensions/design.md): the frame is a **dialer, not a
vocabulary** — it may only ask for what a person could ask for, and never gets a
new `Operation` of its own — and a UI-initiated act that speaks as the viewer
needs the viewer's consent, so `ui/message` opens the composer prefilled rather
than posting silently. The spec agrees on the second point; the first is ours
and is stricter.

## 5. One that is the wrong shape, and why

**Canvas-level checkpoints.** Claude Code's checkpointing saves state before
each change and `/rewind` restores "the code, the conversation, or both"
([Anthropic, 29 Sep 2025](https://www.anthropic.com/news/enabling-claude-code-to-work-more-autonomously)).
It is the most-loved safety feature in the category and the obvious thing to
want here: *put the canvas back to how it was before the agent started.*

It is a bad fit, and the reason is worth stating because it is a property of
isocan rather than a cost.

isocan's undo is **actor-scoped** on purpose — your undo walks your own ops and
never a collaborator's. A canvas-level rewind is the opposite claim: it says one
person may revert everybody, including work done in parallel by people who never
agreed to it. On a single-player canvas the two are the same and the feature
looks free; on the multiplayer canvas the whole `docs/projects/multiuser/phases.md` build exists to
produce, it is a footgun with a keyboard shortcut. Then the mechanics: it would
need a new op with an atomic composite inverse — the same expensive half
convergence.md ran into, since `invert.ts` returns one `Operation` or `null` —
and it would run into the compaction horizon, past which the ops it wants no
longer exist (`oplog-archive.jsonl` keeps them, but not reachably).

The want underneath it is real and already served differently: an item's version
stack *is* a per-object checkpoint history, `S` fans it out, and
`item.setCurrentVersion` restores one. Good idea, wrong shape for us — and the
right response is to say why in the help, not to build a rewind.

## What to be suspicious of, from this run

- **An MCP adapter because MCP is the standard.** Still a distribution bet, as
  [23 Aug](2026-08-23-agents-on-the-canvas.md) said. What changed is the price,
  and it changed a lot: with the 2026-07-28 stateless core there is no
  handshake, no session id, no held stream — a conformant server is
  request/response over ordinary HTTP, which is what `/api/ops` already is. The
  merit case is still weak; the cost case largely evaporated. Record both.
- **A form builder.** MCP's `requestedSchema` is a good idea *for a chat
  client*. Copying it here would mean inventing a widget vocabulary to avoid
  using the items that are already on the canvas. Resist for as long as
  possible; the rule is two real asks, not one imagined one.
- **Anything that needs a model.** `ui/update-model-context` is the one method
  in the MCP Apps set with no meaning here, and that is fine rather than a gap.
  isocan ships no model.
- **Numbers.** The review-bottleneck figures circulating in the 2026
  practitioner literature trace to a benchmark report this run did not read at
  source, so none are quoted. The specification dates are from the
  specifications.

## Recommendation

**Ship `/ask`.** A comment that parses as a question, an `openAsk` in core that
derives the open state from the thread, `isocan ask` and `isocan comment list
--open` on one surface, chips and an unclearing mark on the other.

Why this one:

- **It costs no operation.** Not "one small op" — none. It is a pure function
  and a render, which is the same shape as the last two things this directory
  recommended and the reason both were cheap.
- **It completes a loop that is already three-quarters built.** `wait` already
  wakes the asker on the answer. `OnIt` already made silence legible one way.
  `#Title` already resolves the candidate set into structured data nobody reads.
  The missing quarter is *visible obligation*.
- **It is the input half of a design that already exists.** convergence.md
  designs `item.adopt` and `isocan choose` as the gesture for "this one won".
  `/ask` is the gesture for "which one?" — and in the web app they are literally
  the same click. Building the answer without the question ships half a
  conversation.
- **The journey needs it.** Atlas Scene 2 has an agent asking twice before it
  draws anything, and today both asks vanish into prose.
- **It is what the field converged on**, from six directions that do not cite
  each other, and isocan's version is cheaper than all of them because a canvas
  has somewhere to put the options.

**Runner-up 1: the frame that speaks — `ui/notifications/size-changed` and
`ui/message`, under the `ext-apps` names.** It lost on sequencing rather than
merit: full conformance needs the content origin, and the two-method subset that
ships today buys a live-fitting prototype and a mock that can post to the main
thread — delightful, and still convenience before capability. But it is the
clearest "do not invent this" in the survey. When tier 3 of extensions.md
arrives, `measure.ts` should be widened into the `ext-apps` methods rather than
into a private isocan bridge, because a private bridge is a third vocabulary and
this one is already written down by somebody else. Build it second.

**Runner-up 2: the tool manifest generated from the `Operation` union.** One
artefact would serve three consumers — an MCP adapter, an MCP App frame's
`tools/call`, and the `does` field extensions.md validates on a declarative tool
— and generating it from the union with `surface.test.ts` watching is the only
way the one-vocabulary rule survives more than two surfaces. It lost because it
is infrastructure for things not yet decided, and because the honest reason to
want it today is still fear that an MCP-only harness cannot find isocan. Worth
building the day the second consumer is real, and not before.
