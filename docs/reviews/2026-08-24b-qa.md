## 1. The title row: three guards, and two of them could not fail

The working tree I was handed changed `ItemView.tsx` and `styles.css` and I was
asked what guarded it. The answer was: nothing, and then — once `5c1d1d5`
landed a guard — nothing that could say no.

### 1a. `worldchrome.test.ts` did not watch the row the bug was in

`worldchrome.test.ts` (`60a1284`, one day old) names three selectors that live
in world space: `.resize-handle`, `.item.selected`, `.item.peeked`. It did not
name `.item-titlebar`, and `.item-titlebar` is where the very next commit found
a bug.

Two mutations on the working tree's CSS, run against the whole web suite:

| Mutation | Result |
| --- | --- |
| `bottom: calc(100% + 1px + 7px / var(--scale, 1))` → `bottom: calc(100% + 8px)` | **SURVIVED**, 226/226 |
| `padding: 0 calc(5px / var(--scale, 1))` → `padding: 0 5px` | **SURVIVED**, 226/226 |

Both are the bug this weekend's commits were about, restored, with the suite
green. The other five mutations in the same batch (the selection outline, the
peek offset, a handle offset, `--scale`'s publication, the star's
`margin-left: auto`) all died on the first run — the file is good, it was
simply pointed one selector short.

**Fixed.** `WORLD_CHROME` now names eight selectors including `.item-titlebar`
and the four corner handles individually (lesson #10: the shared rule gives
them their size, four separate rules give them their positions). `padding` is
added to the `SIZING` property list because the row's inset is one, with a note
saying why `font-size` deliberately is not. **Proved without the fix**: against
`HEAD:packages/web/src/styles.css` — the version before the working tree's
change — the file fails 2 of 6 with `.item-titlebar { left: 1px } is in WORLD
pixels`. **8 mutations re-run, 8 killed**, including one-axis mutations of the
handle's width and its height separately.

### 1b. The vacuity guard was itself vacuous — lesson #16

`worldchrome.test.ts`'s first case reads:

```ts
it("has rules for every selector it claims to check", () => {
  // Without this the whole file passes vacuously the day a class is renamed.
```

It cannot fail. Two mutations, whole web suite, 226/226 green each time:

- **Delete `.item.peeked { outline: … ; outline-offset: … }` outright.** The
  peek ring is gone from the product. `.item.peeked .item-titlebar { opacity: 1 }`
  keeps `rulesFor` non-empty, the existence check passes, and with no lengths
  left the sizing sweep has nothing to reject.
- **Rename `.resize-handle` to `.resize-handle-base`.** Every corner handle
  loses its 12px, its border and its radius. `.resize-handle-nw` and its three
  siblings are *superstrings* of `.resize-handle`, so `includes` still finds
  them.

This is the third appearance of the substring-guard shape in these reviews
(`surface.test.ts:49` was the architect's; `oneblock`'s descendant tail is a
cousin). The generalisation is lesson #16: **existence and function are
different claims, and an existence check any relative can satisfy has asked
neither.**

**Fixed** with two functions instead of one. `mentions(selector, text)` is
boundary-aware — a class name ends where `[-\w]` stops — and `ownRule(selector)`
requires a rule whose selector *list* contains exactly that string. The new
case asserts both halves: the rule exists under that exact name, **and** it
carries at least one length that divides by `--scale`, which is what "this is
world chrome" means. 4 mutations, 4 killed.

### 1c. `titlebar.test.ts` had the identical hole, hours old

`5c1d1d5` landed `packages/web/test/titlebar.test.ts` mid-review with the same
`selector.includes(".item-titlebar")` and the same
`expect(titlebarRules().length).toBeGreaterThan(0)`. Run **on its own**, it
passed 3/3 with the `.item-titlebar` rule deleted entirely, and 3/3 with it
renamed to `.item-titlebar-row`. Six other rules mention the class, so the list
was never empty and the two real checks had nothing to look at. The whole web
suite caught it — but only because §1a had just put `.item-titlebar` in
`worldchrome`'s list, which is a thin thread for a file whose entire subject is
that one rule.

**Fixed** the same way, and split into two cases so each says what it is for:
`has the rule that places the row, under that exact name` (own-rule, and it must
carry a `top`/`bottom` that divides by `--scale`), and `has every rule that
mentions the row` (the sweep's own parser check, > 3). **4 mutations, 4 killed,
running the file alone**: deleted, renamed to a superstring, offset back to
world px, and the selected-only step-in restored.

### 1d. "A floor that was not one" had no guard at all — lesson #17

`e0dc1b2`'s message describes a second, worse bug: the name's width was
`Math.max(MIN_NAME_ROOM, item.width * scale - STAR_ROOM)`, so at 13% a 480-unit
item (62 screen px) with a 26px star had the name handed **48** and drawn
straight through the star. *A minimum that exceeds what exists is not a
minimum.*

Nothing guarded it. The rule lived inline in `ItemView.tsx` beside a
`useCanvasStore` selector, which is lesson #5 — a rule with no importable home
cannot be tested — one file along from where lesson #5 was learned.

**Fixed** by moving it to its one home. `nameRoom(width, scale)` and
`nameFits(width, scale)` now live in `packages/web/src/lib/chrome.ts`, beside
`hasRoomForChrome`, whose docstring already said the reason: "both live here so
they can be reasoned about without a browser". `ItemView.tsx` imports them.

The guard is stated **without the constants**, which is the part worth copying.
A floor is a *bend*, so:

```ts
expect(nameRoom(2 * width, scale) - nameRoom(width, scale)).toBeCloseTo(width * scale, 6);
```

over six widths and six zooms. That survives retuning `STAR_ROOM` or
`CHROME_INSET` and cannot be walked past by a floor of one pixel — which is the
tension lesson #11 named (freeze a tuning constant and the test lies; leave it
alone and the test says nothing). The answer here is to find the shape the
constant cannot change.

**9 mutations, 9 killed:** the original `Math.max(MIN_NAME_ROOM, …)`; a 1px
floor; the star losing its room; the inset counted on one side only; the
measurement in world units instead of screen; `nameFits` asking about the item
rather than the room left; the CSS padding drifting from `CHROME_INSET`;
`CHROME_INSET` drifting from the CSS; and the selected-only step-in returning.

**And one of my own tests was written around the keystroke** — exactly what
lesson #4 warns about, caught within the hour by the other session changing the
numbers. `matches the stylesheet's padding` required
`padding: 0 calc(<n>px / var(--scale))`, so when the inset legitimately went to
zero and the CSS said `padding: 0`, my test failed on correct code. That
session fixed it properly (two legal spellings, `0` or a scaled calc, and both
must agree with `CHROME_INSET`). Recording it because the lesson is that a
cross-file constant guard must parse the *value*, not the spelling.

## 2. Duplicate and out-of-order ops: the scan was tested only at depth one

`Engine.alreadyWritten` (phase 10) is the answer to "the tab retried because it
never heard back". It walks the oplog backwards for the client-minted key.

**8 mutations on the idempotency path, 6 killed as found.** One equivalent
mutant (scanning forwards; envelope ids are unique, so direction is cost, not
answer). One real survivor, and it is the one that matters:

| Survived | What it means |
| --- | --- |
| the loop truncated to **the last entry only** | A replay is recognised only if nothing has landed since. Everything further back is applied a second time. `idempotency.test.ts` green, 7/7. |

Every case in that file posts the retry immediately after the op it retries.
The real shape is the opposite of that: a tab that lost its answer has a queue
behind it, and the seconds before it retries are seconds in which anybody on the
canvas can write. The docstring argues for the *direction* of the scan
("a replay is by construction the most recent thing that could match") and
nothing argues for a depth of one — but a test is the only place that
difference exists.

**Added** two cases: the retry buried under five of the actor's own ops, and the
retry buried under **another actor's** write, which is the ordinary two-people-
on-a-canvas version and also checks that the replay is a no-op rather than a
rewind (Sam's move survives). **4 mutations re-run, 4 killed**, including a
clean `Math.max(0, length - 3)` truncation that does not crash. Lesson #18.

Also checked and correctly guarded, so the next run does not re-do it: the
"which canvas does this op belong to" rule has **two** copies (`engine.ts:483`
in `alreadyWritten` and `engine.ts:1057` in `forwardSubmit`) and both die when
mutated separately — the replica half through `home-link.test.ts`. And

## 3. The flake this run: the copy that never got the fix

The baseline run failed on
`restart.test.ts > a daemon that outlived its build`, with:

```
Error: the other copy never came up
```

That sentence is the exact thing lessons.md already forbids —
*"a timeout message with no evidence teaches people to re-run"* — learned in
`daemon-takeover.test.ts`, written down, and never applied to this file.
`startOtherCopy` had `stdio: "ignore"` (throwing away the one thing that
distinguishes a slow machine from a crash), no fail-fast on an exited child,
and a hardcoded 15s budget that nobody re-measured when `vitest.config.ts` moved
the global limit to 30s.

**Fixed**, and it is a diagnostics fix, not a weakening: nothing about what the
test asserts changed.

- `stdio: ["ignore", "ignore", "pipe"]`, stderr captured.
- Fails **immediately** once the child has exited.
- Reports elapsed time, how much of it was the recursive copy of three
  packages, the root it wanted, what the last probe saw, and the child's
  stderr.
- Budget 15s → 25s, inside vitest's 30s so the failure carries this message
  rather than the runner's, with the reasoning written beside it.

**Proved** by breaking the copied `bin/isocan.js` so it throws at import:

```
gave up after 164ms waiting for the other copy of isocan to answer (61ms of that was copying it)
  wanted root: /private/var/…/isocan-other-copy-h97AZj
  last probe:  nothing answered on 20002 (TypeError: fetch failed)
  other copy:  pid 97905 exited (code 1, signal null)
  its stderr:  Error: deliberate: the other copy cannot boot …
```

164ms with a reason, instead of 15,000ms of silence.

**I did not reproduce the original timeout.** Three runs of the file alone were
green (6.9s, 6.5s, 16.2s — note the third), and under 28 busy loops on a
14-core box already at load 12, four daemon-spawning CLI files ran 41/41 green
in 42.8s. So the honest statement is: the 15s budget was the marginal number,
this machine will not reach it on demand, and the change that matters is that
the next occurrence will say which of the three causes it was.

**And that run turned up a real one.** `restart.test.ts:157` asserted
`expect(before.root).toMatch(/isocan$/)` — a claim about what somebody named
the folder. It is red in a `git worktree`, in a clone called `isocan-fork`, and
in the tarball CI unpacks: a red suite about nothing, in the place a red suite
is most expensive to read. Replaced with an exact comparison against the
resolved repo root, which is stronger *and* portable — it says the daemon is
running from the tree the test is running from, which is what the file is
about. **2 mutations, 2 killed** (the daemon reporting one directory up; the
daemon reporting its cwd).

## 4. The edges: a range parser whose four boundary branches were all optional

Working from the edges the standing brief names — "a blob at the size limit".

**7 mutations on `parseRange` and the blob route, 3 killed as found.** Four
survivors, and every one of them is a branch the author wrote *on purpose*:

| Survived | Reachable how |
| --- | --- |
| `if (start >= size)` → `>` | `bytes=20-` on a 20-byte blob. This is what `curl -C -` sends when the download is already complete. |
| `if (end < start)` deleted | `bytes=9-5` → `Content-Length: -3`. |
| the suffix clamp `Math.max(0, size - wanted)` | `bytes=-1024` on a 20-byte file — a media element reading a trailer — seeks to offset **-1004**. |
| `if (wanted === 0)` (`bytes=-0`) | RFC 9110 says a zero-length suffix is unsatisfiable. |

Every existing case asks for a range comfortably inside the blob or comfortably
outside it. Nothing sits on a boundary, so the boundaries were documentation.

**Added** four cases, each on the exact edge, each with a negative control so it
is a boundary and not a blanket refusal (`bytes=19-` still serves one byte;
`bytes=9-9` is still 206). **3 of the 4 mutations now die.**

`start >= size` → `start > size` **is an equivalent mutant**, and it is named
here so the next run does not chase it: at `start === size` the open form
computes `end = size - 1`, which the `end < start` check catches. The two
guards overlap on exactly that input. Mutating **both at once** is killed by
the new test, which is the property that matters.

**Also added, and this one is a reachability argument turned into a test.** The
parser has no branch for `size === 0`, and does not need one — a suffix range on
a zero-byte blob would compute `end = -1` and answer
`Content-Range: bytes 0--1/0`. It never happens because **all three doors**
refuse a zero length independently: `POST /blobs` checks `data.length === 0`,
and `upload-url` and `register` both go through `badUploadRequest`'s
`size <= 0`. Three copies of one rule, none mentioning the others (lesson #10).
`cannot make a zero-byte blob by any of the three doors` asserts the argument,
so the day one of them relaxes — an empty file is an ordinary thing to drag onto
a canvas — the range parser's missing branch is found by a test rather than by a
user. **2 mutations, 2 killed.**

## 5. Names that are not English: the negative controls were all ASCII

`mentions.ts` says out loud that names are free-form, "spaces, emoji". Emoji
are genuinely covered (`Kenny 🤖`, and well). The two rules that keep `@` honest
were not.

**7 mutations on `mentions.ts`, 6 killed as found.** The survivor:

| Survived | What it means |
| --- | --- |
| `isWordChar` from `/[\p{L}\p{N}_]/u` to `/[A-Za-z0-9_]/` | Every non-Latin letter becomes a separator. `سلام@دیون` — an `@` in the middle of a word, the same shape as an email address — becomes a mention; and `@دیونم`, a longer word that merely starts with somebody's name, resolves to them. |

The existing controls are `dimitri@example.com` and `@Nicolas is someone else`.
Both are ASCII, so the `u` flag and the Unicode property escapes were never
exercised. Same rule, other script — lesson #10 again.

**Added** the two controls in Persian, plus a positive case so the pair brackets
rather than blanket-refuses. **3 mutations re-run, 3 killed** (ASCII-only
boundary; the leading check deleted; the trailing check deleted).

**Also added, and deliberately not "fixed": two people with one name.** This
product makes them on its own — agents are named by their harness, so two
"Claude"s is the default case, and `actorsAnswerTo` keeps old names alive so a
rename onto somebody else's name is one keystroke away. Measured:
`@Claude` reaches **exactly one** of them, and nothing anywhere says the other
was meant. Which one falls out of `Array.prototype.find` over a length sort,
which means it depends on sort stability and on the order the caller happened to
collect actors in.

Deciding whether `@Claude` should reach both, or be disambiguated in the menu
before it is ever written, is a design question and not a test's to answer. What
is a test's to answer is that the answer is **stable**, and that the loss is
visible to whoever comes to fix it. Three cases pin it, with `KNOWN LOSS`
written in the body. **1 mutation** (the last matching candidate wins instead of
the first) kills 4 tests.
