# Review that keeps its scope and repair that keeps its context

The debt is that a source audit and a manually authored receipt do not make a
review run. The existing repair fences the screen version, but its ordinary
`item.edit` is not an admitted task transition: repairing a selected target
makes that task's original context stale. This phase adds a narrow repair act
and shared, resumable review artifacts. It reuses the analyzer, governing
resolver, normal version store and existing completion receipts.

## One review, with three independent readings

Both agent entrances follow the same `design workflow` procedure and `design
review` progression. The acting harness performs its actual supported tools
between steps; the daemon does not acquire a model, browser or quality judge.
Reading a plan or opening a URL does not execute a check. The shipped path
must ingest the resulting attributed observations and use them in its next
step, rather than merely returning a checklist.

Starting captures an admitted request/epoch, exact output and relevant context,
full target metadata/scope, governing selection, analyzer version and agreed
obligations. The agent derives sensible task, state and viewport obligations
from the brief and delivery. It does not ask the person to configure technical
tools or approve another specification. A connected app names its actual
repository revision, build and runtime. A canvas HTML preview cannot meet that
contract. Wireframes receive fidelity-appropriate obligations.

Each inspection retains three readings separately:

- Source diagnostics come from the existing shared analyzer, with input hash,
  rule version, governing identity, findings, candidates, prerequisites and
  unsupported/unexamined coverage. No new competing auditor or quality score.
- Browser/task observations identify the actual output/runtime, tool/version,
  action, expected and observed result, state, viewport and retrievable evidence.
  Passing observations must cover each declared required task/state/viewport.
A screenshot alone cannot establish saving or correction.
- Craft findings explain hierarchy, composition, typography, content and state
  treatment against this brief. They retain rationale and criticality, separate
  from deterministic diagnostics and later independent human preference.

The initial review is reserved once. A failed review leads to a repair proposal
and affected rechecks without another permission ceremony within the authorized
scope. At most **two repair attempts** are reserved before generation/work;
invalid output and no-op proposals consume their attempt too. Transport retries
reuse a reservation. If defects remain after two attempts, deliver a failed or
unverified draft with named limits. An unavailable browser is unverified.
Explicit audit-only intent preserves its requested inspection scope and reserves
no repair attempt. `design audit` remains source-only. Ordinary add/edit source
advice never starts a paid model turn.

Source findings and source coverage remain different facts. Actual actionable
diagnostics or off-system values make Source failed; a real report with bounded,
unexamined or omitted coverage makes it unsupported when no findings remain.
Unreadable source or governing identity is unavailable. A run may be ready for
its agreed scope with explicitly reported unsupported static coverage only when
every required task and craft observation passes with readable exact evidence,
its inputs remain current, and no source findings or critical defects remain.
Finishing carries those coverage limits into the receipt. Browser success never
changes the analyzer's coverage reading, and JavaScript alone does not make a
working interactive task categorically unready.

## Shared evidence artifacts, local pending intents

A review run is an ordinary versioned JSON canvas artifact with a bounded
`design.review` discovery property and strict, versioned report schema. It names
its exact admitted request/brief, run ID, optional preceding run, captured plan,
initial inspection, repair reservations/results, observations and current step.
Its contents are **authored reports**, not a new daemon quality authority.
Actual version authorship supplies attribution; a body cannot impersonate a
verifier. Keep its evidence and exact source references readable through the
same API/CLI/browser read model.

New report and offer creations also carry ordinary `design.review.request` and
`design.review.run` string properties naming their request and run. Recover
those discovery bindings from the original canonical creation, including its
archived form, before fetching historical bodies. Mutable current properties
cannot move old history to a different task. Validate each readable body against
its creation binding; contradictory creations remain unavailable for every
scope they name. This is discovery metadata, not admitted quality authority.
A filtered read can ignore history proven to belong to another request/run;
one old run's lost bytes cannot block an unrelated task's first inspection.
Readable older reports can supply a legacy binding; truly unidentified history
stays explicitly unavailable rather than being silently assigned elsewhere.

Use conditional ordinary adds/edits for this artifact, preserving stable item,
version and operation IDs. The shared progression validates each append against
its captured prior version. A run's prior pass identities/records remain in its
cumulative document and version history; a fresh process reads them before
working. Inspect live plus archived canonical operations when recovering
reservations or accepted repairs. Missing, malformed or contradictory history
is unavailable, never a fresh zero counter. Expose an unknown remaining budget
as `null`, not a numeric count: unavailable history blocks progression, and the
surface says why the budget cannot be established. Conflicting canonical writes
that reuse an ordinary report version ID must remain visible as a contradiction;
a map keyed by that ID cannot replace the original evidence or its attribution.
A second process cannot reserve
against a changed run version. Undo, an entrance switch, a missing local file or
a new epoch does not silently replenish this run's budget. An explicitly
requested new review may create a linked run with a reason; the automatic
repair loop cannot escape its cap that way.

The local CLI/browser journal stores unsent or uncertain **immutable** intent,
including the acting identity, full payload and all IDs. Validate authored input
before freezing it; acknowledge journal storage before every send, including
Retry. Another actor may read the pending state but cannot silently submit it
as its own work. An accepted write is separate from a stale or unavailable
follow-up read. Archive-before-reset preserves a refused draft; uncertainty is
not permission to replace its identity.

Each retained report references actual evidence artifacts. Ordinary live items
and versions own their bytes; later canonical completion receipts retain exact
check references using the existing flat roots. Archived operation identity does
not promise eternal blobs after every byte owner is removed. Missing evidence
stays unavailable. A JSON hash alone does not become a new GC root. Source-policy
reads retain their permissions, and private sources are not copied implicitly.

## One explicit repair operation

Add exactly one public `design.repair` operation. It materializes **one ordinary
conditional `item.edit` effect**, with its ordinary one-item inverse. It creates
no comparison, preference comment, admitted-HTML marker or multi-operation batch.
Existing explicit design-audit repair and task-bound repair use this shared act.
The former has no request binding; the latter carries its exact admitted
brief/request/epoch and review-run/pass provenance. The run report is evidence,
not an independent permission grant.

The public intent contains stable operation/version IDs, replacement HTML blob
identity/size and a captured basis: exact target version/hash,
title/description/properties/scope, governing binding and rule version. Preserve
the target filename and HTML MIME. Preparation validates the source before
journaling; upload verifies those exact bytes and never recaptures a newer base.

Existing consumers, including the design-lint evaluation runner, pass the basis
captured by their original audit into this shared preparation path. A second
capture after generating a candidate would conceal intervening metadata or
policy changes. Guaranteed invalid source preparation reports candidate rejection;
missing or unreadable original evidence remains unavailable. Prove both a changed
valid candidate and an invalid candidate through the actual consumer: an unchanged
clean control can bypass submission and cannot establish repair compatibility.

Within the writer queue, validate actual custody, target content and metadata,
actual membership/scope, the same-canvas governing winner and explicit exemption.
For a task repair, require its current source, request epoch, cancellation and
context guards, and an output declared by the brief or its actual target. A
teammate's content, metadata or scope change refuses the repair without effects.
A later governing document cannot be substituted for the captured one. Inherited
policy uses permission-bearing preflight and post-save reads; no operation locks
a different home. Accepted content with changed/unavailable consistency remains
saved and explicitly inconsistent/unverified.

Source conformance and governing identity are distinct. A functional correction
may proceed with a captured known absence or unsupported source-analysis coverage;
that does not turn unavailable analysis into a pass or waive the workflow's
provisional-system guidance. An unreadable or changing governing identity cannot
be represented as a checked unchanged system.

Canonical repair records retain the full before-target version and exact
brief/context/governing references through the existing flat operation roots.
The reducer validates the canonical effect's association; public callers cannot
supply canonical effects/retained fields. Exact full-intent and authenticated-actor
retry returns the original acceptance after Undo/removal/archive and never
reapplies it. The generic submit path also reserves these archived IDs. A
canonical different-intent/actor conflict is definitive; a generic access or
source-read failure after uncertain delivery is not proof of non-acceptance.

The ordinary inverse does not by itself protect a teammate's newer current
version: `item.removeVersion` restores its recorded previous current version.
Before repair Undo, the writer therefore checks the exact adopted full target;
before Redo it checks the captured before target. A conflict leaves both content
and the Undo/Redo candidate untouched. Grouped history walks check each repair
against the evolving planned state, allowing an intact chain to unwind without
rewinding unrelated work. This adds no inverse operation or generic edit rule.
Historical restoration does not require today's request to be active and does
not reactivate a cancelled request or erase later source/policy changes.

The grouped walk also exposed a pre-existing ordering error: after newest-first
Undo, traversing the redo stack from its end already returns oldest-first acts.
`nextRedoGroup` must not reverse that result again. Restore the documented order
and prove it with both sequential ordinary edits and sequential repairs; a
special repair path that works around an incorrectly ordered generic group
would preserve the underlying bug.

## Exact continuation, not recaptured context

Derive active repair transitions from existing live and archived canonical
operations and their Undo/Redo causes. Combine them with phase 4's exact live
adoption edges when checking the brief's original context. Each transition
names this request, brief item and epoch, exact before/after source identities
and full target metadata/scope. The latest cause determines whether a repair is
active; matching bytes alone never proves it. Undo disables its edge; Redo
restores original authority. Missing/forked/cyclic paths and unrelated later
changes remain stale. A brief correction within an epoch cannot manufacture a
missing edge; a new epoch is explicit continuation with a new capture.

Do not patch `brief.context` after each repair, silently resume the request,
or fabricate an outstanding decision to reuse `design.decide`. Source/receipt
freshness consumes the same derived transitions on both surfaces. Checks remain
bound to their actually inspected output; a repair requires affected rechecks,
not relabeling prior observations with its new version.

Receipt context may retain the originally selected target identity when the
same exact active transition chain reaches the current target. The receipt's
output must still be the actually inspected current version; later output
changes stale its checks. This applies to writer admission and both read
surfaces, without substituting the current version's bytes for old evidence.

Completion is a separate canonical transition from a captured active brief to
its completed version. Review and repair history may remain current across
that exact completion at the same epoch, when the canonical completion names
the captured brief and current source/context/governing facts still hold.
Missing history, a corrected brief, a resumed epoch or changed inputs cannot
borrow that exception. New repair writes still require the active exact brief.
This preserves a finished run's immutable original request identity without
making every successful finish stale or silently accepting arbitrary revisions.

Negotiate `design-repairs-v1` on the new operation and any reads, histories,
replication or inverses carrying its new semantics. Gate what the response
actually contains; do not add an HTML marker only to trigger a guard. An actual
archived phase 4 daemon must refuse the new act without a write. Ordinary
canvases and original explicit audit reads keep their existing behavior.

## Handoff and completion

Browser capability is an attributed, expiring **offer by the actual acting
agent/session**, naming supported delivery and tools with observed versions.
Use a separate ordinary versioned offer artifact linked to the request/run;
its actual version author is the reporter. It is not inferred from harness
name, `PresenceSession.capability` (access level), a tool-call title, login
settings or a browser-open command. Unknown/unavailable is a valid report.
A positive offer must be current, match the actor's live session, and declare
support for this output. Automatic expiry is at most five minutes; refresh by
probing again, not by extending someone else's declaration.

Agent classification still comes from the daemon's actual registry. The existing
canvas actor lookup includes actors in that canvas's current live presence,
even before their first authored item or comment. Pass those live actor IDs
through the existing registry/join classifier; do not infer eligibility from a
session's label or expose the home's unrelated global actor roster. Expired
presence supplies no such discovery, and an unknown registry identity remains
unknown. Offer eligibility separately requires the live native session and
current tool probe.

A handoff requires that current report, actual reachability and existing
`mayWake` authorization. It uses an ordinary addressed request and existing
summons state, with the exact run/output and remaining budget. The UI says
Requested or Picked up until actual retained observations arrive. A reply or
presence change cannot complete inspection. With no eligible offer, report
verification unavailable; do not provision a tool or guess a capable agent.
Handoff to a new observer changes future observation authorship, never the
owner of an uncertain earlier repair.

Finishing uses the existing conditional brief completion and canonical
`design.receipt`, preserving their separate acts and exact retry identities.
The run must meet all of its declared obligations, have no unresolved critical
findings, and retain required evidence before its own ready claim. Historical
receipt parsing is not silently strengthened or rebranded: its older minimum
of one browser pass does not establish this new complete review. Keep Source,
Task checks and Craft visible, with failed, unsupported/unavailable and stale
results, exact evidence and remaining limits. The existing manual receipt form
remains explicitly authored reporting, not the default agent review path.

## Both entrances and proof

Expose one `design review <request> [--run <id>]` read/progression surface:
start, record actual observations, begin-repair, offer-verifier, handoff and
finish. Extend `design repair` with explicit review/pass association and
prepared retry. CanvasHandle and browser-safe API exports supply the same
steps. `design workflow` exposes their actual next action. Both agent guides
point to this procedure; no new skill restarts discovery.

The web shows a lazy review panel beside the existing task, with its three
readings, repair history, exact output and eligible verifier. It does not ask
people to enter tool configuration to obtain normal review. Existing Design
check consumes the shared prepared repair path and full receipts, replacing
version-presence inference. Preserve refreshable drafts, scoped pending identity,
responsive frame ownership and existing entry/export ceilings.

The phase 5 proof remains the phase's existing paragraph, strengthened by its
actual boundaries: seven counterexamples and add/revision parity; actual
broken-save and phone-overflow discovery/repair/recheck; two competing pass
reservations and cross-entrance continuation; no third attempt after invalid
or unsuccessful fixes; target/system/source/epoch drift; exact uncertain retry,
Undo/Redo, archive/GC and old-daemon refusal; unavailable/expired/unauthorized
verifier; and a genuine incumbent repository runtime. Walk local Scenes 1–6 as
one continuous candidate journey. Authored synthetic repairs and real tool
observations prove this orchestration, not generated-design quality or a human
preference uplift. No paid services, recruitment or model calls are authorized
by this mechanism.

Scenes 1–2 map to the existing questionnaire protocol as two consequential
design questions and an explicitly optional sketch upload in the same batch.
These are three controls and consume all three initial slots; the proof must
not describe them as two total prompts. The upload uses the existing upload
renderer, can be skipped, and does not add a third design decision or require
a reference before work starts. This avoids changing the closed answer schema
merely to stage the continuous journey.
