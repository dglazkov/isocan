# Browser acceptance scenarios

These are planned walks, not recorded successes. Each phase's verification
page records the exact built revision, fresh daemon, synthetic canvas, browser,
viewport, actions, output identities and evidence when its walk actually runs.
Scripted agents can establish protocol routing. They cannot establish
model-generated design quality or stand in for the phase 7 human study.

| Phase | Walk | Observable failure that prevents closure |
| --- | --- | --- |
| 1 | CLI publishes a question to a known human; browser uploads a synthetic sketch, navigates back, refreshes and restores drafts; another agent replies; a failed submit retries once | Filename without retrievable bytes, lost draft, unrelated reply closes question, duplicate answer, hidden failure |
| 1 | Browser and CLI reverse producer/consumer; two successive upload questions and two URL questions retain separate data; keyboard and narrow viewport remain usable | Cross-question leakage, unreadable reference version, inaccessible control, unintended respondent resolves question |
| 1 | Undo and redo one answer; reissue the source; inspect valid and malformed legacy messages | Undo leaves resolved state, redo changes authorship, stale answer accepted, malformed message crashes UI |
| 2 | Equivalent sparse requests from canvas chat and an external agent; resume through the other entrance; complete the same inventory task | Repeated settled questions, different durable facts, lost context, receipt without actual task proof |
| 2 | Precise edit, archive import, connected application, and browser-unavailable path | Unnecessary interview, automatic design enrollment of an import, mock replacing a real runtime, unsupported verification claimed |
| 3 | Operational, reading and persuasive recipe surfaces at agreed narrow/wide widths, with keyboard and relevant long/empty/error states | Overflow, unreachable action, broken state, generic content substituting for the primary task |
| 3 | Two scoped systems; follow-up through the other entrance; an incumbent component repository; concurrent governing-system edit | Adjacent system wins, component conventions discarded, stale context still reported current |
| 4 | Try comparable structural alternatives, then comparable visual alternatives; choose, delegate, undo and reject a stale adoption | Palette-only comparison, unequal fidelity, brief overwritten, alternatives deleted, agent choice counted as human preference |
| 5 | Receive shared source feedback; perform bounded repair; recheck browser task and layouts after a version change | Independent auditors disagree, old repair overwrites new work, lint substitutes for browser proof, stale evidence reported ready |
| 6 | Discover optional package capabilities; project identified context; reconcile working-file edits; repeat without package | Repeated discovery, untracked context copy, unavailable hook claimed, optional package required for ordinary completion |
| 7 | Paired controlled generation, blinded independent ratings, real participant tasks and hosted rollback/resume | Changed comparison conditions, discarded failures, missing human evidence, hosted behavior unwalked |

The first reference upload must be downloaded independently through the CLI
and compared byte-for-byte with the source file. A browser screenshot is useful
for appearance; the recorded actions and observed state establish interaction.
Both are tied to the inspected output version. Resource-dependent steps remain
unperformed until their required authorization and capability exist.
