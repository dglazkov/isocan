### First minute phase 3: a barrel that meant "and also fastify"

`9df802c`

Phase 3 was to move the server, the MCP layer and the design stack behind
`import()`. Both of its proofs were already green when it opened — splitting
the bundle and inlining the dependencies had taken `isocan --version` to 33
modules and 0.12 s, under the "40 modules" and "0.5 s" bars — and the module
count had stopped meaning much, because once every dependency is inside the
bundle a chunk is one module however much is in it.

So the phase was re-aimed at the number that still moves, bytes read at
startup, and the first look at those found what the design had not:
`@isocan/server`'s index re-exported `startDaemon`, and sixteen files in the
CLI and the API import that index for `paths` or `readConfigFile`. Printing a
version string read a 2.1 MB chunk of fastify and its plugins. The daemon is
now `@isocan/server/daemon`, reached with `await import()` by the one verb
that serves; its types stay in the index, because a type import is erased and
costs nothing. 5.8 MB became 4.5, and 0.12 s became 0.10. `HOME_HEADER` went
with it: it was the other thing the index re-exported from `http.ts`, and
nothing outside that file had ever read it.

The rest of the list was left alone on purpose. Moving zod, `ws` and undici
out of startup would be a large change through the CLI's import graph for
perhaps 2 MB, and the targets are met with five times the margin. A
startup-bytes budget now sits in `test/cli-bundle.test.ts` so the next person
to add a static import to a barrel finds out on their own laptop, where the
whole command is a tenth of a second and nothing else would tell them. The
module guides needed no laziness at all: phase 1 made them build-time text
constants, which is the same end by a different means.

Phases 4 and 5 each open with a proposal and stop, as the walk says they
should. `guide-cut.md` proposes a core of about 6,600 tokens against today's
46,700, names its 46 topics, and puts three judgements to Dimitri — the
largest being that most of "Practices that earn trust" is the design stack,
which is a manual rather than a protocol. `no-secret-identity.md` names the
three shapes, recommends environment variables (the #332 sandbox is launched
rather than operated, and its disk is gone tomorrow), and separates out the
proxy half, which has no decision in it.

Across phases 0 to 3, in phase 0's sandbox: install 14.2 s to 4.1 s, 227
packages to 3, `isocan --version` 1.12 s to 0.10 s, 4397 file opens to 49.
Journey 1's targets are met.

### First minute phase 2: the install resolves nothing

`b84628c`

`npm install -g github:dglazkov/isocan#release` took 14.2 s in phase 0's
sandbox and installed 227 packages and 115 MB. It now takes 3.9 s and installs
three packages and 22 MB, and none of the three is code: every dependency is
inside the bundle, and `@types/node` is there so an editor can read what
`connect()` returns.

`RELEASE_DEPENDENCIES` lists the survivors with the reason each survived, and
the build fails on a name main does not declare — "which of these is still
real" is a question somebody has to answer on purpose, not a filter.
`RELEASE_DROPS` is what leaves the branch: `docs/` (15 MB nobody runs),
`test/`, and the sources, which go for a stronger reason than size — after the
bundling nothing resolves them, so a `.ts` file on the release branch is a
second copy of the CLI that can silently disagree with the one that runs. With
them: the web app's build inputs (`public/` is 1.4 MB of the pictures `dist`
already has), this repository's own workings, the tool configuration, and
`package-lock.json`, which listed 227 packages the manifest no longer asks
for. Of `scripts/`, three files survive — the two a CLI verb can spawn and the
browser helper they share; the other forty import a package's `src`. 40 MB
became 17.

Two things only running it could find. Half the dependency tree is CommonJS
and esbuild's `require` shim needs a real `require` to fall back to: the first
fully-inlined bundle died on its first command with `Dynamic require of
"node:events" is not supported`, which a `createRequire` banner on each chunk
answers. And `index.mjs` and `rc.mjs` — `import { connect } from "isocan"` and
`from "isocan/rc"` — register tsx and import the API from source, so dropping
the sources would have broken the package's own module entries. They are built
in the same esbuild pass as the CLI so all three share one set of chunks, and
the release commits one re-export line for each.

`test/cli-bundle.test.ts` starts a daemon from a tree with no `node_modules`
in it at all and asks it for `/healthz` and the page, and holds the manifest
to declaring only what `RELEASE_DEPENDENCIES` names.

### First minute phase 1: the release CLI is a bundle

`08167b0`

`scripts/release.mjs` builds `packages/cli/dist/isocan.mjs` with esbuild and
the release manifest's `bin` names it, so an installed copy starts without tsx
and without opening 297 `.ts` files. A checkout is unchanged and still runs
`packages/cli/bin/isocan.js`.

It is split into 35 chunks rather than one file, and the measurement is the
reason. Bundled into a single output `isocan --version` loaded 538 modules —
MORE than source mode's 437 — because esbuild hoists an inlined module's
external imports to the top of the file it lands in, so every
`await import("./design-system.ts")` in the CLI dragged fastify, the MCP SDK,
ajv and the remark stack into startup. With `splitting` each dynamic import
keeps its own chunk: 142 modules and 0.20 s against 437 and 0.38 s. Phase 3's
work now counts instead of cancelling out. The cost is that a thin artifact
fetchable with `curl` (design.md's open door 1) would be a second build rather
than a flag on this one.

A bundle breaks every path counted up from `import.meta.url`, because every
folded-in file shares the bundle's. `packageRoot()` in
`@isocan/core/packageroot` walks up to the `package.json` named `isocan`
instead — one answer from a checkout, the bundle, `npm i -g`'s tree and
`~/.isocan/current/node_modules/isocan`. It is a subpath rather than part of
core's index because the index is bundled for browsers, where a `node:fs`
import anywhere in the closure fails the build. `packageBin()` beside it reads
a tree's own manifest: `daemonBin()` used to name
`packages/cli/bin/isocan.js`, which a bundled install does not have.

Guides are imported rather than read: `import guide from "./agent-guide.md"`
is that file's text, one rule declared in `md.d.ts` with four adapters — the
source-mode loader, the two esbuild builds, and the suite. `agentGuidePath()`
went with the disk read; nothing called it.

Two things the design had not named. `@isocan/cloudstore` must be declared
external — esbuild follows the static `import()` specifier that exists
precisely to keep its 156 packages out of a CLI install, and the first bundle
built here carried @google-cloud/firestore. And design-competition's own packs
cannot be found through `competitionCore.name`, which is the scoped package
name and not a path.

`test/cli-bundle.test.ts` holds both halves: the bundle answers `--version`,
`--help`, `--agent-help` and a module verb from a tree with no `.ts` in it,
and `--version` loads fewer than 150 modules with no tsx among them.

Two fixtures corrected on the way. `setup-npx.test.ts` assembled an npx copy
with no root manifest, which npm never does and `packageRoot()` needs; and
`packages/api/test/identity.test.ts` had a recursive `rm` with no retries,
which `test/teardown.test.ts` has always meant to catch.

### First minute phase 0: a sandbox on the laptop, and the numbers

`af27223`

`node scripts/first-minute.mjs` installs today's `release` into a container
with four cores, Node 22, a cold disk and no tsx cache, and prints what an
agent in a small sandbox actually waits for. Against `release` built from
61f7616a: install 14.2 s for 227 packages and 115 MB on disk with `docs/`
included; `isocan --version` 1.12 s cold and 1.07 s warm, where `node -e ''`
in the same container is 0.04 s; 4397 `openat` calls for that one command, of
which 1396 found a file.

The container reproduces seconds-per-command but not #332's 3.3 s, and gVisor
was not available to close the gap — `docker info` here lists `runc` alone. So
the file count is the number the later phases are held to: 3001 of the 4397
opens found nothing, a resolver walking directories that do not exist, and a
sandbox that intercepts the file system charges full price for every one. That
is the most likely reason 0.3 s becomes 3.3 s there, and it now has a number
instead of an argument.

The measurement runs as a shell script piped into the container
(`scripts/lib/first-minute-sandbox.sh`) rather than several `docker exec`s:
each step's cost has to be paid on the same cold disk, in the order an agent
pays it. `--local` installs this machine's `release` ref through a temporary
bare clone, so a phase can measure a release CI has not seen yet.
