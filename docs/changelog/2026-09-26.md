# 26 September 2026 — Seeing what changed

The day's thread was one question asked of two things: *what is different
now?* Asked of an item's versions, it became a diff engine in core with a
terminal verb and a side-by-side inspector. Asked of a wire and the DESIGN.md
it was drawn from, it became a "behind" tag and a restyle one click away.
Both came out of the Stitch Loop review, as did a batch of smaller fixes. The
entry chunk lost 30 KB, and five of the fourteen browser journeys turned out
to be red for a reason that had nothing to do with the product.

The performance commits that landed on this date (`38a9f701`, `2016c2bc`,
`4dba76f7`, `cb9308c1`, `9b385b34`) were written up under
[25 September](2026-09-25.md), when the work was done.

## Version diff (`fed2aa93`, `dce876ed`, `c543324d`)

Choosing between variations without seeing what changed is guessing, and
nothing showed a person what an agent's edit had actually done.
[The design note](../projects/version-diff/design.md) argues the shape; the
engine is `diffVersions` in core, on its own export path
(`@isocan/core/diff`), so parse5 stays out of the entry chunk. What a diff
means depends on the kind of item:

- **Text:** lines aligned, then words.
- **HTML:** parse5 trees aligned by a weighted match, so an inserted card is
  one added element rather than a cascade of changed siblings.
- **Wires:** the embedded spec, slot by slot, including intents, which are the
  links.
- **Images:** metadata only, and the diff says so.

Two doors read it. `isocan diff <item> [from] [to]` prints the summary and one
numbered line per change (`--source` compares a variation with the item it was
made from, which is the pair `choose` decides), and it only reads: its test
holds the log length unchanged across every diff. In the web, *Compare
versions* in the item menu, and a Compare button on each card of the version
fan, open a lazy inspector with the two sides at one scale, the same summary,
a stepper, and the decisions that apply. It adds no new op; comparing writes
nothing.

The highlights inside a sandboxed frame are the interesting part. Nothing
outside can reach into it, so `markSource` writes the marks into the changed
elements' own start tags, plus one style and one script, and the frame is
handed that as its `srcdoc`. The first screenshots found two faults, both
fixed before landing: a phone-sized wire was cut off at the card's height,
and a screen-level change tinted the whole frame and buried the block marks.

## A wire that has fallen behind its system says so (`efbaa096`)

The review's finding: a DESIGN.md changes, and the wires it governs go on
drawing the old look with nothing on the canvas saying so. `wire style
--check` knew; the canvas did not. Now a wire behind its system wears a quiet
"behind" tag, the DESIGN.md says how many wires are behind it, and a click
restyles those wires' flows in one op group. The restyle is still never
automatic (design §9); the click is the person's.

"Behind" is deliberately narrower than "drawn from an older version". A
version that only adds tints is not behind, because the restyle would write
nothing for it, and a mark no click can clear is noise. `--check` and the tag
read the same function (`behind.ts`).

## The entry chunk gets 30 KB back (`88c5e47e`)

The nightly performance run found the entry 1,346 bytes past its ceiling.
Four things that mount behind a condition were in every first visit: the
context menu, the `view` face, the Agents tray and the Files panel. The menu
was the surprise. `openContextMenu` lived beside the component, so three eager
callers that only *open* a menu pinned the whole thing, submenu and all. That
alone was 11.5 KB, twice the component's own size. Moving the opener to its
own file and making the four lazy took the chunk from 731,300 to 701,021
bytes. The ceiling went *down* to 701,300. Its entry records the 1,346 bytes
as carried un-itemised rather than claiming somebody agreed to them.

## Five journeys were pressing the Chat (`c97081f6`)

Five of fourteen browser journeys failed on unmodified `main`, and none of
them was the app. Since 24 September a new canvas opens with the Chat docked
on the left, and the journeys pressed at fixed coordinates that now landed on
it. The press was real; it pressed the Chat. `openSpot()` now asks the
browser's hit test for a box of bare canvas, and failing to find one is a
failure in its own words.

The pen journey was worse than red: it was green for the wrong reason. Its
stroke also hit the Chat, and it asserted only that nothing threw. It now
waits for the ink to settle into an item, which is what "draws" in its own
description promised. Each fix was proved red with the old behaviour put back.

## Around it

- **Every op has words** (`a235a4e1`). The activity phrase table was typed
  `Partial<Record<…>>`, and five ops had fallen through it, showing "did
  something" on a card. It is a full `Record` now, so a new op without a
  phrase fails to compile.
- **One `canonicalJson`** (`e287b323`, cleanup DU-6). It had been written
  privately seven times, four of them hashed into ids already on disk, so the
  copies agreed only as long as nobody improved one. The test runs the old
  copies verbatim beside the new one.
- **A live React component as a canvas item** (`49539211`). An HTML item
  already runs inline scripts and the content policy allows jsdelivr, so one
  file can load React and Babel and render JSX with no build. Nobody had
  written it down. It is now a recipe in the agent guide's `items` topic, run
  for real, with the example held byte for byte by a test.
- **An agent's arrival note** (`0362a4c2`) stays twelve seconds, not five, and
  holds while pointed at. Five seconds was gone before the person who had
  typed "@Scout are you around?" looked up.
- **A flow's own keeps are signed with its real answerer** (`ce29136a`). An
  agent-answered flow signed its picks `jev`, which erased the distinction
  `wireKeepBy` exists for. Found by judge phase 1; no shipped path reached it
  yet.
