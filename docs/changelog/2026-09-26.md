### A remote drag no longer re-parses every comment, and the # roster stops being quadratic

`cb9308c`

After the whole-canvas subscriptions went (2016c2bc), a collaborator's drag
still cost this browser ~50 ms a frame at 4x CPU on 250 notes. The profile
named what was left, and it was one shape three times: something rebuilt on
every operation that is a function of far less than the canvas.

- The `#` roster's candidates are a function of item ids and titles, but were
  memoised on the canvas object — new on every operation. That list is what the
  Chat and every open thread hand the markdown renderer as its chip plugin, so
  every comment on the screen re-parsed on every op. The candidates are now
  kept while the ids and titles are (one pass of string joins to check), and
  `Markdown` is memoised, so a parent re-rendering with the same words no
  longer parses them again.
- `referableNames` de-duplicated with `names.some(...)` inside its loop —
  quadratic, 125,000 comparisons for 250 items, run for every text run the chip
  plugin sees and every composer render: 8.8% of the main thread during a
  remote drag. A seen-set makes it linear with the same first-kept order and
  the same stable sort, and it is kept per candidate list.

Measured with the frame census (three runs, 250 notes, 4x CPU): remote drag
p50 50 / 50 / 50 ms → 33.3 / 33.3 / 33.3 ms; `core/itemrefs.ts` 8.8% → 1.5%
of samples; markdown parsing 3.6% → 0.4%. From the original, the remote drag
is 500 → 33 ms, fifteen times.

`canvaswide-rerender.test.ts` adds the roster guard — the same candidate list
through five moves, a new one the moment a title changes; it fails on the old
file. The item-reference tests pass unchanged.

### Zooming no longer re-renders every item on every step

`4dba76f`

Every `ItemView` subscribed to the raw `viewport.scale` and worked its chrome
out in render, so each step of a zoom re-rendered every item on the canvas.
Frame census on 250 notes, headless Chrome at 4x CPU, a 30-step ctrl-wheel
zoom out and back:

                          before     after
  ItemView renders         7,500     1,250   (250 x the 5 thresholds crossed)
  frame p90                83 ms     50 ms
  react-dom share of time  19.8%     8.6%

What the scale drives splits in two, and this moves each half to where it can
be cheap. The CONTINUOUS half — the counter-scale on the chrome, the row's
screen width, the room the name may run to, a text or kind mark's size — is now
CSS against the world's existing `--scale` and each item's new `--w` / `--h`,
so the browser recomputes it and React never hears about it. The DECISIONS —
`roomy`, the title row's icon and name, a text node's legibility, whether the
under row spells its button out, whether a kind mark is big enough to draw —
are one selector (`zoomDecisions`) that packs them into bits, so an item
re-renders exactly when one of ITS decisions flips. Each rule is the same
function with the same hysteresis memory; only where it runs moved. The one or
two items that may reach (hovered or selected) still follow the raw scale.

The CSS forms live in lib/chrome.ts beside `counterScale`, `underRow` and
`titleRow`, which is the reason those are functions at all: a rule written out
again at each site is the rule that gets missed. The guards that hold that —
worldchrome, kindmark, zoomrule — now check the CSS forms by name, and
chrome.test.ts evaluates every CSS form with `--w`, `--h` and `--scale`
substituted and holds it to its JS twin to nine decimal places across widths
and zooms from 5% to 400% (a 0.8 → 0.7 change to the mark turns it red).

Proved identical in a browser as well as in arithmetic: the chrome geometry of
24 varied items — seven sizes, short and long titles, text nodes, reactions, a
hovered item reaching — captured at ten zoom stops from ~2% to 800% on the old
build and the new: 1,920 element states, 817 of them visible, 0 differences at
half-pixel resolution.

The remaining zoom cost is the browser's own style, layout and raster (39% of
samples) and markdown re-parsed when items remount their content at the size
threshold (~7%). Pinning `.world` with `will-change: transform` was measured
and rejected: zoom p99 116 → 383 ms, and pan began dropping frames.

### One collaborator dragging one item no longer re-renders every item on everybody's screen

`2016c2b`

Measured with a frame census on a real daemon and a real canvas — 250
markdown notes, headless Chrome at 4x CPU throttle, a rAF probe that refuses
to report unless the camera actually moved, and render counters in `ItemView`
and the markdown renderer. While another client moved ONE item 60 times:

                      before     after
  ItemView renders    15,455        60   (the moved item only)
  markdown renders    15,000       332
  frame p50           516 ms     50 ms   (every frame >32 ms before)

The page was effectively frozen for as long as anybody dragged anything. Three
subscriptions to the WHOLE canvas made every op a canvas-wide re-render:

- `useVotesHiddenOn` and `useRoundMarks`, called by every `ItemView`, read
  `useCanvasStore((s) => s.canvas)` and worked their answer out in render. The
  answers are a boolean and a list of marks; they are now computed inside the
  selector (the list through `useShallow`), so an item re-renders when ITS
  answer changes. For a sprint feature most canvases never run.
- Every note's `MarkdownBody` subscribed to the canvas to resolve links, and
  react-markdown parses on every render. Only a link to a PATH on the canvas
  needs it; a fragment, an external address or a refused scheme is settled
  without it. That half of `markdownResource` is now its own function,
  `markdownTargetOffCanvas` — one rule, two callers — and a note subscribes only
  once a render has met a path, so a note linking a canvas file still follows
  it and a note of external links never does.
- `moduleRounds` asked every module for its rounds once per item per store
  change; it is memoised per canvas object and module-registry version, the way
  `sprintForCanvas` and `wallIdsFor` already were.

`packages/web/test/canvaswide-rerender.test.ts` counts it — fifty cards through
the two hooks, and markdown parses through a rehype plugin, while a different
item moves ten times. Run against the old files, the two guards fail and the
third (a note linking a canvas file still re-parses when the canvas changes)
passes on both, which is the behaviour kept. `stablehooks.test.ts` allows
`useRoundMarks` with its reason: a useMemo keyed on the canvas is exactly what
made a new array on every op.

Not in this commit, measured and left: zoom still re-renders every item on
every step (7,500 renders over a 30-step zoom, p99 116 ms) through `ItemView`'s
subscription to the raw scale — that is the next change. Pinning `.world` with
`will-change: transform` was tried for zoom and made it WORSE (p99 116 → 383 ms;
pan began dropping frames): one layer of 250 cards costs more to tile than to
re-raster.

### bundle-what read the wrong sourcemap field for 18 days, and it overturned a correct reading

`38a9f70`

A sourcemap segment is [generated column, source index, original line,
original column, name]. `bytesBySource` walked `sources` by `fields[3]` — the
ORIGINAL COLUMN delta — under a comment saying the fourth field was the source
step. Every per-file figure it has printed since 8 Sep was noise with a
plausible shape: the right total, sensible percentages, and a 66 KB
"(unknown)" row that was simply the walk running off the end of the list.

Read with `fields[1]`, the entry chunk (729,760 bytes today) is:

  43.4%  @isocan/web      (the tool said the web files were ~1 KB each)
  29.3%  @isocan/core     (the tool said 52.6%)
  18.1%  react-dom        (the tool said 7.8%)
   5.2%  react-router

and the canvas is its largest part — `ItemView` 27 KB, `CanvasViewport` 18 KB,
`CanvasPage` 17.5 KB, `canvasStore` 12 KB. Which is what the architecture
review inferred on 6 Sep ("the canvas itself") before this tool's table
"corrected" it on 8 Sep. The correction stood for eighteen days; the review
now says so at the point it went wrong. The 8 Sep namespace-import fix itself
stands — 699,999 → 635,728 is a total, which the attribution never touched.

`test/bundle-what.test.ts` decodes a map built by hand in which the two fields
disagree; both of its cases go red on the old line. Lesson 100: an instrument
