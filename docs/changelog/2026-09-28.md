# 28 September 2026 — isocan as a Jetski plugin

Dion asked for isocan as a plugin for Jetski. He wanted the workspace's canvas
in a pane beside the Jetski chat, with no second chat column, because the
steering happens in Jetski. He wanted the conversation to arrive on the canvas
ready to work, and a quick way to bring on agents pinned to different models.
That became [`docs/projects/jetski/`](../projects/jetski/) (#364), four phases
built in one day. Phase 0 is closed. Phases 1–3 are part-done, and each is
waiting on a walk that only a person can do:
[the verify page](../verify/2026-09-28-jetski-plugin.md).

## A canvas without its own Chat (phase 0)

`isocan embed` now mints an address carrying `?embed=1`, which hides the
canvas's Chat. `--chat` keeps it. The web reads the switch once, at load, so a
navigation inside the page cannot turn the Chat back on. Hiding the dock, ⌘J
and the rail was the easy half. The review found four more ways in: the
palette's *Open Chat*, the palette's slash commands (choosing one opens the
Chat with it typed), the canvas menu's Chat row and the module workspace's
Chat button. Every entrance now asks `chatHiddenNow()`, and
`embed-chat.test.ts` fails when a file outside `panels.ts` opens the Chat
without asking.

`hostbridge.ts` is the canvas's half of a conversation with whatever frames it.
It says it is ready to anyone. Only after the parent says hello does it tell
that one origin what is selected. `scripts/journey-jetski-pane.mjs` walks it in
headless Chrome, framed and as a tab, with real clicks and keys: 17 checks.

## Pinning a model (phase 1)

`--model <id>` on `agent add`, `rc add` and `bench add` rides the enrolment row
into `adapterFor`. The id always goes out as `ISOCAN_MODEL`, but no harness
reads that variable, so on its own it would be a pin that silently does
nothing. The id reaches a harness only through a door the harness documents:
`ANTHROPIC_MODEL` for Claude Code, `model` in Codex's `CODEX_CONFIG`, or
`{model}` in an `acpAdapters` declaration. `isocan harness` shows
`model: pins` or `model: own`, so nobody compares two "pinned" agents while one
of them is running its default. The fake ACP adapter now reports what it was
handed. With that, `acp.test.ts` proves that a pinned model reaches the spawn
and an unpinned one leaves no template behind. Still owed: a summoned turn on a
real pinned model.

## The plugin (phases 2 and 3)

`plugins/jetski/` is the bundle Jetski loads from
`~/.gemini/config/plugins/isocan`, and `scripts/install-jetski-plugin.mjs`
links it there. It holds:

- the `isocan-collab` skill, as a symlink, so there is still one file;
- a rule for bound workspaces;
- the `canvas-builder` and `visual-arena` agents;
- the `isocan mcp` server;
- a SessionStart hook;
- the pane.

The hook names a new conversation in a bound workspace and starts its session,
so what the conversation writes is attributed to it rather than to the person.
An early wiring also hooked `PreInvocation`, which fires before every model
call. Jetski had read that `hooks.json` at load and kept it, so an existing
conversation took a name and started presence on a real canvas mid-session.
The hook is now wired to SessionStart only. The script also ignores any input
carrying `invocationNum`, which SessionStart input never has, so a host still
holding the old wiring does nothing. The lesson: Jetski reads a plugin's hooks
and rules once, so restart it after changing them.

The pane is a sidecar. Every route is one or two `isocan` commands, run as the
person, in the folder the host names. It:

- frames the bound canvas through `isocan embed`;
- binds an unbound folder to an existing canvas or a new one;
- shows the selection as chips, with an Ask box that hands the question to the
  conversation;
- has an Agents bar that enrols the presets in `presets.json` through
  `isocan rc add <name> --harness … --model …`.

A preset's name belongs to the agent (Orla, Bram), never to its model.

The plugin is not in `#release`. It runs from a clone, and the pane imports
`sidecar_sdk`, which only the Jetski host provides. The release tree's import
check (cleanup phase 4) refused it on the first full run, so the release now
drops `plugins/` as it drops `scripts/`.

## What the review changed

A review of the whole diff before staging found these, and fixed them:

- **Open ↗** opened the chat-free address in a tab. It now opens the plain
  canvas address.
- The pane accepted relative workspace paths. Only absolute paths count now.
- The installer compared unresolved paths. It now resolves them first, and
  uses a junction on Windows.
- A pane opened by hand did not forward its token the way the SDK does.
- `--model` had no test at the CLI level.
- The plugin had an unused export.
- Two internal URLs had reached public docs.

## A test that wrote into the person's own home

Checking that the hook joins only the open folder's canvas turned up 26 rows
for `/tmp` directories in Dion's own `~/.isocan/dirs.json`. The daemon's
directory routes (the tree, the picker, the bind and the backing) asked the
process where the isocan home was, not the daemon they belong to. In a real
daemon that is one directory. In a test it is not, so `bind.test.ts`, whose
daemon runs on a temp home, added two rows to the person's roster on every
run. The case's own check passed because the tree read the same wrong file.
The daemon now hands the routes its own home, as it already did for modules.
The test points the process at a decoy home and requires the decoy to stay
empty; with the old wiring it fails. Lesson #104.

## Stitch Loop's findings, background tabs, and a rail tip

isocan's Stitch Loop workspace had been mining the repo with nothing here
reading it (`464a0b8a`, `6da16655`, `459d7bbe`, `cb6ba70f`). Each insight is
now a finding in `docs/loop/` whose front matter holds our decision;
`docs/LOOP.md` and the Loop counts on `docs/ROADMAP.md` are generated from
those files. Thirty-six insights were pulled and decided: 8 accepted, 18
declined and 10 stale, with the declined and stale dismissed in the workspace
and `scripts/measure.mjs` sent back as context. `loop.yml` runs the nightly
pull.

An outdated tab in the background now reloads itself instead of waiting on the
pill (`9effb990`, `25a92357`). `mayReloadUnseen` reloads only when the tab is
hidden, every write is confirmed, and no sketch, draft or focused field holds
unsaved work. And the design-system door on the rail (`b9a81396`), which lived
in its own component file and kept the browser's `title` popup, now uses
`data-tip`, while `railtips.test.ts` walks every component file.
