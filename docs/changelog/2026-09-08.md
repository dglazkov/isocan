### Inline local linked assets for HTML and Markdown items in CLI and web renderer (#212)

`5c873e4`

Automatically resolve and package local filesystem assets referenced by HTML and Markdown items directly into self-contained blobs upon `isocan add` and `isocan edit`.

1. HTML Asset Inlining (packages/cli/src/inline.ts):
   - Scans <img>, <source>, <video>, and CSS url() for local image references, converting them to base64 data URIs.
   - Inlines local stylesheets (<link rel="stylesheet">) and local scripts (<script src="...">).
   - Preserves external URLs and missing assets gracefully.
2. Markdown Asset Inlining:
   - Scans markdown image embeds (![alt](path), ![alt](<path> "title")), inline HTML <img> tags, and reference-style definitions ([ref]: path), converting local images to base64 data URIs.
   - Preserves code blocks and inline code snippets untouched.
3. CLI Commands (packages/cli/src/main.ts):
   - Hooks inlining into `isocan add` and `isocan edit` for text/html and text/markdown.
   - Adds `isocan inline <file>` command for standalone bundling and pipe inspection.
4. Web Markdown Renderer (packages/web/src/lib/markdown-body.tsx):
   - Supplies custom safeUrlTransform to ReactMarkdown allowing data:image/* URIs for <img> src attributes, preventing default protocol filtering from stripping base64 images.
5. Loader fix (packages/cli/bin/workspace-loader.mjs):
   - Chains tsx module loader with next(url, context) instead of short-circuiting.

### Allow Tailwind CSS and jsDelivr CDN scripts and stylesheets in content CSP (#211)

`d618b0d`

Real-world design prototypes, mockups, and AI agents frequently rely on Tailwind Play CDN (https://cdn.tailwindcss.com) and jsDelivr (e.g. Tailwind v4 browser runtime) for styling and interactive UI demonstrations.

### The wash under the top controls was washing the wrong ground

`c810b9c`

"when the background is dark, the top fade should be dark, and when it's
light it should be light."

The fade is `var(--ground)` — the APP's page ground, near-white in the
light theme. A canvas standing on Space Galaxy is near-black whatever
the app's theme is, and `.canvas-theme-galaxy` says so in as many words:
"Space is dark whatever the app's theme is". So in light mode the top
96px of a starfield was a white bar dissolving into black, which is the
exact artefact a fade exists to prevent.

The same shape as the context menu borrowing its ground from the canvas
behind it, arrived at from the other end: there, chrome that let the
canvas set its colour; here, chrome that assumed the app did.

`lib/groundtone.ts` names the token the ground ITSELF paints with —
--theme-space, --theme-ocean, --theme-rock — so the wash and the thing
it washes cannot drift: recolour the sea and the bar above it moves. A
picture answers --ground-under, the backdrop it is composited onto: no
token can name one canvas's photograph, and a scrimmed picture is dark,
so erring to the backdrop is both honest and on the side that reads as
ground rather than as a bar. A canvas with no ground of its own answers
nothing and keeps the stylesheet's --ground fallback, which is why this
was right for every canvas until one wore a sky.

The guard is that there is a row for every name in THEMES and that each
row names a token the ground's own rule paints with — because the second
failure here is a ground added later with no row, which falls back to
the app's colour silently and reintroduces the bug for that ground
alone. topfade.test.ts asserted the gradient's exact text, which is the
mechanism; it now asserts that the canvas's ground comes first and the
app's is only the fallback.

### Three white dots at three densities is a starfield, not a galaxy

`323c62f`

"the space background is a lil boring... is there a way to spice it up
and make it feel even more like a galaxy?"

He is right, and the diagnosis is more specific than "add more". The
ground had one colour, one kind of star and no structure — which is
exactly what a night sky looks like through a small telescope, and a
galaxy is the thing you cannot see that way. Three things were missing,
and each is a layer that still never repaints:

Colour. Real stars are not white. Hot ones read blue, cool ones amber,
and a temperature per field is the cheapest of the three and does the
most to stop a field of dots reading as a texture.

Depth. Every star was a hard dot. A dust field below the size where a
dot resolves, under a handful of near stars with a halo, is what says
the sky has a front and a back. Five fields now, not three.

Structure. The thing that actually makes a picture a galaxy: clouds.
Nebulae are enormous and soft, so they tile at thousands of world units
against the stars' hundreds, and they are `::before` to the stars'
`::after` — a cloud in front of the stars is fog.

The restraint is the ocean's own sentence: a background somebody has to
turn off to read the canvas is not a background. Three clouds overlapping
at full strength composite to #2a244a over --theme-space, where a card
still reads 14.5:1 and a pen stroke keeps its contrast. Measured, and
asserted from the component's own tables so a later "spice it up" moves
the arithmetic rather than quietly spending the legibility.

The cloud tiles were chosen down from 4,300 world units to 3,400 for a
reason worth stating: MAX_SCALE is 8, so a tile is drawn at eight times
its number, and the only evidence in hand that a tile that size is free
is the 910-unit star field already reaching 7,280px since #195. That a
CSS gradient is a shader rather than a rasterised bitmap is a claim about
the engine, not a measurement of this app; it is written down where
somebody chasing a heavy zoom will find it.

### A sheep is a process you started that does not live on your laptop

`05449de`

#210. Research, nothing built — spec only.

A standing agent's one structural weakness is that `isocan rc` is a
process on a MACHINE. Laptop shut, agents gone. A sheep is a session in
a cell: an address, constructed on every wake, hibernating with its
sockets when idle, resuming itself after eviction through an alarm.
isocan solved "where is everybody" by being a canvas; it never solved
"where does the agent RUN".

**The obvious join is a shape this project already refused.**
`on-demand/design.md` had an agent advertising reachability through
`ISOCAN_HOOK`, and three review questions killed it: "No agent is ever
spawned at a distance by machinery nobody launched." So calling a cell
on a summons is not a gap to fill, it is a decision to re-argue.

The reconciliation is that **custody is about who started it and whose
credentials it uses, not which computer it is on** — a sheep is listed
by `sheep ls`, ended by `sheep abort`, and runs as itself. That makes
the first two shapes available today without touching the principle.

**Personas first**, because it is the only use with no unresolved
principle and a gap that is real: #205 found the cheap tier does not
exist, and a persona run is short, unattended, bounded and ends in a
page — with nothing standing anywhere.

**The rc in a sheep second.** No change to isocan: `rc` resolves through
`ctxOf`, so `ISOCAN_DIRECT` applies and it can park against a remote
home with no local daemon — proved twice here by `shelf.test.ts` and
`ground.test.ts`. And the cost is stated rather than buried: a parked
long-poll is not idle, so this gives up exactly the property cells exist
for. Renting a machine to hold a socket buys an agent that answers at
three in the morning; it is not free.

One decision unlocks all of it — a badge at the door, which is the same
question as #206 phase 7's bearer. Decide it once or end up with two
credentials in two settings pages with two revocation stories.

And a word before anything is named: herdr herds machines, a sheepdog
herds sheep, and a sheep on a canvas would be herded by an rc. Three
layers, one metaphor, in a codebase that has paid for a word meaning two
things twice in a week.

### A finding is answered by reacting to it

`1f04f85`

#206 phases 2 and 3 — the phase the whole note was for. #148 built the
board and refused to make any panel editable, naming exactly one fact
that must be decided there and leaving it unbuilt: "if the canvas only
ever displays, it is a dashboard and will be looked at twice."

**One item per QUESTION, not per row.** A missed bound writes a row
every night and `findingKey` already says those nights are one question
— the goal and the bound, not the number, which moves. That is also
what stops the silting #148 names as the way this goes wrong in week
two.

**The decision is a reaction.** ✅ accepts, ❌ rejects. No new op —
`item.react` predates all of this, so the vocabulary stays at 33 — and
three things come free: the decision carries WHO made it, two people
disagreeing is visible instead of last-writer-wins, and taking a
reaction off is an undo. A question wearing both marks is not a tie to
break; it stays on the docket, because writing either answer would be
this tool picking a side.

**The canvas decides; the repo keeps.** Reactions are read, the run
pages are edited, and a commit carries it — so `findUnanswered` goes on
reading markdown with no daemon and no network, and every decision lands
in git history with an author. Staged by path, never `-A`: a reaction on
a canvas must not sweep up another session's work.

Idempotent, because it reads STATE rather than ops. An item's reactions
are the truth; reconciling twice writes the same bytes and a missed tail
entry costs nothing.

Walked end to end on a real canvas: question found, card published,
reacted, read back as `accepted by Sonia`, the run page's row went
`unanswered` → `accepted — decided on the canvas by Sonia`, and the card
came off the docket. The walk caught two things reading could not — the
snapshot's `names` is a record and not a Map, and the API could add and
edit but not REMOVE, which is why `remove` is new on the canvas handle:
`add` and `edit` had been enough because a board only ever grew.

**And the flake instrument found its first one.** The suite went red on
`contentauth.test.ts`'s forged-signature case, which forges by replacing
the first character with `A` — and signatures are base64url, so one in
sixty-four already began with `A` and the "tampered" URL was the real

### Nine personas declare when they run; nothing has ever read it

`1efd500`

#206 phase 1: cadence, observed.

The phase was written to catch one duplicate key. It found the reason the
duplicate could exist: **`trigger` is read by exactly two things in this
tree — `isocan persona ls` and the board's panel — and both only DISPLAY
it.** `.github/workflows/persona.yml` holds one hardcoded cron and runs
`persona-run.mjs --all`, which filters on nothing. A persona could say
anything about when it runs, be believed by every reader, and be
contradicted by the machine.

Three of nine were wrong.

`design-auditor` declared `trigger` **twice**. YAML takes the last key,
so `parsePersona` returned 08:23 while the workflow ran it at 08:43 —
and the 08:43 line written above it was dead text in a file whose entire
job is to say when this runs. It got there by one commit ADDING the
correct value above the stale one instead of replacing it.

`market-researcher` declared **nothing**, so `readTrigger` called it
`manual` everywhere it was shown, while it wrote a page every night for
nine nights.

`journeys` declares Mondays and runs nightly. **Not fixed**: that is a
decision about what a browser walk should cost, not a typo, and this
phase exists to put it in front of a person rather than answer it. Held
at a ratchet of 1, so a tenth cannot join it quietly.

`scripts/cadence.mjs` is the reading — declared against fired against
last actually written — and counts the declarations from the RAW front
matter, because the parser is the thing that cannot tell: it builds a
map, so a key written twice is silently the last one.

`docs/reviews/README.md` carries it above the runs. It reports staleness
and does not fail on it: a run whose pull request is still open reads a
day behind through no fault of the persona, and a guard that reddens for
that is one people learn to ignore. What IS guarded is the declaration,
which is true or false in the tree and nowhere else.

Making `trigger` load-bearing is deliberately not in this phase. A
filter that got "is it due" subtly wrong would stop a persona silently,
which is the failure this row exists to end.

### A test that has already passed can still fail on the way out

`dbe1b75`

Dion: "The flakiness keeps on going.... what can we do to help there?"

Measured before answering. Six clean sequential runs of the whole suite
on an unchanged tree: **one failed, and its assertion had passed.**

  ENOTEMPTY: directory not empty, rmdir '…/isocan-rc-hGlGQ0'

`rc.test.ts` removing its scratch home in `afterEach` while something
the daemon started was still writing into it. Run alone, twelve times,
it never failed — it only loses the race with the whole suite on the
machine, which is why fixing one file would have moved the flake rather
than removed it.

**140 call sites across 99 test files removed a tree with
`{ recursive: true, force: true }` and not one had a retry** — while
`scripts/journeys.mjs` and `scripts/lib/browser.mjs` had been passing
`maxRetries: 5, retryDelay: 100` for days. The habit existed and had not
reached the suite.

That is what makes this expensive rather than merely annoying: the loser
of the race is whichever file happened to be holding a handle, so the
same defect wears a different name every run. Nobody can name it, so
everybody re-runs — and re-running is how a REAL failure gets dismissed
too.

Retrying is not hiding a signal. The scratch directory is scaffolding;
nothing asserts anything about it; Node gave `fs.rm` `maxRetries` for
exactly these errors (EBUSY, EMFILE, ENFILE, ENOTEMPTY, EPERM); and a
genuinely wedged directory still fails half a second later with its
name.

**Measured both sides: 1 failure in 6 runs before, 0 in 12 after.**
Twelve clean runs is suggestive rather than proof — at the old rate the
odds of that are about one in nine — but the mechanism is understood and
the fix is the one the API exists for.

Two guards, because the numbers were the easy part:

`test/teardown.test.ts` walks every test file and fails on one that
forgot. The hundredth file is what it is for; the cost lands on somebody
else's test, months later.

`scripts/flakes.mjs` runs the suite N times against an unchanged tree
and names every test that failed in some runs and not others — which IS
the flake set, since the code did not change. It acts on the flake-family
note's own conclusion: "The next round should add to what a failure
RECORDS, not to what we believe about it." Until now the rate lived in
people's memory of having re-run something.

It cannot be a persona goal — `ratchet.mjs` takes every goal on every
push and twelve runs is twenty-five minutes, the objection
`test/journeys.test.ts` already makes by name. So it is a measurement
that MUST live on a schedule and today has nowhere to be declared, which
is exactly #206's cadence row; noted there.

### Herding machines, when the thing you are herding has no machine

`38b24ec`

Dion asked whether there is a place for herdr in the persona / sheep
work. Surveyed both, and the answer is no — for a reason worth writing
down rather than a shrug.

herdr aggregates agents that live on MACHINES into one terminal client,
over SSH, and it is good at it: 700,000 downloads, a thousand plugins,
and the clearest statement of the cost anywhere — "remember where each
agent was running and switch between those tabs". Its whole architecture
rests on one premise: a session lives on a machine, so to see several
you must reach several machines.

Both of these projects removed that premise, by different routes.
**sheep dissolved it**: a session lives in a cell — one SQLite database
with an address — so there is no machine to remember and no list to
keep. **isocan answered it, and the answer is the product**: `rc --all`
stands one name on every canvas its enrolments name, the facepile says
who is standing by, and `history <actor>` is a row per canvas. herdr's
client is a window onto several places; a canvas is one place.

For the personas it is a clean no. They are unattended by construction —
a cron, a page, a column somebody decides — so herdr's value is watching
and the persona system's value is not having to. And #206, one day old,
argues at length that what this project needs is a surface where a fact
is DECIDED; #148's line is that a canvas which only displays "will be
looked at twice". herdr is an excellent display.

Three things are worth taking, and only one is a design: the split
render — client draws the chrome, each session supplies its view — which
is the right shape for the gap sheep actually has, that a dog herding
six sheep cannot watch them. `ls`/`status`/`log` are polls and `attach`
is one at a time. The transport does not transfer; sheep's cells already
speak WebSocket, so that is a client, not a protocol.

Filed as an observation about another repository, not work for this one.

And the naming, before there is anything to rename: herdr herds
MACHINES, sheep's dog herds SHEEP. One metaphor, one layer apart. This
codebase has paid for that twice — `archive` when the shelf wanted the
word, and a `fold.test.ts` overwritten this afternoon by a second
feature that also called itself folding.

### Fold a long message and the thread lurches 1,205 pixels

`f34564e`

Your one "change it" from the validation page: "sometimes it jumps and
hard to know what just happened. What if the item gets a background fade
for a second IF the location jumps... so you know where the item is?"

Measured before building anything, and it is worse than a jump. Folding
a long agent report in a panel scrolled 1,015px down: the content went
1,728px to 713px, `scrollTop` was clamped to 0 because that much scroll
no longer existed, and **every message in the thread moved 1,205 screen
pixels at once**.

**Anchoring cannot fix it, which is why your answer is the right one.**
Content above a folded message does not change height, so leaving
`scrollTop` alone already holds it still — that is not what broke. The
browser is what moves it: fold away more than the scroller had slack for
and the clamp is forced. There is nowhere to stand.

Two wrong tests for "did it move" were measured and rejected, and both
are in the guard so neither comes back looking reasonable. **A pixel
threshold** fired on a fold that shifted the thread 18px — the list
settles against the bottom, so nearly every fold moves everything a
little, and a light that goes off every time is one people stop reading.
**"Does it still overlap where it was"** is worse: a report taller than
the panel has an old rectangle covering wherever the new one lands, so
the one fold that threw the thread a thousand pixels reported no
movement at all.

So the test is the CAUSE — whether the fold forced the scroller to move.
No constant to tune, zero in the ordinary case, nonzero in precisely the
case where somebody loses their place.

**And I clobbered a test doing it.** `packages/web/test/fold.test.ts`
already existed and was about something else entirely — "Fold into
<name>" on the identity roster, where folding is one persona taken up by
another. Two meanings for one word, meeting in a filename. Caught by
accident: the deleted file's import was the only consumer of
`primeOwnActors`, so `unused-exports` went 39 to 40 and a ratchet
reddened for a reason unrelated to exports. Restored, mine is
`messagefold.test.ts`, and it is lesson 37 — a bound on dead surface

### Four places said the grid comes back, and it never did

`db0a0b9`

`THEME_ANCHOR_PROP` claimed a `window`-anchored ground let the dot grid
return, and called it "the last spatial reference" under a fixed backdrop.
It was wrong from the day it was written. `.canvas-viewport.themed
{ background-image: none }` is correctly skipped for a pinned ground — and
skipping it changes nothing, because `.canvas-theme` is an opaque
`inset: 0` CHILD of the viewport and a child paints over its parent's
background. The dots are drawn and then covered, for every ground.

Measured on a pinned galaxy at a real daemon: the viewport keeps its dot
`background-image`, `.themed` is absent, and not one dot reaches the screen.

Making it true was the other option, and it was rendered before being
rejected. Over a starfield the dots read as more stars in a regular lattice
and the sky is gone. On the dark theme they are #2b2f36 on #05060c and
barely register — still ambiguous with stars, and no longer a reference.
Over a photograph they punch through the dark parts of somebody's picture
and vanish over the light ones, so the "reference" appears and disappears
with the image under it. A grid that is invisible, or indistinguishable
from the ground, is not a spatial reference; it is damage to the ground.

So the comment is corrected, and it now names what actually says where you
are under a pinned ground: the items travelling across a sky that does not
move — which IS the picture `window` is for — and the minimap, second
because it folds away.

The claim had spread to four places, three of them not the one that was
reported: the `--pinned` flag's help text, so the CLI was telling people
something false; the Sticky menu entry's comment; and `CanvasViewport`'s
own. One report, four copies.

`groundcovers.test.ts` is the part that matters. The behaviour emerges from
STACKING rather than from any line declaring it, so nothing in the suite
touched it — which is exactly how a comment gets to assert a rendered
behaviour the app does not have with 3,800 tests green. Nine mutants were
run against it before it was committed: grid moved off the viewport, ground
not full-bleed, ground not absolute, a ground gone translucent, a ground
painting a literal instead of a token, a ground with no fill, a third layer
painting the grid, `.themed` deleted as dead code, and the ground layer
moved out of the viewport. All nine caught.

### A port nothing answers on can still kill somebody else's daemon

`a8e67a5`

`direct.test.ts` picked 4497 by hand. The file never binds it — that is
the whole assertion, that nothing ever comes up on the direct machine —
so the number looked harmless. But `afterEach` hands it to `stopDaemons`,
and `stopDaemons` kills whoever answers on the number it is given. The
hazard is not this file binding the port; it is this file killing what
did. A collision there would not fail direct.test.ts, it would end
another worker's daemon and fail an unrelated file.

That is exactly the case `test/ports.ts` was written for, and its header
says to move any hardcoded port it finds. So: `reservePort()` in
`beforeEach`, a `let directPort`, the same shape `shelf.test.ts` uses.
The comment keeps its real point — direct mode must never start a daemon
— and adds why the number is no longer chosen: a port has two readers,
and only one of them is this file.

Swept `packages/cli/test/` and `packages/server/test/` for the rest.
Nothing else to move. Every other `listen(0)` in the tests keeps its
socket, and the two server tests that pass a number to `startDaemon`
(`claims`, `door`) are re-binding a port they read off a server they
started themselves — which `ports.ts` explicitly allows, because
`port: 0` is atomic and those never have to tell another process.

17 tests in direct.test.ts pass; test/ports.test.ts, whose guard reads
every reservePort user, passes too.
