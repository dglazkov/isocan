# 12 October 2026 — A proxy at the door, and a gateway on the wire

## Hosting behind an authenticating reverse proxy

A hosted home standing directly behind an authenticating reverse proxy already knows
which person knocked on every HTTP request and WebSocket upgrade — the proxy proves
that before the socket ever reaches the daemon — yet `isocan` knew only how to borrow
a Firebase Identity Platform project (`ISOCAN_AUTH_PROJECT` + `ISOCAN_AUTH_API_KEY`)
and pop a sign-in flow in the browser. On an internal deployment where browser
requests arrive already authenticated by the proxy and agents run inside capsules
whose identities carry an environment prefix, popping a third-party sign-in window is
both redundant and unreachable for headless clients.

Two vendor-neutral seams answer the whole topology without naming any single proxy or
changing anything on `isocan.io`:

- **Trusted reverse-proxy email attestation (`ISOCAN_PROXY_EMAIL_HEADER`).**
  `resolveProxyAuth`, `attestationFromProxy`, and `ensureProxyAttestation` in
  `packages/server/src/attest.ts` read the configured header list (`x-forwarded-email`,
  `cf-access-authenticated-user-email`, `x-goog-authenticated-user-email`, or a
  base64url protobuf wire payload when `ISOCAN_PROXY_EMAIL_PROTO_FIELD` names the
  field), strip an optional capsule prefix (`ISOCAN_PROXY_EMAIL_STRIP_PREFIX`,
  compiled once at boot), reject anonymous sentinels, and record
  `verifiedVia: "proxy"` onto the badge at `POST /api/door`, page cookie mint,
  `onRequest`, and WebSocket upgrade admission (`ws.ts`). `attestersOf` advertises
  `attesters: ["email"]` while keeping `auth: null`, so private email/group grants
  work immediately without rendering a Firebase sign-in button, and `proveOperatorFromProxy`
  in `packages/server/src/operator.ts` allows operator acts from configured
  `ISOCAN_OPERATORS` addresses over the same header.
- **Per-home transport gateways (`gateways` in `config.json`, `ISOCAN_HOME_GATEWAYS`).**
  Workstation CLIs and local syncing replicas cannot dial an enterprise proxy's
  `https://` hostname directly without a local authenticating tunnel, yet replacing
  `homeUrl` itself would pollute `.isocan/project.json`, `homes.json`, `identity.json`,
  and fail `expectedHome` authority checks on the server. `gatewayBaseFor` in
  `packages/server/src/config.ts` resolves a transport-only `dialUrl` while keeping
  canonical `homeUrl` intact everywhere in state: `HomeLink` (`home-link.ts`) dials HTTP
  and WebSocket upgrades through `dialUrl` while storing credentials and assignments
  under `homeUrl`, and `DaemonClient` (`packages/api/src/client.ts`) + `askTheDoor`
  (`packages/core/src/badge.ts`) route direct API calls and door knocks through the
  same gateway on exact origin boundaries.
