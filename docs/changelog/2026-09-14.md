# 14 September 2026

## Design lint research and roadmap

The `@shadcn/lint` announcement prompted a compatibility study against the
actual HTML authoring path. Its useful contribution is a diagnostic that tells
an agent which existing component treatment or token can repair a violation.
The package itself targets Tailwind v4/JSX, while canvas screens are
self-contained HTML and the app uses ordinary CSS.

The synthetic probes found both sides of the boundary: the upstream plugin
reported five findings for a TSX example and ignored HTML/CSS; the existing
HTML auditor credited an undefined CSS variable, missed spacing and font
shorthand, and flagged a color string in prose. Tailwind's suggested `p-3.25`
also demonstrated why removing arbitrary-value syntax does not enforce a
canvas's discrete spacing scale.

The [research](../research/2026-09-14-design-lint.md) keeps the executable probe
and results beside the argument. [#299](https://github.com/dglazkov/isocan/issues/299)
tracks shared HTML diagnostics, scoped contracts, a browser/agent repair loop
with an equal-budget eval, and an optional Tailwind repository spike. No
product behavior or application dependency changed. Implementation, visual
acceptance and agent lift remain future work.

## Design partnership research

The ordinary request to build an app was traced through both canvas chat and
external agents. The [assessment](../research/2026-09-14-design-partner.md)
finds strong existing primitives—scoped systems, variations, preferences and
versioned artifacts—but no dependable default that composes discovery,
exploration, implementation and browser review.

The newer remote-main questionnaire was included even though it had not
reached this checkout. Its upload handler retains filenames rather than
reference bytes; an executable helper probe confirms another agent's comment
can close a question. The report distinguishes those findings from browser
acceptance and from output quality, neither of which was measured here.

Recommendations center on an adaptive brief, useful visual choices with a
recommendation, reusable design context and evidence from the browser. The
current Impeccable package was inspected at a pinned revision: its references
and runtime cannot be supplied by importing a single command file. The report
proposes a bounded integration and controlled evaluation, building on the
existing design-lint work. Product implementation remains future work.

## Design partnership execution plan

The research now has an execution home in
[design-partner](../projects/design-partner/journey.md): a target journey,
shared-state contract, eight phases with named proofs, and a preregistered
evaluation proposal. The next step is phase 0, reconciling the implementation
baseline and fixing the protocol and synthetic evaluation corpus.

The delivery order produces a complete opt-in path early, then deepens systems,
alternatives and repair. The existing design-lint issues retain ownership of
their mechanisms. Impeccable must earn its place through a compatibility probe
and incremental comparison; the core workflow does not depend on it. Technical
acceptance, human design quality and the experience of partnering with isocan
have separate gates before broad default rollout.

The research's implementation outline is superseded by this project, while
its findings remain the evidence baseline. All eight phases are NOT STARTED;
this session adds the plan, not product behavior, model measurements or a
production rollout.
