## The rc's room is walked on a real home, and the room project closes

Journey 1 was walked on dev.isocan.io from Dimitri's own `~/.isocan`,
after sheep-2 was redeployed at sheep d663fcb:
- The first start of the new `isocan rc` moved seven agents across his
  homes to machine-derived keys.
- A claude-code agent and a sheep agent each answered a comment. The
  sheep was resumed from its pasture, with a three-minute cold setup.
- Withdrawing the sheep ended it and kept the pasture.
- `rc-agents.json` kept its shape.

The walk found one gap, and it predates the module: a sheep resumed
rather than born has no recorded pass, so withdrawal cannot name the
badge its cell holds, and that badge was ended by hand.

Journey 2 ran overnight on a scratch daemon, with two real rcs and real
turns. Each answered its own agent, and neither traded the other's
cursor or failed a turn. With the first rc stopped, the second stayed
silent about its agent. The walk script hung, because it signalled the
subshell rather than the rc, and the last steps were finished by hand.
Journey 3 walked again against the `release` that carries the machine
keys.

A measurement on dev settled what the claim rule had assumed about
hosted homes: admission does not narrow the old hole. A fresh door
badge presenting another badge's agent under its derivable
`agent:<name>` key was accepted. Only agents that an upgraded rc has
moved to a machine key are closed, so isocan.io needs the release and
each owner's rc needs to run once.

The "not held by this machine" sentence dropped "or re-add it here",
which was false on a machine still holding a dual-held agent under its
old key. It now says a pass from whoever holds the agent hands it over.
A turn whose adapter fails to open still leaves the agent's face on;
that is #298.

## `isocan/rc` carries the client a host constructs

Sheep's collie hosts the rc's room in a Cloudflare Worker, and the
Worker has to speak to the daemon. The room declared the calls it makes
as `RoomRoutes` and said a host could construct `DaemonRoutes`, but no
entry a host with no Node could import exported it: the root registers
tsx. Writing the wire again in sheep would make a second client, so
`isocan/rc` now re-exports `DaemonRoutes` and `ApiError` from a new
`@isocan/api/routes` subpath, with core's `BadgeStore` and
`StoredBadge`. A host builds it as
`new DaemonRoutes(base, badgeStore)` over the global `fetch`.

What stood in the way was `Buffer`. `downloadBlob` answers a
`Uint8Array` now, and `DaemonClient` wraps it back into a `Buffer`
without copying, so the blob reads in the CLI and the modules did not
change. The
boundary test names `routes.ts` as the one `@isocan/api` file the entry
reaches, and adding a `node:` import to it fails that test. The
release's declaration rewrite learned the subpath. The installed-bundle
test checks that `DaemonRoutes` is inlined into the browser bundle.
