### mv --beside: the terminal can say "next to" (#337)

`eff8665`

at 35; "beside" is a way of SAYING where, not a new kind of where.

No side said means to its right, matching the voice planner's reasoning
that a canvas is read like a page. It deliberately does NOT hunt for a
free spot the way `--in` does, and there is a test for that: landing
somewhere else because the place was busy is how a spoken or typed
command stops being trusted. Two answers to one question — `--beside`
with coordinates, or with `--by` — are refused rather than ranked.

rather than copied numbers, since a literal would pass while the two

### CLI drawings know their colour too, by reading the ink back (#337)

`ba75c0f`

A drawing added or merged from the terminal came out colourless, because
both paths are handed an SVG rather than strokes and `drawingProperties`
needs strokes. I had called that the decoder problem and left it; it is
smaller than that. `drawingSvg` writes a CLOSED format — `<path>`
elements with a literal hex `stroke`, a `stroke-width` and a `d` of
`M`/`L`/`Q` in world coordinates — and `merge.ts` was already pulling
`<path>` elements out of one. Reading ink back is the inverse of a
writer we own, not general SVG rendering.

`inkFromSvg` is that inverse and is held to being it: the test is the
round trip, that whatever `inkColour` said about the strokes it still
says after they have been through `drawingSvg` and back, including which
colour covered the most ground — the part an approximation could break,
since a `Q` contributes its endpoint and not its control. Ink this
canvas did not draw reads as nothing, an arc stops the read where
understanding stops rather than taking its radii for coordinates, and a
dot comes back as one point because `inkColour` measures a dot by its
width.

So every path that makes a drawing now fills the same field: the Pen and
`drawing_add` from the strokes in hand, add and merge by reading them
back. Measured, same file and same command as before the change, both
items still on the canvas:

    itm_OFrxTTbPkc  Sketch  {kind: drawing}
    itm__fJDWnFcnI  Sketch  {kind: drawing, ink: red}

Two gaps remain, and the comments that used to wave at "a decoder that
does not exist" now name them instead: drawings made BEFORE this carry
no word, because nothing rewrites old items, and a picture's FACE is
pixels rather than paths and needs a raster decoder this does not have.

### voice: a drawing says what colour it is, and undo retracts (#337)

`b21abdb`

Two bugs found by driving a real Gemini Live 3.8 session against a
scratch canvas. Both are in the demo sentence the voice note is named
for, and both looked fine from the inside.

**"The red one" could not be resolved on any canvas.** The projection's
header has always offered three colour sources — a note's paper, an
area's tint, a drawing's ink — and the third never worked. `Item` has no
colour field and a drawing's strokes live inside its SVG blob, so the
only two production callers of `itemColour` hand it `properties` alone
and the stroke branch is unreachable. `colour.test.ts` exercised that
branch directly, so the unit was green while the seam was dead. It
mattered because red is not a paper: `PAPERS` is yellow, pink, blue,
green, grey and an area's tint reuses it, so ink was the ONLY route by
which a canvas could know something was red.

A drawing now writes the word down when the ink is laid, beside `paper`
and `tint` and read through the same field by both surfaces — the cheap
half of the mechanism the note called for, needing no decoder. The
expensive half, colouring drawings made before this and a picture's
face, still needs one and this does not pretend to it.

**There was no `undo` tool.** Undo here is per-actor, which the note
called a free advantage; it was not free, because the model had no way
to ask for it. Told "actually, undo that" it improvised an inverse
`move_item` back to the old coordinates — which demos beautifully and is
wrong: it records a second change instead of retracting the first, so
the log claims both were meant, and it only works for operations
invertible from memory. A delete or a rename is not. The tool says so in
as many words. The standing harness retracts through the daemon's
per-actor undo; the browser dialog declines in words, as it already does
for presence, because `WebHost` has no retract and widening the module
API is a versioned decision rather than part of a bug fix.

Measured against `models/gemini-3.8-live`, same canvas, before and after:

    "move the red one next to the blue one"
      was: ask "I'm not sure which item is the red one"
      now: move_item {item_ref: itm_OFrx…, beside_ref: itm_6GCx…}  958ms

    "actually, undo that"
      was: move_item {to_x: 1100, to_y: 600}
      now: undo {}                                                  596ms

The new tests are at the SEAM rather than the unit, which is the whole
lesson of the first bug.

### judge: a typed judgment tier, researched and designed (#334)

`1aa5bd3`

Asked: research use cases for isocan, typesafe.ai and the ledger. The survey
is docs/research/2026-09-19-system-one-and-the-ledger.md; it became a project
the same day, because the shape it found is one this repository has twice
written down that it needs.

**What a System One model is.** TypeSafe's Jev returns a typed answer with a
calibrated probability and no prose — you declare the fields and their allowed
values, it fills them in, each with a number. Reportedly $0.042 per million
input tokens with free output at 70-500ms. Every vendor figure in these docs is
second-hand and says so: typesafe.ai and docs.typesafe.ai are both blocked by
this container's egress proxy, and phase 0 exists to replace the table with one
read from the reference.

**Where isocan already asked for it.** #205 opens by correcting the claim that
the nightly personas are the cheap tier — all nine are opus at xhigh, there is
one tier and it is the expensive one — and asks for a declared cost, because "a
bound nothing enforces is a comment". The evals plan's first calibration
reading was 30 comparisons at $11.77, which is $0.39 each for 63% agreement,
κ 0.26. Neither document names a vendor. Both describe this shape.

**The constraint that shapes the project.** The evals bar says judges must
cite, and a System One model structurally cannot — citation is not in its
output shape. So the rule is that a typed judge triages and never rules. What
it buys is not a cheaper verdict but a cheaper sort: spend the citing judge
only where the cheap one is unsure, which is the handoff #197 described and
#205 found missing, and which needs a confidence number to exist at all.

**The finding that makes it testable is a corpus, not a model.** Calibration
needs labels, and isocan's own preference harvest has twelve pairs. A personal
knowledge base reachable over MCP has 3,643 cards in a ~130-node tree, each in
a folder a person chose — labels nobody has to write. It carries the pathology
that motivates the first use case too: 1,366 cards, 37% of the base, sit
directly in a folder that also has subfolders, the parent doing double duty as
a category and a junk drawer. isocan has the surface and the discipline and no
labels; the ledger has the labels and no surface.

Six phases. Phase 0 reads the API from its reference and is the only step
needing a person — a key and a machine outside the proxy, under a dollar.
Phase 1 exports the corpus and deliberately writes no classifier. Phase 2 lands
the `Judgment` seam in core with a uniform stub as a first-class implementation
and publishes a reliability curve beside the 4 September reading; it is allowed
to end the project, and that is its job. Phases 3-5 act on the judgment only
after that: the band on a canvas with confidence as position, the folder that
wants to split, and the cheap tier at last.

Design decisions taken: the seam is one interface in core so the vendor is
replaceable and a stub is testable without a key; the cost is returned rather
than estimated, so "cheap" is a fact at the call site; no new Operation,
because a judgment is not a mutation and what it causes is an ordinary act one
undo takes back; and it ships as a module, because a vendor seam should be
deletable.

Docs only. Nothing is built and the roadmap says so.

### extensions phase 3: the panel manifest, and one reader

`877ea31`

`role=panel` makes an item a panel the way `role=tool` makes one a tool and
`role=design-system` makes one a design system. No new kind, no new op, no new
route or store: `isocan panel add` is `item.add` with one property and the
manifest as the blob, `isocan ls` sees it as an ordinary item, and `rm` removes
it — there is no removal verb of its own, and a test proves it.

`readPanelExtension` sits beside `readToolExtension` in the same file and takes
the canvas as its second argument for the reason the tool reader takes the
command registry: the rule is enforced where it is stated. Refusals are prose
naming the field, because they are read by whoever wrote the file and "invalid
manifest" tells them nothing. `panelCapabilities` is derived, never declared —
a manifest that stated its own capabilities could understate them — and it is
honest about the phase, naming what a panel will be able to do and saying it
cannot run, cannot send an operation and cannot talk yet.

**Nothing renders, and that is the phase.** The manifest is readable, refusable
and removable before there is a frame to argue about, and a refusal that
arrives when the file is written is worth more than one that arrives when the
panel is already on screen.

Two things came out different from the phase text, both settled against the
shell rather than guessed, both in the Trajectory:

`src` names a page ITEM on this canvas, not a blob hash, and the reader
resolves it to that item's current version. That keeps what the design says an
extension is an item FOR — editing the page is what changes the panel, and a
bad one rolls back with `S`. A pinned hash would have thrown that away.

`PANEL_SIDES` has one member, `left`, because `.dock-panel` is
`left: var(--edge)` at 320px and the right edge belongs to the tool rail. A
closed set of slots is the closed icon set's argument applied to geometry: the
app draws the slot, so a manifest may only name one that exists. Accepting
"right" would have promised phase 4 a slot nobody has built.

**Proof.** Core 28 tests, CLI 3 against a real daemon, surface guard 8 — 39
passed, exit 0. Typecheck exit 0. The whole fast suite 5,902 passing, the only
failures this container's shallow clone and a stdio child that does not inherit
CHROME_PATH, both reproduced independently and neither touching this diff.

The CLI test's real claim is that the terminal's refusal IS the reader's rather
than a copy of it: it asserts stderr contains what `readPanelExtension`
returned instead of transcribing a sentence. I falsified that directly —
replacing the CLI's `${problem}` with its own hard-coded sentence turned two
cases red — so a second parser cannot appear quietly on either surface.

No WHATSNEW entry: nothing a person can see changed, and that file's own rule
is that a day with nothing anybody would notice does not go in it. README gets
the cheat-sheet line, because the verb genuinely exists and can be typed, but
not a feature bullet beside the tools one — that list is what a person can see,
and phase 4 is what earns it.

Three Open entries for phase 4 and one for phase 7, all in phases.md: the dock
is a closed union of five literals read in four places and a carried panel is
an item id rather than a literal; the dock shows one panel at a time on purpose,
so a canvas with three needs an answer to which shows; and phase 7's tier-2
example is the same `kind` with `rows` and no `src`, which this reader requires,
so that reader branches rather than growing a second kind when its gate opens.

### memory phase 6: copy a source piece into a local pin

`4c683e5`

Closes the original `context pin --from` promise. `isocan context pin <item>
--from <canvas>` and the Context picker's "Copy a piece here" take one current
piece of an ordinary inherited source and make an editable, pinned copy here.
The source is unchanged, and the copy keeps working after the source is
edited, removed or unlinked.

**It is the existing copy act, not a new one.** `groupCopySource` and
`groupCopyAction` freeze and remap exactly as an ordinary copy does.
`groupCopyAction` gained one optional `decorate` hook, because the root-only
`properties` hook could not reach descendants and this act must put provenance
on every copied item and strip the design role from all of them — so the pin,
the provenance and the stripping ride the same `group.change`, which is what
makes one undo take all three. The byte transfer and hash verification moved
out of `CanvasGroups.copyFrom` into `api/copy-bytes.ts` with the digest
injected, and `copyFrom` now calls it: one byte path, so a browser cannot grow
a second answer to "are these the bytes the new item will claim".

No new Operation, no new reducer path, no new permission-bearing op. No
dedicated MCP mutation tool — the existing Context summary carries the copied
piece's provenance, as phase 4 decided.

`api/context-pin.ts` owns the order of the checks for both surfaces, and the
order is the contract: the destination is judged first, so a legacy canvas
gets its conversion guidance before anybody's content arrives; classification
precedes every read, so a personal card relabelled `memory=inherit` is refused
before a snapshot or blob request is made on it; then freeze, resolve with no
bytes written, transfer and verify, and only then re-read the destination and
re-check the same visible edge before submitting.

The provenance is a RECORD, never a capability: six plain facts, no badge, no
token, nothing private, and read by nothing that fetches. It lives in its own
core module apart from the eligibility rules, because local Context reads it
on every canvas while the picker is opened rarely — the third time this repo
has learned that the eager half of a feature must be a separate file from the
lazy half. Malformed provenance is ignored as metadata rather than refused.

**Proof.** The browser walk is `scripts/journey-pin-from-source.mjs`: a real
daemon, the built app, a real browser at 1440px and 390px. It measures rather
than asserts — area, visibility, viewport containment, no horizontal spill,
and `elementFromPoint` resolving back to the element, which is what catches an
overlay. It checks the picker names its source, offers exactly the eligible
pieces and not a group's child alone, that the "copies the current version /
will not update it" sentence is readable, that a group row says how many items,
that the log grew by exactly one `group.change`, and that the source snapshot
is deep-equal afterwards.

It was proved able to fail twice, by mutating the product and rebuilding: once
by blowing the piece rows out of the rail, which the overlay check caught, and
once by rendering the group count off by one, which the rendered-text check
caught. Both reverted; the entry rebuilt to 746,891 byte-for-byte each time.

Also run: typecheck exit 0; the fast suite 5,879 passing with the only failures
a shallow clone and a stdio child that does not inherit CHROME_PATH, both
reproduced independently and neither touching this diff; the entry measured at
746,891 against a ceiling of 747,000, corrected in 05e73a3 because the number
the Proof named was eleven kilobytes stale and self-contradicting.

The deep lane found one real failure and it is fixed here: changing memory's
front matter without regenerating `docs/ROADMAP.md`. `test/roadmap.test.ts`
passes.

Two Open entries, neither a phase and neither blocking. No acceptance walk in
this project is re-run by anything — this script and phase 5's journey-recap
are both absent from `JOURNEYS`, so they pass at acceptance and are never asked
again. And `GroupContext.tsx:38` renders "1 items", seen on the 390px walk,
pre-existing and owned by canvas-groups.

Every phase of memory is now closed.

### extensions: the walk, and the order the demand actually asked for

`ffd15a7`

The extensions project had no `phases.md`, so `conduct/status.sh` could not
read it at all and the roadmap's "stages 3-5 not built" was the only thing
saying where it stood. This writes the walk, and writing it turned up a
finding that changes the order of the work.

The design gates stage 3 (declarative panels) on "once two real tools have
asked for the same shape", and gates stage 4 (extension actors) on "a panel
that acts" — it checked on 6 Sep and found the stage had no subject, because
a tier-1 tool asks rather than acts. Both of those are still right. What was
wrong was the numbering: the demand that has arrived since went to the other
end of the list. Nothing at all has asked for the rows shape, and two things
have asked for the hosted tier — modules phase 5's browser sandbox node,
which names a panel that acts, an extension actor and `connect-src` as its
three blockers, and the workbench Sandboxes section, which the modules
research note calls "a page plus a hosted panel".

So stage 4 cannot come third: it would be the machinery with nothing to
attribute that the 6 Sep check already found. And stage 3 cannot come third
either, for the reason stage 3 itself gives — a declarative vocabulary grows
until it is a bad programming language, and one shaped by fixtures instead of
by a second real tool is exactly that.

The walk is therefore hosted tier first, cut into the three acts it turned
out to be (phase 3 the panel manifest and its one reader, phase 4 the frame
on the content origin, phase 6 the narrow postMessage door), with the
extension actor as phase 5 because that is where it first has a subject, and
declarative panels last as phase 7, waiting on evidence rather than on work.
The stages keep their numbers in design.md because other projects cite them
by number; phases.md maps each to where it now falls, and modules/phases.md
is corrected where it named the old ones.

Nothing is built here. Phase 3 is next and needs no person: no provision
step, no cloud resource, and the content origin — the one gate the design
named for this tier — went live on prod 6 Sep.
