# 14 October 2026 — A fold made at the home reaches the laptop

## Why one person still looked like two

Dion folded his old dev.isocan.io identity ("Dion") into "Dion Almaer" from a
browser at dev itself. dev agreed straight away. His Mac, which replicates the
same canvas, went on listing "Dion" as a separate person.

The home had been sending its fold record (`joined`) to replicas all along:
it rides on every `snapshot`, `resumed` and `presence-roster` message, because
the web app needed it in multi-identity phase 5. The replica's
`mergeRemoteIdentity` took the names and colours beside it and dropped the
map. Names caught up, since the home sends a folded id under the survivor's
name. Everything that compares ids did not: undo, the inbox, mentions,
presence and canvas and agent ownership on the laptop still saw two actors.

A join made AT a replica was never affected: `joinActors` forwards it up to
every home and records it locally. Only a fold made elsewhere had no way down.

## What landed

- **`mergeJoins` in core** (`packages/core/src/claims.ts`): a home's folds
  added to the ones a replica holds. Additive and first-recorded-wins, because
  a join is forever and a second home saying otherwise is a disagreement, not a
  correction. A fold into itself, or one that would close a loop, is skipped.
  It returns null when nothing is new, so the roster path (every cursor beat)
  still writes nothing.
- **The replica takes them** (`Engine.mergeRemoteIdentity`, and the three
  call sites in `home-link.ts`), saved with the rest of the registry so a
  restart keeps them.
- No protocol change and nothing at the home: the field was already on the
  wire.

The replica does not repeat the home's badge check: the home is the desk that
saw both claims, and a replica already takes names from it on the same terms.

Lesson 112 is the shape: a field received and silently not merged, the
read-side twin of lesson 99. `home-link.test.ts` folds at the home and checks
the replica, live and in the file a restart reads; `core/test/join.test.ts`
holds the merge's rules.

## Seven bugs from a brainstorm session, fixed

A session that built ten concept screens on a canvas hit seven problems in
isocan. They were traced to their code paths on 13 October and fixed today,
each with a test that failed first (lessons 113–117):

- **`design workflow` on a replica** read its history from a copy that had
  started from the home's snapshot and so held no sequence 1. It now reads
  the home's log when the local one starts late, and still refuses a history
  with a real hole.
- **`canvas shot` failed with only `Node.js v24.20.0`**, because a crashed
  script's last stderr line is Node's version trailer. The line above the
  first stack frame is reported now. The size failure itself did not
  reproduce.
- **Text nodes**: `fit` and `edit` measured height at the default 320
  column, so a widened node became a tall narrow one. They measure at the
  node's own width and keep a width set by hand. Fit also stopped moving a
  node that only shrank, past neighbours it already touched.
- **`isocan mv <item> x,y`** works, as `--at` and `--by` always did.
- **The design audit** resolves a `var()` inside a gradient or `rgb()`, and
  reports a missing variable once. `color-mix()` stays unexamined, with one
  clear line. `DESIGN_AUDIT_VERSION` is 1.2.0, so repair captures made
  under 1.1.0 are refused as stale.
- **A canvas deleted at its home while this machine was away** greeted every
  inbox with *canvas not found*. A replica never forgets on its own, so the
  fix is explicit: `isocan canvas forget <id>` moves the copy aside,
  recoverably, and is refused while the home still has the canvas. The
  inbox now says once that the canvas is gone.

## Two experiments specified: proactive, and critique

**`proactive`**: an agent that proposes without being asked, from a
brainstorm of ten drawn concepts, read in full from their canvas. One
primitive carries nine of them: a proposal, an item hanging dashed under the
screen it came from, never replacing it, citing its trigger, kept or
dismissed in one key into an editable Taste card.

**`critique`** is the first of those built in full. Critics are personas
that live on the canvas, seeded from design-competition's nine packs. They
pin typed notes and never edit, and one voice reads them into agree, split
and blocker. A survey found that no grant can comment without editing, and
that roles rejected a commenter rung on purpose. So "never edits" is a
`note` ceiling on one critic's claim, which only narrows.

## critique phase 0: critics on the canvas

A critic is now a markdown item on the canvas in the persona format,
`critic: true` in its front matter, read back through `parsePersona` like
the repository's own reviewers: personas' step 6 for the one kind a second
person edits. `isocan critic add <pack>` writes one of design-competition's
nine lenses into an editable card; `critic new` writes a skeleton; `critic
ls` reads them back, budget included. The naming rules (named for a
principle, never a person; credit that says not affiliated; no first-word
clash) moved into core (`homage.ts`) so critique uses them without depending
on competitions, which it proves by working with that module absent. Two
small changes in core came with it: a module renderer may require a
property as well as a mime (module API 0.2.8), so critic cards do not take
over every note; and `parsePersona` stopped dropping `color`. Behind the
`critique` experiment. Next is a critic asked and answering, which spends
model tokens and waits on a yes to its budget.

## critique phase 1: one critic, asked

`isocan critique <item> --by <critic>` enrols the critic once (its working
directory rewritten from the card each time it is asked, so an edit to the
card changes the next critique) and opens one thread on the screen that
mentions it. The ordinary wake does the rest. A critic writes with
`critique note <item> --at fx,fy --kind working|risk|blocker --question N`:
a thread pinned at a point, its first line written by the verb so prose
cannot fake a blocker. It finishes with `critique done`. `comment add
--item <i> --at fx,fy` pins any comment the same way, through one core
function.

The critic's budget is enforced by the rc: turns per run, and dollars from
ACP's `usage_update.cost` with the turn cancelled past the cap. The first
real critique ran on Codex: *Inevitable*, 38 seconds, one turn, four notes —
"Pay and Save … divide the checkout into two competing destinations. Make
Save for later a text link." The screen's version did not move. Codex
reports no cost, so the dollar cap is still unproven, and a "turn" counts
summons rather than model steps. Phase 1 is part-done for that.

## critique phase 2: the ceiling

A critic that tries to edit is now refused by the home, not by its prompt.
The ceiling lives on the critic's enrolment row in canvas state, written by
a new op, `agent.ceiling`, and checked in `Engine.applyAndPersist`, the one
place a home applies a write, so a replica forwarding an op meets it there
too. Under the `note` ceiling a critic may pin a thread to an item, reply,
and react; everything else is `beyond-ceiling`, with a sentence, and nothing
written. It cannot lift its own ceiling, by op or by undo; `isocan critic
release` does, for the person who set it. It is a new op rather than a field
on enrolment because an older home refuses an op it does not know, but would
drop an unknown field and leave the critic uncapped.

What it is not: a sandbox. Agents ride their machine's badge, so a critic
process that drops its session key speaks as the person. And a capped
critic can still mention another agent in a reply. Both are recorded.
`critique --by <roster id>` (`ive`) works now, through one resolver.

## critique phase 3: two critics, and the read

`critique <item> --by a,b` and `/critique` ask several critics in one
thread; each reads only the screen. `critique read` folds their notes
into agree, split and blocker by where the pins fall; `critique both`
asks a builder (never a critic) for two variations of a split, each citing
the note it answers. The first two-critic walk called "remove the banner"
and "replace it with a photograph" an agreement, because both were risk
in one place, so the read now classifies each move by verb and calls
opposed moves a split. On the same notes, re-read, it did, and *Build
both* made both variations. Critics had also woken on every Chat message
and on a "thanks", spending each time; core's wake rule now wakes an
agent with a `note` ceiling only when it is mentioned.

## critique phase 4: the web's doors

Everything a terminal can do, a browser can now: a Critics panel (the
roster, this canvas's critics, add, new, release), *Critique with…* on a
screen's menu, pins in each critic's colour that open their note, the read
in the thread, and *Build both* on a split, which asks a standing agent
that is not a critic and sends nothing until the person presses. The
roster comes from the daemon (`GET /api/points/:point`) and the lens text
from the same `critique.md` files, so there is one copy. A journey plays it
end to end in a real browser with scripted critics. What remains is a
person's walk ([the page](../verify/2026-10-14-critique-in-the-browser.md))
and phase 1's dollar cap.
