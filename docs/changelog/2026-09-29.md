# 29 September 2026 — the Jetski tie goes both ways

Yesterday put the canvas beside the Jetski chat. Today Dion asked for a
*killer* integration: *how can we teach the Jetski side what the user can do?
How can we surface how skills work across both?* It started on his cloudtop,
where a Jetski conversation widened the host bridge, and it finished as
[phase 4](../projects/jetski/phases.md) of the Jetski project, with four new
scenes in [the journey](../projects/jetski/journey.md).

## The bridge can drive the frame (cloudtop, 04252a58)

The canvas used to tell its pane what was selected and obey one command,
*focus this item*. Now the pane can also move the camera (fit, 100%, the
selection, zoom in and out, a point, a box), set the selection, follow a
session's cursor and open a comment thread. The CLI can do the same through
the pane: each `isocan session point|select|move|on|work` records a `bridge`
cue in the session file. `/api/workspace` hands the cue to the pane, and the
pane posts it into the frame once per timestamp. An agent that says *look
here* now actually moves the person's view.

## Skills on both sides

The canvas's skills are its slash commands, the built-in ones and any added
with `/skill add`. The pane could not reach them, because they post into the
Chat the embed hides. Now `/` in the pane's box lists them from `isocan command
ls`, leaving out the ones the web app answers itself. A skill can run in two
ways:

- **In this conversation.** It arrives as `/name args`, which is the canvas's
  own grammar, with one extra sentence: `isocan command show <name>` holds the
  instructions.
- **Handed to a standing agent.** It is posted as the person's own comment,
  `/design-audit @Orla …`, and Orla answers there.

So there is one catalogue, and where a skill runs is a choice of who runs it.
Nothing about skills is Jetski-only.

## The pane teaches by offering

The composer is there before anything is selected, and starters under it
change with the canvas. With a selection they offer *Build this in the repo*,
the design skills this canvas has, and *What's wrong with it?*. Without one
they offer *What's on this canvas?*, *Answer N open questions*, *Put what we
did here on the canvas* and `/ N skills`. A starter fills the box and sends
nothing, so reading them costs nothing. The two cross-world acts, from the
canvas to the repo and from the chat to the canvas, are among them by name.

## The canvas can reach the conversation

This was the real gap. A Jetski conversation arrives on its canvas under its
own name but is told not to park, because the person steers it in the chat.
So a comment on the canvas that mentioned it reached nobody.

The sidecar now runs a relay. It parks `isocan wait` as each recent named
conversation and hands that conversation whatever the wake printed, through
`agentapi send-message`, with a note to answer on the canvas. It adds no
vocabulary: which comments wake a conversation is the daemon's usual rule, and
the cursor is the conversation's own. The relay steps back when a conversation
parks itself, and only one relay runs per machine, because two parks for one
actor would push each other out forever. To make the relay possible, the hook
now writes down which conversation became which actor
(`jetski-conversations.json`). The desk keeps that claim and never hands it
back, so nothing else on the machine could have said.

Two more pieces use the same record:

- **Asks.** An *Asks N* button in the pane's header lists the questions agents
  left for the person. *Answer with Jetski* hands one to the conversation to
  work out first.
- **Fan out.** This asks Jetski's own tiers (`flash`, `pro`, `flash_lite`) the
  same thing in new conversations. Each arrives on the canvas through the hook,
  under its own name and with its tier shown. A face that is a conversation
  gets 💬 to open it, and the pane's own face says *this chat*.

Fan-out is narrower than the Agents bar's standing agents on purpose, and
design §12 says why. Phase 3 chose standing agents over agentapi
conversations. A standing agent stays, answers later and runs on any harness.
A fan-out uses Jetski's tiers, now, once, and needs no `isocan rc`.

**Proof:** `test/jetski-tie.test.ts` has 20 tests. The pane was also walked in
a real browser against its real routes, with a fake CLI, a fake `agentapi` and
a stub canvas that speaks the bridge. What only Jetski can prove is part three
of [the verify page](../verify/2026-09-28-jetski-plugin.md).

## Also

- `/isocan` and `/fan-out` ship as Jetski chat skills in the plugin: typing
  `/isocan` in chat surfaces the `[Isocan Canvas](sidecar://isocan/canvas/)`
  pill (or runs a canvas request alongside it), and `/fan-out` launches
  parallel `flash` + `pro` canvas conversations directly from chat.
- Space-saving pane polish from live use: starter prompts rotate as an `e.g.`
  in the input placeholder rather than a separate pill row; the header title
  (`#where`) becomes a clickable link when framed and shows the destination URL
  in an instant hover popover (dropping the separate `Reload` button); the
  `Agents` toggle shows an active `▾`/`▸` state; hovering `Agents:`, `Open ↗`,
  and `Asks` shows instant CSS popovers; transient poll blips auto-clear and
  the status banner has `Retry` and `×` dismiss; and `sessionStorage` caches
  workspace URIs and host theme tokens across frame reloads.
- When the same actor name is open in two tabs, the remote cursor wears an
  `other tab` badge with a dashed ring and muted opacity while the local cursor
  badge says `(you)`. A cursor's mark stays on the same line as the name, on
  remote cursors and your own (f705a84c).
