### The canvas could not be moved with a finger

`5ad7e68`

#182 stage 0, the touch half. Measured 5 Sep on a 375x812 Android
emulation and true until today: a one-finger drag on empty canvas
started a MARQUEE, so the canvas could not be panned unless the Hand
tool was up — and the Hand tool is a 24px button on a rail. Two fingers
did nothing at all: zoom was a ctrlKey wheel, WebKit's gesturestart and
the +/- buttons, none of which a phone has. `touch-action: none` had
switched the browser's own pan and pinch off, correctly for a canvas
that handles touch itself and a trap for one that did not.

One finger pans, two pinch, a tap clears the selection. The mouse is
untouched — every mouse gesture behaves exactly as it did, which is what
makes this safe to ship without a device in the room.

`pinch` composes the two folds that already existed rather than doing
its own arithmetic: the fingers' distance is the factor through
`zoomAt`, their midpoint's travel is a `pan`. Zoom FIRST, about the OLD
midpoint — zooming about the new one applies the pan twice, once scaled.
Asserted in `viewport.test.ts` because the property that matters is
geometric: the point under your fingers must not move, and a browser
test cannot see a canvas sliding out from under the hand doing the
gesture.

Driven with real touch events on a phone emulation before landing: a
one-finger drag moved the transform, fingers spreading 80px to 176px
scaled by 2.2, and the world point under them drifted **0 world px**.

Three decisions the note left open. **Lifting one finger ends the
gesture** rather than becoming a pan — continuing lurches the canvas on
the frame the second finger leaves. **A pinch does not coast**; a flick
out of a zoom is a hand leaving the screen, not a throw. **A tap does
not coast either**, which is new: a finger resting on glass reports
movement, so a tap arrives with jittery samples and a real velocity, and
the canvas would drift away from somebody who only meant to deselect.

Two bugs found by driving it rather than reading it. A second finger has
to REPLACE the gesture in flight, not extend it — a pan still running
under a pinch is the line-between-the-fingers bug. And fingers are
pruned at the viewport, not inside each gesture: a touch that started a
stroke or an item drag reaches neither, so the map kept a finger nobody
was holding and the next single touch pinched against a ghost.

Not built, and still broken at 375: the minimap and the zoom cluster
overlap, the identity badge is cut off, and eight buttons are under the
44px floor. Long-press for the context menu wants a device to judge the
hold time against.

### A blob a property names is a blob somebody is using (#204 phase 1)

`83d626f`

The sweeper marked item versions, the trash and retained log entries, and
nothing else named a blob — so nothing suffered. It would have suffered the
moment something did: a custom background is a tile stored as a canvas property
pointing at an uploaded blob, and a home sweeps itself on an hour's timer. The
ground would be unreachable the second it was set and gone within the hour,
with nothing logged and nothing to see.

Written before the feature rather than after the bug report, and matched by
SHAPE — a 64-character hex string in any property value — rather than by a list
of blessed keys, because a list is a second thing to keep right and its failure
is silent. The two mistakes are not equal: a false positive keeps bytes a later
sweep reclaims, a false negative deletes somebody's work, so it errs toward
keeping.

Two things learned building it, both worth the record.

**The name I had written into the spec was taken.** `export.ts` already exports
`blobsNamedBy(log)` — every blob the LOG names, "by shape rather than by op
type… so a new op that names bytes is backed up the day it ships rather than
the day somebody remembers this". That is the same argument this made, made
earlier, for backup instead of sweeping. Two surfaces name blobs and both are
matched by shape now; `blobsInProperties` is named apart because a caller
wanting one would be badly served by the other. Fifth time this week I have
started building something this repo already had.

**It takes CanvasState, not CanvasContents.** A canvas's own properties live on
the RECORD; the contents carry items, threads and trash. A signature over the
contents could not have seen a background tile at all — the same distinction
that made the themed cursor read `s.project` rather than `s.canvas`.

The gc test is aged past the grace period on purpose. At a non-zero `graceMs`
it would pass for the wrong reason — protected by the upload's freshness rather
than by the property — and would go on passing if the property were never read.
Both halves are held: retained while the property names it, swept once the
property lets go.

### The hover border survives zoom, and a thing says what it is when the chrome goes

`23aaa06`

Three findings from the border audit Dion asked for, and the fix he expected
was only the first of them.

**The hover outline was never counter-scaled.** `.selected`, `.entered` and
`.peeked` all use `calc(Npx / var(--scale, 1))` so they stay N SCREEN pixels;
`.item:hover` was still `1px` in world units, so at 10% zoom the preview of the
box a click would give you is a tenth of a pixel. Dion: "we had this issue with
selected border and then we fixed it" — right, and this was the one place the
fix was missed. Kept at 1px rather than matched to selection's 2px: a preview
as heavy as the thing it previews stops being one.

**The audit then found the real gap, and it is not colour.** Border carries
what a thing IS; outline carries what is HAPPENING to it. That system is
coherent and worth keeping — `--accent` means "this one, wherever you are
pointing at it from", shared with the files panel row and the minimap peek, so
colouring hover by type would spend that invariant and add a fourth colour
language to pixels already carrying three.

What actually happens is that `.item-titlebar` is `display: none` below
`hasRoomForChrome`, and the kind icon lives in it. At exactly the zoom where a
wall of pale rectangles is hardest to read, every signal of what each one is
disappears at once — and only three of nine kinds have a border colour anyway,
which is why the ask was "I can't tell the types apart".

So the mark comes back when the chrome goes: centred, quiet, sized off the item
by the same rule the text mark uses, because "forty oversized glyphs are the
same smear in a different hat". Pictures are exempt — an image, a video and a
drawing already ARE their small form, and a mark over one covers the thing it
names. It is the same rule `textIsLegible` applies to words, reaching the other
kinds.

**And a version drew as something the item never was.** A DESIGN.md carries its
tokens as swatches, and every older version fanned out beside it as a wall of
raw markdown. `VersionContent` takes `designSystem` and three callers pass it;
the fan was the fourth and did not. `canvasOf` and its source went with it for
the same reason — a canvas card's earlier versions should be the place drawn
small, not its address as text.

Measured rather than asserted: at 10% zoom on a canvas of eighteen, seventeen
have their chrome hidden and two draw a mark — correct, because fifteen are
pictures — and the mark computes to 136 world px, which at that scale is 13.6
on screen. What I have NOT seen is it rendered: a day of headless sign-ins
exhausted the daemon's door meter, and the numbers above are from the one run
that got through.

## The queue hole, which had to be closed first

The soft half is a warning into a void unless findings reach `main`, and they
did not: reports land in a PR on `personas/$DAY`, and eight piled up unmerged
while the number one of them described grew. The guard I added yesterday was
watching an empty room.

Two things were wrong, and the second is why the first was not enough.

**Findings had no identity.** A persona writes one finding per missed goal per
RUN, so a bound that stays missed writes a new `unanswered` row every night.
Merging the reports would have demanded a fresh answer daily for a question
nobody's answer changed — and a guard that nags every morning is a guard
somebody turns off. A bound-finding is now identified by its goal and its
bound, not its text, so one answer stands for the nights that repeat it.

With the correction that matters: an answer stops covering when the number gets
materially worse. Ten per cent, chosen against the failure this whole thing
exists for — 600,420 to 768,993 is +28%, so it would have been asked again.
Drift is measured from the SMALLEST number anybody said yes to, or a series of
small accepted steps launders a large one.

**And the reports merge themselves now**, only when the diff is confined to
docs/reviews/. The workflow's comment says a PR rather than a push because "a
machine writing into main every night is how a directory quietly fills with
things nobody agreed to" — that worry was right and is now answered somewhere
better. Agreement is forced on the FINDINGS, which is what anybody was ever
going to disagree with, rather than on the act of filing a dated page. Both
arguments are in the workflow, so the next reader sees the trade.

### Two more specs: a ground of your own (#204), small personas (#205)

`f9bac80`

Both research, nothing built, and each turned up something that would have bitten
whoever built it first.

**#204, custom grounds.** The blocking finding is that the garbage collector
does not know a property can name a blob. `reachableHashes` walks item
versions, trash and retained log entries and never looks at canvas properties,
and a home collects itself on an hour's timer — so a tile stored the obvious
way is unreachable the moment it is set, and the canvas silently loses its
background within the hour. The fix is a rule rather than a special case,
`blobsNamedBy(canvas)`, because the next feature that names a blob from a
property should not have to teach gc again.

The cursor half is the real design question and the answer is probably not
"upload one". #195 requires a themed cursor to wear the viewer's own identity
colour, which rules out an uploaded image outright — six people would share a
pointer. Choosing from a shipped library of tintable shapes gives the feature
away while keeping the rule, and it puts the cost where it belongs: drawing a
cursor that reads at 18px took six candidates across four sizes to get three,
and asking a user to do that is asking them to fail.

**#205, small personas.** It opens by correcting #197, which is a day old and
said confidently that "the nightly personas ARE the cheap tier". They are not —
all nine declare model: opus, effort: xhigh. There is one tier, it is the
expensive one, and it runs nine times a night. So this request is #197's
missing half rather than a new direction.

The idle trigger is expressible here and in few other systems, because presence
already answers "is anybody on this canvas" — with the subtlety that there are
TWO idlenesses, per-canvas and per-machine, and conflating them starts a heavy
build while somebody is mid-sprint elsewhere.

And the registry is not the findings queue. The queue records what IS wrong and
must be able to fail a build; a registry of what MIGHT be worth doing must not,
because a backlog of ideas that reddens the build teaches people to stop
writing them down. Its honest failure is going stale, and the guard for that is
dates and evidence rather than a test.

The write rule falls out of #197's own escape clause: a small persona may open
a PR only where a pre-existing guard would fail if the change were wrong, and
never writes the guard it is judged by. A dependency bump qualifies; "a variety
of performance work" does not.

### Semantic zoom, researched and specced (#203)

`c3518c0`

Asked for as research: what the Google Maps town/city/state ladder could mean
on a canvas.

The finding that shapes it — a map zoomed out is not a map with things hidden.
Portland at z12 is a street network; at z6 it is a dot and the word Portland.
The streets were not faded, they were REPLACED by something that stands for
them. Substitution, not subtraction.

And isocan already subtracts, in four places, with four thresholds written
separately: textIsLegible turns words into a T mark, hasRoomForChrome drops the
title, underRowSpellsItOut abbreviates, the ground fades. The codebase already
knows they are one idea — textnode.ts says "the canvas already keeps a rule of
exactly this shape for item chrome". So the gap is not zoom-responsiveness. It
is aggregation: nothing knows what a SET becomes when it is too small to read.

The thing that has to be decided first is that a canvas has no canonical
hierarchy and a map does. Portland is in Oregon, always, for everybody. A
canvas has areas (a box, a title) and lineage (a tree of where a thing came
FROM, not where it sits), they can disagree, and most canvases have neither.

Which makes the obvious move the trap: cluster nearby items at zoom-out and
label the cluster. A cluster invented at render time has no box until it is
invented, so its label lands where nobody put anything; it moves as you pan;
and it has no identity, so you cannot click it, link it, or have an agent act
on it. An animation, not information. Aggregate only over things that already
have a box and a name.

Four rungs then, triggered by how big a thing is on YOUR screen rather than by
an absolute zoom level — already this app's pattern, and the reason the rules
compose. Rungs 1-3 exist; rung 4 is the feature: a sheet whose contents have
all become marks stops drawing forty dots and draws "Lake House · 8 screens".

Phase 1 is worth doing even if nothing else is: unify the four existing rules
and give them hysteresis, because every one of them can flicker today if
somebody rests at the threshold.

### Click a message's date to fold it away

`ea12371`

Asked for after a thread where one agent's report ran longer than the screen
and everything said before it was somewhere above.

The date is the right target, and it is worth saying why, because "make it
clickable" is usually the wrong answer. It is on every message, it is inert
today, and it is the one part of the header that is not already an identity or
an action — clicking a NAME should go to that person and clicking the body
should select text. The date was the only surface here saying nothing.

A folded message keeps its FIRST LINE rather than collapsing to nothing. A
column of names and times is a list you cannot read down: you would open each
one to find the one you meant, which is worse than scrolling past them. The
preview strips markdown rather than rendering it, because a heading's ## is
noise in a summary and a bold run would change the line's height — the one
thing a folded row must not do.

A button with `aria-expanded`, not a span with a handler: this is a control
now, and the half that is invisible in a screenshot is the half a test has to
hold.

The state is per-reader and not persisted, deliberately on both counts. Two
people reading one thread are not reading it for the same reason, so one of
them folding a long report must not fold it for everybody; and a thread you
come back to tomorrow should look like the thread, not like the shape you left
it in and have since forgotten.

`CommentWhen` and `CommentFold` are shared because the Chat panel and the pin
popover both render a comment and neither owns the other — the same drift that
made the minimap re-derive ITEM_KINDS.

Driven in the running app rather than asserted: clicking a date drops that
message's body (23 bodies to 22), replaces it with its first line, and flips
aria-expanded on that one only; clicking again restores it exactly.

### Prompts for the themed cursors too, and why they are a different job

`f70049d`

Three more blocks, and a correction: the first version of this doc said the
cursors were "not an image job" and left it there. That is half right and not
useful. They are not ONE job — an image model can draw a silhouette worth
judging, and a model that writes SVG produces the thing that ships. The doc now
says do the first if the shape is not obvious, then the second.

The constraints are stated where somebody generating will read them: one filled
path, viewBox 0 0 18 20, starting at M1.5 0.5 because that point is the hotspot
where the click lands, and NO colour — the fill is the viewer's own identity
colour at runtime, and a cursor carrying its own would delete the one signal
saying who is who.

And the evidence, so nobody spends the generations again: the issue suggests a
rocket and a rocket does not work. At 18px a rocket silhouette IS an arrow —
the fins never register, and both candidates read as a ragged pointer at every
size up to 32. Six candidates across four sizes produced the three that
shipped, so the honest instruction is to expect to reject most of what comes
back, and to judge it at 18px on a dark ground rather than at the size the
model renders it.

### Two research notes asked for and deliberately not built: i18n and analytics

`5e4a1be`

### Every open canvas was burning a third of a core, and had been for two days

`0ca0676`

The chevron did not freeze the page. The page was already looping, and the
chevron mounted one more consumer into the loop.

useCommands ended `return withModuleCommands(...)` — a new array on every
call — and useCanvasTools has that value in an effect's dependency list, with
setTools(read) at the end of it. Render makes a new array, the deps look
changed, the effect runs, setTools renders, render makes a new array. Forever,
on every open canvas, from the moment the page loaded.

Measured rather than reasoned about, which is the whole story of this bug: a
canvas sitting untouched with nobody near it profiled at 68% IDLE, with no app
function above 2% and React's ReactElement/jsxDEV/diffProperties at the top.
After the fix, at rest and with the chevron clicked, 100% idle. That is the
76-117% CPU on every isocan tab in the Task Manager, and it explains why the
tabs felt worse the longer they sat beside the memory problem rather than
because of it.

Neither commit that made it was wrong. Modules phase 4 (5 Sep) made the return
unstable, harmless because nothing held its identity. Extensions stages 1-2
(6 Sep, the next day, another file) added the consumer. react-hooks/
exhaustive-deps is enforced here and had nothing to say: the dependency WAS
listed. The rule checks that deps are complete, never that they are stable,
and nothing warns at the seam.

So the guard goes on the first half, where the cost is one useMemo and the
author is present: packages/web/test/stablehooks.test.ts requires every
exported hook to return a primitive, a memo, or a value on a short ALLOWED
list carrying its reason. The sweep it forced found four more loaded guns —
useSprint, useSettling, useSectionHeight and useOnScreen, this session's own —
none of them firing, all of them now memoised. Two dependencies are read

Date.now() are inputs no dependency array can name.

lessons.md #36 and #37: the hook rule, and the one that matters more — reading
the code found five wrong diagnoses over three sessions, and a six-second
profile named it in one step. When the symptom is slow or frozen, profile at
rest before forming a hypothesis. Idle is the measurement.

### Nothing polls a tab nobody is looking at, and no hold outlives its window

`34d0030`

Taken from the patterns Dion uses elsewhere, checked against this codebase
rather than adopted wholesale. Two of the six already held here — flushing
pending writes on hidden (canvasStore) and re-measuring iframes on return
(not applicable: items are sized from stored dimensions, so nothing here
reads a frame's content box). These are the ones that did not.

Every repeating fetch was a bare setInterval, so a background canvas went on
asking the daemon who was present and whether an rc was answering for as long
as the tab stayed open. Chrome throttles a hidden tab's timers to about once
a minute, which is why this was never the thing that froze a browser — but
"the browser mostly stops us" is not stopping, and the daemon answers either
way.

everyWhileVisible is the shared primitive, borrowed from waitForDocumentVisible
with one addition that matters more than the saving: coming back READS
immediately. Resuming the interval alone leaves somebody who has just
returned looking at an answer up to a full period old, and these are answers
like "is anybody listening right now", where stale is worse than absent.

A plain function rather than a hook, because useAnswerable keeps ONE timer
shared across every row on screen and a hook could not live there. Four polls
converted, plus the sprint's one-second clock: a countdown nobody can see does
not need to tick, and the tick is a re-render of every subscriber.

It deliberately does not pause on blur. A canvas beside a terminal is
unfocused and fully visible, and somebody watching an agent work on the other
half of the screen is exactly who needs presence to keep moving.

And the momentary holds: Space, Z and P all borrow a tool while held, and a
keyup that lands in another window never gives it back. Only the pen was
released on blur — fixed when it cost a lost drawing, a stroke left wet and
invisible to everyone. Space and Z were left because they only cost a canvas
stuck in Hand or Zoom with nothing on screen saying why, which is exactly the
kind of bug that survives.

Three source-shape tests updated rather than deleted: they asserted the
mechanism (clearInterval(timer)) and now assert the invariant, including that
no bare interval is left behind — half a fix is the failure mode this file
has already seen once today.

### A live document lasts as long as you can see it, and no longer

`5f2604e`

The 6 September freeze, second half — and a correction to the first half.

The earlier fix gated the Chat panel's thumbnails and then disconnected the
observer on first intersection: seen once is seen. Its comment claimed the
bound "does not depend on how long a thread is... or how long a tab has been
open." It depended on all three. Monotonic means every card ever scrolled
PAST stays live, so the ceiling was not a screenful, it was everything you
had ever looked at. Writing a bound in a comment does not make it one.

The same canvas froze again the same day, and the Task Manager named the
shape: isocan subframes at 713MB, 940MB and 1.3GB. The canvas holds six live
HTML screens totalling 4.6MB, one of them a 3.3MB photo gallery whose images
decode to a great deal more than they download as.

Two changes:

useOnScreen releases. On screen keeps a document; leaving releases it after a
grace period, so scrolling past and back costs nothing while scrolling away
and staying away costs nothing either. The ceiling is now a screenful plus
what you looked at in the last few seconds, and this time that is the
mechanism rather than an aspiration.

A hidden tab counts as off screen. IntersectionObserver still calls an
element in the layout viewport intersecting when the tab is in the
background, so without this a backgrounded canvas holds every document it
had — which is what those gigabyte subframes were. The browser pauses our
animation frames and throttles our timers for us; nothing but this releases
our memory.

And CanvasViewport had no gate at all: it maps EVERY item to an ItemView
unconditionally, so a canvas of six screens holds six real documents from
load, on screen or not, focused or not. Only the three kinds whose body is a
real document stand down — screen, site, canvas, plus a live Google Doc.
Markdown, images and text are left alone: they cost little, the browser
already manages decoded images, and tearing them down on every pan would
trade a memory problem for a flicker one.

Measured rather than argued, the way this bug was found both times. Prod on
the canvas that froze: 10 iframes settled, still 10 after the tab is hidden
for 13s — nothing released. Local with this change: the live document goes,
one item-standby takes its place, and the heap drops 30%.

What this does NOT claim: headless never reproduced the gigabytes, so the
mechanism is fixed and measured while the freeze itself is unconfirmed.

### The queue can fail: a finding nobody answers reddens a commit

`7b5f35b`

Phase 3 of the agents-you-can-trust note (#197), and the item it calls its
highest-value one. The cheap tier already worked — nine personas, each
measuring a named number, each writing findings with an accepted/rejected
column that IS a handoff protocol. What failed on 6 Sep was that the column
was ignorable, so it was decorative: 26 findings sat unanswered across six
nights while the number one of them described grew a hundred kilobytes.

ANSWER_DAYS is 3, chosen against that failure — the pile sat for six nights,
so a bound the failure would have passed is not a bound. It lives beside the
parser in reviews.mjs, and the report template and the index both interpolate
it, so the number a page promises is the number the guard enforces.

A bound, not a ratchet — the one place this differs from the bundle. Only
possible because the queue had been drained to zero hours earlier; the next
time findings pile up this test could only be added at whatever the pile
happened to be. A guard is cheapest to install at the moment the thing it
guards is already true.

The mutation proof found a hole while proving it. Back-dating a real finding
to `unanswered — the metric was retired` PASSED: matching `unanswered`
exactly meant any trailing word made a plainly-open row invisible to both the
index and the guard. An exact match on the OPEN state fails open. It now asks
whether somebody DECIDED — the cell begins `accepted` or `rejected` — so an
empty cell, a typo, or a qualified `unanswered` all stay in the queue. A
guard against neglect has to fail closed, because the failure it guards
against is nobody looking. Reclassifies nothing today: all 26 findings on
file begin with one of the two words.

reviews.mjs grew exports and a main() guard rather than a second parser, so
the guard and the index cannot disagree about what unanswered means.
