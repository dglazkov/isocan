# 7 October 2026 — The judge in the tab, measured, and stopped by its own rule

## Where the model lives

Before phase 0 started, Dion decided two things:

- **The licence.** The community LiteRT bundle of EmbeddingGemma 2 is
  ungated and its card says Apache-2.0, which is accepted for local use.
- **Where the model lives.** On the person's own machine, in
  `~/.isocan/models/` beside `keys.json`, put there by a new verb, `isocan
  model fetch embeddinggemma-2-text-270m`. It downloads 164.6 MB from one URL,
  checks it against a pinned SHA-256, and refuses anything else. The local
  daemon serves the model at `GET /models/<name>`, to its own pages only. A
  hosted home answers 404.

It was a verb rather than a script because an agent's hands are the CLI.
Later in the day he asked for the features behind an experiment. isocan
already has the mechanism, the Experiments list Stickers and Voice live in, so
the design uses it.

## local-judge phase 0

Built: the verb, the route, a `local` Answerer, and a Worker running MediaPipe
Decision Maker 1.1.0. Also a lab page, its own Vite build so the app's entry
chunk could not move (it did not: 703,834 bytes before and after), and
`scripts/local-judge-measure.mjs`, which drives the lab in Chrome over CDP with
outbound network blocked.

**What it found on an M3 Max**
([the page](../research/2026-10-07-embeddinggemma-in-the-browser.md)):

- **Fast at the median, slow in streaks.** The median answer is 33–35 ms on
  WebGPU up to 128 tokens. But answers come in streaks of 170–220 ms, so warm
  p95 is 170–200 ms in most runs, and 580–810 ms at 512 tokens. The streaks
  move between rows from run to run and survive a headed window, so they are
  neither the option count nor headless rendering. Their cause is not
  established.
- **MediaPipe phones home.** Its bundle POSTs metrics to
  `odml.pa.googleapis.com`. A `fetch` guard in the Worker caught it first. The
  claim is now enforced by the browser: a `connect-src 'self'` policy in the
  lab page and on the Worker script's own response. With the guard off, Chrome
  blocked the request before it existed. Offline, every request went to the
  daemon, and none carried the state text.
- **The CPU path is broken as shipped and slow when fixed.** MediaPipe 1.1.0's
  CPU delegate throws on every evaluation, so the Worker wraps it, on CPU
  only. It then answers in 0.8–3 s, about 25 times the GPU.
- **The model costs memory and install size.** It adds 1.2–1.7 GB of resident
  memory, and its wasm adds about 18 MB to every `#release` install.

**Phase 0's rule says the project stops** if desktop warm p95 is over 100 ms,
and it is. Phase 0 is PART-DONE and phase 1 waits. What would change it is
explaining the streaks (a timed warm-up, MediaPipe's nightly, the adapter's
power preference and thermal state are all untried), or Dion deciding the bar
should be the median plus a miss rate rather than one answer's p95.

## Verifying it found three things

- **A test cleanup without retries.** Two scratch-directory removals in the
  new tests had none; `test/teardown.test.ts` caught them.
- **Privacy guarded by a patch, not the browser.** A guard on `fetch` alone
  left MediaPipe's `XMLHttpRequest` paths open. That is why the policy above
  exists.
- **A `--headed` flag that did nothing.** It appended `--headless=false`
  after the shared launcher had already passed `--headless=new`. The
  launcher now takes `headless: false`.

## The phone

A phone cannot reach a laptop's loopback route, and WebGPU needs a secure
context. So the lab also takes a model file a person chooses (`?file=1`), runs
any number of answers per row (`?n=`), and shows its progress. The phone walk
runs it from dev.isocan.io:
[`docs/verify/2026-10-07-local-judge-on-a-phone.md`](../verify/2026-10-07-local-judge-on-a-phone.md).
Tapping *Measure on GPU* with `?n=10` was driven end to end before it landed.
