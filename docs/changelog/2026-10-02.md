# 2 October 2026 — Test shards carry equal work

The promotion investigation found the same slow shard in ten successful
releases: shard 4's median test step was 8m56s, against 4m41s–4m55s for the
other three. In run `36963426667`, 25% of the files carried 41% of the summed
file duration. The gate already had four runners; their work was unequal.

Vitest now partitions its discovered files using one committed duration
snapshot and schedules longer files first within each shard. The snapshot
is an estimate, never a test inventory: new files get a default cost, deleted
files do not reappear, and every discovered specification belongs to exactly
one shard. The same snapshot on every runner prevents cache drift from making
different partitions. Local unsharded ordering and worker limits are unchanged.

Each run records its revision, dirty state, runtime, workers, shard and file
durations. Both CI workflows keep the profiles as artifacts, including failed
runs. An explicit refresh command accepts one complete successful CI run and
rejects missing shards, mixed attempts and filtered or dirty measurements.
`timings --ci` now separates queue and elapsed execution instead of adding
parallel jobs and calling their sum wall clock.

Once all shards and checks pass, `green` advances before the publication
toolchain is installed. CLI publication installs Node and dependencies without
Java or the emulator, and skips `prepare` because the release builder already
builds the web app. The full anti-skip gate and non-fast-forward protection
remain. A faster `green` step is deployment eligibility, not deployment
completion.

The checkout's local human-verification roadmap commit was integrated with
current main first. Both the roadmap queue and incoming Loop work survive;
four newer verification walks gained the front matter the queue reads.

The first local validation passed 7,441 fast tests and 7,964 deep tests,
typechecking and the web build. The deep run took 441.5 seconds; local
unsharded speed was not changed by this work. Firestore's emulator is absent
on this machine, so its required coverage remains CI's. An independent check
of the configured sequencer assigned all 766 discovered specifications once,
with 928.687 seconds of estimated work on each of the four shards.

The first production CI run, [37050069871](https://github.com/dglazkov/isocan/actions/runs/37050069871),
passed all four shards, checks and publication. Against the immediately
preceding successful release, the slowest test step fell from 551 to 378
seconds (31%), and first job start to `green` from 706 to 475 seconds (33%):
3m51s less waiting, excluding the queue. The four test steps took 378, 356,
291 and 298 seconds. All 766 files appeared exactly once in the profiles.
This is one comparison, not a new median; the remaining shard spread is a
reason to keep measuring. The merged tree also passed a second local deep
run in 385.49 seconds, typechecking, lint and the build.

Those first CI artifacts exposed a telemetry gap: Vitest leaves its default
worker limit out of the resolved config. The reporter now records Vitest 4's
default when no explicit limit is set, and refresh refuses profiles without
a worker limit. This changes the measurement, not the pool size.

## The fixture is not the behavior under test

The next pass removes repeated setup from the two expensive files. The voice
harness used to start a daemon and claim a CLI identity for all 102 cases,
including grammar, keys, file brokers, memory brokers and the ACP wire mapper.
Those 37 cases now keep only their isolated scratch directory. Integration
groups explicitly request a fresh daemon; ordinary fixture claims use the
same `claimSessionIdentity` function and machine badge as the CLI. The eight
enrollment, rename and restart cases retain the CLI's full directory handshake.
A new regression test proves that the source CLI and voice server resume the
API-created claim as the same actor. No mutable home or daemon is shared.

The canvas-board cases inspect three scenarios: recent history, a successful
CI reading and an unavailable CI reading. They previously spawned nine board
processes, including three complete runs of the persona instruments. Each
scenario now renders once, lazily, retaining its HTML and stdout for all its
assertions. The real board script, real graders and failing `gh` shim still
run; the full instrument collection runs twice instead of three times.

With one Vitest worker, the two-file baseline passed 139 tests in 183.63s.
Two optimized runs passed all 139 original test names plus the new parity
check, in 131.51s and 115.29s. Voice fell from 94.81s to 47.23s and 40.12s;
canvas-board from 86.93s to 80.47s and 72.64s. Individual grader cost varied,
so these are measured runs, not a promised percentage for the whole gate.
The fixed reduction is 94 redundant fixture CLI claims and six board starts
per run; the new parity assertion adds one deliberate CLI invocation. Neither
test selection, worker limits nor timeouts changed.

## Build the CLI once for the integration run

The next repeated cost was loading and transpiling the CLI's source graph in
every child process. Vitest now calls the release builder once before its
workers start, and the shared CLI test launcher runs that fresh bundle. Each
run owns a unique directory under `.isocan`, separate from both other runs
and the release-layout tests' `dist`. A failed build fails the run; teardown
removes the directory. The real manifest still locates the checkout and
chooses the launcher for daemon children. Test homes, badges, daemons and
command processes remain isolated as before.

Source execution still has jobs of its own. Watch mode uses it so edits take
effect on every rerun. The agent-help suite keeps exercising the workspace
and Markdown loaders, and a new parity check compares the source and bundle
for version, the full guide and module registration. The voice fixture's
identity parity check explicitly keeps the source CLI. In `pass`, the two
identity-race cases use source whenever their IPC hook is installed: a hook
patching a source module would miss the bundled instance and could otherwise
stop testing the regression. Their assertions and schedules are unchanged.
Its output collection now uses the shared UTF-8 and exit-status handling.

On the same source revision, a one-worker baseline of `rc`, `pass` and `share`
passed 64 tests in 161.02s. The first bundled run passed those exact 64 names
in 96.73s: `rc` 65.59 → 39.83s, `pass` 56.66 → 40.31s, `share` 36.50 → 14.06s.
A repeat passed the same 64 cases in 96.07s, a 40% reduction across the three
files. That is a focused measurement, not a claim about whole-gate elapsed
time. The incoming copy-edit and voice-door changes were incorporated only
after this comparison, before the full validation run.

The next incoming keys phase exposed a test-isolation gap during that gate:
an empty keys directory did not suppress environment keys, which the new
resolver correctly prefers. Two voice-model "no key" cases inherited a
Gemini key and reached their provider stubs. Shared test setup now clears the
model-key environment settings too; tests still supply their own synthetic
overrides after setup. Production key resolution is unchanged.

The strict CI comparison then confirmed a whole-gate gain. Against the
preceding run on the same application code, the slowest test step fell from
379s to 222s, and first job start to `green` from 468s to 318s (32%). All 780
existing test files remained, plus two new guards. Runs
[`37078156780`](https://github.com/dglazkov/isocan/actions/runs/37078156780) and
[`37078908337`](https://github.com/dglazkov/isocan/actions/runs/37078908337)
both passed on their first attempt. That comparison excludes initial queue
time: the optimized run still waited 315s before verification could start.

## Let verification start while an earlier release finishes

That remaining queue came from a workflow-wide concurrency group protecting
two ref writes. It also serialized every test and setup step across commits.
The group now belongs only to `publish`, after that commit's four strict
suite shards and other checks pass. Verification can overlap across commits;
ready publishers queue without canceling a writer. The group keeps its old
name so a run of the previous workflow still excludes the new publisher
during rollout. GitHub runner capacity remains a separate limit.

Moving the lock alone would let a slow older suite publish after a newer one.
The generated release's first parent is the prior release, so Git would
accept that rollback as a fast-forward. `scripts/release-order.sh` now
refreshes the remote refs under the lock and compares their source ancestry.
Superseded CLI builds skip publication and its toolchain setup. An
already-green commit can retry a failed CLI publication; a newer untested
main does not hold up the latest passing source. Divergence, a wrong checkout
or a failed remote read is an error, not a silent skip. Publication runs only
for `main`, including manual workflow dispatches.

Real temporary Git repositories prove first-release setup, ref refresh,
out-of-order completion, retries, generated-tree rollback and failure cases.
Workflow guards require the complete gate, restrict the lock to publication,
and hold both ref writes and skipped toolchain steps to the ordering result.
This removes the workflow-imposed verification queue; it does not promise a
shorter suite or an unlimited pool of runners.

## Copy edit, phases 0–4: words as data

Copy edit (#377) began with research. A screen's words are a **copy deck**:
strings with a role, an address and a budget. Once the words are data, every
later step is an edit to words only, and markup outside text stays
byte-identical, which a test checks in every phase.

- **Phase 0** fixed two bugs the research found. One is a content edit that
  rewrote structure.
- **Phase 0.5** added `/api/text`, so the browser can reach a text model. It
  stays PART-DONE until isocan.io has a key.
- **Phase 1** is `isocan words`.
- **Phase 2** is *Vary the copy…* and `words vary`: N voices from one
  generation call, judged by one validator, so a model's answer and an agent's
  `--from` file are held to the same rules.
- **Phase 3** is *Compare the copy…* and `words mix`.
  - A mix is `convergeOps`'s shape with a spliced file in place of the
    winner's, so one undo restores the words and brings back the voices.
  - The web and the CLI land the same blob hash for the same picks.
- **Phase 4** marks strings that do not fit.
  - The compare's frames are sandboxed, so each measures itself and posts
    line boxes up; core judges.
  - A `## Voice` section in DESIGN.md reaches the prompt.
  - `words lint` reuses `SLOP_RULES` rather than inventing a list.

## Model keys, phases 0–4: one place, and only for you

A survey of where keys lived found one hole first. The voice harness's
loopback door had no Origin or Host check, and phase 0 closed it.

Keys now live in `~/.isocan/keys.json` (0600), behind `isocan keys` and
*Model keys…*, and are read on every call.

**Phase 3 decided whose keys pay.** A stored key pays only for the machine's
person, through joins. A collaborator is refused by name until sharing is
turned on.

**Phase 4 changed in verification.** The builder handed stored keys to every
agent the rc summons. That silently moves Claude Code, Codex and Gemini from a
person's login to per-call billing, so it went back as opt-in (`keys agents
on`). The talk module now asks the daemon for a one-use voice token, and the
browser holds no key. The first run against Google's real endpoint is still
owed.

Two of the commits carry a process lesson:

- `ccb593f5` shipped only its new files, because `git pull --autostash`
  returned the staged modifications unstaged. The rule now is to pull first,
  then stage.
- `625fb9fa` swept in another builder's half-written script, because it staged
  a filtered `git status` while that builder was live. The rule now is to stage
  an explicit list.

## The inline text editor stops jumping

A single click in *Edit text* opened the properties strip above the frame,
which pushed the words down. The second click of a double-click then landed on
a different line.

The strip now keeps a one-line row whether or not anything is selected. That
was chosen over an overlay, which would cover the words being clicked, and
over a delay, which would only postpone the jump.

`wire-text-edit` now double-clicks plainly and checks between the clicks. The
row moved 55px with the old strip and 0 with the new.

## Wireframes: fidelity layers, and a pill that fits the lane

A wireframe screen now has four layers over its wires — System, Copy, Low-Fi,
High-Fi — switched non-destructively by keeping each tier's version pointer on
the item, so "back to the wires" is a pointer move and one undo. `isocan wire
layer` from the terminal; on the canvas, a tier pill under the screen.

The pill went through three shapes in one day, and the second is the lesson:
a five-pill checkbox bar under the screen was in the right lane but the lane
is counter-scaled, so zoomed out it outgrew the screen and lay across *Full
screen* and the size pill. What shipped is one pill the size of the size pill,
`◧ High-Fi ▾`, and a popover with the checkboxes and a row that says what it
does — *Apply to all 11 screens in “Showcase”* — where "Sync flow" had said
nothing. Under 300 on-screen pixels the pill waits for a zoom with room.

Two misses on the way, both the kind the house rules name: the pane commit
(`1e860955`) was pushed after running one of the two tests that read the
pane's HTML, and `jetski-tie.test.ts` reddened main until `86758fdd`; and the
popover's first shadow was a literal colour, caught by `tokens.test.ts` in the
deep lane, not the fast one.

## The practice: the build loop measured

The way isocan is built had nine instruments, each sound and none read
together. Three sweeps audited them, and
[`docs/projects/practice/`](../projects/practice/design.md) holds the audit,
the plan, and evals of both the product and the build loop.

Some of what the audit found:

- Three records disagree about the same projects.
- Fourteen open issues are named nowhere.
- 14 of 15 verify walks are owed.
- Grades have read one unchanging page for 34 nights.
- Main's release went red 4 times in 40.

Phase 0 makes the audit re-run itself. `practice.yml` writes a page each night
with every number beside yesterday's, and a morning lap fixes the worst row.
The first page had 22 of 29 rows leaking.
