# 2 October 2026 — Test shards carry equal work

The promotion investigation found the same slow shard in ten successful
releases: shard 4's median test step was 8m56s, against 4m41s–4m55s for the
other three. In run `36963426667`, 25% of the files carried 41% of the summed
file duration. The gate already had four runners; their work was unequal.

Vitest now partitions its discovered files using one committed duration
snapshot and schedules longer files first within each shard. The snapshot
is an estimate, never a test inventory: new files get a default cost, deleted
files do not reappear, and every discovered specification belongs to exactly
one shard. The same snapshot on every runner prevents cache drift from making
different partitions. Local unsharded ordering and worker limits are unchanged.

Each run records its revision, dirty state, runtime, workers, shard and file
durations. Both CI workflows keep the profiles as artifacts, including failed
runs. An explicit refresh command accepts one complete successful CI run and
rejects missing shards, mixed attempts and filtered or dirty measurements.
`timings --ci` now separates queue and elapsed execution instead of adding
parallel jobs and calling their sum wall clock.

Once all shards and checks pass, `green` advances before the publication
toolchain is installed. CLI publication installs Node and dependencies without
Java or the emulator, and skips `prepare` because the release builder already
builds the web app. The full anti-skip gate and non-fast-forward protection
remain. A faster `green` step is deployment eligibility, not deployment
completion.

The checkout's local human-verification roadmap commit was integrated with
current main first. Both the roadmap queue and incoming Loop work survive;
four newer verification walks gained the front matter the queue reads.

The first local validation passed 7,441 fast tests and 7,964 deep tests,
typechecking and the web build. The deep run took 441.5 seconds; local
unsharded speed was not changed by this work. Firestore's emulator is absent
on this machine, so its required coverage remains CI's. An independent check
of the configured sequencer assigned all 766 discovered specifications once,
with 928.687 seconds of estimated work on each of the four shards.

The first production CI run, [37050069871](https://github.com/dglazkov/isocan/actions/runs/37050069871),
passed all four shards, checks and publication. Against the immediately
preceding successful release, the slowest test step fell from 551 to 378
seconds (31%), and first job start to `green` from 706 to 475 seconds (33%):
3m51s less waiting, excluding the queue. The four test steps took 378, 356,
291 and 298 seconds. All 766 files appeared exactly once in the profiles.
This is one comparison, not a new median; the remaining shard spread is a
reason to keep measuring. The merged tree also passed a second local deep
run in 385.49 seconds, typechecking, lint and the build.

Those first CI artifacts exposed a telemetry gap: Vitest leaves its default
worker limit out of the resolved config. The reporter now records Vitest 4's
default when no explicit limit is set, and refresh refuses profiles without
a worker limit. This changes the measurement, not the pool size.

## The fixture is not the behavior under test

The next pass removes repeated setup from the two expensive files. The voice
harness used to start a daemon and claim a CLI identity for all 102 cases,
including grammar, keys, file brokers, memory brokers and the ACP wire mapper.
Those 37 cases now keep only their isolated scratch directory. Integration
groups explicitly request a fresh daemon; ordinary fixture claims use the
same `claimSessionIdentity` function and machine badge as the CLI. The eight
enrollment, rename and restart cases retain the CLI's full directory handshake.
A new regression test proves that the source CLI and voice server resume the
API-created claim as the same actor. No mutable home or daemon is shared.

The canvas-board cases inspect three scenarios: recent history, a successful
CI reading and an unavailable CI reading. They previously spawned nine board
processes, including three complete runs of the persona instruments. Each
scenario now renders once, lazily, retaining its HTML and stdout for all its
assertions. The real board script, real graders and failing `gh` shim still
run; the full instrument collection runs twice instead of three times.

With one Vitest worker, the two-file baseline passed 139 tests in 183.63s.
Two optimized runs passed all 139 original test names plus the new parity
check, in 131.51s and 115.29s. Voice fell from 94.81s to 47.23s and 40.12s;
canvas-board from 86.93s to 80.47s and 72.64s. Individual grader cost varied,
so these are measured runs, not a promised percentage for the whole gate.
The fixed reduction is 94 redundant fixture CLI claims and six board starts
per run; the new parity assertion adds one deliberate CLI invocation. Neither
test selection, worker limits nor timeouts changed.
