## Browsing for the directory, and two words that were pointing at the wrong thing

**The picker.** Paste-a-path unlocked attaching; it only helped somebody who
already had the path in their head. The Attach row grew a `…` beside it: one
level of directories at a time, from `$HOME` down, and picking fills the
field rather than binding — so the browsed route and the typed route end in
exactly the same place, and you can see what you chose before it becomes a
fact.

It is deliberately thin, because it is deliberately wide: `readTree` lists
inside a directory somebody bound, and `pickList` lists directories nobody
has bound to anything — the first enumeration surface this daemon has ever
had. So it names DIRECTORIES only, one level, never files, never bytes,
never a recursive walk that would turn a picker into a map of a disk. The
jail is `readBound`'s, held the same way: resolved paths (so `..` cannot
walk out by spelling), `$HOME` as a ceiling with `up: null` at the top so the
app hides the step rather than offering one that would be refused, and
symlinks not followed at all. Shaken with the tree's own discipline —
`/etc`, `~/../../etc`, `/`, a symlink pointing out, a file, a missing path,
and the system temp directory every other fixture in that file lives in,
which is outside and is correctly refused. Directories already bound say so
rather than being offered and refused a click later.

Two things the live run caught. The path readout clipped its head with the
usual `direction: rtl` trick, which reorders the neutral characters at a
string's edges — `/Users/dalmaer` rendered as `Users/dalmaer/`. It is
clipped in JS now. And a picker inside a height-clamped section is a
three-row keyhole, so browsing asks the section for room and gives it back on
close, leaving the height somebody dragged untouched.

## The staged item is what you are pointing at

The Chat's composer attaches the selection as chips — "the chips ARE the
selection", one answer to what a message is about. But staging an item did
not select it, so whether the thing you were looking at got attached depended
on how you arrived: clicking it on the canvas and pressing Enter attached it;
opening it from the files pane or with `isocan open --workbench` did not.
Same screen, two behaviours. Staging now selects, which keeps the one answer
and makes it the true one.

And the composer's placeholder stopped naming the wrong object. "Message the
canvas — agents hear this" reads as addressing a surface; you are addressing
the people and the agents on it. It says "Message everyone — agents
included", which is also what the panel's header and its empty state say.

## Content origin, stage 3: everything that renders, nothing that talks

The origin split stopped INBOUND theft — a page on the content origin has no
cookie, no badge and no API to call, which is what made `allow-same-origin`
safe to grant there. It did nothing about OUTBOUND: a scripted page can still
compute something and send it somewhere. That is what this stage closes, and
the policy was **measured rather than guessed**, because one too tight
silently breaks screens agents write.

76 HTML blobs across this machine's canvases, 15.5MB of real agent-written
screens: 48 run an inline `<script>`; 28 load a remote stylesheet, and
**every single one of them is Google Fonts**; 14 use `localStorage`; and
**zero** use a remote script, `fetch`, XHR, WebSocket, an `<iframe>`, a
`<form>`, a remote image, or `eval`. The only hosts named anywhere are
`fonts.googleapis.com` and `fonts.gstatic.com` — `www.w3.org` appears 27
times and is an SVG namespace, not a request. These pages render and they
remember, and they do not phone anywhere.

So: `default-src 'none'`, inline script and style allowed because that is
what these screens are made of, Google Fonts as the one remote allowance,
images and media confined to `data:`/`blob:` (an image URL is exfiltration
with extra steps), and `connect-src 'none'` — the main channel, free to
close today by the measurement. **No `sandbox` directive, ever**: it would
intersect with the iframe's and re-impose the opaque origin, taking back the
storage stage 2 exists to grant.

Verified live on the content origin: the visit counter still incremented
(inline script and storage intact), a Google Font stylesheet loaded, and both
a `fetch` and an image beacon to an external host were blocked. One hole is
recorded rather than papered over — a page can still navigate ITSELF to an
attacker URL, and no portable CSP directive stops that.

## The editor stops looking like a default install

CodeMirror shipped stock — its own greys, its own blue, its own idea of a
gutter — and read as a component sitting *in* the app rather than part of it,
which was plain beside the stage's own panes.

Split by where each half belongs. **Chrome** is CSS in `styles.css`, next to
every other surface and reading the same tokens, so it follows the theme for
free and the guards that watch that stylesheet watch it too: the editor takes
`--card`, the gutter recedes to the chip grey this app uses for "a rail, not
content" with the same hairline, the active line wears the accent wash that
means "you are here" everywhere else, and the caret, selection, matching
brackets, search matches, fold placeholders and the autocomplete list all come
onto the app's surfaces. Scoped under `.stage-editor-cm` so a bare `.cm-`
rule can never reach into another editor later — with a guard that says so.

**Syntax** is `lib/cmtheme.ts`, because a mapping from Lezer's grammar tags
to colour is not something a stylesheet can express. Its colours are
`var(--syn-*)`, never literals, so light and dark are one declaration apiece
in the place every other colour is decided — and deliberately NOT the
semantic tokens: `--good` for a string and `--danger` for a tag would read
right and mean wrong, since those say "this went well" and "this is a
problem" everywhere else, and a tag name is neither. `--danger` appears once,
on `invalid`, which genuinely is one. Nine hues, each chosen against the
ground it actually lands on rather than dimmed from the other theme.

Measured in both, on the real editor: light 5.22–15.18, dark 6.41–13.74
against `--card`. Every colour above AA, most above AAA, and every one of
them resolved from the app's own tokens rather than falling through to
CodeMirror's defaults.

## The parse5 upgrade: entities and repeats stop being refusals

In-place editing shipped with a rule that could not corrupt a file and could
not edit two things people do. Text the source spells with an entity — a
headline reading `Rest & Play` is `Rest &amp; Play` on disk, so a search for
the DOM's text found nothing, which is what the very first in-place edit
anybody attempted hit. And text that appears twice — two buttons saying
`Submit` made either one unpatchable, because a string search cannot tell
which was clicked.

Both are ordinary edits now, on a correspondence the frame turns out to
guarantee: **parse5 implements the same parsing algorithm the browser does,
and the edit frame's scripts are DEAD, so nothing mutates the DOM out from
under that equivalence.** The nth text node in the frame IS the nth text node
parse5 sees. An edit names its node by ORDINAL, `sourceCodeLocation` gives
the byte range, and the splice is exact — entities are irrelevant because
nothing is searched for, repeats are unambiguous because a position is not a
string, and what a person types goes back in ENCODED so text can never become
markup. `from` survives as a check: if the node no longer says what it said,
the file moved under the edit and the save is refused.

Proven on a real artifact, v1 → v3, both cases in one file: `<h1>Rest &amp;
Play</h1>` → `<h1>Work &amp; Play</h1>`, and
`<button>Submit</button><button>Submit</button>` →
`<button>Submit</button><button>Send</button>` — second only.

parse5 rides in its own 164KB lazy chunk (48KB gzip), imported inside the
save path, so it is fetched only by somebody who actually saved an edit.
Whitespace text nodes count — in this walk and in the browser's — and are
pinned by a test, because miscounting one would point every later edit a node
off. `<script>` and `<style>` are refused, since their content is not
entity-decoded and encoding it back in would corrupt them.

Driving it turned up one real bug: an engine sometimes REPLACES the text node
rather than mutating it, and the ordinal lookup then had nothing to point at.
The element is the stable thing, so a detached node now falls back to its
parent's first text child.

## The files pane names its directory

Reported as a bug and it was not one: a canvas holding ten screens showed two
files. The pane was telling the truth — the bound repo really does contain
only `index.html` and `README.md`, and the other nine screens are canvas
items an agent made and never wrote to disk.

The failure was the WORD. This section said "Files"; so does the canvas's own
Files panel, which lists everything ON THE CANVAS. Two panels, one label, two
different sets — and the mismatch is silent, so the honest pane looks broken.
Exactly the Chat/Main problem from yesterday, in the other corner of the same
screen.

So it names what it is showing: the bound directory's own name, with the full
path on hover and a quiet "on disk" to draw the line the word could not.
Unbound, there is nothing to name and the plain word is right — the bind
field underneath explains the rest.

Worth recording, because it is the gap the report actually exposed: `＋`
carries a file from the disk onto the canvas, and nothing carries an item the
other way. Nine of those screens exist only as canvas items.
