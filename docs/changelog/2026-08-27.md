## Browsing for the directory, and two words that were pointing at the wrong thing

**The picker.** Paste-a-path unlocked attaching; it only helped somebody who
already had the path in their head. The Attach row grew a `…` beside it: one
level of directories at a time, from `$HOME` down, and picking fills the
field rather than binding — so the browsed route and the typed route end in
exactly the same place, and you can see what you chose before it becomes a
fact.

It is deliberately thin, because it is deliberately wide: `readTree` lists
inside a directory somebody bound, and `pickList` lists directories nobody
has bound to anything — the first enumeration surface this daemon has ever
had. So it names DIRECTORIES only, one level, never files, never bytes,
never a recursive walk that would turn a picker into a map of a disk. The
jail is `readBound`'s, held the same way: resolved paths (so `..` cannot
walk out by spelling), `$HOME` as a ceiling with `up: null` at the top so the
app hides the step rather than offering one that would be refused, and
symlinks not followed at all. Shaken with the tree's own discipline —
`/etc`, `~/../../etc`, `/`, a symlink pointing out, a file, a missing path,
and the system temp directory every other fixture in that file lives in,
which is outside and is correctly refused. Directories already bound say so
rather than being offered and refused a click later.

Two things the live run caught. The path readout clipped its head with the
usual `direction: rtl` trick, which reorders the neutral characters at a
string's edges — `/Users/dalmaer` rendered as `Users/dalmaer/`. It is
clipped in JS now. And a picker inside a height-clamped section is a
three-row keyhole, so browsing asks the section for room and gives it back on
close, leaving the height somebody dragged untouched.

## Content origin, stage 3: everything that renders, nothing that talks

The origin split stopped INBOUND theft — a page on the content origin has no
cookie, no badge and no API to call, which is what made `allow-same-origin`
safe to grant there. It did nothing about OUTBOUND: a scripted page can still
compute something and send it somewhere. That is what this stage closes, and
the policy was **measured rather than guessed**, because one too tight
silently breaks screens agents write.

76 HTML blobs across this machine's canvases, 15.5MB of real agent-written
screens: 48 run an inline `<script>`; 28 load a remote stylesheet, and
**every single one of them is Google Fonts**; 14 use `localStorage`; and
**zero** use a remote script, `fetch`, XHR, WebSocket, an `<iframe>`, a
`<form>`, a remote image, or `eval`. The only hosts named anywhere are
`fonts.googleapis.com` and `fonts.gstatic.com` — `www.w3.org` appears 27
times and is an SVG namespace, not a request. These pages render and they
remember, and they do not phone anywhere.

So: `default-src 'none'`, inline script and style allowed because that is
what these screens are made of, Google Fonts as the one remote allowance,
images and media confined to `data:`/`blob:` (an image URL is exfiltration
with extra steps), and `connect-src 'none'` — the main channel, free to
close today by the measurement. **No `sandbox` directive, ever**: it would
intersect with the iframe's and re-impose the opaque origin, taking back the
storage stage 2 exists to grant.

Verified live on the content origin: the visit counter still incremented
(inline script and storage intact), a Google Font stylesheet loaded, and both
a `fetch` and an image beacon to an external host were blocked. One hole is
recorded rather than papered over — a page can still navigate ITSELF to an
attacker URL, and no portable CSP directive stops that.

## The editor stops looking like a default install

CodeMirror shipped stock — its own greys, its own blue, its own idea of a
gutter — and read as a component sitting *in* the app rather than part of it,
which was plain beside the stage's own panes.

Split by where each half belongs. **Chrome** is CSS in `styles.css`, next to
every other surface and reading the same tokens, so it follows the theme for
free and the guards that watch that stylesheet watch it too: the editor takes
`--card`, the gutter recedes to the chip grey this app uses for "a rail, not
content" with the same hairline, the active line wears the accent wash that
means "you are here" everywhere else, and the caret, selection, matching
brackets, search matches, fold placeholders and the autocomplete list all come
onto the app's surfaces. Scoped under `.stage-editor-cm` so a bare `.cm-`
rule can never reach into another editor later — with a guard that says so.

**Syntax** is `lib/cmtheme.ts`, because a mapping from Lezer's grammar tags
to colour is not something a stylesheet can express. Its colours are
`var(--syn-*)`, never literals, so light and dark are one declaration apiece
in the place every other colour is decided — and deliberately NOT the
semantic tokens: `--good` for a string and `--danger` for a tag would read
right and mean wrong, since those say "this went well" and "this is a
problem" everywhere else, and a tag name is neither. `--danger` appears once,
on `invalid`, which genuinely is one. Nine hues, each chosen against the
ground it actually lands on rather than dimmed from the other theme.

Measured in both, on the real editor: light 5.22–15.18, dark 6.41–13.74
against `--card`. Every colour above AA, most above AAA, and every one of
them resolved from the app's own tokens rather than falling through to
CodeMirror's defaults.

## The parse5 upgrade: entities and repeats stop being refusals

In-place editing shipped with a rule that could not corrupt a file and could
not edit two things people do. Text the source spells with an entity — a
headline reading `Rest & Play` is `Rest &amp; Play` on disk, so a search for
the DOM's text found nothing, which is what the very first in-place edit
anybody attempted hit. And text that appears twice — two buttons saying
`Submit` made either one unpatchable, because a string search cannot tell
which was clicked.

Both are ordinary edits now, on a correspondence the frame turns out to
guarantee: **parse5 implements the same parsing algorithm the browser does,
and the edit frame's scripts are DEAD, so nothing mutates the DOM out from
under that equivalence.** The nth text node in the frame IS the nth text node
parse5 sees. An edit names its node by ORDINAL, `sourceCodeLocation` gives
the byte range, and the splice is exact — entities are irrelevant because
nothing is searched for, repeats are unambiguous because a position is not a
string, and what a person types goes back in ENCODED so text can never become
markup. `from` survives as a check: if the node no longer says what it said,
the file moved under the edit and the save is refused.

Proven on a real artifact, v1 → v3, both cases in one file: `<h1>Rest &amp;
Play</h1>` → `<h1>Work &amp; Play</h1>`, and
`<button>Submit</button><button>Submit</button>` →
`<button>Submit</button><button>Send</button>` — second only.

parse5 rides in its own 164KB lazy chunk (48KB gzip), imported inside the
save path, so it is fetched only by somebody who actually saved an edit.
Whitespace text nodes count — in this walk and in the browser's — and are
pinned by a test, because miscounting one would point every later edit a node
off. `<script>` and `<style>` are refused, since their content is not
entity-decoded and encoding it back in would corrupt them.

Driving it turned up one real bug: an engine sometimes REPLACES the text node
rather than mutating it, and the ordinal lookup then had nothing to point at.
The element is the stable thing, so a detached node now falls back to its
parent's first text child.

## Items backed by files: the design, and the half that writes

`＋` carries a file from the disk onto the canvas; nothing carried an item
back, so a screen an agent wrote lived on the canvas forever unless somebody
copied it out by hand. The ask is not sync — it is a CHOICE, per item, by
whoever made it: a view run up to answer "let me see" stays on the canvas; a
screen that is a new part of the system wants to be a file.

**Two facts, and keeping them apart is the design**
(`docs/projects/workbench/files-on-disk.md`). Where a file belongs is a
CANVAS fact — it replicates, it reaches a teammate who clones the repo, and
it rides as an item property (`file`), written by `item.update` like
`annotates` and `role` before it, so **zero new operations again**. Whether
it is written is a fact about ONE MACHINE, derived and never stored:
`written`, `drifted`, `absent`, or `unbound` — that last one keeping "you
have no checkout here" from reading as "somebody deleted your file".

**The write is the dangerous half**, and `tree.ts` opened with "Nothing here
writes." It gets the read jail's rules — resolved-path containment, no
dotfiles or secret shapes at any segment, no symlink anywhere on the way —
plus two this direction needs: parent directories only where every segment is
listable, and **drift refused rather than overwritten**.

That last one has a nice answer that needs no bookkeeping: **the version
stack already records everything the item has ever been.** A file whose hash
matches any version was written by this canvas — current, or an older one the
disk is behind — and updating it is safe. A file matching none of them is
somebody's work done outside the canvas, and the write refuses and says so.
No "last written" state, per-machine or otherwise.

Ten cases shaken, each failing without its rule: the escapes (`../`,
`a/../../`, absolute), the dotfiles (`.env`, `.git/config`, `src/.ssh/key`,
`id_rsa`), a symlinked directory on the way and a symlinked file as the
destination — both verified to leave the outside target untouched — writing
over a directory, and the empty path, which was refusing for the wrong reason
until a test said so.

## Items backed by files, finished

The visible half, and the round trip closes.

**A mark on the item.** Only backed items wear one — an untracked item is the
default and the common case, so silence is its signal. A small square beside
the kind icon: what this item IS, then where it LIVES. Solid when the file
matches, hollow when it has a place and has not been put there, `--warn`
coloured when the disk and the canvas disagree, and barely-there when this
machine has no directory at all. Drift is the state worth catching from
across a canvas, so it is the only one that takes a colour.

**A button on the stage**, offered only where there is a disk to write to —
`unbound` gets no button rather than a button that refuses. A drifted file
takes two presses: the first is refused by the daemon, the second says
`force`. Two presses rather than a confirm dialog keeps the decision in the
same place as the gesture. After a write the disk is asked again, so every
mark on the canvas stops saying what used to be true.

**Both verbs for agents**, which is where the user put the emphasis:
`isocan set <item> --file <path>` says where a screen belongs and
`isocan save <item>` takes it there — two steps on purpose, because the first
costs nothing and the second touches somebody's filesystem. The agent guide
gained a section on the judgment rather than just the syntax: most of what you
make should stay on the canvas, and a path in somebody's repo is theirs.

**And `＋` now says where the file it carried came from**, which is what
closes the loop — before, the canvas had no idea, so an added file could
never be put back.

Proven end to end on a real repo: a screen that existed only on the canvas
became `views/start.html`; a hand-edit outside the canvas was refused with
the file left untouched; `--force` took it; a `../../../tmp` path was refused
by name; the app's button wrote `views/question.html` and then correctly
turned into "Overwrite file" in warn colour once the file drifted. The demo
files and properties were removed afterwards — the repo and the canvas are
exactly as they were.

## The seam between the panes is a handle

Both panes open and no way to say how much of each — so the editor and the
preview split the stage evenly whether you were reading code or looking at a
page. The border between them drags now, the way the docked panel's edge
does, and for the same reason it is a strip rather than a line: a pointer
cannot be asked to find one pixel.

`PanelResizer` is reused whole — it was generalized the day the workbench
grew a draggable edge, and this is its third caller, so there is no second
kind of resizer for a second kind of edge. Double-click or Home puts the
split back to even, arrows nudge it, and the clamp lives in the OWNER as that
component's own doc insists: neither pane can be squeezed below 200px however
far the pointer travels.

**Stored as a FRACTION, not a width**, which is the one design call here. A
width is an answer to a question that keeps changing — the left panel is
draggable and the window resizes, so a width chosen at 1600px is most of the
stage at 900. One key for both covers, unlike which panes OPEN: Enter and W
genuinely differ about what you came to do, but how wide you like your editor
is a preference about proportion and setting it twice would be the annoyance.

Driving it caught a real bug in the first version: the handle read the stage's
width from a ref DURING RENDER, which is null on the first one — so it opened
believing the stage was 0 wide and the first drag slammed the editor straight
to its floor. It observes the width now, which also keeps it honest while the
left panel is dragged and the window resized.

## A favicon, and a tab that says where you are

**The mark is the product, not a letter.** The stylesheet opens by naming this
app's identity — a vellum ground with a dot grid carrying hairline cards — so
the icon is one card on a field of dots, which is what a canvas looks like
from far enough away. Drawn for SIXTEEN pixels, where a favicon actually
lives: two shapes, no text, no hairlines, and a card big enough to survive
being drawn four times smaller than the artboard. The dots become texture at
that size, which is the right thing for them to do. One SVG rather than a
pile of PNGs — sharp at every size, carries its own dark-mode rule, 1KB.

Checked by rendering it at 16/24/32/64/128 on both grounds rather than
trusting that an SVG is an SVG — which is how the first draft's bug turned
up: **an SVG is XML, and XML forbids a double hyphen inside a comment.** The
comment named the app's colour tokens the way the stylesheet does, so the
whole document failed to parse. It served correctly, decoded as nothing, and
rendered as a broken image. The file now says so, in the file.

**The tab says which canvas and which place.** It said "isocan" on every page
of every canvas, which is the least useful thing a tab can say to somebody
holding six of them — and a canvas, its workbench and a screen full-size are
three addresses you keep at once. Now: `Love Languages · isocan`,
`Love Languages · workbench · isocan`, `View · Start · Love Languages ·
isocan`, with the unread count still leading when there is one.

The specific part goes FIRST, which is the one place this departs from how it
was asked for ("isocan: $project canvas"): a tab strip gives each tab about a
dozen characters before it truncates, so a title opening with the product
name renders every tab identically — and the thing the title was added to fix
is exactly the thing that gets cut. The name still rides at the end, where it
reads fine in a bookmark or a history list.

## The hook that blanked a cold full-screen load

Wiring the tab title surfaced a bug I had shipped an hour earlier: the
backing lookup in `ArtifactStage` sat beside the value it feeds, which is
BELOW `if (!item) return`. React counts hooks per render, so that is fine on
every render you get by clicking around inside the app — the canvas is
already loaded — and breaks the moment somebody opens a full-screen item URL
COLD: the first render has no item and returns early with fewer hooks, the
snapshot lands, and the counts disagree. Error #310, and a white page.

Every hook is above the early returns now, and a guard reads the component
and fails if one is not — verified by moving one back and watching it fail.
