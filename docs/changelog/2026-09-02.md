Two threads. The morning finished the text tool — words that stayed where
they were typed, a composer that kept what it opened on apart from what was
being typed, hover previews on every control of the bar, sizes named as
sizes — and turned `/sprint` into a board. The afternoon chased a canvas

## A canvas that took a lifetime, and what versions actually cost

The repo-admin board (`prj_KCQQaoVSdv`) was slow to show its screens, and
every panel wore a badge like **×149**. The hypothesis was that render
time scales with the number of versions. It was checked rather than
believed, and the answer is in
[`docs/research/2026-09-02-version-scaling.md`](../research/2026-09-02-version-scaling.md):

- **The render is already O(current versions).** `ItemView` finds the
  current version and mounts one document; no path on a canvas load fetches
  an old version. Reproduced at 14 items × 150 versions on a scratch daemon:
  the snapshot arrives in 16 ms, each blob in ~70 ms, the page is drawn in
  well under a second.
- **What does scale with versions is the snapshot** — every version's
  metadata rides on every hello, every `GET /canvas`, and every CLI command
  (`canvasAndSnapshot`). On the real board that is 837 versions, ~220 KB of
  metadata against ~90 KB of content actually shown. On the scratch canvas,
  544 KB against 33 KB after pruning. Real, and not a lifetime.
- **And the storage.** 7.4 MB of panel HTML nobody would open twice,
  growing by the repo's commit rate because the board republishes on every
  commit. The design note called this silting and named a new item per run
  as the way it happens; a new version per run is the same silt, slower.
- **The one place the canvas ever paid for every version at once was the
  fan.** Press S on a 150-deep stack and it mounted 150 iframes and fetched
  150 blobs to compare the newest few.

So the slowness on isocan.io is somewhere the versions are not — the hosted
path (a Cloud Run instance replaying its Firestore tail on a cold start,
GCS blob reads per panel) — and it was not measured today because the
badge to measure it with is the person's, not this session's. Two things
observed on the way and left as findings rather than fixes: `isocan gc
--dry-run` took 4–24 s against BOTH a big remote canvas and a small local
one, so that wait is the engine's single-writer queue and not the log; and
the local file backing rewrites a pretty-printed 431 KB `canvas.json` on
every op, which is fine at fourteen ops a run and worth knowing.

## What was built: `item.pruneVersions`, on every surface

**One operation, not maintenance.** `item.pruneVersions { itemId, keep }`
keeps the newest `keep` versions by stack order and ALWAYS the current one,
whatever its age — pruning is about size and must never change what an
item shows. It is an op and not a field on `GcRequest` because a replica
folds the log: a stack shortened at the home outside the log would leave
every replica carrying versions the home has forgotten. In the log, it
replays. Like `trash.empty` it inverts to `null` — an undo that restores
versions whose bytes the collector may already have swept is worse than
one refused at the door — and every surface that offers it gates it.

The rule has one home: `pruneVersions`/`prunedVersions` in the reducer,
exported so the CLI, the API and the fan can say what a prune WOULD drop
from the function that will drop it (lessons.md #5). The bytes are the
collector's business as before — the old versions' blobs fall out of
`reachableHashes` once the `addVersion` entries that introduced them pass
the undo horizon, and `gc` sweeps them then. `gc.test.ts` holds that
sequence: inside the horizon nothing is swept, past it only the surviving
version's bytes remain.

- **CLI**: `isocan version prune <items…> --keep N --force` (`--all` for
  every item), refusing without `--force` with the count it would drop, and
  sending nothing for a stack already within the bound. `isocan gc
  --keep-versions N --force` prunes every stack first and then collects —
  one command that says "bound this canvas". The agent guide names both.
- **API**: `canvas.pruneVersions(itemId, keep)`, and the board generator
  calls it after every `edit` with `KEEP_VERSIONS = 14` — a fortnight of
  daily runs, enough to see a goal drift. The generator that makes the
  versions is the one that bounds them.
- **Web**: the version fan mounts live documents for its newest 24 cards
  and folds the rest to a label and a click (`FAN_LIVE`), and past 14 deep
  it offers "Keep only the latest 14…" with the trash panel's two-step
  confirm. `fanout.test.ts` holds the window and the offer's arithmetic.

Measured on the scratch canvas after `gc --keep-versions 5 --force
--keep-ops 0`: 2,100 versions → 70, snapshot 544 KB → 33 KB, 2,030 blobs
and 9.6 MB swept. The real board was NOT pruned — that is a person's call,
and the command is ready:

```
isocan --canvas prj_KCQQaoVSdv version prune --all --keep 14 --force
```

**Deliberately not built: a snapshot that omits old versions and loads them
lazily.** It would make the hello O(items) rather than O(versions), which
the numbers above say is a 220 KB problem today, and it would cost the
isomorphism — the web folds queued ops over its confirmed state through
the same reducer the daemon runs, and `setCurrentVersion` validates against
a stack the client would no longer hold. Pruning bounds the same cost
without a second shape of state. If a canvas ever wants a deep stack AND a
small snapshot, that is the day to design it.

## Worktrees, once more

A worktree under `.claude/worktrees/` has no `node_modules`, so every
`@isocan/*` import resolves up the tree to the MAIN checkout's packages —
the new op typechecked in core and was "not exported" from the CLI, the
API and the server, all of which were reading somebody else's core. The
fix is a worktree-local `node_modules` of symlinks: every entry of the
root's, and `@isocan/*` pointed back at this worktree's `packages/`.
Lessons.md #7 said "node_modules symlinked" and this is what it meant.
