# 13 October 2026 — Webview pan performance: pre-decoded WebP proxies and zero background OOPIFs

## Why trackpad wiggling lagged over HTML screens

Earlier performance investigations (`docs/research/2026-08-29-performance.md` and
`docs/research/2026-09-26-frame-budget.md`) benchmarked boards of 250 `text/markdown`
notes (`0` iframes), missing the cliff hit when panning quickly across `text/html`
webview cards (`<iframe sandbox="allow-scripts">`):

1. **Unbatched two-finger wheel deltas & missing `panning` flag (`CanvasViewport.tsx`).**
   Trackpad pinch (`ctrlKey` / `metaKey`) coalesced multiple trackpad ticks per display
   frame via `requestAnimationFrame`, whereas two-finger scroll called `ui.setViewport(...)`
   synchronously inside a `{ passive: false }` listener on every raw packet and never set
   `panning = true` — leaving pointer hit-testing active across cross-origin child frames
   under a stationary cursor while wiggling.
2. **Mid-swipe `<iframe>` instantiation (`onscreen.ts`).** Crossing the `800px` observer
   margin mounted brand-new subframes mid-gesture while holding each swept-past frame alive
   for `10_000ms`.
3. **Cross-origin child frame surface stalls in Chromium Viz.** Measuring a 24-webview cold
   board in headless Chrome (`1440×900 @ 2x`, `4×` CPU throttling) showed that even when
   main-thread JavaScript + style/paint dropped under `6 ms` per frame (`Stage 1`), 24 live
   `<iframe sandbox="allow-scripts">` surfaces (`RenderWidgetHostViewChildFrame`) stalled
   Chromium Viz surface synchronization for `200–600 ms` (`p90 = 100.0 ms`, `p99 = 200.0 ms`,
   `30` long frames). Toggling `display: none` only during pan (`Stage 2A`) shifted the same
   `620 ms` surface allocation stall onto gesture boundaries.

## What landed (`Stage 1 + Stage 2B`)

- **Input batching & pan fast-path (`CanvasViewport.tsx`, `uiStore.ts`, `onscreen.ts`, `styles.css`).**
  Coalesced two-finger wheel deltas into `requestAnimationFrame`, marked a `160 ms`-debounced
  `panning` state on wheel scroll and trackpad pinch (with no-op equality guard in `uiStore`),
  suppressed pointer hit-testing and multi-blur shadows on non-entered cards during camera
  motion, and held new `useOnScreen` mounts until camera panning settles (`watchPanSettled`).
- **Idle WebP snapshot proxy & inert `<iframe>` shedding (`htmlsnapshot.ts`, `ItemView.tsx`, `htmlsnapshot.test.ts`).**
  Added `useHtmlSnapshot`, which sanitizes HTML screen documents into self-contained XHTML
  `<svg><foreignObject>` trees, rasterizes them off-thread into GPU-predecoded `image/webp`
  object URLs (`MAX_CONCURRENT = 4`), renders `<img class="html-snapshot">` permanently beneath
  the live frame stack, and unmounts non-entered (`!actor && warm.length === 0`) `<iframe>`
  instances one animation frame after the bitmap paints (`proxyReady`). Entering any card
  (`Boolean(actor)`) immediately re-mounts the interactive live `<iframe>` on top with zero
  flash; multi-slide decks (`warm.length > 0`) keep their frame pool.
- **Measured result on the 24-webview trace (`4×` CPU throttling).** `visibleIframes` during
  browsing and panning dropped `24 → 0`, cutting `p90` **6× (`100.0 ms → 16.8 ms`)**, `p99`
  **4× (`200.0 ms → 50.0 ms`)**, long animation frames **~90% (`30 → 3`)**, and total render
  time **92% (`329–446 ms → 23.9–39.4 ms`)**.

## An edit that checks first: `isocan edit --if-version`

Keel's weekly "Loop across projects" canvas and its phase 50 pulse card could
only append a new card on every sync, because the public CLI had no
conditional edit. Core has had the act since 13 September: `item.edit`
replaces an item's content and patches its title and properties as one
undoable op, refused with `edit-conflict` unless the item still stands where
the writer read it. The design review and repair flows use it. Nothing on the
CLI reached it.

`isocan edit <item> <file> --if-version <versionId>` now does
(`packages/cli/src/conditional-edit.ts`):

- **One act.** `--title`, `--prop` and `--rm-prop` ride in the same op, and
  one undo takes content and metadata back together.
- **Stale is its own answer.** A moved version, or with `--if-meta` a title
  or property a person changed, exits 4 with nothing written and the item's
  current version id in the `--json` answer.
- **A retry is safe.** `--op-id op_…` is the op's own name. The engine
  already answered a repeated id with the entry it wrote (`alreadyWritten`,
  multiuser phase 10); the CLI now passes one through, so a retry reports
  `replayed` with the version that landed.
- **An older home refuses.** `item.edit` is a distinct op type for this
  reason: `unknown-op` becomes exit 5, and the verb never falls back to an
  unconditional write.

No server change and no deploy: isocan.io has applied the op since September.
The CLI reaches people through `#release`, which CI rebuilds from `main`.

Not built: publishing several cards as one all-or-nothing change, which keel
also asked about at lower priority.

Along the way, `main` was red on the undocumented-exports ceiling again (240
against 238): `sanitizeDocumentToSvg` and `useHtmlSnapshot` in
`packages/web/src/lib/htmlsnapshot.ts` arrived without comments in the webview
pan work. Both have one now.
