# Identity you can prove, and revocation that means something

**2026-08-24** · Phases 9, 10, 10.3, 10.5 · Dimitri Glazkov

The desk gets its teeth. Before today a canvas could stop *new* arrivals and
nothing else: turning off a link left everybody who had already walked in
exactly where they were. Now revoking a grant expels the people it let in —
down a chain of passes, several hops deep — while keeping the ones another
grant still covers. And identity stops being something you assert: prove you
read an inbox and a second browser can be the person your laptop already is.

## The sweep, and why order was the whole problem

"A pass-derived admission inherits the root of the badge that minted it" reads
like a lookup. It is not one: the minter's own root may be changing in the same
sweep. The first implementation read stale roots in whatever order the desk
handed badges back, and expelled Jordan's daemon a moment before Jordan's tab
re-rooted onto the grant that had invited her by name — the design's own named
failure, one hop down, decided by a list order. A badge now adopts its
minter's *outcome*, decided once, recursively. Cycles and dead middles stopped
needing cases and fell out of a wider question: not "rooted in the revoked
row" but **"whose root no longer stands"**.

Measured against a real daemon: a tab on the link, its daemon on a pass, an
agent on a pass from that — one revocation, three expelled, the creator
untouched. Then with an email grant in play: `{expelled: 1, rerooted: 1}`. The
stranger goes; the person invited by name stays. That is the sentence the
design has carried since it was written, as a measurement rather than a
promise.

## Borrow, never mint

isocan still has no accounts, no passwords and no user table, and today's work
was careful not to accidentally create the first one. Identity Platform was
provisioned as the borrowed bench — magic-link email as the floor, Google and
GitHub above it — and what comes back is written onto the badge as one
attestation and nowhere else. There is no Firebase SDK in the web app on
purpose: two REST calls do the whole flow, and the 150 KB alternative would
have parked a second identity, with its own lifetime and its own opinion about
who you are, beside the badge. The ID token is used once and dropped.

The gesture that follows is the point. A browser that had never been Jordan
was refused when it tried to self-claim the name, proved an address, and was
offered *"another surface that proved the same address answers to: Be Jordan"*.
One click, and the tab was her. Meanwhile a home that has borrowed no attester
refuses an `email:` grant with its reasons and shares by link exactly as
before — the trap this work was told not to walk into.

## Two lessons that cost nothing and could have cost a lot

The provisioning script was rewritten from what its first run *measured*. A
`gcloud auth login` credential bills its API quota to gcloud's own shared
client project, so the API answered `403 SERVICE_DISABLED` naming a project
nobody had heard of, moments after the script enabled it on ours. And
`initializeAuth` sits under `v2/` while its neighbours are `admin/v2/` — the
wrong path answers an HTML 404, so a check looking for `"error"` in the body
found none and reported success. That is this codebase's oldest recurring bug,
reproduced in a provisioning script on the day the phase that closed it was
committed.

Then the same shape once more, from the other direction: a documentation edit
used an unquoted heredoc, so backticks around a script path became command
substitution and **writing the changelog's own source ran the provisioning
script**. Nothing broke, and only because every step in that script checks
before it creates. It is a better argument for the idempotence rule than the
one in the README.

## The tab survives its home

Phase 10. A browser tab that loses its home keeps working: the shell comes off
a hand-written service worker, the canvas out of a durable IndexedDB replica,
and writes queue instead of failing. On reconnect the queue flushes **before**
the tail comes down — which is the whole phase in one clause, because getting
it backwards is silent divergence rather than a visible bug.

Driven with the home stopped and a second writer raced in first: the tab's
offline op landed *after* the other writer's, at seq 4, under the id it had
minted while offline. Replaying that id returns the same entry and appends
nothing.

The brief for this phase was wrong, in a way worth keeping. It said a replayed
`item.add` would add a second item. Measured against the reducer, it would not:
every creating op already carries a client-minted id and the second is refused.
**The vocabulary has been accidentally exactly-once since the beginning.** The
real damage of at-least-once is one layer along and much quieter — a replay
comes back as a *refusal*, indistinguishable from the home genuinely rejecting
your work, so a client doing the honest thing (roll back, say so) would be
lying about an item sitting in the canvas. The idempotency key shipped anyway,
with its reason rewritten: it exists so a replay is not mistaken for a refusal.

Two more that only a browser could have found. A service worker **does not
control the page load that registers it**, so a runtime-caching-only worker
holds nothing on a first visit and the second visit offline is the dinosaur;
the fix reads the asset URLs out of the `index.html` it just cached, so the
shell names its own assets and there is still no build plugin. And
"reconnecting" turned out to be truthful about the socket and wrong about the
situation — a tab restored from its own replica sat on it forever, while the
person looked at a perfectly good canvas they were about to write to.

## Also today

- The blob route is **closed**. It had been open since phase 2 on the argument
  that a sandboxed iframe cannot carry a badge; measured in Chrome, the
  iframe's own load is same-origin and sends the cookie — only requests from
  *inside* the blob are cross-site, and those never resolved anyway.
  `Cache-Control` gained `private`, because a credentialed response at a shared
  CDN edge is a closed route with an open back gate.
- Kill-a-badge, scoped to badges that share an identity with you — so a
  stranger admitted by a link cannot end the recognition of the person who
  shared it, and the listing can never become a roster of people to expel.
- `repo:` grants are deferred to phase 11, with the refusal left honest.

# The home turns out to belong to the canvas

**Phase 10.3.** Three pressures arrived at once — a developer's rig holding
canvases born local beside work that should live at dev, the wish to run prod
isocan in one repo and dev in another, and an innkeeper's second commitment,
which always implied a person working for two teams. All three are the same
fact: **the home is a property of the canvas, not of the daemon.** The marker
has asserted it since Scene 0 by carrying an address; the configuration model
has contradicted it since phase 6 with one `home` key and a whole-daemon
demotion.

So a daemon is no longer one of two things. It is the home of some canvases and
a replica for others, holding one link per address, with `homes.json` recording
where each canvas lives — written at binding, never inferred, and daemon-owned,
because the CLI-side cache next door (`dirs.json`) is documented-stale by
design and two writers on one file is how a file drifts. `config.json`'s `home`
kept its name and changed its meaning to the **birth default**: where the
*next* canvas goes. A boot migration freezes every canvas already at that home,
so upgrade day behaves identically — and phase 14's default-address flip
becomes safe, because a shipped default is consulted only at a birth and can
never re-point work that already exists.

## The line that was a data-loss bug

The sweep added every canvas on the local disk to the set it dialled at its
home. That was correct for exactly as long as a daemon had one home: "on this
disk" and "this home's" were the same set. With two they are not, and two homes
can hold one canvas id — the twin case. The wrong home answers a dial with a
**snapshot**, and the code that applies it overwrites the local copy with a
stranger's canvas of the same name. Narrowing the sweep to the recorded rows is
a data-loss fix, and its test asserts the *negative*: each link's handshake
count for the other's canvases stays at zero, with a positive control beside it
so the assertion cannot pass by the links being broken.

## What measurement reversed

The design claimed a two-home name flap was "transient and self-healing" — a
rename that reached one home and not the other, corrected by the next write.
Run, it is not: a stale roster overwrites the rename permanently, and a live
relay never fixes it because the roster overwrites the name before the claim
cache can see it. The control is the finding, though: **one home shows the
identical flap.** The seam predates the phase entirely. What changed is the
window, because a down home used to refuse every write on the machine, so
nobody was ever working during an outage to notice.

## The wrong answer that nearly shipped

A badge is a fact about a desk, and a desk belongs to a home. `isocan badges`
asks "what surfaces of mine exist there" without ever saying where — a question
that answered itself while a daemon had one home. With two and no birth default
it has no answer, and the code's instinct was to fall through to the *local*
desk: a short, plausible, completely wrong ledger, delivered in silence, about
a credential. It refuses now, naming both homes. A pass escaped the same seam
by carrying its own address — which it can, because a pass is never handed over
alone: it arrives as `address#pass`, so whoever holds the token holds the
address too.

## Also today

- **Page serving became per canvas**, which the phase text did not anticipate:
  a daemon serves the app for canvases it is the home of and a signpost for the
  rest. Without it a developer's local canvases would stop opening in a browser
  the moment they joined one dev canvas.
- That left a hole only a browser could show: the front page navigates
  **client-side**, so the server's per-canvas guard was simply bypassed and the
  local origin would happily render a stale replica of a dev canvas. The list
  asks a narrowed question now, and the canvas page is a **gate** rather than a
  branch — a React effect dials the socket on mount, so a check made inside the
  page is a check made after the damage.
- Two races that were safe only by accident, exposed by links being created
  lazily: an un-gated badge fetch that made the home answer `not-your-actor`
  about an actor just claimed, and a badge write whose second writer erased the
  first's key.
- The map's socket ceiling was wrong *before* today and in the wrong direction:
  `/ws` is per canvas, so a thick replica is one socket per canvas, not one per
  machine. Phase 6 built it that way on day one and nobody revisited the
  arithmetic.
- A raw NUL byte had been written into a source file. It compiled and tested
  fine — and made `grep` skip the whole file in silence, in a repo whose own
  tests grep its sources.

# Two doors into the repo, and the bug that writing them found

**Phase 10.5.** `docs/development.md`, written for the two developers who
actually exist rather than an abstract one. Dion is not new — he has been
landing changes from a rig built before multi-user — so his door is the
**upgrade**: what current main does to a local daemon serving pages the old way,
with canvases born local and markers naming no home. Paul is new: clean machine,
`git clone` to a canvas of his own at dev. Every command in it was run rather
than remembered, on a scratch clone and a reconstructed pre-multiuser rig.

Beside it, the dev deploy learned to gate. Cloud Build used to fire on push to
`main` while the test suite ran in a separate pipeline that nothing waited for —
so either developer could take down the other's dogfood home with a commit that
was green on their laptop. Now CI fast-forwards a **`green`** ref once
`npm test` and `npm run typecheck` pass with the Firestore emulator *required*,
and the trigger watches that. Three refs with three jobs: main is the source,
`green` is the tested source, `release` is the shipped CLI.

## What writing the doc found

Phase 10.3 had shipped a bug on the exact path this phase exists to protect. On
a rig that predates `homes.json` — Dion's, precisely — the first `isocan home
<address>` **froze every locally-born canvas at that home**. Pages 404'd,
`isocan add` answered `project not found`, and the verb that did it printed
*nothing already here moved*.

The migration's branch is "no record and a configured home → these canvases live
at that home", written for a phase 6–7.5 replica. It never wrote its record when
no home was configured, so it stayed armed forever; `isocan home` writes
`config.json` and *then* restarts, and the restart walked into it. Its own
comment had specified the correct behaviour all along — "an empty `{}` is a real
answer and must be written, or the migration re-runs at the next boot" — and the
code returned before reaching it, which is the most ordinary way for a guard to
be missing.

That was only the first of three. `homes.json` says absent and `null` mean the
same thing, and three separate places disagreed: the migration armed on the
absent *file*; the page server counted only explicit nulls, so a daemon
signposted away pages for canvases it was the home of; and `/api/homes` reported
only rows, so `isocan home` listed nothing and `isocan status` called a daemon
that hosts three canvases a replica of somewhere else. Each was defensible
alone. Together they are one invariant nobody was enforcing.

## The discriminator, and the test that lied

Fixing the ordering is not enough, because `isocan home` can be the *first*
command run on upgraded code — there is no earlier boot to write the empty
record. So a configured home is no longer taken as evidence a machine was ever a
replica. The evidence is a **badge at that address**: a replica knocked on that
door and was recognised, and a machine merely told an address a moment ago has
not. It fails toward "this is mine", which loses nothing; the other direction
hands somebody's local work to a stranger's home.

The sharpest lesson was in the tests. The first three regression tests passed
against the bug they were written for — because they built their fixture with
today's code, and **birth writes a row**, which silently disarms the migration.
A machine that predates a file cannot be reconstructed by a process that always
creates it. Every guard here was re-checked by restoring the bug and watching
the right test fail.

# The front door opens, and the code starts saying canvas

**2026-08-24** · Phase 13.5 · Dimitri Glazkov

isocan had no front page. `/` was the canvas list, and the app rendered the
identity dialog *instead of* the router whenever a browser was nobody yet — so
a stranger arriving at the origin met "pick your name" before learning what
isocan is. Scene 0 asks for the opposite: the home origin itself wearing a
front page, handing over the next move where the reader is already standing.

It has one now, on one address with two faces — the front page when nobody is
here yet, the canvas list once somebody is. And the identity door stopped
gating the router, while a share link's arrival is untouched, because that path
is what phases 7 through 9 proved.

## Two front doors, and only one was reachable

`marketing/` had been sitting in the tree since the 23rd: a static site with
its own thesis, a split ledger, a real screenshot. Its README called it "the
logged-out surface for isocan.io". Nothing built it, deployed it, or linked to
it. Scene 0 settles the tie in words — not a brochure standing apart from the
product — so its craft moved into the page that is actually served and the
directory went. Its webfont did not: a Bricolage Grotesque subset is 30–80KB
from another origin, and a headline is not worth a blocking fetch on the first
page a stranger sees. The screenshot came in at 49KB instead of 484KB, lazily,
so nobody opening a canvas pays for it.

Serving the result immediately found a bug the page could not: the daemon's
hand-rolled six-entry mime map had never seen a `.webp`, so it went out as
`application/octet-stream` — and *rendered*, because Chrome sniffs an `<img>`.
Invisible until the day anything sets `nosniff`. The guard is the rule now, not
the instance: every extension under `public/` must be named.

## The spam fix turned out to be code

Phase 9 left a finding: the magic-link floor lands in spam, because Identity
Platform sends from `noreply@<gcp-project>.firebaseapp.com`, aligned to nothing
isocan owns. `phases.md` recorded the fix as "a sender domain isocan owns, not
code". That was wrong, and finding out why was the day's best detour.

The provider moves the **From: address and the action-link domain together**.
So the sender domain must answer `/__/auth/action` — and measuring the
candidates disqualified two of them by their own answers: the apex `isocan.io`
has no A record at all, and `dev.isocan.io/__/auth/action` returned **200 and
isocan's own app shell**, which would have swallowed a sign-in code in silence.
That pointed at a second origin, `auth.isocan.io` on Firebase Hosting — and a
second origin is what this project refuses everywhere else. A sign-in link
landing on a different hostname than the product would put the badge cookie,
the service worker and the browser replica behind two doors.

So the daemon serves the route. It was only ever a redirect: `signin.ts`
redeems the code and writes the attestation itself, with no Firebase SDK. Ours
is a real 302 rather than a page that redirects in JavaScript. It throws the
host away rather than checking it — `continueUrl` is chosen by anyone holding
the browser API key, so honouring it would carry a live `oobCode` out of the
origin in a `Location` header. There is no allowlist, because a comparison is a
thing to get wrong.

A worker's own mutation pass found two of its security tests were decorative —
the URL parser was passing them on the code's behalf — and digging into why
turned up a real hole: an unknown scheme is not "special", so
`continueUrl=foo:\\evil.example/x` keeps its backslashes into `pathname`, and a
`Location` of `\\evil.example/x` resolves off-site.

The link now arrives from `noreply@dev.isocan.io`, in an inbox, and clicking it
comes home through isocan's own handler.

## The instrument was lying

Worth its own paragraph, because it nearly produced a false report. Identity
Platform's `returnOobLink` renders the **default** sender domain whatever the
custom-domain config says. It was probed twice, answered `firebaseapp.com`
twice — while real mail had already been arriving from the new address. The
only valid instrument for what a sent email says is a sent email.

## The rename, and the contract nobody had listed

`projectId` and its 1439 friends became canvas vocabulary — identifiers, types,
files, CSS classes, the CLI verb (`isocan canvas`, with `project` a hidden
alias), help, guide, README, docs. Six things deliberately did not move: the op
type strings written into every oplog, the `/api/projects` routes, the
`.isocan/project.json` marker in people's repos, the on-disk layout, the `prj_`
id prefix, and two `CanvasState` field names.

The seventh category was one neither the plan nor the decision had named:
persisted and wire JSON **keys**, which are neither a route nor an op string.
Measured, a pre-rename CLI *reads* from a post-rename home perfectly and fails
on the first *write* — with `error: internal error`, naming neither cause nor
remedy. The break was taken deliberately, while the audience is three people,
and made legible: **426** with the upgrade command. Detection needs both halves,
which a mutation proved — checking only for the missing new key turned all seven
tests red, because the door's own bearer request carries no `canvasId`.

Anyone with an installed isocan needs `npx github:dglazkov/isocan#release setup`
before their next write.
