# 28 August 2026

Thirty-five commits of work, and the day divides cleanly: a morning of research that
mostly argued against building things, an afternoon and evening rebuilding the
app's chrome in six planned phases, and — in a separate lane — the CLI learning
to notice that it has fallen behind its home.

The thread running through all of it is guards that did not bite. Four separate
tests passed against the bug they were meant to catch — three written the same
day, one already in the tree — and each was found only because it was
mutation-tested rather than trusted for being green. Two commits say so out
loud by mid-afternoon, and it happens twice more before midnight.

## What's new

- The side panel floats over the canvas instead of shoving it aside, so nothing jumps when you open it.
- Copy and paste works on the canvas, on both the app and the terminal.
- Closing the panel leaves a slim strip showing who is here and what is unread.
- Full screen now fades the chrome away after a few still seconds, so a canvas can be presented from.

## The morning: five pieces of research, and four of them said no

**Mind maps are a file, not a graph of items** — and then, four commits later,
they are a graph after all. The first draft turned on a fact about this
product: **the canvas has no edges.** There is no connector or link between
items as a canvas fact; what relationships exist are `#Title` references inside
a comment body and `annotates` on ink. So a mind map is either one item whose
blob is an outline, or it is nodes plus a new op type — and each of the three
things actually asked for (a file, a riff, memory) ruled the second out on its
own.

Then a second requirement arrived — click and move nodes, with the arrows
following — and the revision is worth more than the original. **The mistake was
in the sizing, not the reasoning.** The nodes already exist: a text node is an
item, positioned, versioned, undoable, draggable by `item.move`. And the edges
need no op type either, because `lineage` already carries `parent=<itemId>` on
an item's properties, written by `item.add` and undone by undo, which is
exactly an edge's shape. The first draft had argued against something more
expensive than what was asked for.

What actually settles it is structural rather than a matter of effort: for a
dragged node to stay where it was dropped, the position must be a canvas fact,
which means the node must be an item. An outline has no coordinates to write
back to. And with the map on the canvas, the outline is *derived* on demand —
so it cannot drift, which a stored copy would the moment somebody dragged a
node. The requirement the first draft was trying to protect is met better by
the option it rejected.

**Should Honcho or Hindsight be brought in as a memory system?** The answer is
index, never record. isocan is already a memory system with three properties
most are not: the memory IS the artifact, it can be UNDONE because it is ops,
and it is SHARED by construction rather than being a per-agent recollection
that may differ. Those three are exactly what adopting an external store as the
place a fact lives would spend. Three tests for any candidate, each a redesign
rather than a caveat when the answer is no — can it be undone, can everyone see
it, does it work with the network off. That points at MCP rather than a
dependency, and at isocan offering the canvas over MCP for somebody else's
index to read. The gaps are named rather than dismissed: nothing crosses
canvases, there is no semantic retrieval, nothing accumulates about the person,
and `recap` decays by TIME when what should survive is importance.

**Seven component libraries, six of which ship React.** The fact that decides
it is the artifact: an isocan screen is one self-contained HTML file — inline
`<style>`, custom properties, no build step, no npm, no bundler. There is
nowhere to put a React component. What transfers is the part nobody thinks of
as the product: tokens. So the proposal is `isocan design import`, landing a
theme as this canvas's DESIGN.md. Two risks recorded rather than skipped: a
component library is a house style, and if every canvas is built from one every
canvas looks like it; and `transitions.dev` has a paid tier, so an agent
pasting Pro CSS into somebody's canvas hands them a problem they did not
choose. One library could not be verified at all — its fetch failed on a
certificate error — and it has no row of claims rather than a guessed one.

**Motion: the only kind missing is the kind that decides state.** This
codebase has been sorting motion into two kinds without naming them.
Decoration is skippable, and the rule is already in the toast's CSS: the
settled state IS the base state, the keyframes are only an entrance. Motion as
data is not decoration — the camera eases so a jump "reads as travel rather
than teleportation", and remote cursors are lerped at three rates by who is
moving them: 0.22 for a human, 0.11 for a CLI hop, 0.07 with deliberate
sub-pixel jitter while an agent works, which the code calls "a hand, not a
tween". The gap is a third kind: motion that *decides* state, where the settled
state is exactly what the motion produces. Pan inertia is worth adding
narrowly, because trackpad users already get momentum free from the OS and the
people without it are mouse users and anyone on the Hand tool. Throwing items
is refused: a position is an op, it replicates, undo reaches it, and fuzz is not
a feature in a value other people read.

A sixth look, at `mdx-graphs`, does not move the mind-map design — it is React,
static, and renders nothing draggable — but it sharpens what the
component-library research found: it is the third library in one session
distributed through the shadcn registry, which makes adopting shadcn nearer to
adopting a package manager than a look. What it is suggestive about is the
other end: in a terminal, box-drawing beats whitespace for reading a tree at a
glance, and the terminal is where agents read.

**And the one that said yes.** Should the log be able to say that several ops
were one act? The answer turned out to be evidenced rather than argued.
`ops.ts` already carries `items.move`, `items.delete` and `items.restore` —
each the same op as its singular twin with a list where the id was, each
existing because undo is per operation. That is grouping, implemented ad hoc,
once per gesture, at the cost of a permanent addition to the shared vocabulary
every time. Three more gestures hit it in one day and none can be fixed by a
fourth plural op.

## Copy and paste, and a bug that did nothing exactly

⌘C/⌘V on the canvas and `isocan copy <items...> [--to <canvas>]` from the
terminal, the same ops from both.

**The clipboard is the app's own, not the system's**, and that is a decision:
`navigator.clipboard` is permissioned, a refusal is indistinguishable from
having none, and Chrome blocks it outright while the tab is `hidden`. Holding
it in the UI store also makes the interesting case work — it survives
navigating from one canvas to another in the tab, which *is* pasting across
canvases. It holds the item records rather than their ids, because ids would be
unresolvable the moment you navigate.

**The arrangement of a selection is part of what was copied.** Four screens in
a row must paste as four screens in a row, and placing each item independently
loses that silently: every item lands somewhere legal and the group is gone. So
the group is placed as one box. That also sidesteps `resolvePlacement`'s nudge
rather than fighting it — it only nudges on an actual collision, so a group
placed where the whole box is clear has no collisions to nudge. No exemption,
no core predicate changed.

Then: **⌘C did nothing. It did nothing exactly** — no error, no toast, no copy,
which is the worst shape a bug can take. The copy branch read `canvas` from the
component's closure and `canvas` was not in the keydown effect's dependency
array, so the handler kept the value from before the canvas loaded: `null`.
Every other handler in that file already reads
`useCanvasStore.getState().canvas`. And the confirmation was going to the wrong
channel — `setNotice` is what every other caller uses to report a *problem*,
and those stay until dismissed, so "Copied 2 items" would sit there as a
message about a failure that never happened.

Between the two: the projects index was claiming a fixed defect was still
broken. The auto-upgrade row read "the hosted home currently cannot say which
build it is", which had stopped being true when phase 1 landed the day before —
and every promote that morning was verified by reading `"commit"` off
`/healthz`, the exact capability the row called missing. An index that
disagrees with the project it indexes is worse than no index, because the whole
point of the table is that somebody can read one line instead of a directory.
(The same row went stale again by evening, for the opposite reason, and was
corrected in the phase-2 review.)

## The flaky tests were pointing at a real bug

Six full runs and eight parallel ones. The flakes are not timeouts, and calling
them that — repeatedly — was wrong: `testTimeout` is already 30 seconds and
these failed in four to eight. They are a family of load-sensitive failures
with several distinct causes, and one of them is a product defect worth the
whole exercise.

**`isocan setup <address>#<pass>` could silently not redeem the pass.** Every
step after the first is gated on `daemonUp`, which came from `ensureDaemon`
giving up after five seconds. On a busy machine a daemon still starting reads
as no daemon at all — so setup wrote no home, redeemed no pass, admitted
nobody, and **exited 0**. Somebody pastes a line out of a chat window, is told
it worked, and is not on the canvas. `ensureDaemon` waits 20 seconds now, a
pass that was not redeemed says so, and `awaitHealth` replaces two single 2s
probes taken right after a restart.

Honest about what it did not do: two failures in nine runs before, two in six
after — statistically indistinguishable. Each fix removed a real cause and
another surfaced. Capping parallelism was measured and rejected: six workers
ran clean four times but cost ~14% wall, and seven failed anyway.

## One gesture, one undo

Researched in the morning, built in the afternoon. `LogEntry.group` is an
optional label, and everything that made it cheap was already true: the op
vocabulary does not change, `UndoStacks` already held seqs per canvas and per
actor, it rebuilds from the log the way `undoneBy` does, and an entry with no
group is a group of one — which is what every entry written before today
already is. No migration.

**A label, not a transaction**, and the distinction is load-bearing. If the
fifth op of eight fails, the four that landed are real and undo handles exactly
that. Promising atomicity would mean rolling back a distributed write across a
replica and a home. The rule for what one ⌘Z reverses is the contiguous run at
the top of the stack that shares a group, not every member found anywhere —
nothing writes a broken-up sequence today, but a rule that cannot reach past
its neighbour needs nobody to keep that true.

An hour later it met its fourth caller without being asked to. **Dropped files
land where you dropped them**: `addFiles` had sent every file with the same
placement, so a drop of five asked for five items at one point, and the
daemon's ring search put the third one most of a screen away. Asking for ground
that is actually free gives that search nothing to do. The whole drop is
selected, the camera moves only if what landed is not already in front of you,
and one ⌘Z takes back all five.

## `isocan notify`, and Caveat comes home

**Saying something in the Chat is one command now.** It was three steps and a
lookup, so an agent with something to announce reached for `comment add` —
which is a *pin*, stuck to a spot — and a canvas collected markers for
announcements that were never about anywhere in particular. The guide now says
which to reach for and why: the Chat is the canvas's conversation, a comment is
pinned to a thing.

**And the handwriting face is served from here.** Caveat went to Google Fonts
deliberately and as a stated temporary, with the two costs written down beside
the link; both are paid off now rather than carried. One file, because the
latin subset is a variable font — 400 and 700 are the same 73KB. `statictypes`
failed the moment the font landed, which is exactly the failure it was written
to prevent. And the caching needed a third case: `/assets/*` may be `immutable`
because Vite hashes those names, but a font in `public/` has a stable name, so
`immutable` would pin a replaced font in caches with no way to bust it.

## The UI refresh: seven screens, six phases

The spec lives on a canvas and was checked rather than trusted. It held on
every claim that can be checked, including the two that decide the shape of the
work: the panel *already* overlays the canvas, so opening the Chat covers
rather than reflows, and `followViewport` already exists as "the one mutation
that does not read as the user grabbed the wheel". The constraints are written
as gates rather than cleanup, because both the rationale and the spec defer
light mode and deferring it is how it ends up broken.

**Right-click** came first, and the rule it is built to is that a menu is not a
place to invent vocabulary — almost every entry has a key, a double-click or a
CLI verb behind it. The accelerators are looked up from `SHORTCUTS` in core
rather than spelled, and that choice immediately earned itself: Copy and Paste
rendered blank, because ⌘C and ⌘V had been implemented that morning and never
registered. Neither `?` nor `isocan shortcuts` knew copy/paste existed.

**Phase 1 — the rail floats.** Inset on all four sides, rounded, frosted. Chat
and Files had byte-identical rules written out twice, so restyling one would
have left the other clamped to the edge; `.dock-panel` is the frame now.
`--panel` with a blur rather than a new colour token, because that ground is
already used for floating chrome in four other places. Contrast measured on the
composited ground in both themes, light checked *first*. One acceptance item
was outstanding and was not claimed: the blur's cost under motion could not be
measured, so the design spent less than it asked for — blur(12px) rather than
20 — and said so.

**Phase 2 — opening the rail pans the canvas.** Docking takes width; floating
borrows a pan and returns it. The distance is `dockEdges`, never a fresh
measurement, which is what stops the pan and the framing from disagreeing about
one rail. Two findings worth more than the phase: `requestAnimationFrame` does
not fire in a hidden tab, and the browser pane these phases are built in
reports `document.hidden === true` permanently — which explains phase 1's
unmeasurable blur *and* exposed a real defect here, an eased pan that stops half
applied and finishes whenever the tab is next brought forward.

**Phase 3 — the shut rail is a 48px strip**, carrying unread count and which
agents are working. One constant, `STRIP_WIDTH`, did the whole layout: framing,
the stage rect, the minimap, the hover cards and phase 2's pan all followed
from that one line. The ring is `sessionState`, the same reader `isocan who`
prints from. A bug found by looking rather than testing: the badge sat on the
Chat button but summed unread across every thread, so a comment pin anywhere on
the canvas landed on the Chat's count.

**Phase 4a — the lane.** isocan has recorded this since versions existed and
has never drawn it: a comment carries the item ids it #-referenced, and every
version carries who made it and when. `laneFor` is in **core**, not `web/lib`,
because what a message made is a fact about the canvas rather than about a
panel. The rule needed an upper bound the sketch did not have — with only a
lower bound the first message that ever mentioned an item claims every version
made afterwards. A message owns what its author did between it and *their* next
word, so a person saying "thanks" does not end what an agent is still doing.

**Phase 4b — the tether.** Every rule in `tether.ts` is a reason not to draw,
because the costs are asymmetric: a missing tether costs a nicety, one pointing
at the wrong thing costs trust in every other tether including the right ones.
The run is measured from where the line becomes *visible*, not from the chip —
the chip sits inside the rail, so measuring from it makes the limit depend on
the rail's width, and somebody who widened a panel would have silently switched
the feature off. Found by accident on a canvas whose rail had been widened by
the phase-2 experiment. Follow — the camera tracking the lane — is deliberately
not built: it moves the canvas on the person's behalf, which puts it in phase
2's class and deserves phase 2's treatment.

**Phase 5 — the title row's two ends.** Most of §5 was already true, which is
said plainly rather than claimed as work. What was not true is that the row's
two ends behaved alike: at 30% zoom the title read at 11px and the chip saying
an agent is working here read at 3, gone at exactly the zoom somebody uses to
scan a whole canvas for where the work is. The version count did **not** move
beside the name, and the conflict inside the phase as written is recorded
rather than resolved by gambling the most-tested file in the package on the
least important change.

**The header stops being a block**, and `.floats` now exists: one ground, one
hairline, one radius, one shadow, spelled once and worn by Chat, Files, the
strip and the three clusters. The bar still reserves its 48px, because floating
changed what you can see through and not what is in the way.

**One inset, everywhere.** "The top elements are tight" was the symptom. The
app had four insets — header 7, rail 20, minimap 14 and 16, tool rail 14 — each
sensible the day it was written, none of them as a set. `--edge: 20px` is the
whole answer, and three guards broke and all three came back stronger. The
`tokens` guard's exemption was a *list*, and the list wanted a fourth entry
within the hour, which is the fate its own comment predicted; it reads the
value now, so a colour cannot be smuggled past by being called `--edge-2`.

**One handle, not eight buttons.** The phase the plan flagged as the one where
"do not lose features" is most at risk, because "we moved it into a menu" is
the sentence that precedes a feature nobody can find again. So `drawer.test.ts`
asserts every swallowed control is reachable, that none is a duplicate still in
the bar, and that each toggle says which way it will go. What stayed *out* of
the drawer matters as much as what went in.

**Full screen presents.** The canvas gets used as a slideshow, and that is the
use this view has to serve first, so the same slab language arrives here and
the stage becomes the whole window — the old bar's own comment had already
argued against it: "every pixel this takes is one the thing you are reading does
not get." **And it rests**: after a few still seconds the chrome fades, and a
pointer move brings it back. A key press deliberately does not wake it, because
flipping slides *is* presenting and ⌘→ reviving the chrome would blink it into
view on every slide. Focus wakes it regardless, because a focus ring on an
invisible button is the worst of both. Opacity rather than `display: none`, so
nothing reflows and the slide cannot twitch on a projector every few seconds.
Scoped to `.fs-bar` and not `.fullscreen-bar`, because the workbench renders
that same class and making it absolute would have collapsed a screen nobody was
looking at.

**The agent tray** closes the day's UI work: the least novel feature in the
redesign and the most isocan-specific one. Nothing here is computed — the
states were already correct and already printed by the terminal, and had simply
never been shown to the person at the canvas, who has had to read a facepile of
initials and guess which of them is working. `roster()` from core is the same
function `isocan who` calls.

## Two bugs in the app's foundations

**The Pen tool whited out the app.** React error #300, "rendered fewer hooks
than expected", straight out of the render phase and into a blank page.
`OwnCursor` early-returns for tools other than Select, and the colour was read
*below* that return — fine for as long as it was `actorColor(actor.id)`, a
plain function. Yesterday's stale-cursor-colour fix swapped it for
`useActorColor(actor.id)` and left it exactly where it sat. **The call site
never moved; what changed was what the call was**, from a function into a hook,
and nothing was watching for that. The existing guard could not have caught it:
`livecolor.test.ts` asserts the file matches `/useActorColor\(/`, and it does,
in both the broken and the fixed version.

**So the repo has a linter now**, which it had deliberately gone without. What
changed the calculation is that a conditional hook has no seam to test — no
exported function, no observable state, just a render that throws and a blank
page. `rules-of-hooks` over the whole web app reports zero other instances,
which is worth more from a parser than from the hand-rolled scan written that
morning; the scan knew exactly one shape and would have called four other ways
of writing the identical bug clean, so it was deleted rather than kept beside.
`exhaustive-deps` is on at error too, because it is the *other* bug from the
same week: ⌘C copied nothing because a keydown effect closed over a canvas that
had not loaded. It found seven existing effects, every one a deliberate
narrowing that gets its freshness another way — so none changed behaviour, and
seven unwritten assumptions became seven written ones. The lint runs *as a
test*, because `npm test` is what decides whether a commit reaches `green`.

## Words that were pointing at the wrong thing

**Inter, self-hosted**, following the path Caveat cut that morning: the app had
`font: 14px/1.5 system-ui` and nothing else — no scale, no weights, no tracking
— which is three different products with every measurement in the design taken
against a face that changes underneath it.

**CHAT → Chat**, reported three times. The panel headers were uppercased in
CSS, so the panel shouted its own name at a volume nothing else on screen uses
and disagreed with the button that opened it three inches away.

**And the minimap overlap, which was three bugs wearing one coat.** Phase 1
floated the rail, so what it occupies became `20 + panelWidth`. Three surfaces
that stand beside the rail had each hand-spelled the old arithmetic — the
minimap `panelWidth + 14`, the files hover card and the thread hover card
`panelWidth + 10` — and all three landed 20px too far left, on the panel's
rounded corner. Only the minimap was reported; the two hover cards were
waiting. All three go through `railSpan` now, and the guard holding the line is
an **allowlist** rather than a search, because the first version looked for
`panelWidth +` and passed while the bug was in the tree: the line it was
written for reads `(panelOpen ? panelWidth : 0) + 14`, where the arithmetic is
on the parenthesis and not on the name. A guard that can be side-stepped with a
bracket is worse than none.

**"back to canvas" emptied the Chat in silence.** Pressed by mistake on a
canvas with 36 messages, and read as losing the lot. Nothing was lost —
`thread.setMain → null` demotes the conversation back to its pin, and that op
has always had an inverse. **Reversible and seen to be reversible are different
properties, and only the first one had a test.** Not a confirm dialog: that
taxes every deliberate press to catch the rare accidental one, and would still
not have said the conversation survived. The fear was never "did I mean to do
that", it was "where did it go".

Then the label itself: **the Chat was never on the canvas, so it cannot go back
there.** A thread can be a promoted pin, or it can be born as the Chat —
`thread.create` with `main: true` — and such a thread has never been anchored
to anything. The button claimed the first origin for both, and the tooltip went
further by naming an anchor that has never existed. It says "make it a pin" now,
and it *shows where the pin went*: for a born-main thread the coordinates are
the centre of whatever view the first message was typed in, which on the
reported canvas was a spot chosen nine days and one other person ago.

**The minimap jumped across the screen on reload** — reported as a minimap bug
and never one. The rail's remembered state was restored only after `canvas`
arrived, a network round trip, so for that whole time everything positioned
against the rail was drawn in the wrong place. The remembered choice is a
string in localStorage and needs nothing from the network, so it is applied
synchronously now. And the first position is not a move, so it is not animated.
The fix used `requestAnimationFrame` at first and the harness caught it by
reporting `placed: false` for thirteen seconds straight — phase 2's lesson
applied rather than relearned.

## Auto-upgrade phase 2: a third kind of stale

In its own lane, and the only work today outside the web app. `stalenessOf`
knew two ways to be stale — another copy holds the port, and this copy changed
under a running daemon. This adds the third and the one that crosses machines:
**the daemon disagrees with the home it forwards writes to.** Notify only:
nothing is fetched, applied or restarted.

`upgradeVerdict()` sits beside `stalenessOf()`, pure and given both sides.
**Null is the answer whenever either side cannot name its build** — a home with
`commit: null` is most of what is deployed, and telling it "you are current" is
the false success this project's standing lessons name. The daemon asks its
home on a self-rescheduling hourly timeout, and again whenever a home starts
answering after not answering; not on the poll loop, which at 2000ms would be
1,800 requests an hour for an answer that changes about twice a day. It is a
plain `fetch` rather than the badged `api()`, because the health routes are
open — so a replica whose badge has been swept can still find out it is behind,
which is the machine most likely to be. The verdict rides the health body
`makeCtx` already fetches, so no command pays a round trip.

The notice says it once per **sha pair**, not once per daemon: a daemon lives
for days while its home moves about twice a day, so `warnIfStale`'s `startedAt`
key would report the first skew and stay silent for every later one. It states
facts and names a command; it does not instruct. Who may act is a separate rule
— in notify mode the upgrade decision belongs to a person even when the reader
is an agent, and the agent guide says so now.

`available: false` is a real answer, distinct from an absent field: "the home
was asked and this copy is current" and "nothing could be asked" are different,
and only one may be reported as reassurance. On a machine with several homes
the verdict comes from the birth home, or the single home when there is exactly
one, and otherwise there is none — picking the newest would be choosing a
distribution channel on somebody's behalf.

**And the review found two bugs the phase would have shipped.**
`HomeLink.start()` was running twice for every link created at boot —
`HomeLinks.linkFor` fires it, then `HomeLinks.start()` awaits it — which is two
`setInterval` polls, of which `close()` can only clear the one the field still
holds. Pre-existing, doubling the sweep rate against every home for the life of
the daemon, and phase 2 would have inherited it because the build probe is a
second timer started in the same method. Found by counting the new probe's
requests rather than by reading. The reconnect trigger also fired at boot,
because `was !== true` treats a fresh link's null as a reconnect.

The review's third finding is the day's theme again: **the first guard for the
double start passed against the unfixed code.** It measured the sweep rate, and
`sync()` coalesces, so two intervals produce nowhere near twice the requests.
Deleted rather than adjusted. A fourth: an assertion wrapped in `if
(body.upgrade)` is vacuous on a checkout that cannot name its own commit, which
this one cannot on reftable.
