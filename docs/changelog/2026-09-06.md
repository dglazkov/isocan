Two threads and a long tail. Going to another canvas without the trip through
the home screen — the branch was cut at 4 September's head and forward-ported
over the module work and the two days after it. And the answer to yesterday's

The tail is the more interesting half of the day, and none of it was planned:

## Read auth on the content origin: signed URLs, isocan.store, five minutes

Yesterday's [`content-read-auth.md`](../projects/multiuser/content-read-auth.md)
costed three options and left two numbers to the owners. Both are answered
and the code is in.

**The collision, restated because it is the whole design.** Expulsion reaches
the bytes (23 August: the blob route requires a badge and an admission, and
sends `private` so no shared cache can hand a swept badge what it was just
expelled from). And the content origin holds nothing (26 August: no cookie to
steal, no API to call, which is what makes `allow-same-origin` safe to grant
there). The origin that must serve private bytes is the origin that must not
carry the credential saying who is asking.

**So the URL is the credential, and it dies in minutes.** The badged app
origin mints an HMAC over `(canvasId, hash, expiry)`; the content origin
verifies it and serves or refuses, looking nothing up. `content-auth.ts` is
the scheme on its own — no Fastify, no desk, no store — with four verdicts
that collapse to one 403 for the caller and stay four for the log, and the
signature checked *before* the clock so nobody can pick which refusal they
get by writing a date in the query.

**The mint is a `GET`, and that is load-bearing rather than tidy.**
`GET /api/projects/:id/blobs/signed?hashes=…` sits under the canvas-scoped
prefix, so the door's one hook has already re-asked `canvasId ∈ admissions`
before a signature exists — the whole enforcement, with signing knowing
nothing about it. A POST would have been refused by the capability hook to
any badge below `edit`, and a view-only member who cannot mint is one who
sees an empty canvas.

**The TTL is five minutes, and the argument for the calmer hour evaporated.**
That argument was the cost of a mint per frame render. Signatures are minted
in one batched call per canvas visit, so a canvas of forty screens is one
round trip either way; with the cost gone, the number that makes expulsion
nearly immediate wins. `ISOCAN_CONTENT_TTL` overrides it.

**The key is a desk ledger** (`Desk.contentKey()`), minted on first ask and
create-once across concurrent callers — a Firestore transaction on
`meta/content-key`, the file desk's own write chain. A rollout runs two
instances of a home for a few seconds, and two keys would have broken half
the frames on every open tab.

**Invariant 4 needed a second mechanism.** Locally the content origin is its
own listener and "blobs and nothing else" is an enumerable route table. The
hosted origin is a Host header on the app's single Cloud Run `$PORT`, so it
is a refusal at the top of the door hook instead — before the badge is even
resolved — plus one on the WebSocket upgrade, which is hijacked off the raw
server and no Fastify hook would have reached. The predicate matches a sha256
path segment rather than any segment, and that was not caution: a shape-only
pattern let `/blobs/signed` — the *mint* route — through to an unbadged
caller on the origin that exists precisely because it carries no badge. The
invariant-4 test found it by enumerating the refusals, which is the argument
for enumerating them.

**Invariant 2 grew a third answer.** `itemFrame` may now return `null`,
meaning "the signature has not landed yet", and the web half renders the
empty card the frame would sit on. Falling back to an app-origin src for that
beat would have paired it with `allow-same-origin` — the exact whole-home
compromise the invariant exists to make unbuildable.

**The edge copy comes back.** A verified signed read is `public, max-age=<what
is left of its TTL>` — never `immutable`, because the bytes are permanent and
the URL's right to them is not. That reasoning holds only while the cache key
includes the query string, so `infra/82-content-origin.sh` sets it explicitly
rather than inheriting Cloud CDN's default: a future "include-query-string=
false" typed by somebody optimizing hit rates would be a silent, total
authorization bypass.

**The honest cost, written into the blob route's ledger in `http.ts` where
the promise it qualifies lives.** On the hosted shape expulsion reaches the
bytes *within one TTL*: an expelled badge cannot mint (immediately), and what
it already minted lives out its minutes. Both halves have a test —
`contentauth.test.ts` asserts the second as deliberately as the first,
because a documented cost that nothing tests is a claim.

**Infra:** `82-content-origin.sh` (the certificate beside the app's on the
same proxy, the host rule turning yesterday's parked 301 into a route to the
same backend, the cache-key policy), `ISOCAN_CONTENT_DOMAIN` in `config.sh`
with `isocan.store` in `prod.env`, and `70-cloud-run.sh` passing it to the
daemon as `ISOCAN_CONTENT_HOST`. That one variable turns the hosted half on —
frames move, reads sign, that Host is refused everything else — and unsetting
it is the rollback for all of it. Dev has no second domain and every one of
these does nothing there.

## Deploying it, and the four things that were in the way

The design was the easy half. Getting it onto prod took four detours, and each
one was a real defect that had been sitting there quietly.

**Main was red and nobody knew.** `docstatus.test.ts` requires every research
note owing work to name the issue that follows it; the architecture-review note
had landed `status: partial` with no `issue:`. One assertion, 348 other files
passing — and because `release.yml` only advances `green` on a green run,
`green` had been stuck **eleven commits** behind main, which had stopped
dev.isocan.io deploying, and none of it was noticed until somebody went to
promote to prod and found `green` four days stale. #185 carries the note's
remaining work; the front-matter line is what turned main green again.

Adding it made `docs/ROADMAP.md` stale, which `roadmap.test.ts` catches — so
the fix for a red main would itself have reddened main, one commit later, had
the suite not been run by hand first. That is luck, not a system, which is the
third finding below.

**Two commits of real work existed on one laptop.** Merging the content-origin
branch produced "ahead by 9" where 6 was expected. The extra two — teleport
carrying blobs, and canvas export/import — were four days old, on local `main`,
never pushed, and one `git push origin main` from reaching the trunk unreviewed
as a side effect of somebody else's deploy. Four differently-named branches all
pointed at the same stale tip, which is the signature of branches **created but
never checked out**: each session cut its branch, committed to `main` instead,
and never pushed. #186 has the story, #187 the work, and `lessons.md` the habit
it earns — `git log origin/main..main` before trusting a branch count.

The teleport commit is worth reading on its own. *A canvas naming any blob
could not move*: bytes went first, into a canvas the far home did not hold yet,
where every route 404s until `adopt` creates it — so the first upload was
refused and the move stopped, safely and uselessly. **The only teleport test
moved a blob-less canvas, which is why it was green.**

**Nothing runs on pull requests.** Every workflow here triggers on `schedule`,
`workflow_dispatch` or `push: branches: [main]` — so main is the first place
anything is ever tested, and every problem above follows from it. `pr.yml` runs
the same suite, the same emulator and the same anti-skip switch on
`pull_request`, sharing setup with `release.yml` through a composite action
rather than a comment asking two files not to drift. Advisory, not a required
check: deleting the file is the whole rollback. `lessons.md` #30 states the
shape — **ask when a check first CAN fail, not whether it exists.**

**And the infra scripts had two bugs only a real run could show.** The test for
"is this certificate already on the proxy" used `grep "…$\|…,"`, and `\|` is a
GNU extension: BSD grep, which is what macOS ships, reads it as a literal pipe,
and then the `$` stops being an anchor because it is no longer last. It passed
on Linux and failed silently on the machine the operator was using. Worse, the
re-write it caused was not harmless — `--ssl-certificates` REPLACES the list
and the replacement was a hardcoded pair, so a proxy carrying a third
certificate would have had it dropped by a script that only meant to add one.
Separately, `70-cloud-run.sh` defaults to `:latest` while the build trigger
deploys by commit sha, so re-running it to change one environment variable
could have rolled production backwards without saying so. Both fixed; the
second now prints both images and asks.

The shape those two share is worth keeping: **a control that only runs on the
maintainer's platform is not a control**, and these scripts are written on
Linux and run on a Mac.

## What the browser showed

The proof, in one attribute, off a real canvas:

```html
<iframe class="html-view"
        src="https://isocan.store/api/projects/prj_…/blobs/a9a722b…?exp=1788678125&sig=GKAz8HW…gicEA"
        sandbox="allow-scripts allow-same-origin">
  #document   <!-- DOCTYPE, html, head, body: the bytes arrived -->
```

The src left the app origin. The credential is the URL. The signature is 43
characters, which is HMAC-SHA256 in base64url and nothing else. And
`allow-same-origin` is present *because* the src is cross-origin — invariant 2
as a rendered attribute rather than an argument. The `exp` decoded to three
minutes and sixteen seconds in the future, which is the whole answer to the
23 August ledger's objection to a token in a URL: a durable token is a
credential where people paste, and this one is not durable.


## The switcher: the launcher's second face

Going to another canvas meant the home screen: the `⌂`, a scroll, a click.
Right for choosing, and a tax when you already know where you are going —
which, nearly always, is the canvas you were on ten minutes ago.

**One window, two faces.** The ⌘K palette now carries a `mode`:
`commands` is the launcher it was; `canvases` is a list of canvases with a
field over it. `uiStore.paletteOpen` went from a boolean to
`PaletteMode | null` so that one state says both whether the window is open
and which face it wears. It is one component rather than a second dialog
because it is the same gesture — a field, a list, Enter — and a second
modal over the first would have had to answer which of two Escapes closes
what. Backspace on an empty field steps back to the commands.

**Three doors.** `⌘O` (it crosses a cover like ⌘K does: leaving is the one
act that makes sense whatever is covering the canvas, and it acts on
nothing here); the "Switch canvas…" row in ⌘K, which flips the window
rather than closing it — closing first would have unmounted the palette and
mounted a new one, a flash and a lost keystroke; and a `⌄` beside the
canvas's name in the bar, the shape every app with several documents uses
for "the others are under here", and the one entry point that needs no key
to be found. The commands face also finds a canvas on its own: type a
title and up to five matches appear under the actions as "Switch to", so
the common trip is ⌘K, three letters, Enter, with no mode to know about.

**Lately first.** The list leads with the canvases this browser was on,
most recent first, then everything else by activity — the home screen's
default order, so it is the one already learned. "Lately" is a fact only
the browser knows (the daemon sees writes, not visits, and a canvas read
for an hour without a change is exactly the kind you come back to), so it
is `localStorage` (`lib/recents.ts`, `isocan.canvases.recent`, twenty
rows, title riding along). The title is why the list paints before
`GET /api/projects` answers, and why it paints at all when it never does:
offline, the recents are the whole list, and every one opens from the
replica. The fetch is the home screen's own `listCanvases()` — the canvases
this origin is the home of — for the same reason the home screen narrows:
a client-side navigation never asks the server, and a row for a canvas
homed elsewhere would open a stale local copy of it (phase 10.3).

**Fuzzy, where the launcher deliberately is not.** The launcher matches
whole terms, because a matcher that scores letters anywhere is how a
palette starts offering "Delete everything" for "de". That rule is about
what a wrong match DOES. Switching canvases does nothing to any of them and
Back undoes it, so here the trade goes the other way: `fuzzyMatch` in
`core/canvasswitch.ts` takes the letters in order from anywhere, and the
scoring still prefers the certain reading — letters together, letters that
start words, a prefix — so among titles that all contain the letters the
obvious one comes first. `rankCanvases` is in core because it is pure
logic a test can hold still, and because the terminal could show the same
order tomorrow; it does not today, and deliberately: an agent switches
canvases by naming one, so a viewport gesture gets no verb.

**A move rather than a cut.** The route element is the same `CanvasPage`
for every canvas, so without anything the surface was simply replaced
between one frame and the next, which reads as the page breaking and then
fixing itself. `lib/canvasswitch.ts` sets `switching: "out"`, waits 140ms
for the surface to recede, navigates, sets `"in"` for 220ms while the next
canvas comes forward from a touch larger. The class is on `.canvas-surface`
— the viewport's wrapper — and not on the page, because the bar and the
rail are the same chrome on both canvases and chrome that lurched would
say the app reloaded. Under `prefers-reduced-motion` the keyframes are off
AND the wait is skipped: a person who asked for no motion should not be
asked to wait for motion they cannot see. A test holds the CSS durations
to the helper's constants.

**Two things corrected on the way.** The `?` panel's ⌘K row still said
"Message your emissary from anywhere", which had not been true since ⌘K
became the launcher; it now says what the launcher does. And the accent
guard caught the first draft of the highlight painting text in `--accent`
(2.5:1 on graphite); it is `--accent-text`, as every other accent-coloured
word is.

Tests: `core/test/canvasswitch.test.ts` (the matcher's preferences, the
ranking, the tiebreaks, the highlight runs) and `web/test/switcher.test.ts`
(the recents rule, the three doors open one window, the key the palette
prints is the key the help panel prints, the durations agree, the surface
moves and the chrome does not).

## The plan behind the switcher, and every open note gets an issue

and was corrected the same afternoon:

## Working the architecture review: three steps, and one that changed shape

[`research/2026-09-06-architecture-review.md`](../research/2026-09-06-architecture-review.md)
verified an outside review item by item and left a nine-step plan. Steps 2, 3
and 7 are done.

**2 — the bundle bound can redden a commit now.** The nightly said MISSED
three nights running and CI said nothing, so the entry chunk drifted about a
hundred kilobytes past the 640,000 bound as a hundred unremarked commits.
`test/bundle-budget.test.ts` reads it in the ordinary suite, through
`scripts/measure.mjs` rather than a second copy of the measurement.

It is deliberately a **ratchet, not the bound**: the chunk is 725,291 against
a goal of 640,000, so asserting the goal would redden main from the moment it
landed — a red trunk rather than a guard, and this repository had just spent a
morning on what a red trunk costs. The assertion is "no bigger than the last
number somebody agreed to", the distance to the goal is printed on every run,
and raising `CEILING` is one line in a diff with a reason beside it.

**And it measures the build without ever making one**, which took two goes.
The first version built when `dist` was stale — reasonable, until it built
*from inside a parallel suite* and reported **1,093,766** for a tree that
produces 725,291. Four other test files read `packages/web/dist`; a test that
rebuilds a shared artifact mid-run is not measuring, it is racing everybody
else, and the number it invented was fifty per cent wrong in the alarming
direction, which is how a guard teaches people to ignore it. Missing or stale
is now a loud SKIP naming the command, and `ISOCAN_REQUIRE_BUNDLE=1` — set in
both workflows — turns that skip into a failure. The `ISOCAN_REQUIRE_EMULATOR`
shape, for the same reason: a contributor may have a green run that says what
it did not check; CI may not.

**3 — `formatBytes` to core, and the terabyte it had already lost.** Two
copies, and the review's argument was duplication; the better argument is that
they had already drifted. The CLI's unit list ran to terabytes and the web's
stopped at gigabytes, so a large enough trash panel would have said "1024 GB".
`core/bytes.ts` now holds it — beside `elapsed.ts` and *not* in `format.ts`,
which is the canvas tidy, and a size is not a layout. The CLI re-exports it
from `output.ts` so `main.ts`'s import list is untouched. The test leads with
the terabyte, and a guard names the two files that used to hold a copy each,
so a re-introduction is caught where it happened.

**7 — the roadmap test did not need a longer timeout; it needed its cause
removed.** The review is right that `roadmap.test.ts` killed its child at 60s
inside a test allowing 120s, and raising the child would have made it pass.
The question that does not ask is *why a script reading front matter out of 62
markdown files needs a minute.* `scripts/roadmap.mjs` was spawning the whole
CLI once per document — and every spawn registers tsx and transpiles
`main.ts`'s 11,818 lines plus core, api and server before it reads a single
`---`. Measured: 571ms a spawn, 62 documents, **~35 seconds**, the slowest
file in the suite by an order of magnitude, paid on every run.

It registers tsx once and imports `docStatus` directly now: **0.42s for the
whole script**, and the test file 35s → 1.8s. The "one reader" invariant is
untouched, because the reader was never the CLI — it was `docStatus`, reached
through eleven thousand lines of command definitions that have nothing to do
with front matter.

**The guard is the part worth keeping** (lesson #31). It used to assert that
`doc", "status"` appeared in the script — the *mechanism*, not the invariant —
which is what made 35 seconds a thing the suite required, and why the review's
recommendation was to raise the timeout rather than to look at it. Lesson #4
is a test written around the keystroke catching nothing; this is its other
half, a test catching the right thing and freezing the wrong thing doing it.
The assertion is now the property (core is the one reader; no second parser
here), plus what a textual check cannot say at all: that the roadmap and
`isocan doc status` **agree about a document** — one spawn instead of 62.

## Three board tests were failing for a reason none of them is about

Found while running the suite for the roadmap change, and unrelated to it.

`canvas-board.mjs` exits 1 to **report** an instrument that would not run —
deliberately, and documented at its last line: a board that goes red every
morning on a missed goal trains everybody to stop looking, so a number nobody
could take is the one thing it must never render as fine. `execFileSync`
throws on any non-zero exit. So on a machine where the accessibility and
design-auditor instruments are unavailable, all three Build-signal tests
failed with `Command failed: node …/canvas-board.mjs` — naming neither the
amber panel nor the fact that nothing was wrong with the Build panel. Every
panel had rendered; the HTML was sitting in the exception's `stdout`.

**And the second failure was hiding behind the first** (lesson #32). With the
exit code read as the verdict it is, the NO-SIGNAL test finally reached its
assertion — and failed: it pinned the headline word, which `signal()` folds
the board's own readings into, on a fixture that controls only `gh`. That is
the identical coupling the sibling test's comment already warns about
("pinning it would have coupled this test to board state on disk that no
fixture here controls"), unnoticed for as long as the throw stood in front of
it. A test failing for the wrong reason has not evaluated its right one.

The board itself is correct and stays as it is: `RED` outranks `NO SIGNAL`
when an instrument is broken, because a broken instrument is something the
board *knows*, and a second unknown must not soften a certainty to grey. What
changed is the test — it asserts the CI line, which `c.unknown` alone drives
and the fixture therefore controls, plus the rule the light exists for: never
GREEN, and never AMBER either, since nothing was asked. Two mutations killed
(a `signal()` that goes green when blind, a CI line that renders absence as
"all good").

## Extensions stages 1 and 2: a canvas that carries its own buttons

[`projects/extensions/design.md`](../projects/extensions/design.md) has been
`designed` since 29 August. Stages 1 and 2 are built, and the whole thing turns
on one sentence that the code is an application of:

> **An extension may only ask for what a person could ask for.**

Not "an extension runs in a sandbox" — sandboxes are a mitigation, this is a
model. Every mutation here is an `Operation` applied by one reducer and
attributed to an actor, so an extension whose requests go through the same door
as everybody else's can at worst do what a collaborator could do, which is a
thing this system already knows how to see, attribute, undo and revoke.

**A tool is an item.** `role=tool`, the same move `role=design-system` already
makes, and that is not a saving of effort — it is what the tool *gets*:
versions (a bad one rolls back with `S`), per-actor undo, comments, trash and
restore, and `isocan add rail.json --prop role=tool` for free. Plus the part
that is actually new: **a canvas carries its own UI.** Open somebody's canvas
and their tool is on the rail, because the tool is on the canvas. Nothing was
installed. No new operation, no new route, no new store — and the CLI test
proves that the honest way, by asserting `isocan ls` sees a tool as an ordinary
item and `rm` takes it off the rail.

```json
{ "kind": "tool", "label": "Tidy", "icon": "broom", "does": "/format" }
```

**The rules are enforced where they are stated**, in `core/extensions.ts`, and
both surfaces call the same reader — so a manifest the terminal refuses is one
the rail refuses, with the same sentence, and the refusal names the field
rather than saying "invalid manifest". `does` must name a command this canvas
actually has. The icon comes from a closed set, which is a security decision
rather than a style one: an icon is a place somebody would otherwise paint
anything at all, including a convincing copy of a control that already exists.
And the label may not be one of the app's own tools — compared with case and
punctuation flattened, because a check that only catches the exact string is a
check that catches nobody who is actually trying.

**Pressing one posts the ask**, through `postToMain` — the same door the
composer and ⌘K use. A guard forbids the rail sending an operation of its own,
because that is the one failure that would look completely fine from the
outside: a button that "just does it" is an extension acting directly, which is
precisely what the model forbids.

**Stage 2 arrives with stage 1, for the reason the design gives** — *the habit
has to exist before the tier that depends on it.* `isocan tool add` prints
everything the tool may do and adds nothing until `--yes`, the gate
`command add --from` already has. The list is **derived, never declared**: a
manifest that stated its own capabilities could understate them.

Stages 3 (declarative panels — and only once two real tools have asked for the
same shape), 4 (extension actors) and 5 (hosted panels, whose gate the content
origin cleared this morning) are not built.

## Dragging a JSON file onto a canvas had never worked

Found by the above, which is the first code in the repo to upload a blob with a
deliberate media type.

`addContentTypeParser("*", { parseAs: "buffer" })` is commented *"Raw bodies for
blob uploads; JSON stays JSON"*, and `"*"` does not mean every type — it means
every type Fastify does not already have a parser for, and it has one for
`application/json`. So a blob whose media type IS JSON was parsed into an
object before the route saw it, `Buffer.isBuffer` said no, and the upload was
refused with **`empty blob body`** — a message about a body that was neither
empty nor wrong, which is the kind of refusal nobody traces to its real cause.

It was invisible from the terminal: `.json` is not in the CLI's mime table, so
those files fall through to `application/octet-stream` and upload fine. It was
live in every browser, because `mimeTypeOf` prefers `file.type` and a browser
reports `application/json` for a `.json` file. **On every deployment, for as
long as the drop path has existed.**

The fix is an encapsulated Fastify scope holding its own parser for that one
route — replacing it on the root app would take the body away from every API
route, all of which are JSON. `blobs.test.ts` guards four things: the type
round-trips, the bytes come back **byte-identical** (spaced JSON on purpose, so
a parse-and-re-serialise still in the path shows up as a changed length rather
than passing), a genuinely empty body still gets its 400, and `/api/ops` is
still JSON. Three of the four die when the scoped parser is removed, the
negative control included. Lesson #33: after registering a catch-all, list what
the framework already claims and check each one against it — and read a refusal
that names a condition as a claim to verify, not a description to trust.

## Two more from the review: one table, and an invariant that had stopped being true

**4 — the mime table and `defaultSize` to core, keeping two entry points.**
The review read the web's five extensions as an incomplete copy of the CLI's
fourteen and proposed one canonical `mimeFor`. That would have been a
regression dressed as tidying: `mimeFor(filename)` has only an extension to go
on, while `mimeTypeOf(file)` already holds `file.type` and reaches for a table
only as a patch — a browser gets `image/png` right and `.md` wrong. What was
genuinely duplicated is the table, the ORDER it is consulted in (a loaded
module's extensions first, then the table — two copies of that is how one
surface keeps calling a file a diagram after the other has stopped), and
`defaultSize`, which was three number pairs written out twice.

`core/media.ts` holds all three. `mimeFromName` answers **`undefined` rather
than a default**, which is exactly what lets the entry points stay two: the CLI
falls back to `application/octet-stream`, the browser still has `file.type`.
The web now sees all fourteen rows rather than the five, which is not the dead
weight it looks like — the table is reached only when the browser declined to
say, so extra rows can only improve that answer and can never override one it
gave. `media.test.ts` names the three files that each held a copy.

**5 — the cloud desk's invariant had stopped being true, without breaking.**
`cloud-desk.ts` promised *"nothing writes a badge except `writeBadge`"*, and by
September `mutate`, `killBadge` and the claim transaction had each grown a
`tx.set` of their own: four write sites where the sentence said one. The
invariant held — all four pass through `denormalize()`, and `touch` merges only
`lastSeen`, which is not one of the arrays. **Its statement had broken**, which
is worse than an ordinary stale comment, because the sentence went on to tell a
reviewer that their whole job on the file was to confirm there is one writer.
Anybody doing that job would conclude the file was broken — or, having
satisfied themselves it was fine, add a fifth writer by yet another path.

What is at stake is phase 3's warning: `claimIds`, `claimKeys`, `admittedTo`
and `attested` are `array-contains` queries here and a whole-table scan
everywhere else, so a badge written around `denormalize` **passes the entire
suite on a FileDesk and answers nothing in the cloud**.

So the comment says what is true and says out loud that it used to say
something else, and the rule got a guard instead of a request.
`cloud-desk-writers.test.ts` reads the source, resolves each `.set(` to the
collection it targets — chained, `tx.set(ref, …)` and plain receiver, all three
shapes — and requires `denormalize` on every badge write with the `lastSeen`
merge as the one named exception. Deliberately **not** in
`cloud-desk-arrays.test.ts`, which needs a Firestore emulator and so does not
run on most machines or most pull requests: a guard that catches a fifth writer
has to run where the fifth writer is written. Anything it cannot classify comes
back as unresolved and **fails** rather than passing as "not a badge write" —
the first version silently missed the chained
`collection(BADGES).doc(id).set(…)` altogether, which is a guard reporting
green about code it never looked at. Three mutations killed, including aliasing
the ref to a new name to dodge it.

## The last two review steps, and the one the review undersold

**6 — a list of ABSENCES rots quietly, because nothing fails.**
`architecture.md`'s "Distance to the map" said the Share dialog and the grant
routes were unbuilt for the three weeks after phase 14 built them. The dispatch
path on the same line is built too; `registrations/{id}` really is not, and now
stands alone. This is the shape the roadmap exists to end for a document's
status, one level along: a fact kept by hand beside a thing that moves.

Each bullet now says how it would be checked, and `test/architecture.test.ts`
checks the two that can be — no client mentions `MAX_DIRECT_UPLOAD_BYTES`, and
nothing queues blob bytes offline. Build either and the suite asks for the doc
in the same commit. The rest carry their reasoning instead, because "queueing
bytes offline is a second durable store with its own eviction story" is a
design position and not a grep. Both guards mutation-tested.

**8 — the review said "49 unused exports, not 47". The finding is worse than
that.** `.agents/personas/reviewer.md` has said **`at most: 0`** since 2
September, with the reasoning written out beside it: *"a ratchet set above its
floor is slack nobody decided to leave. The next one fails on the commit that
adds it, which is the whole point."*

Four days later it measured **56**. The ratchet was at its floor, the principle
was on the page, and fifty-six arrived anyway — because only the nightly ever
read the number, and a nightly report is not a commit failing. **That is
exactly this morning's bundle finding, on a second metric**, which is what
turns it from an incident into a pattern: a bound nothing enforces is a
comment.

`test/unused-exports.test.ts` measures it in the ordinary suite now, through
the same `scripts/measure.mjs` the persona declares rather than a second copy
of the scan. 56 → 39 by un-exporting every server and web `lib/` name on the

confirmed each one.

**The 39 that remain are all in `packages/core/src`, and that is a different
question rather than a smaller one.** Core is what a runtime module is handed
at load, so deleting from it decides what `@isocan/core` promises a module
author: `ModuleEdge`, `ModuleActionFacts` and the DTCG token types look exactly
like surface somebody would build against, and an unused export in a published
package is not the same fact as one in a private package. That decision wants a

about something else. The drift is not left: 39 is the line, the fortieth

With this the review's plan is done except step 1 (the entry chunk, where
splitting is spent) and step 9 (the monoliths, to be split opportunistically
rather than in one move).

## A guard that had been sitting on an unmerged branch for twelve days

`packages/web/test/themes.test.ts` was written on 24 August, against a real
class of defect: **a colour held in an SVG presentation attribute takes no
`var()`**, so no theme can move it, and no test that reads `styles.css` can see
it. Its branch never merged. From `main`'s point of view a branch with a real
guard on it and a branch with nothing on it look the same — and by September
that diff had drifted too far to merge, so the guard had quietly become a thing
somebody once wrote (lesson #34).

Recovered today, it found **four live literals on `main`**: both cursors
outlined `#fff` — the panel colour in light, a hard halo on graphite — and the
minimap's follow ring and viewport rectangle in the *light* accent, measured
2.25:1 against the dark panel. All four are classes coloured in the stylesheet
now, so the tokens test can see them too.

**And it needed a matcher it never had.** It looked for a hex after `stroke=`
with no quote in between, which catches `stroke="#fff"` and is blind to
`stroke={followed ? "#1f3fd0" : "#fff"}` — the colours there live inside quotes
inside braces. Three of four, reporting clean about the one line carrying two
of them. That is lesson #27 again (a check that enumerates the forms of a
defect has to enumerate all of them), and the reason the recovery re-derived
the finding rather than trusting the branch's own count. Both passes
mutation-tested.

**What is deliberately not salvaged.** The branch's other half re-values how an
identity colour is turned into ink — `--identity-mix`, a different percentage
per theme — because as a WORD the seven-colour palette clears 3:1 but not
4.5:1: Violet measured 2.75:1 on graphite, and on vellum all seven measured
3.11–4.22:1 inside a `.mention-me` chip, whose background is a 24% wash of the
very colour written on it. That is a real accessibility defect and the branch's
arithmetic looks right, but landing it changes the text colour of every cursor
chip and every mention on both themes, and nobody has looked at the result. It
is left as a decision with its numbers written down rather than made in a
commit about something else.

## Extension actors: the gate moved its own dependency into view

Named as a priority alongside the architecture work, and building extensions
stages 1 and 2 answered it in a way that is worth writing down: **stage 4 has
no subject yet.**

A tier-1 tool does not act, it asks. Pressing one posts the slash command the
person would have typed, under that person's actor, and the acting is done by
whatever agent picks the comment up — already attributed, already undoable per
actor, already revocable by the desk. Giving the tool its own actor there would
make the log say the Tidy button asked for something, when what happened is
that a person asked for it with one click instead of eight keystrokes. A worse
record, not a better one.

The subject appears at tier 2 and 3, where a panel acts on its own, and becomes
load-bearing at tier 3, where the panel is somebody else's code. So stage 4's
real predecessor is **a panel that acts** rather than a place in the queue —
and building the desk wiring first would be machinery with nothing to
attribute, tested only against a fixture, which is precisely what this design
forbids about panel fields: *added when two real extensions need it, never
because one might.*

This matters beyond the extensions project, because extension actors is one of
the three named gates on modules phase 5 (sandboxes). Of those three: the
content origin **cleared** this morning, extension actors turns out to wait on
extensions stage 3 rather than on anyone's calendar, and compute consent is
untouched. One gate moved; the second moved its own dependency into view.

## The CI fix went red on the first pull request that ran it

`pr.yml` — added this morning so the suite stops meeting main first (lesson
#30) — failed on PR #193, and the cause is a sequel to its own lesson.

It shares node, Java, the emulator and `npm ci` with `release.yml` through a
composite action, deliberately, with a comment saying the drift that matters is
these two files falling out of step. **A checkout cannot live in a composite
action**, so it was the single step that could not be shared. `release.yml` has
`fetch-depth: 0` with a reason written beside it — it pushes a release commit
naming two parents by sha, and a shallow clone cannot push a history it does
not have. That reason is true and is not the suite's: **the suite reads git
history too**, because `changelog.test.ts` drives `changelog-day.mjs`, which
asks `git log` what landed on a day. `actions/checkout` defaults to depth 1, so
the earliest changelog day had no commits in view and the generator answered
"nothing landed" where the test expects "already written".

So a reader checking whether the setting was needed would find a reason that
did not apply and conclude, correctly from the comment and wrongly in fact,
that it could be left off. Reproduced in a real `--depth 1` clone before
fixing: 1 commit visible says "nothing landed", 802 says "already written".

`pr.yml` gets `fetch-depth: 0` with the suite's own reason beside it, and
`test/workflows.test.ts` asserts every workflow that runs vitest checks out
full history — finding them by reading the files rather than listing them, so a
third one is covered without anybody remembering. Lesson #35: after
deduplicating two files, enumerate what the mechanism could not carry and
assert each one.
