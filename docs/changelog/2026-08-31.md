# 31 August 2026 — Agent custody, and a slide deck

Two issues from live-testing the web tray, one gap between them, and a
design call that made most of the mechanism unnecessary.

**The finding (#83, #81).** An agent added from the web tray on a
dev-homed canvas worked invisibly: the rc on the laptop ran its turns,
but the home dropped its face on every relay. The mechanism was correct
at every step and wrong in composition — the web dialog claimed the
agent's actor on the *browser's* cookie badge, and when the laptop's
daemon later relayed the agent's face, that was a different badge asking
to speak as the same actor. The desk's one-actor-two-faces refusal is a
security posture, so the drop was silent by design. Beside it, the
liveness half: "answerable" is a connection-bound fact an rc asserts by
holding `/api/rc/hold` open — against its *local* daemon, and holds
never travelled, so the home's answer was empty forever and the Web UI
read every standing agent as "nobody listening". And the "＋ Add an
agent" button stood for people with no rc anywhere, doing — from their
side — nothing. Each ingredient was tested alone and correct; the
composition fell between the suites.

**The design, and the reversal inside it.** The first draft built a
desk-side hand-off: the enroll op as the sponsor's word, written as a
keyless row the relaying badge's claim would redeem. The user's call
replaced it with something smaller: **don't offer the button until the
handshake is possible.** No "＋ Add an agent" without a visible rc —
for people who don't use `isocan rc` the button was only ever weird —
and with one visible, enrolment becomes an *ask addressed to the
machine that will answer*. The rc makes the same two moves `isocan
agent add` makes, so the actor is born first-claim on the badge that
relays its face, the records become indistinguishable from CLI
enrolment at the desk too, and #83 dissolves rather than being patched.
The identity desk changed not at all. The hand-off row is recorded in
`docs/projects/agent-custody/design.md` as set aside, not refuted — it
is what an enroll-with-no-rc invitation flow would need, if that ever
becomes worth offering.

**The build.** The inline hold map in `http.ts` grew into
`server/src/rc-holds.ts`: local holds (the connection is the fact,
unchanged) plus mirrors of what member daemons relay. A daemon now
sends `rc-relay` up the home-link beside the faces — connection-bound
at every hop, so home-side answerability dies the instant the laptop's
socket does — and the home believes a hold only about ids that are both
enrolled agents on the canvas and vouchable by the relaying badge: a
hold shouting an arbitrary id relays nothing. The ask rides the
channels that already existed: `POST /api/projects/:id/agents/ask`
finds an open local hold or sends `rc-ask` down the mirroring socket,
and the rc receives it *inside its own hold's response* — the long-poll
it was already re-issuing back-to-back. A fifteen-second queue covers
the microsecond gap between holds. The asker is checked the way an op's
actor is: the rc narrates "«from» asked to add …", and those words must
not be puttable in someone else's mouth. On the web, the dialog gates
on `useRcParked`, sends a name, watches for the enroll op to land in
the roster, and has a twenty-five-second countdown that fails out loud
— because a name already worn is refused at the rc's claim, and from
the dialog that can only look like silence.

**Two guards had frozen the old design.** The tray's tests asserted the
dialog's claim-then-enroll as "the CLI's exact moves" — true in the
oplog, false at the desk — and derived the rc line from the presence
announcement's TTL. Both were rewritten to freeze the new facts, each
carrying the history of why.

**And one line of housekeeping with teeth:** `innkeeper.md` now opens
by saying it is a record, not a living document — the multiuser project
is complete, and new design work (this project included) starts in a
new document that cites the records rather than editing them. Stated in
the doc because an agent picking up #83 had to be told.

## The slide deck (#87)

The issue asked for a way to mark items "presentable" and a special URL
that shows the canvas as a slide deck. Most of it already existed: full
screen is an address, ⌘-arrows already flip it item to item, and the
chrome already rests while you present. What was missing was three
things, and none of them is a new mechanism.

**The flag is a property.** `core/src/slides.ts` is `contextmark.ts`'s
shape again: one key (`slide`), `item.update` carries it, zero new op
types. The issue's comment suggested an emoji as the mark, and the
obvious candidate — a reaction — was considered and rejected for a
per-item fact: a reaction belongs to the actor who left it, so nobody
else could take a slide out of the deck. The emoji survives as the
*face* of the property: marked items wear 🎬 in their title row, because
a deck you cannot see is a deck you cannot arrange.

**Bare arrows flip the deck, linearly.** ⌘-arrows stay spatial over
everything; bare arrows (and Page Up/Down, so a presenter's clicker
works) walk `deckStep` — the marked slides in reading order, or every
item with none marked, so the feature works before anyone sets it up.
Linear rather than spatial on purpose: a presenter at the end of a row
pressing → must land on the next row's first slide, not on the edge.
Reading order is geometry — rows top to bottom, left to right, ties by
id per the `canvassort` rule — so there is no slide number to maintain
and none to drift.

**The special URL is the URL there already was.** Full screen is a
route; the deck's address is the first slide's full-screen link.
`isocan slides show` prints the running order and that address;
`slides add|rm` mark and unmark. Guide, quick reference, README, help
panel, and guards in `slides.test.ts` (core) and `slideshow.test.ts`
(web) all landed with it. The keystroke behaviour is harness-blocked as
ever, so the flip was checked by hand — on isocan.io, on a real deck,
the same day it shipped.

## Read-only access: the roles question, answered by the deck (#88)

The deck made the gap concrete: sharing a presentation link meant sharing
the power to rearrange the canvas. `identity-desk.md` had left roles
open on purpose — *"the journey never played a read-only member, so that
waits for a scene that forces it"* — and #87 was the scene.

**The answer is two words, not a matrix.** A grant may carry
`capability: "edit" | "view"`, absent meaning `edit` everywhere, so every
grant row and every admission written before the field keeps its meaning
and no migration runs. The Share dialog's link row grows a "Can edit /
Can view" choice; `isocan share --link view` is the same gesture from
the terminal; both drive the same `POST /grants`, which replaces a
standing link of the other capability in one call.

**The admission carries the copy that gets enforced.** The door test
short-circuits on `canvasId ∈ admissions` and never consults the grant
again, so `admittingGrant`'s winner writes its capability onto the
admission (`Admission.capability`, view-only-when-narrowing, both desk
backings). Enforcement is server-side at the two places every write
already passes: the `onRequest` hook refuses any non-GET canvas-scoped
request from a view admission — undo, blobs, gc, grants, passes,
sessions, and whatever route lands next month, covered by default — and
`/api/ops` (its canvas travels in the body) takes the same test by hand,
before the submit, for the door's own reason: a refusal after the op has
landed is not a refusal. The refusal is 403 `view-only`, its own code,
because "go to the door" and "ask for the link" are both wrong remedies
for somebody who is badged and admitted.

**Three consequences fell out of existing machinery rather than being
built.** Replacing the edit link with a view link demotes the people
already inside instead of expelling them — the replacement tombstones the
old row, writes the new one first, and lets phase 9's sweep re-root
everybody onto it at its capability. The same sweep runs the other
direction, so `--link on` promotes them back. And a view admission
re-asks the door per request (`heldCapability`), so proving your email
after entering by a view link lets the invitation that names you take
effect — the one place the short-circuit had to be softened, paid only by
viewers.

**What a viewer actually sees is the deck, not a disarmed canvas.** A
view badge at any address of the canvas gets the viewer face
(`Viewer.tsx`): the current slide full screen, arrows and Page Up/Down to
flip, a resting bar with a `1 / 3` counter, no exit into editing chrome —
deliberately not `CanvasPage` with controls filed off, because a surface
built from editing chrome hidden one flag at a time is a surface where
the next panel forgets the flag. Nobody is asked their name: a stranger
at a canvas address now meets a gate that asks the home "may this badge
only look?" before the identity dialog (one snapshot GET — the same
request that admits the badge), and a viewer has nothing a name would
attach to. The capability rides the socket hello and the snapshot
response, present only when it narrows, so pre-field clients read the
hello they always read. A view socket's presence beats are dropped
server-side; the viewer client sends none.

Guards in `view-only.test.ts` (ten cases: the read that says `view`, the
write refused before it lands, the hook's coverage list, the creator
outranking the link, the socket hello, both directions of the replace
sweep, the upgrade re-ask). Checked by hand against a real daemon in
Chrome the same day: stranger path, named-visitor path, the Share
dialog's choice, and the self-demotion of the tab that flips its own
link to view.

**And the bug that shipped with it, found by the user within the hour.**
On isocan.io, "Can view" answered 200 and stayed "Can edit". The write
was fine; `CloudDesk.toGrant` rebuilds grant rows field-by-field and
dropped `capability` on every READ — so the flag sat in Firestore while
the door, the dialog and the sweep all saw `edit`. The file desk stores
rows whole, which is why the whole suite and the real-browser walk
passed. Fix is one spread in `toGrant`; the guard is a round-trip
assertion in `desk-conformance.ts`, which runs against both backings —
and lessons.md #24 now names the shape: when a type grows a field, grep
the backings for functions that rebuild that type field-by-field.

## The deck flip pushes (#87 follow-up)

A flip was an instant cut; now the new slide pushes in from the side the
key named while the old one recedes a quarter of the way, scales down a
touch, and fades — 220ms, hard ease-out. The direction is the content:
the motion answers "which way did I go".

**The mechanism is a view transition, and that choice is the whole
trick.** A slide is a live sandboxed iframe; any hand-rolled crossfade
means two mounted at once — scripts running twice, and a reload flash in
view. `document.startViewTransition` animates the outgoing slide as a
browser-painted snapshot instead, wrapped around a `flushSync`'d
navigate (declarative router, no loaders, so the DOM settles inside the
callback). `lib/deckflip.ts` owns it, shared by `FullScreen` and
`Viewer` so the two faces of the deck cannot flip differently;
`data-flip` on the root tells the CSS the direction, and the `root`
group's default cross-fade is switched off under that scope so the bar
stays pinned.

**The rule that keeps it from being annoying:** a flip within 300ms of
the last is a cut, not a push — hammering → to reach slide 14 stays
instant. So do browsers without view transitions and anyone asking for
reduced motion, both decided in the JS before any snapshot is taken.
⌘-arrows stay instant on purpose: that is the spatial walk, not the
deck. One casualty en route: `oneblock.test.ts` refused a second bare
`.fullscreen-stage` rule, which is exactly what it is for — the
`view-transition-name` moved into the existing block.
