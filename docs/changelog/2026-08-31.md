# 31 August 2026 — Agent custody

Two issues from live-testing the web tray, one gap between them, and a
design call that made most of the mechanism unnecessary.

**The finding (#83, #81).** An agent added from the web tray on a
dev-homed canvas worked invisibly: the rc on the laptop ran its turns,
but the home dropped its face on every relay. The mechanism was correct
at every step and wrong in composition — the web dialog claimed the
agent's actor on the *browser's* cookie badge, and when the laptop's
daemon later relayed the agent's face, that was a different badge asking
to speak as the same actor. The desk's one-actor-two-faces refusal is a
security posture, so the drop was silent by design. Beside it, the
liveness half: "answerable" is a connection-bound fact an rc asserts by
holding `/api/rc/hold` open — against its *local* daemon, and holds
never travelled, so the home's answer was empty forever and the Web UI
read every standing agent as "nobody listening". And the "＋ Add an
agent" button stood for people with no rc anywhere, doing — from their
side — nothing. Each ingredient was tested alone and correct; the
composition fell between the suites.

**The design, and the reversal inside it.** The first draft built a
desk-side hand-off: the enroll op as the sponsor's word, written as a
keyless row the relaying badge's claim would redeem. The user's call
replaced it with something smaller: **don't offer the button until the
handshake is possible.** No "＋ Add an agent" without a visible rc —
for people who don't use `isocan rc` the button was only ever weird —
and with one visible, enrolment becomes an *ask addressed to the
machine that will answer*. The rc makes the same two moves `isocan
agent add` makes, so the actor is born first-claim on the badge that
relays its face, the records become indistinguishable from CLI
enrolment at the desk too, and #83 dissolves rather than being patched.
The identity desk changed not at all. The hand-off row is recorded in
`docs/projects/agent-custody/design.md` as set aside, not refuted — it
is what an enroll-with-no-rc invitation flow would need, if that ever
becomes worth offering.

**The build.** The inline hold map in `http.ts` grew into
`server/src/rc-holds.ts`: local holds (the connection is the fact,
unchanged) plus mirrors of what member daemons relay. A daemon now
sends `rc-relay` up the home-link beside the faces — connection-bound
at every hop, so home-side answerability dies the instant the laptop's
socket does — and the home believes a hold only about ids that are both
enrolled agents on the canvas and vouchable by the relaying badge: a
hold shouting an arbitrary id relays nothing. The ask rides the
channels that already existed: `POST /api/projects/:id/agents/ask`
finds an open local hold or sends `rc-ask` down the mirroring socket,
and the rc receives it *inside its own hold's response* — the long-poll
it was already re-issuing back-to-back. A fifteen-second queue covers
the microsecond gap between holds. The asker is checked the way an op's
actor is: the rc narrates "«from» asked to add …", and those words must
not be puttable in someone else's mouth. On the web, the dialog gates
on `useRcParked`, sends a name, watches for the enroll op to land in
the roster, and has a twenty-five-second countdown that fails out loud
— because a name already worn is refused at the rc's claim, and from
the dialog that can only look like silence.

**Two guards had frozen the old design.** The tray's tests asserted the
dialog's claim-then-enroll as "the CLI's exact moves" — true in the
oplog, false at the desk — and derived the rc line from the presence
announcement's TTL. Both were rewritten to freeze the new facts, each
carrying the history of why.

**And one line of housekeeping with teeth:** `innkeeper.md` now opens
by saying it is a record, not a living document — the multiuser project
is complete, and new design work (this project included) starts in a
new document that cites the records rather than editing them. Stated in
the doc because an agent picking up #83 had to be told.
