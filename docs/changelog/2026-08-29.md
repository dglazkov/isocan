# 29 August 2026

Phase 11, most of the way: a machine can now work a canvas with **no daemon at
all**. And along the way, two decisions worth more than the code — what the
switch is called, and the question of which way it should point by default.

## The switch is called `--direct`, not `--thin`

The journey has called this seat "thin" since Scene 6 was written, and that word
is fine in prose about a topology. As a flag it tells somebody who has not read
the journey nothing about what will happen. What the switch actually means is
*do not stand up a local daemon or replica here; commands talk to the home
itself* — so it is `--direct`, `ISOCAN_DIRECT`, and a `direct` key in
`config.json`, one spelling across all three surfaces.

The alternative that nearly won was `--no-daemon`, which is more literal and
matches `setup`'s existing `--no-install` and `--no-open`. It lost on the other
two surfaces: `ISOCAN_NO_DAEMON=1` and `{"noDaemon": true}` are both negative
names, and a setting whose natural spelling is a double negative is one people
get wrong. "thin/thick" stays in the journey as the name of a seat.

## No provider is named in the code, on purpose

The obvious way to build "setup notices what it stands on" is to sniff for the
cloud you expect to be running in. That is wrong here, and not only for taste:
**direct-versus-daemon is a property of the directory, not the vendor.** A CI
runner is disposable; a cloud development workspace has disk and persists for
days and would reasonably want a daemon; a headless box in a closet wants one
like any laptop. A table of vendor fingerprints gets half of them wrong.

So the shape is `harness.ts`'s, for `harness.ts`'s reason — a table isocan
happens to know, a `config.json` hook so an environment isocan has never heard
of works the day it ships, and an environment variable that beats both. The
built-in table has exactly **one** entry, `CI`, because that one probe covers
every continuous-integration system worth covering and nothing else can be
guessed on somebody else's behalf. Anyone else adds a line of
`{"ephemeralVars": [...]}` rather than waiting for a release.

The guess is narrower still: it runs **only in `setup`**, only when nobody has
declared, only when nothing is attached to a terminal, and only when an address
is already in hand — because direct mode with no home is a CLI with nothing to
talk to. Then it is written down, which is the phase-14 birth-default shape
again: decide once, record with a receipt, and leave every later command with
nothing to re-derive. A per-command sniff would let an exported variable move an
agent's canvas between two replicas halfway through a session.

## The seam was one function, because the CLI never touched the store

The expected cost of this phase was a transport rewrite. It was not. Grepping
first turned up that the CLI's use of `~/.isocan` is identity, actors, config
and session files — `paths.canvasesDir` has exactly one caller, in
`neverHeldACanvas`. **Canvas data and blobs already travelled over HTTP.** So
pointing `DaemonClient.base` at the home is most of direct mode, and the work
was collecting ten hardcoded `http://127.0.0.1:${port}` sites into one
`resolveBase` — which is worth doing on its own, since ten call sites each
learning the rule separately is ten chances to reach the wrong replica, silently,
because both answers are real daemons that will cheerfully serve the request.

Two things turned out to be already correct, both written for phase 10.3's many
homes: `redeemPass` omits the `home` field when it equals its own base, which is
exactly right when the base *is* the home; and `joinFromHome` answers
`not-a-replica` with a 409 that callers already swallow. Neither needed a line.

What refuses now: `serve`, `restart` and `stop`, because they are about a
process the machine has decided not to run, and starting one would give it a
second replica queueing toward a home the CLI is already talking to. `isocan
home` too — a canvas made on a direct machine is born at the home, so there is
no birth default to hold. `isocan status` stops saying "daemon: not running",
which is the answer a broken machine gives, and describes the home instead.

## Why isn't `--direct` the default?

Asked mid-build, and the answer moved a debt. **The daemon's headline
justification is offline, and offline has never worked for the CLI:**
`HomeUnreachableError` refuses a replica's CLI write when the home is
unreachable, deliberately, and says so in its own message. Writes forward
synchronously to the home's single-writer pipeline either way, so the replica
*adds* a hop rather than removing one; only reads are served locally.

And the part that reaches further: a machine with no CLI replica has exactly
**one** replica — the browser's, from phase 10 — instead of two that cannot see
each other. That is the entire premise of the local-bridge debt. Flipping this
default would retire phase 12.7, its Private Network Access dependency and its
failure-mode list, by deleting the thing they exist to reconcile. What it costs
is the airplane thesis, converted from a debt into a decision: a person in the
browser and their agent in the terminal with no network becomes
impossible-and-honest rather than half-built-and-silent.

It cannot be unconditional — a locally-born canvas needs a daemon to be its
home — so the honest formulation is *direct when the canvas lives elsewhere,
daemon when this machine is the home*, and since phase 14 the first is the
common case. It is `DEFAULT_MODE` in `direct.ts`, one line, and it is filed in
Deliberately open rather than decided, because the evidence is a real session
rather than an argument.

## The kill test came back with a finding

The lap was driven by hand against a scratch home — name, create, list, park,
wake, reply — and `isocan wait` parks at the home and wakes on a mention with
nothing bound to `127.0.0.1`. The kill test did not pass, and is the more useful
result: **a killed agent's ring lingers for five minutes.**

CLI presence is TTL-based (`SESSION_TTL_MS`, five minutes, swept every ten
seconds) and touched by commands — it is not bound to a connection. Measured
after a `kill -9`: still there at t+250s, gone at t+300s. So Scene 6's *"her
ring fades only if her sandbox dies, which is the truth"* holds only within a
five-minute window, and for that window the pile says "here" about a sandbox
that no longer exists. It is not caused by direct mode — a thick agent behaves
identically — but direct mode is what makes it matter, because a torn-down
sandbox is the ordinary way this agent ends. Filed open; the fix is presence
bound to a connection rather than a clock, which belongs to the ephemeral plane
and not to this phase.
