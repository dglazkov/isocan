# 6 October 2026 — A kernel that resets, and a judge in the tab

## macOS 27 changed what a full accept queue does

The gate went red in `packages/api/test/connect-deadline.test.ts` on a Mac
updated to Darwin 27, on `main` as well as under keel's update, after passing
that morning. Nothing in the repo had changed. Running the same test under
Node 24.20 and 24.21 failed identically, which ruled out the Node bump.

Two things had happened at once:

- **The kernel changed.** The connect-deadline rigs stage a full accept queue
  by stopping a listener. Darwin 25 silently dropped the overflow SYN, which
  is the ~7.8 s retransmit ladder the deadline exists to cut. Darwin 27 resets
  it instead. Probed directly: of twenty connects to a stopped listener with a
  backlog of one, nineteen failed at once with `connect ECONNRESET`. In the
  test's own sequence, some connects report success and are reset a
  millisecond later, so the first write fails with `EPIPE`.
- **undici 7 crashed on it.** undici 7.30 calls `socket.setTypeOfService(0)`
  on every HTTP/1.1 request, between connecting and writing. Node throws on
  any `setsockopt` failure except on Windows, so a socket the kernel had
  already reset threw `EINVAL` from inside undici's write path, uncaught. That
  was a crash risk for the CLI on any reset loopback connect, not just in the
  test.

Upstream had fixed the second in July, in undici 8 only
([nodejs/undici#5544](https://github.com/nodejs/undici/issues/5544)); 7.30,
the last 7.x, still throws. So undici is now `^8.11.2` (jsdom already pulled
8 in). The bounded client in `packages/api/src/client.ts` and the suite's
fetch in `test/setup.ts` now also retry `connect ECONNRESET` and `write
EPIPE` on loopback: both mean the daemon never held a whole request, which
is the same licence the timeout retry already relied on. `read ECONNRESET`
stays out, because by then the request may have been read.

A parallel session on a Darwin 25 Mac had pushed a test-only guard the same
evening (`1fb06526`), wrapping the suite's connector so the EINVAL became a
no-op. It could not reproduce the failure there, and it left the product
client unprotected. With undici 8 the guard can never fire, so it was
removed; its broader assertion in `test/connect-deadline.test.ts` stays.
Lesson 109: a test rig built on one kernel's answer to overload is a test of
that kernel.

## The judge in the tab, specified

Dion brought a test plan for EmbeddingGemma 2 as a browser-local decision
model. It became a project, [`local-judge`](../projects/local-judge/), with
nothing built. The model is a fourth backing for the judge seam (`local`,
beside Jev, stub and home), running in a Web Worker through MediaPipe's
Decision Maker. It is opt-in and never loaded on a first visit, and it only
suggests: a deterministic policy layer and a person's own act sit between its
answer and any change.

[`ideas.md`](../projects/local-judge/ideas.md) ranks ten use cases by what
already exists to measure them against. The Chat intent router comes first
because the test plan's rules-only baseline already exists in the repo:
`categoriseAsk`, at 84% agreement with hand labels. The voice fast path is
second because its shadow log is a free labelled set. Find-by-meaning comes
third, and is the answer a person may choose for Loop's untriaged finding
that every search here is substring matching.

The phases are built to stop. Phase 0 measures the instrument on a real
desktop and a real phone and proves the privacy claim with the network off.
Phase 1 puts the regex, zero-shot EmbeddingGemma, a linear head on its
embeddings and Jev against the same hand-labelled asks, and the project goes
on only if EmbeddingGemma beats the regex. Two steps wait on a person: the
Gemma licence for serving the model from isocan's own origin, and where the
~165 MB bundle lives.
