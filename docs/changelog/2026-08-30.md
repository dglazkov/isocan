### The home screen says what happened, and holds up at a hundred canvases

`bb3f98c`

The card read `8/17/2026 · Admiral One` — a date and a name, which says when
somebody was here and nothing about what they did. **And the date was wrong.**
`withCanvas` returned the project untouched, so `project.updatedAt` moved only
for `project.update` — the Lake House card reported 17 Aug while the last
actual operation was 29 Aug by somebody else. Twelve days out, wrong person,
labelled as activity.

That was never a display bug. "Updated" on a canvas means the canvas changed,
and adding an item changes the canvas; the list was showing the only number it
had. The reducer stamps every operation now, and records `lastOp` alongside —
stored rather than derived because `listCanvases` reads one metadata file per
canvas, and a log tail per canvas would make the home screen O(canvases) log
reads: cheap on a laptop and the wrong shape on a store where a read is a
request.

**Nothing asserted the stamp**, which is exactly why it survived — the mutation
that removes it passed every other test in the suite. It has its own tests now,
and they bite.

**Canvases older than the field are repaired once**, in the background at boot,
never on the request path and never twice for the same canvas. Without it the
new ordering would have sorted every existing canvas by when it was last
retitled — quietly, which is the worst way to be wrong. On this machine it
fixed nineteen.

**The words come from one table.** `opWords` in core, which `timeline.ts`'s
seams now read too — a card, a tick on a track and `isocan canvas list`
describe one event identically. The fallback belongs to the CALLER and that is
not a fudge: a track names an unknown op type precisely, which a test already
held it to, and a card says "did something" rather than showing a person
`item.setCurrentVersion`. Every op the system HAS is in the table; they differ
only on one that does not exist yet, where their audiences want different
things.

**At a hundred canvases the order is the feature.** `sortCanvases` and
`filterCanvases` in core, so the app and the CLI cannot disagree about which
canvas is most recent. Recent activity by default, name, or newest-created;
ties break by id so a list never reorders itself when nothing changed.
Filtering matches every word in any order — "lake rules" finds "Rules of the
Lake" — and it runs BEFORE the sort, because ordering what is about to be
discarded is work nobody sees. The controls appear only above eight canvases,
counted on what the person HAS rather than what is showing: testing the
filtered length would remove the box you are typing into.

`isocan history [who]` is step one of the standing-agents plan — the
cross-canvas fold over what was already recorded, no new state. It answers the
question a per-canvas view cannot: `8 of 286, across 9 canvases`.

Driven against real data: cards read "Repo Admin deleted something · 2h", zero
fell back to "did something", all three orderings sort, the filter finds and
says so when it finds nothing.

**Not built, and worth naming:** the hover detail (the last few seams per card)
and the cross-canvas lens. The lens is step two of that plan and explicitly not
a canvas — an item's x/y belong to the canvas it is on, so it must derive its
layout and refuse the drag.

### The full-screen arrows say which way, and how much is that way

`bae006c`

Resting on one named the destination and the keystroke and never the
DIRECTION — which is the one thing a 10px arrow glyph cannot carry on its own,
and the thing somebody hovers to find out. Now: `to the right: Sherwood, and 2
more · ⌘→`.

The words are written from the reader's position — "up there", "down here" —
because that is how somebody standing on a slide describes the canvas around
them, not "north" or "+y".

**The count is not decoration.** "and 2 more" is the difference between the
last slide of a row and the middle of one, which is the question somebody
presenting is actually asking, and it was unanswerable before without pressing
the key to find out.

Answering it needed "is this item that way", which `findNextItem` had inline in
a switch. Asking it a second time in the pad would have been **a second opinion
about which way a thing lies** — the arrow could then advertise a direction the
key does not travel, or count items it would never reach. So `isToward` came
out and both callers use it, and the test that matters is the property between
them: whenever something is counted that way, the key must move that way, and
when nothing is counted the key must not move at all.

The accessible name gets the same sentence rather than the thinner one — for a
reader the direction only exists there.

### Count the copying, not the omission — a ratchet on duplicated CSS rules

`66d9b67`

The Personas panel's broken header, generalised. Five dock panels each
hand-rolled a `<header>`; four carried a private rule to lay it out, byte for
byte identical; Personas was the fifth and never got a copy. **Nothing could
have caught that by reading the Personas panel, because nothing there was
wrong** — what was wrong was four copies elsewhere, none of which can notice a
missing fifth.

So the thing worth counting is the copying. `measure.mjs copied-rules` reports
CSS rule bodies that already exist word for word elsewhere in the sheet, and it
is now a `reviewer` goal at 45 — a ratchet, so it may fall and never rise.

**It would have caught this one.** Run against the sheet as it stood before the
fix: 48. After: 45. Exactly the three redundant copies of the header rule,
visible as a number without anybody looking at the panel that was broken.

Declarations are sorted before comparing so a reordering cannot hide a
duplicate, and bodies under three declarations are ignored — `flex: 1` and
`display: none` are vocabulary rather than structure, and counting them would
bury the signal under noise nobody should act on. `--selftest` passes: 45
clean, 46 with the shared header pasted back as a private copy, which is the
exact shape the metric exists to see. Twelve metrics now, all of which move
when the thing they measure breaks.

The practice is written down in `docs/development.md` rather than left in a
commit message, in three parts: a shared component cannot half-arrive; prefer a
DERIVED guard to a listed one, because a list protects the cases somebody
already thought of; and count the copying, because the bug never appears where
the breakage is.

### One header for every dock panel, because four correct copies could not notice the fifth

`a058640`

The Personas panel shipped with its icon sitting on top of its own title, no
padding, and no rule beneath it. Reported with the right question attached:
*are we not using the same component for the sidebars?*

**We were not.** Five panels each hand-rolled a `<header>`, and four of them
carried a private CSS rule to lay it out. Those four rules were byte-identical:

    display: flex; align-items: center; gap: 7px; flex: none;
    padding: 10px 14px; border-bottom: 1px solid var(--line-soft);

Personas was the fifth and never got a copy. It borrowed `.files-glyph` and
`.files-count` — standalone classes, which worked — but the layout lived in
`.files-panel header`, a DESCENDANT rule, and a `.personas-panel` is not a
`.files-panel`. So the header fell back to `display: block`, and measured live
it was exactly that: no flex, no gap, no padding, no border, the glyph and the
word flush at 0px apart. The one line it did have,
`.personas-panel header .spacer { flex: 1 }`, assumed a flex container nothing
created — a rule written for a layout that was never there.

**The lesson is not that somebody forgot a rule.** It is that four correct
copies cannot notice a missing fifth, and the copy is always correct on the day
it is made — which is why review does not catch this and a month later the
panel ships broken. So the guard is DERIVED rather than listed: it finds the
dock panels by reading which components render `dock-panel`, and requires each
to use the shared header. A panel added next month is already covered.

`PanelHead` takes the frame out of negotiation and keeps the differences as
slots — a hint, a count, or neither. `Trash` and `Help` deliberately keep their
own and are named in the guard as exceptions rather than passing silently:
Trash has no glyph and no hint and its close is a different control, Help is a
popover and not in the dock. Dressing either as a dock panel would be a
redesign rather than a repair.

The consolidation caught a regression I had just introduced: the workbench's
compact Chat header still targeted `.main-glyph` and `.main-hint`, which had
become `.panel-glyph` and `.panel-hint`, so its smaller sizing would have
silently stopped applying. The guard found it before the suite did.

Two existing guards in `chrome.test.ts` asserted the old structure — the panel
containing `<b>Chat</b>`, and three separate `…-panel header b` rules not
shouting. Both protect decisions that still stand (the panel says the button's
word; a name is written one way everywhere), so they were re-pointed at the new
structure rather than weakened, and the uppercase check now has one rule to
read instead of three copies.

Two small deliberate unifications: the glyph takes `--accent-text` rather than
`--accent`, which is the ink token and what the two most recently written
panels had already chosen; and a count of zero is now hidden rather than
rendered as "0" beside an empty state that already says so.

All five headers measured identical in a browser afterwards — flex, 7px gap,
10px/14px padding, a bottom rule, and a real gap between glyph and title. Three
mutations bite: hand-roll a header again, bring the duplicate rule back, or
make `.panel-head` a block.

### Optimistic everywhere, and a mark that means "late" rather than "new"

`6fa02d2`

Text, ink, uploads and new versions posted with `sendOp`, which has **no local
echo** — the item appeared only when the home's broadcast came back down the
socket. On a healthy connection that is invisible. On a sick one the gesture
does nothing at all, which is how "⌘Enter and nothing is added to the canvas"
happened: the node WAS created, and the tab never learned. They go through
`sendEchoed` now, the same door drags and resizes already used, so the canvas
answers the instant you act whatever the socket is doing.

The blob is uploaded before the op is sent on every one of these paths, so the
optimistic apply describes something that genuinely exists at the home. An echo
of a version nobody else could fetch would be a different and much worse idea.

**The cost of optimism is the waiting**, and that is what the rest of this is
for. A change shown instantly and never confirmed looks exactly like one that
worked, right up until it is lost — so the view has to be able to say "this has
not landed".

**The whole design is in WHEN it says it.** Marking a change the moment it is
made would put a flicker on every gesture, because a healthy round trip is tens
of milliseconds — and a signal that fires constantly is one people stop seeing,
which means it cannot work on the day it matters. Waiting `SETTLING_MS` first
changes what the mark MEANS: not "this is new" but **"this is late"**. Under a
good connection nobody ever sees it. Under a sick one it appears exactly where
the work is stuck, which is the question somebody is actually asking when a
canvas stops responding.

Quiet on purpose — a dashed outline and a little less ink, no colour and no
spinner. Nothing has gone wrong yet, and a warning would be a lie about a
change that is merely in transit. When something HAS gone wrong the refusal
banner says so in words, and a refused write is explicitly NOT settling: it is
over, and leaving it marked would say the opposite of what happened.

`itemsTouchedBy` was already in core — I wrote a second copy before finding it,
and deleted mine. Two opinions about which items an op concerns is the shape of
bug where one surface highlights the wrong thing for a month.

One timer for the whole canvas, not one per item, and it is only scheduled
while something is actually unconfirmed — a canvas at rest schedules nothing.

`group` now rides in the queue. A revise is three ops under one group id and a
flush is a RE-send, so without it a reconnect would turn one gesture into three
separate undos.

Driven in a browser against a stalled POST: the item moves at once, **nothing
is marked at 300ms**, the mark appears by 1s, and it clears when the home
finally answers. On a healthy connection nothing is ever marked. Three
mutations bite — mark immediately, keep marking a refusal, drop the group.

stays on now, and the gesture composes rather than conflicting: pressing on the

### A socket that dies without saying so, and the tab that believed it

`9eb6f6e`

Reported as: asked something in the Chat on Repo Admin, nothing happened,
reloaded, and an agent had picked it up and been working the whole time. The
tab said `live` throughout.

**Every recovery in the store was reactive to an event a silently-dead socket
never delivers.** `onclose` reconnects — a half-open TCP connection never
closes. The seq-gap check resyncs — it only runs when a message ARRIVES. The
`online` event dials — but it returned early whenever a socket object existed,
which is precisely the case worth acting on, because a dead socket is still an
object. A lid closing, a wifi-to-cellular hop, or a proxy reaping an idle
connection leaves `readyState === OPEN` indefinitely: nothing writes to the
socket, so nothing fails, so nobody finds out. HTTP writes keep working the
whole time, which is why the canvas looks fine — your own comment even echoes
locally — while nothing anyone else does ever arrives.

**The recovery underneath was always correct**; it resumes from a cursor and
has since phase 10. What was missing was DETECTION, and that is all this adds.

The home now beats every 25s, and it is an ordinary message rather than a
protocol ping because a browser cannot see pings or pongs — liveness has to
arrive as something `onmessage` can observe. It carries nothing: a heartbeat
carrying state would be a second way to learn the canvas, and there is exactly
one. The same timer pings at protocol level and reaps sockets that miss a
window, which is the mirror problem — a room broadcasting into a connection
nobody is on the other end of, holding a presence face up for somebody gone.
Reaping terminates rather than closes, because a half-open socket will not
answer a closing handshake either.

The tab watches the one thing a dead socket cannot fake: messages arriving.
Any message counts, not just the beat — a busy canvas proves itself with its
own traffic, and a store that only accepted heartbeats would reconnect in the
middle of somebody typing. After 70s of silence (two missed beats plus slack)
it drops the ref, closes, and calls `retryLater` directly rather than waiting
for an `onclose` that may never come.

Two wake paths that had nothing: **visibility becoming VISIBLE** had no handler
at all — only `hidden`, to flush writes — and coming back to a tab is both the
likeliest way to arrive holding a dead socket and the moment somebody is
looking. `pageshow` covers the restore the visibility change misses.

Measured against a real daemon rather than asserted: 3 heartbeats and 3
protocol pings over 58 seconds, at 25s. Three mutations checked — no watchdog,
messages not counting as life, a 5s window — and each one bites, including the
one that would have made this reconnect all day over an ordinary quiet minute.

**Not covered, and worth saying:** `home-link.ts` is the same class of bug
between a replica and its home, with a worse symptom, since a browser reload
would not fix it. It has an independent HTTP poll that this does not, and the
home's new pings reach it, but it has no watchdog of its own yet.

### The repo tells its canvas when code lands — the write half, where it is buildable

`f9eb835`

`docs/research/2026-08-30-repo-admin-canvas.md`'s write half, for the one place
it can exist today: **this machine**. CI cannot reach a canvas — no daemon, no
badge, no route in — but the machine you commit on is the machine the daemon
runs on, so a git hook is the entire mechanism, and no new server surface is
needed for it.

`scripts/hooks/post-commit` keeps two rules that are the difference between a
hook people keep and one they delete in week two. **It can never fail your
commit**: the commit already happened, and a canvas that was unreachable is not
a reason to make somebody think it did not — every path exits 0. **It never
blocks the terminal**: eleven metrics is about fifteen seconds, which is
unacceptable in front of a prompt, so the run is detached and writes to a log
whose name it prints. Silent background work is the kind that gets ripped out;
a named log is why this one survives.

It is opt-in by construction rather than by a flag — no `.isocan/board.json` on
this machine and the hook exits immediately, and `.isocan/` is git-ignored, so
a clone does nothing until somebody sets a board up.

`scripts/install-hooks.mjs` installs **one symlink per hook, not
`core.hooksPath`**: pointing hooksPath at a directory seizes every hook at once
including ones this repo does not ship and somebody else's tooling installed. A
symlink each is the smaller promise, and `--remove` can honour it exactly. It
refuses to overwrite a `post-commit` it did not write — a hook somebody wrote
by hand is theirs, and moving it aside helpfully is how tools lose trust.

### JSON Canvas export, and the edge question answered from the other direction

`e234be9`

`isocan export <file>` writes a canvas as JSON Canvas (jsoncanvas.org, MIT) —
the format Obsidian and others read. `toJsonCanvas` in core does the mapping.
Geometry crosses unchanged: same units, same origin, no scaling and no flipped
axis.

`json-canvas.md` could not say what an edge should be because isocan had no

holding a map exports as a real graph. Verified end to end rather than in a
unit test alone — a map built on a scratch canvas came back as two
`toEnd: "arrow"` edges, and the scratch nodes were trashed afterwards.

**Import is deliberately not built and is not next.** The format carries no
versions, no threads, no actors, no timestamps, no properties and no oplog, so
reading one in would mint a canvas whose history begins at import. That is a
different feature with a different argument, and pretending a round trip exists
is how somebody loses work.

**So the export says what it could not carry**, every time:

    /tmp/lake.canvas — 13 nodes, 0 edges
    the format has no room for 28 older versions, 6 comment threads,
    4 properties — this is not a backup

because it looks like one.

its `text/uri-list` blob, not in the version record. The resolver is an
explicit parameter, so its absence loses the node TYPE (link becomes file) and
never the node — and the CLI fetches only those blobs rather than downloading a
whole canvas to read four of them.
