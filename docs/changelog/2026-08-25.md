# isocan.io

**2026-08-25** · Phase 14 · Dimitri Glazkov

The launch train's last car. `isocan-io-prod` exists: its own project, its own
Firestore, its own bucket, one always-on instance, a load balancer at the apex
of isocan.io, nightly exports, an attester, and a deploy that happens only when
somebody moves a tag. And the CLI stops asking a stranger where their canvases
should live — a machine that has never held one is pointed at the hosted home,
once, with a receipt and a one-command way back.

## The default, and where it is consulted

Phases 7.5 and 10.3 both deferred this line to launch, and both were careful
about the same thing: *where* the default is read, not what it says. The
obvious place is `resolveHomeUrl`, the function every daemon calls at boot to
find its birth home — and putting it there would have changed where every
existing daemon's next canvas landed on the day it shipped. No gesture, no
report, nothing on screen for somebody who had been working locally for months.
`config.ts` refused it in those words and predicted the answer: *"that default
belongs to phase 14, where setup writes the address down on purpose."*

So `isocan setup` writes it, and the care is in who gets flipped. Only when
nothing is configured. Only when `~/.isocan/projects` is empty, so a machine
that already holds canvases keeps birthing them where it always did. Only for
an installed copy — a git checkout is a developer's machine, and pointing this
repo's own `npm run dev` at production would be dogfooding somebody else's
home by accident. And never fatally: a first run on a laptop with no network
still leaves a working local daemon and a line saying why the canvas stayed.

What makes any of this safe is phase 10.3, which is why it ran first. A birth
default used to be a whole-daemon property — setting one demoted every canvas
on the disk to a replica of somewhere else. It decides one thing now: where the
*next* canvas goes. A shipped default is consulted at a birth and can therefore
never re-point work that already exists.

## The flag, demonstrated before it was closed

Phase 13.7 metered the door and left one hole open on purpose, because closing
it was provisioning rather than code: `--ingress=all` leaves the `*.run.app`
URL reachable *around* the load balancer, and on that path the forwarded chain
is short enough that the entry the meter keys on is one the caller supplied.

That was reasoning from Google's documentation. Before spending a flag with a
blast radius on it, it got measured against the real prod service. With the
honest bucket already refusing at 429, eight invented `X-Forwarded-For` values
each minted a badge; one invented value repeated metered at exactly 21. The
caller's fiction really is the key on that path. Prod now runs
`internal-and-cloud-load-balancing`; dev stays open, having no strangers to
protect from.

The companion question — how many entries the infrastructure appends — is
settled the same way and needed no code: through the load balancer the chain
arrives `<client>, <lb>`, so one from the right is the client, exactly as
documented. `ISOCAN_PROXY_HOPS` stays unset.

## The instrument that was writing to nowhere

Settling that question meant reading a log line. Phase 13.7 had put the entire
weight of its worst failure on one: a home keyed on its own load balancer
refuses the whole internet at 429 and looks precisely like a rate limit that
works, so every refusal is logged with the chain it was keyed from and the
number of distinct keys the meter holds — *"that log line is how somebody at
3am sees it instead of concluding the limit works."*

Twenty-one mints against dev, a legible 429, and Cloud Logging holding only
Google's own request log. The container's stdout carried nothing at all.
`Fastify({})` with no `logger` key does not give you a quiet logger; it gives
you `abstract-logging`, whose `warn` is `function noop () {}`. Every `app.log`
call in the server had been silent since the day it was typed.

It is this codebase's oldest failure wearing new clothes. The standing lesson
says the default answer to a wrong address is a cheerful one, and phase 13.5
sharpened it to *an instrument can be cheerful too*. This is the second
sighting in as many phases, and the purest: code that reads exactly like
logging, sitting under a comment explaining what the logging is for, emitting
nothing. Logging is on at `warn` now — an instrument, not a firehose, since
Fastify's per-request lines at `info` would be a duplicate of the request log
Google already keeps — with pino's level mapped onto Google's `severity`,
because a deliberate warning arriving labelled INFO is the same bug one layer
up. The guard asserts that `log.warn` is not named `noop`, because a spy
installed on a no-op proves nothing.

## Provisioned

Stage A through E on `isocan-io-prod`, with `prod.env` holding the variables so
a home cannot end up half in one project and half in another. One thing about
prod is genuinely not "the same scripts with other variables": a locked ingress
may only be set on a home whose load balancer exists, so stage A runs once with
the ingress open and `70-cloud-run.sh` is re-run afterwards to close it — and
that script now asks the *domain* rather than the run.app URL whenever ingress
is restricted, since a check pointed at an address closed by design would fail
on a perfectly healthy home.

Promotion is a tag. `green` moves by itself, which is right for a dogfood home
and wrong for the one strangers are on, so prod deploys what somebody named:
`git tag -f prod green && git push -f origin prod`. It was proved end to end —
the tag fired the trigger, the build deployed, and the service came back with
its ingress and every environment variable intact, because the deploy step
changes only the image.

## And the desk, on the real domain

Prod's sign-in mail would have gone out from
`noreply@isocan-io-prod.firebaseapp.com` — no SPF or DKIM alignment to
isocan.io, and a stranger's very first email from the product landing in spam.
Dev solved this in phase 13.5, and the expensive half of that fix already
ships: the provider moves the From: address and the action-link domain
together, so the daemon serves `/__/auth/action` itself rather than sending
anybody to a second origin. What prod needed was a console flow and four DNS
records.

It is finished, and by the only check that counts. Not the console's
"verified" — phase 13.5 caught that exact instrument reporting the old sender
domain twice while real mail already carried the new one — but a sign-in played
all the way through: mail from the aligned sender, link followed, an email
address proved onto a badge in a browser at isocan.io. That is phase 9's whole
attester loop working on prod, which is more than the gap asked for.

Two things learned in the DNS, both cheap to hit and annoying to diagnose. The
Firebase console emits host names as FQDNs and Namecheap's API takes them
relative to the domain, so pasting one through produces
`firebase1._domainkey.isocan.io.isocan.io` — which resolves as nothing and
fails verification in a way that reads as the provider's fault. And after the
records landed, Google's public resolver answered the apex TXT from a split
cache for half an hour: consecutive identical queries disagreed, some backends
still holding the pre-change answer. A propagation watcher exited on a
condition that passed and printed a readback contradicting it a second later.
Nothing was wrong and nothing needed fixing — but a Verify clicked into a stale
answer can stick, which is precisely how prod's certificate came to be
permanently named `isocan-cert-2` earlier the same night. **A single `dig` is a
sample, not a state.**

## The other lane: reactions become the marking system

Before the launch work above, the day's UI lane replaced the favourites star
outright. Reactions are Slack-shaped marks on items (`item.react`, set

168×108 box (lesson #22).

One same-day reversal, recorded as such: the full-screen control shipped in
the morning as a word, became a glyph-always button with a drawn tooltip at

## Stage-aware spatial navigation

Walking items with ⌘-Arrow Left/Right (`jump` / `revealItem`) previously checked
the window's raw bounds rather than the visible canvas stage (`stageRect`).
When the left sidebar (Main thread or Files panel) was open, walking left placed
the node's left edge at `x = 48px` — deep underneath the open sidebar. Walking
right used a margin of 48px, placing the node under the floating right tool rail
(which extends 66px from the window edge). In addition, items too large to fit in
the view were centered on the window width rather than the visible stage.

`revealDelta` now computes pan adjustments against `stageRect` with a 76px margin
that clears both sidebars and floating chrome, centering oversized items on the
visible stage so margins and overflow spill symmetrically.

## The full-screen button always carries its icon, and spells out when roomy

The full-screen button under an item now always displays the `[ ]` expand icon.
When there is plenty of room (`width * scale >= 210px`), it spells out "Full screen"
beside the icon; when space is tighter, it collapses to the compact icon-only
button to ensure the under-item row never crowds marks or size chips.

## Stage rect reserves right gutter for the floating tool rail

"Zoom to fit", "Fit selection", and framing actions use `stageRect()` to compute
viewport framing. `stageRect()` previously assumed the canvas extended to the
window's right edge (`right: 0`) when neither the trash nor the marks panel was
open. This centered fitted items against the window width rather than the open canvas
area, causing wide items to touch or slide underneath the floating right tool rail
(`right: 14px; width: 52px`). `stageRect()` now reserves `MARKS_GUTTER` (76px) on
the right by default, giving fitted content symmetric breathing room and keeping
it clear of the toolbar.

## Clean gap between bottom chrome and selection border

The row under an item (`.item-under`) previously used `padding-top: 5px`. With a 2px
selection outline and corner resize handles extending 6px outside the node, the
bottom buttons (`+` reaction, `[ ]` full-screen button, and size chips) sat directly
against or slightly over the blue selection border when active or hovered.
`padding-top` is increased to `10px`, guaranteeing a clean 8px gap from the selection
outline and 4px from the corner handles so both borders remain clearly separated.

## Uniform Full screen button background

The `Full screen` text inside `.fullscreen-btn` previously inherited the generic
`.item-hint span` styling, wrapping the text in an inner grey capsule with rounded
borders. The rule now targets direct children (`.item-hint > span`) and explicitly
resets `.fullscreen-btn span`, rendering the icon and label across a single, uniform
pill surface without nested chips or borders.

## Smiley-plus icon for reaction add button

The reaction button under selected items previously rendered a text `＋` character.
It now carries a dedicated smiley-face icon with a plus sign in the top corner (`SMILE_PLUS`),
matching the familiar reaction affordance found in modern collaborative tools.

## Smooth ease transition when navigating between nodes

Moving between canvas items (e.g. `⌘ + Arrow` spatial navigation) previously jumped the
camera instantly when revealing nodes outside the viewport. It now smoothly animates
via `glideTo` with a 500ms duration and a smooth cubic ease (`easeInOutCubic`), providing
a natural sense of travelling across the canvas between nodes while respecting reduced-motion preferences.

## The face that never went up, and the silence that hid it

A second agent session, on a canvas born while its daemon was already running,
could see itself on a canvas nobody else could see it on. `isocan home` said
the home was reachable the whole time, `isocan who` printed a confident roster
of one, and the only cure anybody found was `isocan restart`.

The cause is that **the two roads a canvas takes to its home are not the same
road.** Writes forward over HTTP; presence rides only the per-canvas
WebSocket. So a canvas can be born at a reachable home, take every op it is
given, serve its URL, and have a roster that never leaves the machine — and on
the reading end that is indistinguishable from a canvas nobody else is on,
which is the single most misleading sentence this system can produce.

Every failure on that road was swallowed by construction, and each swallow was
individually correct: the `error` listener has to be empty (an unhandled one
takes the daemon down), `reconnect` backs off without a word, a 4404 close
drops the link for the next sweep to re-make, `relay()` returns silently when
the socket is not open, and a face the home will not vouch for is dropped on
both ends with no log anywhere. `GET /api/homes` reported per-home HTTP
reachability and nothing else — the reassuring half.

So: **surfaced** — `CanvasLinkState` per canvas (`connected`, `opens`,
`relayedAt`, `facesRelayed`, `failures`, `lastFailure`), a LINK column on
`isocan home`, and `isocan who` saying on stderr when its answer is only who
this machine can see. **Said out loud** — three consecutive failures complain
once, naming the canvas and the consequence rather than the plumbing, and
recovery says so too, because a line that announces trouble and never
announces its end teaches people to distrust the log.

**Repaired**, in two halves. The sweep read `links.has(canvasId)` as "this
canvas is fine", but a map entry is not a connection: a dial that hung before
it ever made a socket leaves an entry with no socket and no retry timer that
nothing will ever touch again. And the load-bearing half — presence was the
one edge-triggered thing in a system that is level-triggered everywhere else,
so a single lost or refused relay was permanent. The roster is re-stated every
poll for any canvas with local faces, which makes the outage two seconds
instead of forever.

The sharpest finding is that **an open socket was being counted as a
success.** The test for a canvas the home has never heard of reported
`opens: 29` in 1.5 seconds: the home accepts the upgrade and then closes with
4404. A failure count reset by that reads a canvas being refused twenty times
a second as perfectly healthy — and without fixing it, the new complaint would
never have fired for the loudest failure mode there is. `opens` counts the
home's hello now, not the upgrade, and `connected` requires both.

What this does not do is explain the original incident: that machine's
evidence is gone, and the row, the home and the actor claim were all provably
fine. It means the next one answers in one command instead of forty.

## A build that can say which build it is

`version 0.1.0` is what every isocan that has ever shipped answers, so the one
field named after the question carried no information — `isocan status` on a
machine two days behind and one built five minutes ago printed the same line.
The stamp names the commit now, and `--version`, which had been a hardcoded
literal, is the first thing anybody runs to find out which isocan this is.

Two kinds of copy, two sources, because an install has no `.git`. A CHECKOUT
reads `.git` by hand rather than by shelling out, since `buildStamp` sits on
the health route and `isocan status` is a command agents run dozens of times;
it survives the three shapes this repo actually meets — a plain clone, a
worktree (`.git` as a file naming the real directory, which is how agents here
work), and packed refs, where `refs/heads/main` is not a file at all. An
INSTALL reads a block `scripts/release.mjs` stamps into the release manifest,
namespaced under one `isocan` key rather than spread as top-level fields,
because npm owns that namespace and a `commit` key of its own would one day
silently win.

**`builtAt` is not `codeAt`, and the difference is the point.** `codeAt` is an
mtime: the right heuristic for "has this copy changed under a running daemon",
and the wrong answer to "how old is this code", because reinstalling the same
release moves it and moves nothing else. `builtAt` is the source commit's own
date.

Staleness gets an exact test where it had only heuristics — two builds that
name themselves and disagree is the first thing checked, and the message
carries both shas, which is the difference between "restart it" and knowing
what you would be restarting from and to. The mtime check stays and has to: on
a checkout both readings come from one `.git`, so uncommitted edits are
invisible to the sha and visible to the mtime.

The guard worth having is the one on the seam. A checkout reads `.git`, so
every other test here passes whether or not the release branch stamps
anything — and an install is precisely the copy no test runs in. So the
producer and the consumer are pinned to each other: if those two spellings
drift, installs quietly go back to being unable to say what they are, and
nothing anywhere fails.

## The fourth shape of `.git`: reftable, where the honest stamp is silence

The stamp's test promised that a checkout always names its commit, and this
repo's own dev machine broke the promise within hours. It runs
`extensions.refStorage = reftable`, where refs are binary tables and HEAD is a
compatibility stub reading `ref: refs/heads/.invalid` — put there precisely so
hand-readers fail safely instead of plausibly. The reader returned null,
exactly as its "every failure is the same answer" comment says it should, and
the test called that a failure.

The stub is matched explicitly now, so nobody reading a log chases `.invalid`
as a corrupt branch name, and the comment gains a fourth shape beside clone,
worktree and packed refs — including why the answer stays null there: parsing
reftable by hand is a binary-format dependency this best-effort stamp does not
want, and shelling out to git at daemon boot is a failure surface it
deliberately does not have. The guard is shape-aware rather than weakened: a
readable checkout must still name the sha; a reftable checkout must say
nothing rather than something wrong.

## The listener has to be on before the socket can be torn down

Both release runs since the previous day failed, and the failure presented as
something easy to look past: `Tests 1487 passed` over `Errors 2 errors` — a
green test list above a red run. Every test passed; vitest reported the
unhandled errors separately and exited non-zero. The same "1 error" line had
been seen locally the day before and attributed to a leftover daemon from a
manual experiment.

`ws` treats terminating a socket that is still CONNECTING as an error, and an
unhandled `error` on an EventEmitter takes the process down. The supersede
branch added with the stuck-dial repair terminates exactly such a socket, and
it sat ABOVE the line that attaches the listener. So the guard `dial` has
always carried — the one whose comment says in as many words that a missing
listener "takes the daemon with it" — was installed one branch too late.

Moving the listener above the branch is the whole fix, and it is the right
place on its own terms: a socket that nothing has adopted yet is precisely the
one with nobody to hear it fail. **This is a shutdown crash, not a test
artefact** — a closing daemon is when dials are most likely to be in flight
with nowhere to land, and the stuck-dial repair makes superseding a dial a
deliberate act rather than an accident.

`replica.test.ts` reproduces it deterministically — 2 errors on every run with
the bug, 0 without — and that is the regression guard. A bespoke test written
for it was deleted again: three variants all passed with the bug reintroduced,
and a test that cannot fail on the defect it names claims coverage it does not
have.

## A project is a directory

`docs/` had two kinds of document and a convention holding them apart:
whole-product things at the top level, one bounded mechanism per file under
`design/`. That worked while there was one body of work. There are now six,
and the convention had stopped saying which design belonged to which plan —
`identity-desk.md` and `convergence.md` sat side by side with nothing in the
filesystem to say that one answers the multiuser journey and the other answers
the atlas one.

So the convention becomes the structure. `docs/projects/<name>/` holds
everything about one body of work: the ideal (`journey.md`), the walk
(`phases.md`), and the mechanisms it forced, one per file. A project with a
single design names it `design.md`; a project with several names each for what
it designs. Adding a doc to a project now edits nothing outside it, and
reading a project end to end is `ls` and then reading in order. The mapping
was not invented here — AGENTS.md already recorded it in prose, and that
sentence is now the directory tree.

What stays at the top level is what belongs to no single project:
`architecture.md` (one physical map of one system — every project moves it, so
it cannot live inside any of them), the guides, and the three records indexed
by time rather than by subject.

**131 references rewritten across 41 files, and not all of them prose.**
`packages/web/test/terms.test.ts` READS `innkeeper.md` at runtime, `terms.ts`
quotes it by path, and `scripts/grade.mjs` names the evals plan. Every
markdown link in the repo was checked to resolve on disk afterwards — 0
broken.

Two things fixed in passing: `phases.md` told a reader to run
`git log -p docs/phases.md` for the long-form findings, which would have gone
quiet after the rename (it says `--follow` now and names the old path), and
`home-links.ts` cited a section that exists nowhere in this repo and did not
before the change either — so the dead citation goes and the argument it
introduced, written out in full beneath it, stays.

Dated records keep their prose. `research/`, `reviews/` and `changelog/` had
their links repointed so everything still resolves, but a page that says "what
`evals.md` concluded" is saying what the doc was called that day.

New in the same commit: **`docs/projects/auto-upgrade/design.md`** — the CLI
catching up with its home, whose first step is a measured defect rather than a
proposal. `ARG ISOCAN_BUILD_SHA` is passed by cloudbuild, stored in the
image's ENV, and read by nobody, so `/api/healthz` on isocan.io answers with
no `commit` and no `builtAt` — and the Dockerfile comment calling it "the
build stamp /healthz reports" is, today, false.

## The auto-upgrade project gets its journey, and a default

`journey.md` is the acceptance suite for auto-upgrade, written as scenes with
the multiuser cast — and writing it surfaced eight design gaps, now folded
into the phases: the missing fetch step (npm can only fetch the release tip,
so install only what the verdict named), the parked waiter being a process on
the old build, cleanup versus trees in live use, once-per-verdict notices, the
agent as the CLI's ordinary operator, recovery commands running on the build
they recover from, the unstated default mode, and the trust boundary's arrival
date.

**`auto` becomes the managed install's default**, because in notify mode an
unattended upgrade needs four steps that never complete on machines nobody
watches.

The design and phase docs are also rewritten into developer-style-guide prose
— plain statements, no metaphors or arrow chains — with every decision,
measurement and proof unchanged.

## The review: one quantity, one home

A full review of the day's six concurrent UI commits: four reviewers over the
range, findings adversarially verified, then fixed. The commits were good work
with one recurring disease — **numbers and rules that had one home got a
second one, and the two immediately began to disagree.**

**The tool rail was cleared twice.** One commit raised `REVEAL_MARGIN` 48→76
to clear the rail while the stage still ran to the window's edge; another
moved rail clearance into `stageRect` seventeen minutes later without retuning
the margin — and each commit's changelog entry claims its own 76 owns the
rail. ⌘-arrow reveals parked an item 152px off the right edge and 76 off the
left. `REVEAL_MARGIN` is 48 again and its comment no longer claims rail duty:
the stage owns chrome, the margin owns air.

**`stageInsets` was forked from `stageRect`** — two hand-copies of the dock
chain differing in one branch, in the file whose header brags it unified three
divergent computations. One derivation now (`dockEdges`), with the single
deliberate difference argued at the point of divergence. The dock widths moved
INTO `stage.ts` (the components never used their own constants), which frees
the geometry module from the React import chain and makes it testable.

**The gutter feature itself was unguarded.** `stage.test.ts` baked 76 into its
own fixtures and never called `stageRect`, so reverting the feature left the
whole file green — lesson #5's shape, a guard that restates the rule and can
therefore only test itself. Both functions take injectable ui/window now and
the suite calls them.

**`revealDelta` re-centred fully visible items on narrow stages.** The fits
check compared against stage minus DOUBLE margin, so a stage merely too tight
for full breathing room re-centred an item that was entirely on screen, on
every jump. The contract is tiered now and matches its own sentence: visible
means stay, off-edge slides in to the air the stage can give, and only
wider-than-the-stage centres. The first fix attempt kept a subtler version of
the same bug, the mutation suite caught it, and the fixtures are asymmetric on
purpose — **a centred fixture also passes under a mutant that centres
everything.**

**`FULL_LABEL_ROOM` was resurrected against a button that had grown.** The 210
was measured for the label-only form (77px); the icon+gap form is 91px, so the
row overflowed in the 210–212 band — and the threshold never charged for worn
marks at all: two chips on a 215px item ran the size chip 84 measured pixels
past the item's edge with the label proudly spelled out. The threshold is
re-measured (221) and marks-aware, and the frozen point-value test is a
bracket again, per lesson #11.
