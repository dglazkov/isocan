  mount, guarded once per mount so a dev double-mount cannot open two
  sockets. No key → the field still asks.
- item.add on a groups canvas was refused ('insertion placement
  required'): the op now carries geometry (the shared default size),
  a position, and — in groups mode — containerId null + groupPlacement
  auto, the same shape the shell's own creators send. The dialog's
  groupMode rides in; the overlay assumes the groups default.

* fix(talk): reset the auto-start guard when the session stops

StrictMode unmounts a fresh mount in dev — the auto-start fired, the
mount cleanup ran stop() and closed the socket, and the once-guard
blocked the second mount from beginning again. The panel opened dead
on the dev server, which read as 'I still have to press it twice'.
The guard is per session now: stop() resets it, so the next mount
starts clean, and a real close-then-reopen also starts again.

* feat(talk): the mic is the talker; the dialog is only configuration

The floating mic no longer pops anything up. With a key stored, one
press starts the session and one press ends it; the feedback — the
pulsing button, the input/output level bars and the last words — floats
by the button and is gone when the turn is. No key: the press opens
the small config popover, and 'Save and start' is the same gesture.

* fix(talk): real meter maths, and ctrl-click opens the configuration

  pegged or sat dead. Both meters now run the page's own LevelMeter —
  dB gating, attack, release, held peak — fed per audio block and

  the gliding.
- ctrl-click (or ⌘-click) on the floating mic opens the configuration
  even when a key is stored, so the model can be changed without
  deleting the key first.

* fix(talk): only audio parts reach the playback; images are said, not parsed

The model is multimodal and can emit image parts beside its audio. The
first build fed every inlineData part to the playback as PCM, which is
how the model's base64 images turned into meter noise. Image parts are
now skipped with one caption line, only audio/ parts play, and the pen
tool's drawing lands as sketch.svg rather than note.txt.

* feat(talk): hand the session the canvas it is standing on

The dialog's setup now carries the canvas snapshot — items with their
ids, threads with their counts — in the one wording the standing

* fix(talk): address PR #320 review — resolver, session lifecycle, captions, docs

### The "@" menu says which names will not answer you, rather than hiding them

`fba4b87`

Asked the other way round (Dion, 16 Sep 2026): "if you type '@' it shouldn't
show you names that you can't control... filter it". The instinct is right —
the menu was offering names that would bounce a summons and saying nothing
about it — and this takes the remedy one step short of hiding.

An agent whose gate is shut to the reader now carries `won't answer you —
<Owner>'s` and sorts below every name that will answer.

## Why marked and not hidden

Argued at length in docs/research/2026-09-15-reading-the-facepile.md; the short
of it is three things.

A name that is ABSENT reads as "does not exist". Hiding makes "no such agent"
and "not yours" indistinguishable to a reader, and that distinction is the
whole point of the three-state reachability the bench spent a phase building.

The refusal that exists today is the most useful sentence in the flow — "Dolly
listens only to Dion Almaer — this did not wake Dolly, and spent nothing" is
what made a baffling evening recoverable. Saying it BEFORE the click is
strictly better than saying it after. Saying nothing is worse than both.

And it is the rule this very menu already keeps, one case over: the bench puts
agents in it MARKED "not here yet" rather than leaving them out, for exactly
this reason. A second rule pointing the other way would have made the menu
inconsistent with itself.

If the pile still feels crowded the honest lever is overflow, not selection: a
count tells the truth about what is there, a filter does not.

## What it does not do

It does not stop the name RESOLVING. The gate decides whether a summons is
answered, never whether the words point at somebody — a mention that stopped
resolving would quietly become plain text in the posted comment. Asserted.

It marks nothing when no gate is known. An agent nothing is answering for has
no announced policy, and "nobody is listening" is a different fact from "it
will not listen to you". Merging them would be the same silent-gate failure
read from the other end.

The words are the refusal's own, shortened, because the rc already answers a
turned-away summons in the thread and a menu that said something different
before the click would be a second account of one rule.

Four tests, including one that can only pass if the shut flag is consulted —
the shut name is both alphabetically first and the live one, so nothing else
could put it last.

### An agent wears its owner's colour, and the pile says which are which

`044375a`

Built from docs/research/2026-09-15-reading-the-facepile.md, asked after an
hour of real use: the pile held two people, four agents, two rcs and a sheep
in a container, and drew a row of near-identical blue discs.

Every face answered one question — who is this — and the two a person actually
wanted were unanswerable: is that a human, and whose agent is that. The second
has never been answerable at all, and it is the one that matters the moment a
canvas has agents belonging to two people.

Dion's shape, which is the good idea here: an agent is an emoji inside the
colour of the person who owns it; a person is a letter on a solid disc of their
own. One glyph then answers two questions without adding a channel.

The owner's colour goes on the RING rather than the fill, which is the
correction lib/face.ts already argued from experience — an emoji is a small
full-colour picture, and on a saturated disc its colours and the disc's fight.
The ring existed for exactly that, and it turns out to be the shape that can
carry somebody else's colour. So an agent is ringed whether or not it wears a
mark: an unmarked agent keeps its initial on a ringed disc rather than
reverting to a filled one and reading as a person.

## One field, not two

`Face.owner` is `{id, name} | null`, and null IS how a face is a person. An
`agent` boolean beside an `owner` could disagree, and the day it did the face
would say one thing and the card another.

It is resolved once inside `push`, not at the four places a face is made, so a
fifth presence state gets an owner for free instead of being the one that
forgot. The source is the live policy the answering rc announces, falling back
to the enrolment's `writtenBy`; neither known is null, and a face with an
unknown owner draws exactly as it did before owners existed. That is the
honest failure for an unknown — better a plain face than a wrong one.

## The separator, and the card

People first, then a hairline, then the agents: people first because a person
scans for the humans they know, and agents are read as a fleet. The rule
carries person-or-agent structurally, which is why no face needs a badge
saying which it is. Drawn only when both groups exist — a rule with nothing on
one side of it means nothing. `aria-hidden`, because every face already says
what it is in the label a reader is handed.

The hover card gains the two lines it could not say (asked the same day: "if I
mouse over 'Scout' it should point to the owner / who has access to it"):
owned by, and the gate. The gate is `policyWords`, so the card, the tray, the
rc's announcement and the refusal in the thread are one sentence rather than
four accounts of one fact.

## What is not here

The two ladders the note argues for — lightness for reachable, ring thickness
for busy — are not built. They are their own change and want their own look,
and this one is already the whole of the who-and-whose question.

Verified as far as this tree can: 6 new tests on the owner and ring rules,
typecheck, and the full lane (629 files, 6,394 tests). The live states could
not be produced here — an agent face needs a parked rc, which isocan refuses
an agent session by design — so the CSS was checked by rendering the exact
markup the component emits and reading back the computed ring colour, fill and
separator. The walk belongs on dev.isocan.io.

Costs 757 bytes of the entry chunk, which is now 1,113 past the agreed
745,000. Reported by the budget as a warning rather than a blocker, and named
here so it is not discovered later as a mystery.

### Research how a facepile could answer more than one question

`0465288`

A design note, nothing built. Asked after an hour of real use in which the pile showed a row of near-identical blue discs while the canvas held two people, four agents, two rcs and a sheep in a container — none of which was legible from it.

The proposal is one channel per question, so no channel carries two: hue and glyph say WHO, a separator says person-or-agent, lightness says whether it can be reached, ring thickness says whether it is doing something. roster() already computes eight states and the facepile spends none of them.

Dion's refinement is the best idea in it — an agent wears the emoji inside its OWNER's colour, humans the letter in their own — because one glyph then answers two questions without adding a channel, including 'whose agent is that', which the pile cannot answer at all today. The whole project exists to kill the summons into silence, and hiding a name so it cannot be summoned is a quieter silence, not less of one.

### "you" in a listen gate now says who you are

`63bafd7`

`policyWords` wrote "listens only to you" without naming the actor. On 15
September that sentence cost an hour on a real canvas, and the way it did is
worth the change.

A second machine set up with a plain address arrives as its OWN person. The
cloudtop was Admiral One, not Dion Almaer, and `rc listen Dolly --to
usr_NqnR80M_lu` granted Admiral One the right to summon an agent Admiral One
already owned — redundant, so `policy.listen` stayed empty, so the gate said
"listens only to you", which was exactly correct.

Read on a machine whose identity the reader had ASSUMED rather than checked,
that sentence supports three wrong stories: a silent no-op, a silent narrowing,
and replica lag. All three were told, each confidently, before anybody ran
`whoami`. A bug was filed and retracted within the hour (#316).

The tell is that `--json` settled it in one command. The words were carrying
less than the data sitting behind them, and the missing piece was one word.

So: "you (Dion Almaer)". It stays "you" first, because whose gate it is matters
more than what they are called; the name is disambiguation, in brackets, behind
it. The same treatment applies to grant names, so a list of who may summon
reads consistently whether or not the reader is in it.

Eight assertions across four suites move with it, which is the guard doing its
job — this copy is pinned in cli, rc and core because what it says and what
dispatch does have to be the same sentence.

### The design partner's two always-on entrances go behind an experiment

kinda want to get rid of it... it's verbose and I don't get it."

The two entrances render unconditionally for anyone who can edit: `Start design
task` under EVERY comment, `Ask design questions` at the foot of every thread.
A canvas with forty messages grows forty controls. That is a great deal of
permanent surface for a feature that landed the same day and that a reader
cannot yet explain from the control alone — and the cost is paid on every
canvas by everyone, including people who will never use it.

The gate is the house answer for exactly this, and `experiments.ts` already
says so: a module behind an experiment ships in the bundle and is off. The
Inbox went behind one for the same reason — off while its shape settles. So
this is not a verdict on the design partner; it is the same waiting room.

Only the ALWAYS-ON entrances are gated. `DesignTaskPanel` and
`QuestionnairePanel` still draw whenever a canvas already carries design
requests or questions, because hiding work somebody has already started would
be a different and worse bug than showing a button they did not ask for.

Raised to the project rather than done behind its back: the note in
docs/projects/design-partner/design.md says what was gated, why, and what would
take it out of the experiment — an entrance that earns its place by being
somewhere a person is already looking for it, rather than under every message.

### The architect's question about core's dependencies, answered by measuring it

`ebb0e55`

`core-runtime-deps` has been red since 12 September and asked three nights
running, at 6 then 9 against a bound of 1. It went unanswered past three days
and reddened `npm test`, which is the guard working: the queue can fail, so a
correct report cannot be quietly ignored.

Answering it needed a measurement nobody had taken. `core-runtime-deps` counts
keys in `packages/core/package.json`; the bound's stated reason is narrower —
"the reducer must stay portable". Those were the same number until core grew
side entries, and have not been since.

Walking the runtime import graph from `packages/core/src/index.ts` — 133
modules, following only imports that survive compilation — reaches exactly one
of the nine declared dependencies:

    reached from index.ts : 1  (nanoid)
    side-entry only       : 8  (unified, remark-*, css-tree, parse5, entities)

The eight split cleanly by the entry that pulls them: five behind `./markdown`
(`markdown-text.ts`), three behind `./design-audit` (`designaudit.ts`,
`design-contract-rules.ts`). `index.ts:70` reaches `designaudit.ts` only
through `export type`, which is erased.

So the reducer is as portable as the day the bound was set, and the number
saying otherwise measures a different thing. Both rows answered `accepted`,
with the walk written into the 12 September page where the question was first
asked.

The bound stays at 1 deliberately. Nine declared dependencies is still nine
things to audit and trust, and the day the closure goes to 2 is a day somebody
should have to argue for.

What this does NOT do is fix the instrument. Measuring the closure instead of
the manifest would make the bound say what it means — and changing an
instrument so a red number goes green is the move that deserves the most
suspicion, even when the argument is good. It rewrites every past reading and
every future one, so it is not a thing to do inside a turn that was about
something else. Recorded in the page for Dion, not done here.

The line-count finding from the same night is left unanswered on purpose: it is
a different question, it is not yet late, and answering one without looking at
it would be worse than leaving it.
