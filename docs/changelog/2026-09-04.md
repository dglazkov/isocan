# 4 September 2026 — Modules, counted

One research note, and the counting that made it worth writing.

## Modules: adding a kind of thing, and taking it away again

The question was how isocan gets extensibility good enough that a module
— `@isocan/whiteboards`, `@isocan/documents`, `@isocan/sandboxes` — can
add node types, toolbar tools, agent tools, inspectors, panels and whole
sections of UI, and be removed again.
[`docs/research/2026-09-04-modules.md`](../research/2026-09-04-modules.md)
is the answer, and its method was to count rather than to argue.

**The registries a module would fill are all closed, and the diffs say
what filling one costs.** 8 kinds, 6 tools, 5 dock panels, 17 palette
actions, 13 built-in slash commands, 139 CLI verbs in one file, 33 ops,
64 routes. The commit that added the personas panel touched twelve
source files across three packages; the context view the same twelve
plus core and the CLI; the mind map seven. Not because any of them was
hard, but because "the set of panels" is spelled five times — a union,
five booleans, a rail, a menu, a stage rule — and nothing reads a list.
The mind map is the tell: it is already a module in everything but its
address (a core file, a web component, a CLI family, a guide section,
its own property keys, zero ops), and nothing about it is in a registry
because there is no registry.

**Five features in a fortnight added zero operations.** Context,
personas, the map, areas, the sprint — all on `item.add`,
`item.update` and properties. That is what makes modules possible: the
vocabulary is already closed against them.

**Removal is safe because of a decision made for other reasons.** An
item is a file with a mime and a property bag, and no op names a kind.
Remove a module and its items render as files, with the module's name
readable from the mime alone. tldraw was measured for contrast: a
document holding a shape whose util is not registered throws. isocan's
file-first model is the opposite failure mode.

**Two trust classes, not one.** The extensions design's "no app-origin
JavaScript" is right about items, which collaborators put on a canvas,
and wrong about packages, which the operator of a home installs the way
they installed the CLI — which already runs unattended from whatever is
on `release`. A module is trusted like the CLI; an extension like a
collaborator; a module is the runtime an extension may need.

**The walk, in the order that proves something:** move the mind map into
`packages/modules/` and show the app builds without it; Mermaid as the
first node-type module; documents, because it needs the inspector and
the page slots that do not exist; runtime loading for self-hosted homes;
sandboxes last, behind the content origin, extension actors and compute
consent by name.

Prior art read from its documentation today rather than remembered: VS
Code's `contributes.*` for the manifest's shape, Obsidian's
`manifest.json` + `main.js` for runtime delivery, tldraw's `ShapeUtil`
for what a kind must declare. The note is `open`; the roadmap was
regenerated from it.
