# 4 September 2026 — Modules, counted

One research note, and the counting that made it worth writing.

## Modules: adding a kind of thing, and taking it away again

The question was how isocan gets extensibility good enough that a module
— `@isocan/whiteboards`, `@isocan/documents`, `@isocan/sandboxes` — can
add node types, toolbar tools, agent tools, inspectors, panels and whole
sections of UI, and be removed again.
[`docs/research/2026-09-04-modules.md`](../research/2026-09-04-modules.md)
is the answer, and its method was to count rather than to argue.

**The registries a module would fill are all closed, and the diffs say
what filling one costs.** 8 kinds, 6 tools, 5 dock panels, 17 palette
actions, 13 built-in slash commands, 139 CLI verbs in one file, 33 ops,
64 routes. The commit that added the personas panel touched twelve
source files across three packages; the context view the same twelve
plus core and the CLI; the mind map seven. Not because any of them was
hard, but because "the set of panels" is spelled five times — a union,
five booleans, a rail, a menu, a stage rule — and nothing reads a list.
The mind map is the tell: it is already a module in everything but its
address (a core file, a web component, a CLI family, a guide section,
its own property keys, zero ops), and nothing about it is in a registry
because there is no registry.

**Five features in a fortnight added zero operations.** Context,
personas, the map, areas, the sprint — all on `item.add`,
`item.update` and properties. That is what makes modules possible: the
vocabulary is already closed against them.

**Removal is safe because of a decision made for other reasons.** An
item is a file with a mime and a property bag, and no op names a kind.
Remove a module and its items render as files, with the module's name
readable from the mime alone. tldraw was measured for contrast: a
document holding a shape whose util is not registered throws. isocan's
file-first model is the opposite failure mode.

**Two trust classes, not one.** The extensions design's "no app-origin
JavaScript" is right about items, which collaborators put on a canvas,
and wrong about packages, which the operator of a home installs the way
they installed the CLI — which already runs unattended from whatever is
on `release`. A module is trusted like the CLI; an extension like a
collaborator; a module is the runtime an extension may need.

**The walk, in the order that proves something:** move the mind map into
`packages/modules/` and show the app builds without it; Mermaid as the
first node-type module; documents, because it needs the inspector and
the page slots that do not exist; runtime loading for self-hosted homes;
sandboxes last, behind the content origin, extension actors and compute
consent by name.

Prior art read from its documentation today rather than remembered: VS
Code's `contributes.*` for the manifest's shape, Obsidian's
`manifest.json` + `main.js` for runtime delivery, tldraw's `ShapeUtil`
for what a kind must declare. The note is `open`; the roadmap was
regenerated from it.

## The deck, taken somewhere else

A canvas is presented from full screen, and until today the only way to
hand the deck to someone not in the room was the address. Now it is a
document, three ways, and the reasoning is in
[`docs/research/2026-09-04-deck-export.md`](../research/2026-09-04-deck-export.md).

**One view, two printers.** `/deck` on a canvas stacks every slide — the
marked ones in reading order, or everything when nothing is marked, exactly
as full screen walks — in live 16:9 frames with a print stylesheet that
puts one on each landscape sheet. In the app, ⌘K "Export the deck" opens
it and **Save as PDF** is the browser's own print. In the terminal,
`isocan slides export deck.pdf` opens the same address in the graders'
headless Chrome and prints it, and `--png <dir>` photographs each slide.
Same view, same pages, nothing to keep in step.

**One file, two writers.** `deckHtml` in core builds a self-contained
`deck.html` — every slide inlined as a `srcdoc` frame, arrows and Page
keys flip, its own print CSS makes the same PDF. The app's Download and
`isocan slides export deck.html` run the same function on the same bytes.

The constraint every format inherits, and the note's spine: a slide is
HTML that draws itself, so an export is either that HTML carried whole or
a picture a browser took. PPTX (pictures per page) waits until the PDF has
been used for a real talk; Google Slides waits on per-user Google sign-in.

## Modules, phase 1: the mind map moves out, and nothing notices

The morning's note counted; the night built the first phase of what it
argued for. [`docs/projects/modules/design.md`](../projects/modules/design.md)
is the contract and [`phases.md`](../projects/modules/phases.md) the walk.

**Core has a registry and imports no module.** `registerModule(record)`;
the context pieces walk asks every module for its rows, and the JSON
Canvas exporter asks every module for its edges, where both used to call
the mind map by name. **The mind map is `packages/modules/mindmap`**: the
graph functions that were `core/mindmap.ts`, the lines as an underlay the
shell mounts inside `.world` and feeds the canvas and the drag as props,
the `map` family registered through a `CliHost` of the CLI's own helpers,
and the guide section that was in the base guide — printed after it, only
while the module is loaded. **Two lists are the whole coupling**
(`packages/web/src/modules.ts`, `packages/cli/src/modules.ts`).

The tests moved with it, and two guards grew: `surface.test.ts` reads
verbs and guides from modules as well as `main.ts`, and
`test/modules.test.ts` holds a module's name to its directory and the two
lists, and each module to both lists or neither. The workspace loader
resolves `@isocan/<module>/<entry>` by path for git installs. Property
keys, ops, routes: unchanged — the point.

The Sheepdog note is marked superseded: an external sheep CLI covers the
pet-agent role and works with isocan rather than inside it.

## Modules, phase 2: diagrams, and the union becomes a string

The first node-type module, and the cost the note said to pay on purpose.
`packages/modules/mermaid` adds one **kind** — `diagram`, mime
`text/vnd.mermaid`, extension `.mmd` — and nothing else: no property key, no
verb, no op. `isocan add flow.mmd` lands one because the CLI's mime table
asks the registry; a dropped file lands one because the web app's does; the
card and the stage draw it because the module's **renderer** claims the mime
— the second shell slot, asked ahead of the built-in chain and handed facts
(`url`, `readText`) rather than a blob path; the Mermaid library sits behind
a lazy boundary so a canvas with no diagram never downloads it.

**`ItemKind` widened** to admit module kinds. What survives: exhaustiveness
over the built-ins (`Record<BuiltinKind, …>` still names a missing label or
mark) and a lookup with a fallback for everything else — a module's label,
its noun, and the built-in mark it borrows for an icon. `isocan ls --kind`
reads the live list. Unregistered, a `.mmd` is a document: the text it
always was.

## Modules, phase 3: loaded and unloaded outside core

The dynamic half of the ask. `isocan module add <dir>` installs a built
module into `~/.isocan/modules/` — after printing its manifest and refusing
until `--yes`, the gate `command add --from` already has — and `module rm`
takes it out; `module ls` names the build's own, the added ones, and why any
is refused. **No restart on either surface.** The daemon reads the directory
per request: loaded manifests ride `/api/serving`, the fetch the app already
makes at boot, and each module's files are served under `/modules/<slug>/`,
typed, uncached, path-guarded. The app registers every manifest's kinds
before any code runs, hands over its own React and core on
`globalThis.isocan`, imports each web half, and bumps a generation the
slots read. The CLI does the same before it parses argv, through the same
host a build-time module gets.

**No import map.** A module served out of a home directory cannot import
`react` by name, and the app's chunks have hashed names an import map would
chase every build; `scripts/module-build.mjs` rewrites the four platform
imports to reads of the host global instead, and bundles the rest — the
Mermaid module is 108 files and 3.6 MB of code-split diagram grammars,
downloaded only when a diagram is drawn. The engines check (`>=`, `^`, `*`)
refuses with both versions named, at add and at every load.

**Proved by hand, and two things it found.** Mermaid taken out of both
build-time lists, the app rebuilt without it, a daemon run from that tree:
`module add` printed and refused until `--yes`; after it, both diagrams
drew from `/modules/mermaid/dist/web.js`; after `module rm`, both items
were files showing their mime, the kind was gone from `ls --kind` and the
guide, and the served path answered 404. Found on the way: a `.js` CLI
half under a home directory is CommonJS to Node (built as `.mjs` now), and
a web half with only a named export loads nothing (default exports, and a
guard).

**And the deploy the first phase broke.** The Dockerfile copies every
workspace manifest by name before `npm ci`; a missing module manifest is
not refused — npm plans the tree without it, makes no workspace link, and
the web build dies resolving `@isocan/mindmap/web`. No image built for two
merges while dev and prod sat on the commit before. Two `COPY` lines, and a
guard that holds every module directory to one. Measured rather than
assumed: the manifest layer was replayed by hand both ways, and it is the
build step, not the install, that fails.
